# EPIC 018 — Claim, lease and the execution record

Status: **draft**.

## Goal

A harness claims a `ready` task through `POST /v1/node/:id/claim` against **the real composition root**, and the answer carries an objective lease, a task lease, a fence, an external objective run, an external task run and an open attempt. The claim takes the **objective scope**: the actor acquires or reuses the lease on the parent objective, and takes the task lease under it. A second actor is refused `409 lease-held` on that task, on any sibling task of that objective, and on the objective itself. The claim moves the task `ready → running` and moves its objective and its initiative to `running` in the same transaction. The harness keeps the claim alive through `POST /v1/node/:id/heartbeat`, and gives it back through `POST /v1/node/:id/release`. The run and the attempt carry `driver = 'external'`, so they hold no workspace, no worker, no provider and no daemon-produced base object id, and the database refuses the wrong shape at the `CHECK` clause. `node.list` takes the five filters `docs/proposal/api/graph.md:104` records. An expired lease returns its task to the pool at the next claim, with no daemon restart and no background timer. `src/main.ts` binds all three handlers, `src/cli/program.ts` registers all five commands, and one daemon test drives the whole sequence through the real composition root.

## Non-goals

- **No outcome report and no aggregation.** EPIC 019 owns `node.report`, the attempt outcome, the roll-up to a parent, and the objective close by a `human` actor. This epic writes an attempt row with a null outcome and never closes one, except when it cancels its own.
- **No objective attestation.** `objective running → awaiting_approval` is written by `reportObjective` of EPIC 019 and by nothing else. No path of this epic writes `awaiting_approval` at any level, and no path of this epic infers an objective result. This epic moves an objective to `running` through the ancestor cascade, and back out of `running` never.
- **No git and no integration.** The block does no git and no integration. The harness owns its working tree, its branches and its merges. `docs/proposal/api/integration.md` stays phase 2, and no claim path calls `services/git`.
- **No candidate and no automated gate.** `docs/proposal/phase-2/gates-and-approval.md` stays phase 2.
- **No per-node graph write.** EPIC 017 owns `node.create`, `node.update`, `node.delete` and the `plan_revision.origin` migration.
- **No actor table and no token.** EPIC 015 owns the actor identity, the `actor` table, `resolveActor` and the `allowedActors` mechanism. This epic declares the field on its own three operations only. It does take one obligation EPIC 015 assigns it: `015-actor-identity.md:29` decides the lease-fencing policy of a revocation, and the revocation story below implements it, because migration 0007 of this epic is what gives an actor a lease to fence.
- **No readiness derivation.** EPIC 016 owns `pending → ready` and the closed `PlanStore` mutation API. This epic reads `ready` and writes every node state through `setNodeState`.
- **No internal driver behaviour.** No worker loop, no scheduler and no timer exist. `013-external-drive-overview.md:101` decides that for the block. `run.start` stays `stubbed`.
- **No registry-wide completeness sweep and no P1B scenario.** EPIC 020 owns the sweep over every operation of the block, and the CLI inventory assertion over the whole command set. **This epic binds and registers everything it adds, and defers no wiring to EPIC 020.**
- **No node lease field on a node view.** `110-scheduler-leases-and-the-general-worker.md:14` gives that field to EPIC 111. The claim response carries the lease it acquired, and no read route grows a lease member.

## Decisions

These are settled here. No story revisits one.

- **One harness per objective.** Two actors never hold two sibling tasks of one objective. A claim on a task takes the objective scope: it acquires the objective lease for the claiming actor, or reuses the live objective lease that same actor already holds, and then takes the task lease under it. An objective held by another actor refuses the task claim. A task held by another actor refuses the objective claim.
- **Same-owner descendant execution is allowed.** The actor that holds the objective lease claims the tasks under it freely, and claims two sibling tasks under it freely. A same-owner lease is never a refusal at any relation. Without this rule an actor deadlocks itself between its own objective claim and its own task claim.
- **A task claim opens or reuses an external objective run.** The task run carries that objective run as its `parent_run_id`. `CHECK ((kind = 'objective') = (parent_run_id IS NULL))` at `src/services/storage/migration-0003-execution-and-journal.ts:44` therefore **stays intact and unamended**, and no driver-aware replacement is written. `run_one_active` at `:46` gives one active run per node, so a second task claim under one objective reuses the same objective run row.
- **The drive mode of an objective is pinned at its first claim.** `objectiveDrivePin` of `014-external-drive-contract.md` is the rule, and `claimNode` is the one enforcement point. The claim reads the driver of every run ever opened under the objective and refuses `409 illegal-transition` when the pinned driver is not `external`, with `details` naming both drivers. **The claim-side run reuse refuses an active run whose driver is not the driver of the claim, and it never adopts one.** A blind adoption would open an external attempt under an internal run, which the composite driver foreign key of the migration story refuses at the database. The pin holds while the objective is non-terminal, so an internal worker and an external harness never share one objective.
- **The objective lease outlives every task of its owner.** The claim acquires it, and exactly three paths free it. `node.release` on the objective frees it, and that call is refused while any task lease under it is live. `reportObjective` of EPIC 019 frees it at the attestation, in the transaction that writes `objective running → awaiting_approval`. The expiry sweep of this epic clears it when its owner abandons the objective. **No task path frees it.** It survives every task claim, every task release and every task report of its owner, and `reportOutcome` of EPIC 019 releases the task lease alone and never the objective lease. A task path that freed it would hand the objective to a second actor between two sibling tasks, which breaks the one-harness-per-objective rule, and it would leave no live lease for the attestation of EPIC 019 to present, so the claim-to-close journey could not complete. **The objective run ends later than the lease**: EPIC 019 ends it at the human close, so it carries the attested object id while the human reads it.
- **An abandoned objective is freed by expiry, and by nothing else.** A harness that stops without an attestation stops its heartbeat too. `expires_at` on the objective lease then passes, and the next `node.claim` anywhere sweeps it: the objective run ends with outcome `expired`, the lease owner is cleared, and the objective state stays `running`. Any actor claims the objective and its tasks again. Each task lease under it expires on the same clause and returns its task to `ready`. Expiry and the claim-driven sweep therefore cover an objective lease exactly as they cover a task lease, and no objective is held for ever. `leaseTtlMs` is the whole bound.
- **Recovery replaces takeover. There is no in-place takeover.** Step 1 of `claimNode` sweeps every expired external lease before any decision, so no later step observes a `running` node that holds an expired lease. The sweep returns that task to `ready`, ends its run with outcome `expired`, closes its open attempt with `cancelled` and clears its lease. The claim then takes the ordinary `ready` path and mints a new fence over the freed row. A second branch that took a `running` node over in place is dead code behind that sweep, and the two cannot both be asserted. The `lease.takenOver` event type is therefore not introduced: the sweep writes `recovery.leaseRecovered` and the claim writes `lease.claimed`.
- **Revocation expires the actor's live leases, and the sweep does the rest.** `015-actor-identity.md:29` decides the policy and assigns the mechanism here. `revokeActor` sets `expires_at = now` on every live lease the revoked actor owns, in the same transaction as the revocation, and it keeps `owner`, `owner_kind` and `fence`. It cancels no attempt and rewrites no run, which is what that policy requires. The next claim anywhere sweeps those rows, ends each run, closes each attempt and returns each task to `ready`, so the work leaves the pool for no part of the lease term. Clearing `owner` in place is wrong: a cleared lease has a null `expires_at`, so the sweep never reads it and the task stays `running` for ever.
- **An objective claim creates no attempt.** `docs/proposal/database/attempt.md` makes an attempt one try at one task. An objective claim opens the objective lease and the objective run, and it opens no attempt. Only a task claim opens an attempt.
- **The objective lease of this epic and the objective lease of EPIC 110 are one row.** Both are `lease` rows with `subject_kind = 'node'` and the objective identity as `subject_id`. That single row is what arbitrates between a harness and the phase-2 worker, and it is why the hierarchy rule is real rather than advisory.
- **A claim is a node action, not a lease resource.** `docs/proposal/api/execution.md:88` states that leases have no route, because a separate lease collection promotes an internal table to a public resource. That statement stays true and it is amended in one clause: the lease is still not addressable, and a claim, a heartbeat and a release are actions on the node, spelled `POST /v1/node/:id/claim`, `POST /v1/node/:id/heartbeat` and `POST /v1/node/:id/release`.
- **A claim admits a task and an objective, and refuses an initiative.** An initiative is never executed. It reaches `running` through the ancestor cascade. `node.claim` on an initiative is `400 invalid-request` with `details.refusal = "initiative-not-claimable"`, which follows `invalidRequestDetails` at `src/http/contract/error-details.ts:75-79`.
- **The fence increments on acquisition only.** An acquisition over a free lease and an acquisition over an expired lease each write `fence + 1`. A first acquisition over an absent row writes fence `1`. A heartbeat, a release, a same-owner reuse and the expiry sweep never move the fence.
- **The expiry sweep clears the owner and keeps the fence.** Safety comes from the owner match, not from a fence bump: after the sweep `owner` is null, so every later write that presents the old owner and the old fence finds no matching row. This replaces the `fence + 1` of `src/commands/startup/recover-expired-leases.ts:151`, which contradicts the rule above.
- **A stale fence is `409 lease-held`.** A heartbeat or a release that presents a fence other than the current one is refused and writes nothing. The code is `lease-held` rather than `stale-revision`, because `staleRevisionDetails` at `src/http/contract/error-details.ts:9-12` carries revision identities rather than a fence.
- **`now` is passed, never read from a clock inside the lease service.** Every input of `Lease` carries `now: number`. The command reads `clock.now()` once per transaction and passes the same value everywhere, so one claim writes one instant. `110-scheduler-leases-and-the-general-worker.md:73` already assumes that shape.
- **A conditional write reports its row count through `RETURNING`.** `Transaction.run` at `src/services/storage/index.ts:2` returns `void`, so a zero-row conditional `UPDATE` is invisible to it. Every conditional lease write runs through `transaction.all` with a `RETURNING` clause, and an empty result is the refusal. `Transaction` gains no method, and `SELECT changes()` is not used, because it needs a second statement and a second round of parameter binding.
- **Recovery is claim-driven, not timer-driven.** Every `node.claim` transaction sweeps every expired external lease before it evaluates the hierarchy. One claim anywhere therefore returns every dead harness's task to `ready`, with no daemon restart, no background loop and no timer. `013-external-drive-overview.md:101` forbids the timer.
- **Recovery recovers the CLAIM and never the in-flight work.** kanthord cannot inspect, reset or kill a harness process tree. The sweep cancels the attempt, ends the run, clears the lease and returns the task to the pool. The old harness may still edit and commit. The protocol rule below and the fence check of EPIC 019 are the whole protection.
- **A harness stops work after a failed heartbeat.** A heartbeat answered `409 lease-held`, or unanswered for `leaseTtlMs` since the last success, ends the harness's authority. The harness stops and reports nothing. **EPIC 019 must refuse every report that carries an owner or a fence other than the current live pair, with `409 lease-held`.** That refusal is lease safety and this epic states the requirement.
- **Completeness is enforced at claim only.** `017-per-node-graph-write.md:25` decides it. Neither `plan.import` nor a per-node write refuses an incomplete graph; both report the finding. The claim refuses it, scoped to the claimed node and its containment ancestors, never to the whole project.
- **The completeness read costs one full-graph read, and that cost is accepted.** `node.parent_id` carries no index in `src/services/storage/migration-0002-graph-and-plan.ts`, `completenessFindings` of EPIC 014 consumes arrays and runs no SQL count, and `PlanStore.readAllNodes` reads every node and every edge. The check therefore reads the whole graph, O(nodes + edges) per claim, under the 2000-node bound `017-per-node-graph-write.md:41` states. No index is added and no containment query is written.
- **The lease TTL is configuration.** `settings.leaseTtlMs` is added beside `attemptLimit` at `src/services/config/index.ts:29`, default `300000`. A claim with no expiry has no recovery, and the whole epic rests on expiry.
- **Migration 0007 is the number.** EPIC 015 takes 0005 and EPIC 017 takes 0006. This epic does not depend on 017, and it still lands after it, because a version number is a total order.

  1. `PRAGMA defer_foreign_keys = ON` — the one pragma that defers enforcement to commit inside an open transaction. `PRAGMA foreign_keys` is a no-op inside a transaction and is not used.

  3. `ALTER TABLE run RENAME TO run_old`, `ALTER TABLE attempt RENAME TO attempt_old`, `ALTER TABLE lease RENAME TO lease_old`.

  6. `DROP TABLE attempt_old`, `DROP TABLE run_old`, `DROP TABLE lease_old`, child before parent.
  7. `PRAGMA legacy_alter_table = OFF`.

  Every child row keeps pointing at the name `run` and the name `attempt`, which step 4 recreated, so no child table text moves one byte and `defer_foreign_keys` resets at commit. `src/services/storage/sqlite.ts:77` runs the whole list inside the `BEGIN IMMEDIATE` of `src/services/storage/connection.ts:35`, so a failure rolls the database back to version 6. - **The lease hierarchy as a pure function** — a new `src/domain/lease-hierarchy.ts`. `liveLeaseRefusal(input)` takes the target node's identity, its kind, its parent identity, the claiming owner, and the live lease set with each lease's subject, owner and owner kind. It returns `null` or one refusal naming the holding subject, the holder, the holder kind and the relation. `leaseRelations = ["self", "ancestor", "descendant", "sibling"] as const`. **A lease held by the claiming owner is never a refusal, at any relation.** A task claim is refused on a live lease of another owner over the task itself (`self`), over its parent objective (`ancestor`), or over any sibling task of that objective (`sibling`). An objective claim is refused on a live lease of another owner over the objective itself (`self`) or over any of its tasks (`descendant`). The `sibling` relation is redundant in the acquisition path, because the objective lease of story seven already excludes the second actor; it is computed so the refusal message names the sibling a human sees, and so the rule reads whole. The function reads no clock; liveness is decided by the caller, which passes unexpired rows only.

- **`services/lease` gains its complete interface and its SQLite implementation** — `src/services/lease/sqlite.ts` exports `SqliteLease`, which `NotImplementedLease` currently refuses. `AcquireLeaseInput`, `RenewLeaseInput` and `ReleaseLeaseInput` each gain `ownerKind` and `now`. **`ReleaseLeaseInput` gains `owner`**, without which the "release matches owner and fence" promise is unimplementable. `LeaseRecord` gains `ownerKind`. `acquire` returns `AcquireLeaseResult`, `Readonly<{ record: LeaseRecord; acquired: boolean }>`, so a caller distinguishes a new acquisition from a same-owner reuse. `acquire` runs three statements inside the caller's transaction:

  1. one hierarchy `SELECT` over `lease` joined to `node`, collecting the live lease on the subject, on its parent and on its children, ordered by `subject_id`. It supplies the refusal detail through `liveLeaseRefusal`.
  2. when the subject row exists, is live, and its `owner` equals the caller: `UPDATE lease SET renewed_at = ?, expires_at = ? WHERE subject_kind = 'node' AND subject_id = ? AND owner = ? AND fence = ? RETURNING fence, owner, owner_kind, acquired_at, renewed_at, expires_at`. This is the **idempotent reuse branch**, it moves no fence, and it returns `acquired: false`.
  3. otherwise one upsert, which is the authoritative guard: `INSERT INTO lease (subject_kind, subject_id, owner, owner_kind, fence, acquired_at, renewed_at, expires_at) VALUES ('node', ?, ?, ?, 1, ?, ?, ?) ON CONFLICT (subject_kind, subject_id) DO UPDATE SET owner = excluded.owner, owner_kind = excluded.owner_kind, fence = lease.fence + 1, acquired_at = excluded.acquired_at, renewed_at = excluded.renewed_at, expires_at = excluded.expires_at WHERE lease.owner IS NULL OR lease.expires_at <= ? RETURNING fence, owner, owner_kind, acquired_at, renewed_at, expires_at`. **The insert is what makes a first claim work**: the `lease` table is not prepopulated, so a conditional `UPDATE` alone changes zero rows for ever. The initial fence is `1`. An empty `RETURNING` result is `LeaseError("lease-held")`.

WHERE owner = ? AND expires_at > ? RETURNING subject_kind, subject_id`, and returns the affected subjects ordered by `subject_id`. It moves no fence and clears no owner, and it is the mechanism of the revocation decision. Two further methods ship for EPIC 110: `read(transaction, input)` returns one record or null, and `assertHeld(transaction, input)` raises `LeaseError("lease-fenced")` when the row does not name that owner at that fence. - **`services/execution`, the run and attempt record** — a new capability. `src/services/execution/index.ts` declares `openRun`, `activeRunOfNode`, `adoptRun`, `endRun`, `openAttempt`, `closeAttempt` and `attemptsOfRun`, each taking the storage transaction context first, because the transaction rule of `AGENTS.md` requires a claim and its run to be one transaction. `src/services/execution/sqlite.ts` exports `SqliteExecution`. `openRun` writes `driver = 'external'`, the node id, `lease_fence`, `attempt_limit` from `settings.attemptLimit`, `state = 'active'`, and null in every internal-only column. An objective run carries `kind = 'objective'` and a null `parent_run_id`; a task run carries `kind = 'task'` and the objective run id, so the `CHECK` at `src/services/storage/migration-0003-execution-and-journal.ts:44` holds in both cases. `activeRunOfNode` is what lets a second task claim reuse the one active objective run. `adoptRun` updates `lease_fence` on the active run of a node, which is what a re-claim over an active run needs, and it opens no second run, because `run_one_active` allows one. `openAttempt` mints `attempt_no` as `accountAttempts(...).nextAttemptNo` over `attemptsOfRun`, so the number comes from the rows and never from a counter column. `src/domain/layout.test.ts` gains `execution` to its capability inventory list and to the count in its suite name.

- **`claimNode`, the command** — `src/commands/node/claim-node.ts`, dependencies `{ storage, plan, lease, execution, events, clock, ids, sweepExpiredExternalLeases, attemptLimit, leaseTtlMs }`, input `{ nodeId, actorId, actorKind }`. One transaction, one `now` from `clock.now()`, in this exact order.

  1. It calls `sweepExpiredExternalLeases` with that transaction, so every dead harness's task is back in the pool before any decision is taken.
  2. It loads the node. An unknown node is `404 not-found`. An initiative is the `400` of the Decisions.
  3. It runs `completenessFindings` of `src/domain/plan-completeness.ts` over the claimed node and its containment ancestors, built from `PlanStore.readAllNodes`. A finding is `422 plan-invalid` with `details.findings`. **For a task claim the check is nearly tautological** — the task proves its objective holds a task, and that objective proves its initiative holds an objective — so the one meaningful public case is a claim on an objective that holds no task.
  4. It resolves the objective scope. For a task the objective is `node.parentId`; for an objective it is the node itself. It reads the driver of every run under that objective and calls `objectiveDrivePin` of `014-external-drive-contract.md` with `claimDriver: "external"`. A refusal is `409 illegal-transition`, and `details` names the pinned driver and the claim driver. It then calls `lease.acquire` on the objective, which raises the hierarchy refusal as `409 lease-held`. A same-owner live objective lease returns `acquired: false` and moves no fence.
  5. It reads the active objective run through `activeRunOfNode`. No active run opens the objective run. An active run of driver `external` is adopted with the new fence. **An active run of driver `internal` is `409 illegal-transition`, and it is never adopted**, because an external attempt under an internal run breaks the composite driver foreign key of the migration story. The objective moves `ready → running` through the ancestor cascade of the next story.
  6. For a task claim only, it calls `lease.acquire` on the task, reads the active task run under the same driver rule, opens or adopts it with `parent_run_id` of the objective run, and then opens the attempt.

  It then branches on the claimed node's state, and that branch holds exactly three cases, because step 1 already swept every expired external lease. A `ready` node moves to `running` through `plan.setNodeState`, under trigger `claim-taken`. A `running` node whose live lease the same actor already holds returns the current leases, run and attempt with `200` and writes nothing. Every other state is `409 illegal-transition`, and `details` names the current state. **A `running` node held by another actor at an expired fence is not a case here**: the sweep of step 1 already returned it to `ready`, so it reaches the first case with a freed lease row and a new fence. The events are `lease.claimed`, plus `node.running` for the claimed node, each attributed to the calling actor.
