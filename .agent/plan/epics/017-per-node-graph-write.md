# EPIC 017 — Per-node graph write

Status: **draft**.

## Goal

A `human` or a `harness` creates one node, updates one node and deletes one node over HTTP, without an import. Each write mints a `plan_revision` whose `origin` is `node-write` and whose `accepted_blob` is the whole re-rendered graph, so `plan.export` stays byte-identical to that blob. Every revision, from an import or from a node write, is a valid import base. Completeness moves out of both write paths: a write reports a completeness finding in its response and refuses nothing, and EPIC 018 refuses the claim instead. A structural finding still refuses, at `plan.import` and at every per-node write. A field-only update carries the node's own revision token, and a create, a topology change and a delete carry the project revision. The epic closes on `node.create`, `node.update` and `node.delete`, and on `kanthord node create`, `node update` and `node delete`.

## Non-goals

- **No `node.discard`.** `docs/proposal/api/outcome.md:13` keeps it phase-3. A discard records a human decision about real work: it stores a mandatory `reason`, keeps every row, and moves each dependent to `blocked` with reason `dependency-discarded` (`outcome.md:27-35`). This epic deletes a node that never ran, and it writes no `discard_reason`.
- **No completeness refusal anywhere.** EPIC 018 owns the one refusal, at the claim under a node. This epic reports the finding and commits the write.
- **No state field and no transition.** `docs/proposal/api/graph.md:9` holds. None of the three routes reads or writes `node.state`, except through the closed mutation API of EPIC 016.
- **No aggregation and no outcome.** EPIC 019 owns `node.report` and the roll-up.
- **No claim, no lease and no `node.list` filter.** EPIC 018 owns them.
- **No merge of two concurrent writes.** A stale token is a hard `409 stale-revision`, exactly as `008-project-and-plan.md:13` decides for `plan.import`.
- **No kind change, no identity change and no project move.** A kind change moves the identity prefix and the containment legality at once, so it stays an import.
- **No matrix amendment and no readiness derivation.** EPIC 014 owns the `ready → pending` cell and the `plan-format.md` amendment. EPIC 016 owns the derivation and both directions of it. This epic writes topology, and the derivation of EPIC 016 writes the transition inside the same mutation.
- **No composition-root sweep.** EPIC 020 owns it. This epic wires only what it adds.

## Decisions

These are settled here. No story revisits one.

- **Completeness is enforced at claim only.** Neither `plan.import` nor a per-node write refuses an incomplete graph. Both report the finding in the response body and commit. A structural finding still refuses, at both. **This epic amends EPIC 014.** `014-external-drive-contract.md:31` says completeness runs at `plan.import` and at the first claim. It now runs at the claim only. **EPIC 014 and EPIC 018 follow this decision.** EPIC 014 writes the amended proposal wording, and EPIC 018 keeps its claim-time check, which `018-claim-and-lease.md:49` already states.
- **The round trip is total.** Every revision is a valid import base. `plan.export` at revision `R` returns a document set that `plan.import` accepts at `fromRevision: R`. That restores the EPIC 008 guarantee at `008-project-and-plan.md:61-71` for a node-write revision as well as for an import revision.
- **`docs/proposal/phase-1/state-machine.md:47` changes.** The line reads "An objective with no tasks, or an initiative with no objectives, is invalid. Import rejects it." EPIC 014 replaces it, and this epic fixes the replacement text exactly: "An objective with no tasks, or an initiative with no objectives, is incomplete. Every write reports the finding and commits. A claim under an incomplete node is refused."
- **`docs/proposal/phase-1/plan-format.md:135` changes.** The line reads "The database baseline is always valid, so the procedure terminates." It becomes "The database baseline is always structurally valid, so the procedure terminates." The repair loop runs the structural set only, which is the amendment the next decision carries.
- **The repair loop is proved safe on an incomplete baseline.** `src/queries/plan/validate-plan.ts:233` always calls `repairSuggestions`, and `src/domain/plan-candidate.ts:303-309` throws its iteration-cap error when the baseline stays invalid. `repairSuggestions` at `plan-candidate.ts:290` therefore calls `validateCandidateStructural` instead of `validateCandidate`. A database baseline is always structurally valid, so a reset to `database` always clears the finding set and the loop terminates. `plan.validate` still reports both scopes in its own `findings` array.
- **This changes shipped phase-1 behaviour, deliberately.** `plan.import` no longer refuses `initiative-without-objective` or `objective-without-task`. Four named tests change: `src/domain/plan-validate.test.ts:1034` and `src/domain/plan-candidate.test.ts:451-479,694` now assert a reported finding beside a successful import rather than a refusal, `src/domain/plan-candidate.test.ts:53-54` keeps the two codes in the code list, and `src/queries/plan/validate-plan.test.ts:536` loses its component reset, because the repair loop no longer sees a completeness finding.
- **All three routes are `POST`.** `DELETE /v1/node/:id` is refused: `docs/proposal/api/README.md:126` gives `DELETE` the `none` idempotency policy, and a `DELETE` carries no body for the revision token.
- **`POST` gives bounded same-process suppression and nothing more.** `Idempotency-Key` is optional, the cache in `src/http/server/idempotency.ts:112-114` is process-local, it expires, and a restart loses it. A keyed replay inside one process returns the captured answer. This epic claims no durable destructive idempotency.
- **The guard token travels in the body**, named `fromRevision`, exactly as `plan.import` carries it (`graph.md:62`). The comparison runs inside the write transaction.
- **The revision parent is the project revision, never the request token.** Each command reads `PlanStore.newestRevision` inside its transaction and passes that value as `parent_id`. The node token is a guard and nothing else. Two concurrent node-token updates therefore make a linear chain: A from `R0` produces `R1`, and B, still holding `R0`, produces `R2` with `parent_id = R1`.
- **A stale token is `409 stale-revision` for both classes.** `details` holds `guard` (`node` or `project`), `expected` and `actual`. `README.md:194` states the rule this follows: one condition the client answers one way is one code.
- **An update replaces the whole editable field set.** An omitted field is `400 invalid-request` rather than a silent keep, so the differing-field computation is exact.
- **A delete is a hard delete of the containment subtree.** It cascades down the containment tree only, never along a dependency edge, which is the cascade rule `outcome.md:31` already states for discard.
- **A waived edge blocks the delete.** `docs/proposal/api/outcome.md:37-43` says a waiver survives because it records a human decision. A hard delete of a node touched by an edge holding `waived_at` erases that decision, so the delete is refused with `409 binding-in-use` and the blocker `waived-edge`.
- **A structural edit is legal at `pending`, `ready` and `blocked`.** EPIC 014 already made it legal at `ready` in `docs/proposal/phase-1/plan-format.md:109` and in `choiceVerdict` (`014-external-drive-contract.md:24`), and `nodeWriteLegality` carries the same set. The reason is EPIC 016: readiness applies at import, so a task with no unsatisfied dependency is `ready` the moment it is imported. Under the older set almost every node is permanently uneditable, and per-node topology editing delivers nothing. A `ready` node holds no lease, no run and no commit, so a structural edit on it is safe. The edit stays refused at `running`, `awaiting_approval`, `done`, `partial` and `discarded`.
- **A stored graph is always structurally valid.** Every write that can break the invariant enforces it. `src/commands/project/replace-project-repositories.ts:75-82` removes a binding with no plan revision, so it gains the check.
- **`identity-kind-mismatch` cannot arise.** `services/ids` mints every identity, and no request names a new one.
- **The cost is accepted at a stated size.** A whole-graph render is O(nodes + edges) per write. Phase 1b assumes at most 2000 nodes in one project, and no incremental render ships. History is O(writes) revision rows, not O(writes x graph size): `BlobStore` addresses content by hash, so two writes that produce the same graph store one blob.

  7. `PRAGMA legacy_alter_table = OFF`

- **Readiness, corrected** — the three commands write through `mutateGraph`, so readiness applies inside the store and no obligation registry exists. EPIC 016 deleted `readinessObligated`, `readinessExempt`, `upsertNode`, `insertEdge` and `deleteEdge`. **No command of this epic calls `setNodeState`, and no command of this epic names a trigger.** `mutateGraph` takes no trigger, and `deriveReadiness` stamps each transition it returns: a `pending → ready` transition carries `readiness-promoted` and a `ready → pending` transition carries `readiness-demoted`, which `016-readiness-applied.md:42` decides. The transition inventory is exactly this, and it runs in both directions. A create inserts the node as `pending`; with no dependency the same mutation writes `pending → ready`, and with an unsatisfied dependency the node stays `pending` and no transition is written. A create that names an existing node in its `depends_on` set changes no other node, because the new node has in-degree zero. An update that removes a `depends_on` entry can write `pending → ready` on the edited node. An update that adds an unsatisfied `depends_on` entry writes `ready → pending` on the edited node, because a structural edit is legal at `ready`. A delete removes edges, so a `pending` dependent of a deleted node can reach `ready`. A delete never demotes, because it adds no edge. **This epic is the routine consumer of the `ready → pending` cell that EPIC 014 flipped** (`014-external-drive-contract.md:23`), and EPIC 016 already computes both directions in one pass (`016-readiness-applied.md:33`). One pass stays a fixed point in both directions, so no write of this epic cascades. A write that leaves an objective with no task succeeds, and the objective keeps its state.

- **The CLI** — `src/cli/node/create.ts`, `update.ts` and `delete.ts`, each a typed client of `src/http/contract/`. `node create` reads the newest revision through `plan.revisions` and sends it as `fromRevision`. `node update` reads the node through `node.show` to fill the whole editable field set, sends the node revision when it changes no topology, and reads `plan.revisions` when it does. `node delete` reads the newest revision the same way. Each command prints every returned `completeness` finding on standard error and exits zero, because a completeness finding is a report. `src/cli/inventory.ts:6` gains `["node", "create"]` with `["plan.revisions", "node.create"]`, `["node", "update"]` with `["node.show", "plan.revisions", "node.update"]`, and `["node", "delete"]` with `["plan.revisions", "node.delete"]`, so the inventory parity assertion of EPIC 009 covers them.
