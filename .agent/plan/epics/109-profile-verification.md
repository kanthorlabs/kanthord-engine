# EPIC 109 — Profile verification

Status: **ready**.

## Goal

`kanthord profile verify` runs the two gates of `docs/proposal/phase-2/instructions-and-profiles.md`, and it blocks nothing. This epic depends on EPIC 103 for the profile document, on EPIC 104 for the channel compiler, and on EPIC 107 for the check runner. Gate A is deterministic and needs no model: `src/domain/profile-gate.ts` re-parses the stored `kanthord.profile/v1` document from the value the reader returns, re-resolves the template digest, compiles the seven channels of EPIC 104 through the one shared builder of `src/domain/instruction-compose.ts`, and asserts by inspection that the verification command reached the `repository-profile` channel. **Gate A returns its report and persists no row**, because it runs no command and `docs/proposal/database/check_result.md` requires a commit for every result other than `not-applicable`. Gate B runs the declared `unit` command at one exact commit through `SupervisedVerify` of EPIC 107, inside a throwaway checkout that `src/services/checkout/` creates from the bare home and removes, and the command applies the negative control of `src/domain/profile-negative-control.ts` to catch a command that exits zero and checks nothing. `src/commands/profile/verify-profile.ts` orchestrates both gates, and for gate B it opens one `check_result` row of subject kind `profile-gate` as `running` and closes it with its result, at `authoritative = 0`. `profile.verify` moves from `stubbed` to `routed` in `src/http/contract/instruction.ts`, and `src/cli/profile/verify.ts` reaches it over HTTP. The report names the gate, the verdict and the reason. Neither gate needs a provider account, so the whole command runs on a machine that holds no credential.

`docs/proposal/api/instruction.md` needs one amendment, and this epic edits no proposal document: **Gate A returns its report and records no `check_result` row, because it runs no command and a row needs a commit.**

## Non-goals

- No gate C. `docs/proposal/after-the-mvp.md` defers the hermetic canary through a real agent, because it needs a provider account and one model call, and `docs/proposal/phase-2/README.md` proves the same loop once through P2-E4. A request naming gate `C` answers `400 invalid-request`, which `docs/proposal/api/instruction.md` requires.
- No check declaration and no vacuous-command lint. EPIC 103 owns the frontmatter contract, the `checks` map, the `timeout` token, the profile render, the profile hash, the `nodejs` template and the static lint at import. This epic re-reads that document and restates none of those rules.
- No check runner. EPIC 107 owns `SupervisedVerify`, the pinned environment, the toolchain probe, the output cap, the process-tree kill and the outcome table. This epic calls `Verify.run` twice at most and owns no signal, no timer and no environment entry.
- No channel compiler. EPIC 104 owns `resolveInstruction`, `renderPrompt`, `applyBudget`, `daemonInvariants` and `roleContracts`. Gate A calls them through the shared builder this epic extracts, and it defines no channel and changes no budget.
- No attempt and no worker. EPIC 110 owns the run, the lease, the attempt lifecycle, the per-objective profile pin and the `task-diagnostic` check result. A gate result belongs to no node, so `node.checks` of EPIC 111 never returns it.
- No fetch and no reconciliation. EPIC 108 owns the fetch, the ancestry classification and the `sync` journal row. Gate B reads the bare home as it stands, so it starts no network operation.
- No state transition and no event. The command writes evidence only: one `blob` row and one `check_result` row. It moves no repository, blocks no node, edits no profile and appends no event, because no transition happens. `docs/proposal/phase-2/instructions-and-profiles.md` states that a wrong profile surfaces later as tasks that park in `blocked`.
- No journal row. Gate B performs no git write. It clones from the bare home and writes no ref, so the rule of `AGENTS.md` about a bracketed git write does not apply.
- No second template. `template.list` and `template.show` stay `stubbed`. A template other than `nodejs` has no negative control, and gate B reports that as a reason rather than as a failure.
- No `profile instantiate` CLI command. EPIC 114 adds `instantiate` to the same `profile` group.
- No `agent.list`. EPIC 106 routes it.

## Stories

- **The shared contribution builder** — `src/domain/instruction-compose.ts` exports `buildChannelContributions`, one pure function that returns exactly one `ChannelContribution` per channel of `instructionChannels`. It takes `Readonly<{ role: InstructionRole; profile: Readonly<{ section: string; contentBlob: string; check: ProfileCheck }>; taskContract: ChannelContribution | null; ambientContext: AmbientContribution | null; runtimeEvidence: ChannelContribution | null }>`. It builds `daemon-invariants` from `daemonInvariants`, `role-contract` from `roleContracts[role]`, and `repository-profile` from the role section with `from` of `profile:<contentBlob>` and the scalars `verificationCommand` of `check.run` and `verificationTimeout` of `check.timeout`. It emits an empty contribution for `project-policy`, and an empty contribution for each of the last three when the caller passes `null`. `src/queries/instruction/resolve-instruction.ts` of EPIC 104 loses its inline builder and calls this function, so exactly one composition rule exists. **Gate A therefore inspects the composition a real attempt uses**, and the function is the named seam both callers share. The module imports `domain/` only.
- **Gate A, deterministic and model-free** — `src/domain/profile-gate.ts` exports `runGateA`, which imports `domain/` only and runs no process. It takes `Readonly<{ frontmatter: unknown; body: string; contentBlob: string; computedTemplateDigest: string }>`, the two values `DocumentReader.read` returns plus the two the command supplies, and it returns `{ gate: "A", verdict, reason, findings }`. It performs four steps in this order. **One:** it parses the input through `src/domain/profile-parse.ts` of EPIC 103 and reports every finding that parse returns, so an unknown schema reports `schema-unknown` and a body heading that names no role of `agentKinds` reports `role-heading-unknown`. A non-empty parse finding list ends gate A at this step, because every later step reads a parsed document. The command catches `DocumentError` from `DocumentReader.read` and returns a gate A report holding the one finding `document-unparsable`, because `domain/` imports no service error. **Two:** it compares the parsed `template` against the shipped template of `src/domain/profile-template.ts`, and it produces `template-unknown` for an id other than `nodejs`, `template-version-unknown` for a version other than `1.0.0`, and `template-digest-mismatch` when the document digest does not equal `computedTemplateDigest`. The command computes that digest over `canonicalTemplatePayload`, because `domain/` runs no hash. **Three:** it calls `buildChannelContributions` for the role `general@1`, with the `general@1` role section, `contentBlob` and `checks.unit`, and `null` for the last three channels. It then calls `resolveInstruction`, `renderPrompt` and `applyBudget` of EPIC 104. A refused budget is the finding `channel-over-budget`, with the refused channel name as the locator. **Four, the inspection:** `profile-gate.ts` also exports `inspectVerificationCommand(resolved, expected)`, which returns the findings of the one inspection the proposal asks for. The resolved scalar `verificationCommand` must exist, must carry `channel` of `repository-profile`, and must carry a `value` deep-equal to `expected`; the three failures are `verification-command-missing`, `verification-command-channel-wrong` with the winning channel name as the locator, and `verification-command-mismatch`. The rendered `## repository-profile` block must hold the line `- verificationCommand: ` followed by the rendered vector; an absent line is `verification-unrendered`. **The inspection reads the rendered bytes and never a model, and the timeout carries no inspection of its own**, because `docs/proposal/phase-2/instructions-and-profiles.md` names the verification command only. The module exports `profileGateFindingCodes`, the closed list `channel-over-budget`, `verification-command-channel-wrong`, `verification-command-mismatch`, `verification-command-missing` and `verification-unrendered`, and `sortGateFindings`, which orders by `code` through `comparePaths` of `src/domain/plan-path.ts`, then by `locator`, with a `null` locator first. It is a second sorter because one report merges two closed code lists, and the sorter of EPIC 103 is typed to its own list. The verdict is `passed` with `reason` of `null` when the sorted list is empty, and otherwise `failed` with `reason` equal to the `code` of the first finding. Gate A is never `inconclusive`, because every input it reads is already in the database.
- **The gate B verdict table** — `src/domain/profile-gate.ts` also exports `profileGateReasons`, the closed list `baseline-red`, `check-not-started`, `check-orphaned`, `check-pid-file-failed`, `commit-unavailable`, `control-not-applicable`, `declaration-timeout`, `declaration-unrunnable`, `declaration-vacuous`, `output-exceeded`, `profile-unparsable` and `run-cancelled`, and `gateBVerdict`, a pure table over `{ baseline: { result, exitCode, errorReason }; control: { applied, result } }`. `errorReason` is the `CheckErrorReason` of EPIC 107, so the table reads the fault the service already named and infers nothing from a null exit code. **The table separates a wrong declaration from a red baseline mechanically, by the outcome that EPIC 107 already distinguishes, and never by reading output text.** A baseline of `passed` with a control whose `result` is not `passed` is `passed` with `reason` of `null`: the command ran, and it caught the injected violation. A baseline of `passed` with a control whose `result` is `passed` is `failed` with reason `declaration-vacuous`. A baseline of `passed` with an unapplied control is `inconclusive` with reason `control-not-applicable`. A baseline of `error` with `exitCode` of `126` or `127` is `failed` with reason `declaration-unrunnable`, because `/bin/sh` reports those two codes when it cannot execute the program, so the declaration names a command this host cannot run. A baseline of `error` with `exitCode` of `null` reads `errorReason`, and each of the four values of EPIC 107 is `inconclusive`: `output-exceeded` gives reason `output-exceeded`, `not-started` gives `check-not-started`, `pid-file-failed` gives `check-pid-file-failed`, and `orphaned` gives `check-orphaned`. **Each daemon fault keeps its own reason, because `check_result` has no column for `errorReason` and the report is the only place it surfaces.** A baseline of `error` with `exitCode` of `null` and `errorReason` of `null` throws `Error`, because EPIC 107 never returns that pair. A baseline of `timed-out` is `failed` with reason `declaration-timeout`, because the declared `timeout` and the declared command disagree. A baseline of `failed` is `inconclusive` with reason `baseline-red`: the command ran and decided, so the declaration is runnable and the tree is red, and the negative control is skipped, because a command that already fails proves nothing more by failing. A baseline of `cancelled` is `inconclusive` with reason `run-cancelled`. A baseline of `not-applicable` throws `Error`, because `SupervisedVerify` never returns it and the caller records that value without running anything. The table holds **fourteen** cases, and the coverage list below asserts each one.
- **The negative control, and what it proves** — `src/domain/profile-negative-control.ts` exports `negativeControlConventions`, `NEGATIVE_CONTROL_LINE` of `throw new Error("kanthord negative control");`, `isNegativeControlTarget(templateId, path)` and `selectNegativeControlTarget(templateId, paths)`. **The template names its target convention**: `negativeControlConventions` is a frozen record from template id to `{ convention: string; pattern: RegExp }`, and it holds exactly one entry, `nodejs`, with `convention` of `test-or-spec-suffix` and `pattern` of `/\.(test|spec)\.(ts|tsx|js|jsx|mjs|cjs)$/`. A template id the record does not hold has no convention, which is the `Where the template supports it` clause of `docs/proposal/phase-2/instructions-and-profiles.md`. **The violation is one appended top-level throw, because it is valid in TypeScript and in every JavaScript module form, it needs no import, and any runner that loads the file fails on it.** `isNegativeControlTarget` returns `true` when the record holds the id and the last `/`-separated segment matches that id's `pattern`, and `false` otherwise. `selectNegativeControlTarget` filters with that predicate, sorts the survivors bytewise through `comparePaths` of `src/domain/plan-path.ts`, and returns the first, or `null` for an empty list. The order is explicit, so two runs on one commit pick the same file. **State the claim exactly. A passed control proves that the declared command reads the one selected file and reports a failure in it. It does not prove that the command runs every test, that it covers any other file, or that its assertions are meaningful.** A wider claim needs a per-file control, which no epic of phase 2 owns.
