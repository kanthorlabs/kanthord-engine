# EPIC 020 — Wiring, CLI and the external-drive scenarios

Status: **draft**.

## Goal

The block is assembled, and three mechanisms prove it. One assertion names every operation of the registry with the actor kinds it admits. One assertion drives every `routed` operation of the block against a daemon started from the real composition root, so no operation answers `501` there. One assertion runs every declared CLI leaf against a recording client and compares the operation ids it issues with the ids its inventory row declares. Three scenarios then run through `scripts/e2e/run.mjs`, against the packaged `dist/main.js`: a single harness completes the claim-to-close loop, two harness clients in two network namespaces drive one daemon in one run, and a stale harness loses its claim to a second one. `P1B-E2` is the block's exit criterion, and it executes the whole journey `013-external-drive-overview.md:13` states.

**What this epic does not catch.** A handler bound to the wrong implementation, which returns the status the fixture expects, passes every assertion here. A `node.delete` handler bound to a no-op `404` passes a missing-node fixture. That defect belongs to the functional test of the owning epic, and this epic proves reach rather than effect. The three mechanisms catch an unbound operation, an unregistered command, a registered command that reaches no operation, and a missing `allowedActors` row.

**This epic implements no domain behaviour.** EPICs 015, 017, 018 and 019 each own their own `src/main.ts` binding and their own `src/cli/program.ts` registration, and each says so. EPIC 016 owns no CLI command at all. This epic owns only the seams that no vertical epic owns. **A hole this epic finds is a defect returned to the epic that owed it, and never a fix made here.**

## Non-goals

- **No route, no handler and no migration.** EPIC 015 owns the actor routes, EPIC 017 the per-node write routes, EPIC 018 the claim routes and EPIC 019 the report route. Each one binds and registers what it adds. `kanthord event list` calls the `event.list` route that phase 1 already ships, so it adds no route and no handler.
- **No authorization rule and no `allowedActors` row.** EPIC 015 owns the rule and its own rows. EPICs 017, 018 and 019 each own the rows they add. This epic asserts the complete set and decides nothing.
- **One new CLI command, and one only.** This epic ships `kanthord event list`, and it is the single exception to the rule that a vertical epic owns every command. The block claims that a human answers "who did what" across several harnesses, `event.list` is the only read that answers it, and no other epic of the block owes that command. EPICs 015, 017, 018 and 019 author every other command of the block and add their own `src/cli/inventory.ts` rows. This epic asserts the whole inventory.
- **No registry total and no proposal row total.** `src/http/contract/parity.test.ts:16,25` and `src/http/contract/registry.test.ts:20,25` hold the scalar counts, and each vertical epic raises them by its own row count. This epic states no total, because six epics editing one number is how a correct branch goes stale at integration. EPIC 015 already pins totals at `015-actor-identity.md:115`, so a claim that no earlier epic states one is false.
- **No environment proof.** The Podman gate proves the two-host **logic** and never the environment. It proves no routing, no VPN, no TLS and no token distribution. `docs/proposal/README.md:102-106` puts every `deployment` scenario in phase 3, and `011-end-to-end-scenarios.md:13,71` says a container pair never substitutes for one. **The daemon terminates no TLS at all**, per `docs/proposal/phase-1/transport.md:29`, so a bearer token travels in cleartext. Phase 3 proves the environment once, through `P3-E6`.
- **No live mode and no provider account.** The three scenarios are `deterministic`. `011.2-the-deployment-scenarios-move-to-phase-3.md` keeps `P1-E5` as the one `integration` scenario, and this epic adds none.
- **No acceptance run and no verdict.** EPIC 021 runs the scenarios in order and writes the verdict, exactly as EPIC 012 does for phase 1.
- **No git and no integration.** No scenario of this epic drives a merge. The harness reports an object id and the daemon records it.
- **No assertion that restates a `node:test` case.** A scenario asserts a rule against the packaged binary and a running daemon, which is a different subject. `011-end-to-end-scenarios.md:11` sets that rule.

## Decisions

These are settled here. No story revisits one.

- **The block adds eleven `routed` operations and no `stubbed` one.** Four from EPIC 015, three from EPIC 017, three from EPIC 018 and one from EPIC 019.
- **Sixteen operations admit `harness`, and this epic names all sixteen.** Nine from EPIC 015 and seven added by EPICs 017, 018 and 019. Every operation admits `human`. The assertion names the set and states no count of the whole registry.
- **The block adds seventeen CLI commands.** Five from EPIC 015, three from EPIC 017, five from EPIC 018, three from EPIC 019 and `event list` from this epic. `node attest` is one of the three of EPIC 019, per `019-outcome-report.md:85`. The fifth of EPIC 015 is `actor rotate`, which `015-actor-identity.md:39` adds after this count was first written.
- **The CLI covers every declared command and not every route, and this epic names the gap.** `src/cli/reachability.test.ts` proves that every entry of `declaredCommands` reaches its operation. It proves no converse, and **"a CLI for every route" is false for the assembled application**. Eight `routed` operations carry no CLI command after the block closes: `blob.show`, `edge.list`, `project.status`, `system.health`, `provider.show`, `provider.rename`, `provider.remove` and `provider.setDefault`. Each is acceptable for a stated reason, and no epic of this block owes a command for one. **`event.list` left that set, because this epic ships `kanthord event list`**: it is the one audit read the block's human value depends on, and the acceptance checklist of EPIC 021 now drives it through the CLI. `blob.show` and `edge.list` are dereference reads that `node show` and `node list` already summarise for a human. `project.status` and `system.health` are covered for a human by `kanthord status`, which calls `system.status`. The four remaining `provider.*` operations are phase-1 credential management that `114-onboarding-cli` owns. **This epic adds no command for any of the eight**, because a command with no caller is inventory that the parity assertion then has to carry.
- **Two test paths, and neither is the packaged artifact.** `src/http/contract/authorization.test.ts` holds the inventory, and `src/cli/reachability.test.ts` holds the CLI reach proof. A named path that does not exist makes `node --test` exit non-zero, so the Proof fails before this epic is built.
- **The scenarios run the packaged artifact, and `src/main.test.ts` does not.** `scripts/e2e/podman/product.Containerfile:3` links `dist/main.js` as `kanthord`, and the local driver packs and installs the tarball at `scripts/e2e/lib/driver/local.ts:41-69`. `launchDaemon` at `test/helpers/daemon.ts` spawns `src/main.ts`, so every `src/main.test.ts` claim says **the real composition root** and never the packaged binary.
- **A scenario drives the CLI and direct HTTP only.** It opens no database, imports no service and calls no internal function, per `docs/proposal/README.md:110`.
- **The three scenario ids are `P1B-E1`, `P1B-E2` and `P1B-E3`.** `scripts/e2e/lib/main.ts:44-48` recognises a scenario id through `knownScenarioIds`, and the pattern at `:56` validates `--tag` only. Each new id is added to both lists.
- **`P1B-E1` takes the `local` driver, and `P1B-E2` and `P1B-E3` take the `podman` driver.** A single harness needs one host, and two harness clients need two network identities. All three take the `fixture` profile and the mode `deterministic`.
- **`deterministic` is the runner mode axis, and it is not clock control.** The daemon exposes no clock API, so `P1B-E3` waits on wall clock. `P1B-E3` polls `node claim` at **250 ms** to a deadline of **60000 ms**, under `leaseTtlMs` of **2000**. The deadline is thirty times the lease term, which absorbs CI and container scheduling variance.
- **The harness token never enters the runner process.** `actor register` prints the token, `runCommand` keeps stdout in the raw `CommandRecord` of `scripts/e2e/lib/command.ts:5-12`, and `assertNoDisclosure` reads `record.stdout` at `scripts/e2e/lib/disclosure.ts:92-104` before serialization redacts anything. The runner therefore registers a harness through a capture path that writes the token to a mode-`0600` file inside the client container and prints a redacted body. The runner holds no harness token, so it discloses none.
- **The second client is cross-cutting infrastructure.** Nine named places assume one client, and each one is work in the story below. `013-external-drive-overview.md:15` calls it one topology change, and that is an understatement rather than a plan.
- **A caller-selected header needs direct HTTP.** `src/cli/client.ts:61-73` builds a fixed header set and admits no arbitrary header, so no CLI command sends a caller-chosen `Idempotency-Key`. The driver gains `issueAs(role, request)` for that, and `cliAs(role, argv)` keeps the CLI path.
- **The idempotency oracle is a same-node claim replay.** Two report calls under one key on two different node ids prove nothing: `docs/proposal/api/README.md` keys an idempotency record by route parameters, so the two requests are separate even with no actor scoping. Two actors claiming **one** node id under **one** key is the assertion that needs actor scoping, per `015-actor-identity.md:121`.
- **The block needs a third objective, and it needs a dependency between objectives.** `test/e2e/fixtures/two-objective/plan/journey/alpha/objective.md` and `.../beta/objective.md` declare no `depends_on`, so no objective of that fixture becomes ready through another. A new fixture carries the edge.
- **Sequential requests, and one race.** The runner issues one request at a time, so `P1B-E2` proves two identities, two namespaces and server-side arbitration in one daemon run. It does not prove two requests in flight, except in the one phase that drives them in flight on purpose.

For each alpha task in dependency order: `node claim` answers with a fence, a run id and attempt number 1; `node heartbeat` extends the expiry and leaves the fence; `node report --outcome accepted` with an object id moves the task to `done`. `node attest` then moves alpha to `awaiting_approval`, and `node show` returns that same `attestedObjectId` and the computed `projection`, which `019-outcome-report.md:77` adds to `NodeView`. An attest by the human token is `403 actor-forbidden`. `node close` with the **configured human token** moves alpha to `done`. **`gamma` still reads `pending`**, because beta is not done, and beta's first task still reads `ready`. Every state is asserted by node identity, never by count.

- **`P1B-E2` — the two-client exit journey** — a new `scripts/e2e/lib/scenario/p1b-e2.ts`, driver `podman`, profile `fixture`, plan `three-objective`, mode `deterministic`. **It executes the complete journey of `013-external-drive-overview.md:13`, and it combines no fact from `P1B-E1`.** It builds the two-client topology, runs the journey from the first client, and registers **two** harness actors through the configured token, one per client container, each token captured inside its own container. The phases run in this order.
  1. Both clients authenticate independently, and each `node list --state ready --kind task` answers `200`. The two responses are equal by an exact identity-and-state comparison.
  2. **The one race.** Both clients issue `node.claim` on alpha's first task through `issueAs`, both promises in flight, awaited together. Exactly one answer is `200` and the other is `409 lease-held`. The answer order is not asserted. The winner becomes `alphaActor` and the loser becomes `betaActor`, and every later phase names a role rather than a container.
  3. `betaActor` claims alpha's second task and answers `409 lease-held`, and its claim on **alpha itself** answers `409 lease-held`. That is the one-harness-per-objective rule of `018-claim-and-lease.md:25`.
  4. `betaActor` claims beta's first task and answers `200`, while `alphaActor` still holds its alpha lease. Two leases are live in one daemon at one time, asserted from both claim responses.
  5. Each actor works every sibling task of its own objective through `runHarnessTask`, in dependency order, and every report answers `200`.
  6. Each actor attests its own objective. Both objectives read `awaiting_approval`, and each `node show` returns the `attestedObjectId` its **own** harness attested, asserted different from the other.
  7. `node close` by a harness token is `403 actor-forbidden`. The configured human token closes alpha; `gamma` still reads `pending`. The same token closes beta; **`gamma` then reads `ready`, and gamma's first task reads `ready`.** That is the dependent objective the exit criterion names, and it moved because both dependencies closed.
  8. `kanthord event list`, run with the configured human token, shows each `lease.claimed` and each `outcome.reported` event with its own actor id and the actor kind `harness`. The scenario reads the printed records and never raw HTTP, because this epic ships the command. The two actor ids are asserted different.
  9. **The idempotency oracle.** Both actors send one identical `Idempotency-Key` on `node.claim` for **gamma's first task**, one node id, through `issueAs`. The first answers `200`. The second answers `409 lease-held`, and its body is asserted different from the first captured body, so it replayed nothing. That is the actor-scoped record key of `015-actor-identity.md:65,121`.
  10. `runTransportCases` runs from the second client, and `assertNoDisclosure` runs over both client containers.

  **What this scenario does not prove.** Every request except phase 2 is sequential, so it proves two identities, two namespaces and server-side arbitration, and it does not prove concurrent traffic. `src/services/storage/connection.ts:90-101` and the synchronous `node:sqlite` driver make two transactions non-interleaving in one process, per `013-external-drive-overview.md:117`, so phase 2 is the only assertion that needs two requests in flight.

- **`P1B-E3` — the takeover** — a new `scripts/e2e/lib/scenario/p1b-e3.ts`, driver `podman`, profile `fixture`, plan `two-objective`, mode `deterministic`. The daemon runs with `leaseTtlMs` of `2000`. The first client claims one task and records its fence, then stops calling `node heartbeat`. The second client polls `node claim` on that task every **250 ms** to a deadline of **60000 ms**: every answer before the expiry is `409 lease-held`, and the first `200` after it carries a **new** fence, asserted greater than the first. Recovery is claim-driven, so each poll runs the sweep and no background timer exists. **The scenario waits on wall clock, and it controls no clock**, because the daemon exposes no time API. The first client then calls `node report --outcome accepted --fence <old fence>` and receives `409 lease-held`. The non-effect is proved by three observables and never by a node field: the stale report response is `409 lease-held`; `node show` reads `running` before it and `running` after it; and `kanthord event list --type outcome.reported --subject <task id>`, run with the configured human token, prints **exactly one** record for that task after the second client reports, and that record names the second actor. A task carries no reported object id, so `node show` proves nothing about one. The second client's report then moves the task to `done`.

- **The defects this block returns to its siblings** — one is already known and no epic owns it. `scripts/e2e/lib/scenario/journey.ts:393` asserts `tasksAllPending: true`. EPIC 016 makes an imported plan hold a ready frontier, so `runJourney` fails for every scenario after EPIC 016 lands. **EPIC 016 owns that repair**, and it is a defect returned to EPIC 016 rather than work in this epic. This epic reuses `runJourney` unchanged and asserts the repaired oracle.
