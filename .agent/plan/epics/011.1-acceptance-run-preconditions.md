# EPIC 011.1 — Acceptance run preconditions

Status: **draft**.

## Goal

EPIC 012 produces one verdict, and that verdict must rest on a mechanism. Today six of its rules
rest on prose: the report never binds a green `npm run verify` to the commit under test, no command
turns a report into an exit status, the run tag comes from a non-portable shell command, the fixture
remote is used before its phase-1 acceptance rows are proved, a `passed` verdict needs no human, and
the product acceptance the epic demands can never change the outcome. Two inventories also close in
one direction only, so a table with no row schema passes.

This epic supplies each missing mechanism. It ships before EPIC 012 runs, because a defect found by
an acceptance run must be a defect in the product and never a defect in the acceptance procedure.

The verdict gains a second axis. A scenario axis stays machine-checked and untouched by judgment. An
acceptance axis carries the human confirmation: Aelita rehearses the whole run and reports it green,
then Ulrich drives the same surface and signs it. Phase 1 closes only when both axes are green.

## Non-goals

- **No new scenario, and no new oracle.** `docs/proposal/phase-1/README.md` declares the four
  scenario ids and their oracles. EPIC 011 implements them. This epic adds a precondition, a record
  and a verdict around them.
- **No change to a scenario journey.** `runJourney` and the two profiles keep their steps. The real
  profile changes where it reads its inputs, and nothing else.
- **No product code.** Every change is under `scripts/e2e/`, `src/domain/rows.test.ts`,
  `src/services/storage/schema-parity.test.ts` and two `docs/proposal/` files. The daemon and the CLI
  do not change.
- **No human step inside a scenario.** The human confirmation is a record beside the bundles, never a
  pause inside a run. A scenario stays executable unattended, so Aelita rehearses it as often as
  needed.

## Stories

- **The table inventory closes both ways** — `src/domain/rows.ts` holds nineteen row schemas, and
  `src/domain/rows.test.ts` proves every key of `rows` appears in `domain.md`. The reverse direction
  is open: a table created by a migration with no row schema passes today, and so does a table named
  in `domain.md` with no row schema. The phase-1 goal states the rule the reverse direction carries:
  every table of `domain.md` ships a row schema, and a phase-1 caller is not the test. Add the two
  reverse assertions. In `src/services/storage/schema-parity.test.ts`, assert that the set of tables
  in `sqlite_master` after `migrate()`, minus the SQLite internal tables, equals `Object.keys(rows)`
  exactly. In `src/domain/rows.test.ts`, parse the table list of `domain.md` and assert it equals
  `Object.keys(rows)` exactly, so a substring match no longer stands in for a set comparison.

- **The runner mints the tag** — `mintTag` in `scripts/e2e/lib/tag.ts` already produces a portable
  tag from a `Date` and a ULID, and the runner uses it when `--tag` is absent. An acceptance run
  needs one tag across four invocations, so the operator must mint it before the first one.
  `date -u +%Y%m%d%H%M%S%N` is GNU coreutils; BSD `date` emits a literal `N`, so the tag is malformed
  and a second collision is silent. Add `node scripts/e2e/run.mjs --mint-tag`, which prints one tag
  to stdout and exits zero. It claims no bundle directory, writes no file and takes no other option.
  `parseArguments` refuses it beside a scenario id, `--tag` and `--reclaim`.

- **The verify record** — `node scripts/e2e/run.mjs --record-verify --tag <tag>` runs `npm run verify`
  and writes `.data/acceptance-<tag>/verify.json`: the exact command, the exit status, the commit
  under test, the proposal revision and the start and finish timestamps. It exits with the verify
  exit status, so a failing regression suite fails the invocation. The record is a file in the run
  directory and never a field inside a scenario bundle, because a bundle is immutable evidence about
  one scenario. The **proposal revision** is the commit of the last change to `docs/proposal`, read
  as `git log -1 --format=%H -- docs/proposal`. That definition is the one the verdict and the report
  use, and it is recorded beside the commit under test so a report that carries both is unambiguous.

- **The real profile reads `.env.e2e`** — `scripts/e2e/lib/scenario/p1-e3.ts` reads six
  `KANTHORD_E2E_REAL_*` variables from `process.env`, and the repository already holds the throwaway
  credentials in `.env.e2e` behind `loadE2eEnv` in `scripts/e2e/env.ts`. Two sources of truth make
  Ulrich's run different from Aelita's rehearsal, and a difference in the setup invalidates the
  rehearsal. `checkPrerequisites` loads `.env.e2e` through `loadE2eEnv` and derives the origin, the
  default branch and the credential from `E2E_GH_REPO`, `E2E_GH_BASE_BRANCH` and `E2E_GH_TOKEN`. The
  token reaches the daemon host as a mode `0600` file the runner writes and removes, never as an
  argument and never as an environment variable. The plan path and the expected objective and task
  counts stay explicit options, because a real plan is authored per run. An absent or incomplete
  `.env.e2e` raises `unavailable` and names each missing key.

- **A scenario touches the product through the CLI and HTTP only** — `docs/proposal/README.md` states
  the rule, and `scripts/e2e/lib/scenario/discipline.test.ts` covers teardown discipline only. Ulrich
  verifies through the CLI and the API, so a rehearsal that reaches past them proves nothing about
  his run. Assert that no file under `scripts/e2e/lib/scenario/` imports from `src/`. The fixture
  harness under `test/helpers/remote/` stays permitted for the fixture profile, because it is the
  remote and not the product.

- **The fixture acceptance rows are proved before the journey** — `docs/proposal/README.md` requires
  each phase to prove its fixture subset before its scenarios run, and phase 1 repeats the rule.
  `createFixtureProfile` in `scripts/e2e/lib/profile/fixture.ts` creates the origin and goes straight
  to the journey. Add one probe that runs after the origin exists and before the journey starts, and
  that proves the three phase-1 rows against that origin: `HEAD` symref discovery, a `fetch`, and a
  `git-receive-pack` advertisement that refuses a wrong token. A failed row raises `unavailable`, so
  a scenario never proves less than it claims against a broken fixture. The bundle records each row
  and its result. The probe runs for the `local` driver and the `podman` driver, because both take
  the fixture profile, and it never runs for the real profile.

- **The proposal states what a human confirms** — two amendments, and nothing else changes in
  `docs/proposal/`.
  - `docs/proposal/phase-1/README.md`: the goal keeps "a human drives the daemon end to end", and the
    exit criterion gains the sentence that makes it checkable. A coding agent rehearses every
    scenario and reports the run green. Ulrich then drives the same journey through the same CLI and
    the same API, and confirms it. The confirmation is recorded, and the phase does not exit without
    it.
  - `docs/proposal/README.md`: "recorded separately" states what it already means and what it does
    not mean. Product acceptance is not an oracle and not a scenario. It carries its own verdict, and
    a phase exits on the scenario verdict and the acceptance verdict together.

- **The acceptance record** — one invocation of `--record-acceptance` writes
  `.data/acceptance-<tag>/acceptance.json`: the name, the drive confirmation, the judgment, the note
  text, the commit under test, the proposal revision and the timestamp. `--drive confirmed` states
  that a human drove the P1-E3 journey through the CLI and the API on that commit. `--judgment`
  covers the four subjects `docs/proposal/README.md` keeps out of every scenario: the first-run
  message, the validation finding set, the re-import suggestion set and the `plan export` rendering.
  A note is mandatory for `rejected` and for `not-confirmed`. The command refuses a tag that holds no
  bundle, and it refuses to overwrite an existing record, because a signature is not edited.

  ```
  node scripts/e2e/run.mjs --record-acceptance --tag <tag> --by <name> \
    --drive <confirmed|not-confirmed> --judgment <accepted|rejected> --note-file <path>
  ```

- **The verdict command, on two axes** — `node scripts/e2e/run.mjs --verdict <tag>` reads the run
  directory and returns one exit status. It writes nothing, and it modifies no bundle. It exits zero
  only when every condition holds:
  - **scenario axis** — every declared phase-1 scenario id has one bundle under this tag, and each
    bundle reports `passed`;
  - **scenario axis** — `verify.json` exists under this tag and reports exit status zero;
  - **scenario axis** — the commit under test of `verify.json` equals the commit of every bundle, so
    one tag is one commit and a report never mixes a pre-fix bundle with a post-fix one;
  - **scenario axis** — the proposal revision is identical across every record that carries it;
  - **acceptance axis** — `acceptance.json` exists under this tag, reports `drive: confirmed` and
    `judgment: accepted`, and names the same commit under test.

  A failing condition prints the named reason, names the axis it belongs to, and exits non-zero. It
  reuses the runner exit codes of `scripts/e2e/lib/main.ts`: `2` for an argument fault, `3` when a
  bundle or a record is absent, and `1` when a present artifact reports a failure. This command is
  the mechanism behind "a blocked outcome is never reported as a pass": a report claiming `passed` is
  checkable by one command, and the report records that command and its exit status.

  `--verdict <tag> --scenarios-only` checks the scenario axis alone and exits zero on it. That is
  what Aelita runs to report a rehearsal green, and it can never close the phase.

- **The driver matches the mechanism** — this story ships no test. It changes exact text in
  `.claude/commands/e2e.md`, and a reviewer checks each string. `--mint-tag` replaces
  `date -u +%Y%m%d%H%M%S%N` at the top. "The run" gains `--record-verify` and the rehearsal through
  `--verdict <tag> --scenarios-only`. "Product acceptance" gains `--record-acceptance` and stops
  saying the judgment never gates. "The report" gains the verify record, the acceptance record and
  the `--verdict` exit status. `passed` is redefined on two axes. The line "Remote branches a run
  created are named in the report and deleted by a human." is deleted, because no phase-1 operation
  writes a ref on the remote.

  `.agent/plan/epics/012-phase-1-acceptance-run.md` already carries these decisions. It was amended
  ahead of this epic, so the two documents state one procedure.

## Verification gate

Gates: `npm run verify`

Proof:

```bash
TAG=$(node scripts/e2e/run.mjs --mint-tag) \
  && node scripts/e2e/run.mjs P1-E1 --tag "$TAG" \
  && node scripts/e2e/run.mjs P1-E2 --tag "$TAG" \
  && node scripts/e2e/run.mjs --record-verify --tag "$TAG" \
  && node scripts/e2e/run.mjs --verdict "$TAG"; test $? -eq 1 \
  && echo "PASS EPIC-011.1"
```

The verdict exits `1` here, because P1-E4 and P1-E3 hold no bundle under this tag and no acceptance
record exists. That is the assertion: an incomplete run is not a pass, and an unsigned run is not a
pass.

Coverage required beyond the Proof:

- `--mint-tag` prints one tag that `parseArguments` accepts, and two invocations print two tags. It
  creates no directory under `.data/`.
- `--mint-tag` beside a scenario id, `--tag` or `--reclaim` is an argument fault.
- `--record-verify` writes the command, the exit status, the commit under test, the proposal revision
  and both timestamps, and it exits with the verify exit status on a failing verify.
- `--record-acceptance` refuses a tag with no bundle, refuses a second write for one tag, and refuses
  `rejected` or `not-confirmed` with no note.
- `--verdict` exits non-zero, and names the reason and the axis, for each of: a missing scenario
  bundle, a bundle reporting `failed`, a bundle reporting `unavailable`, an absent verify record, a
  verify record with a non-zero exit status, a bundle whose commit differs from the verify record, an
  absent acceptance record, `drive: not-confirmed`, `judgment: rejected`, and an acceptance record on
  another commit.
- `--verdict --scenarios-only` exits zero on a complete scenario axis with no acceptance record, and
  it exits non-zero when the scenario axis fails.
- `--verdict` modifies no file under the run directory, asserted by comparing every file digest
  before and after.
- The fixture probe raises `unavailable` when the origin refuses `HEAD` discovery, when the fetch
  fails, and when the receive-pack advertisement accepts a wrong token. A passing probe records three
  rows in the bundle.
- The fixture probe runs before the first journey command, asserted by command order.
- P1-E3 raises `unavailable` and names each missing key when `.env.e2e` is absent or incomplete, and
  the real token appears in no printed command, no bundle and no log.
- No file under `scripts/e2e/lib/scenario/` imports from `src/`.
- A migration that creates a table with no key in `rows` fails `schema-parity.test.ts`, and a table
  name added to `domain.md` with no row schema fails `rows.test.ts`.
