# EPIC 019 — Outcome report and aggregation

Status: **draft**.

## Goal

A harness reports the outcome of the task it holds through `POST /v1/node/:id/report`, and the daemon applies the transition. An accepted report moves the task `running → done` and records the object id the harness produced. A rejected, a failed or a cancelled report closes the attempt and returns the task to `ready`, and the attempt limit of the run moves it to `blocked` with reason `attempt-limit`. When every task of an objective is terminal, the daemon computes the projection and offers it, and the harness that holds the objective lease attests one combined object id through the same route. That attestation moves the objective `running → awaiting_approval`. A `human` actor then closes the attested objective, it reaches `done` or `partial` with no integration and no candidate, and the initiative rolls up under the same rule. `node.show` returns the attested object id and the computed projection, so the human reads what they close. A dependent objective becomes `ready` inside the closing transaction. `event.list` publishes a typed payload schema for every event type the daemon writes, so `outcome.reported` is a contract rather than a producer-side detail. `src/main.ts` binds the handler, `src/cli/program.ts` registers `node report`, `node attest` and `node close`, and one daemon test drives the whole loop through the real composition root.

## Non-goals

- **No integration and no git.** kanthord merges nothing and produces no object id. The harness owns its working tree, its branches and its merges. `docs/proposal/api/integration.md` stays phase 2, and no path of this epic calls `services/git`.
- **No candidate and no phase-2 approval gate.** `docs/proposal/phase-2/gates-and-approval.md` stays phase 2. `node.approve` stays `stubbed`, no candidate row is written, and the objective carries the attested object id in place of a frozen candidate, which is the amendment `014-external-drive-contract.md:22` lands.
- **No object verification.** The daemon runs no git command, so it never proves that an attested object exists, descends from a task object, or belongs to the objective repository. The attestation records who claims what, and `013-external-drive-overview.md:102` decides that for the block. No check result and no agent invocation row is written.
- **No drive-mode pin implementation.** The pin belongs to EPIC 014 as contract data, and EPIC 018 enforces it at the claim. This epic reads the pin and implements none of it.
- **No internally driven close.** `112-objective-gate-and-mr` owns it. This epic owns the externally driven close only.
- **No `node.discard`, `node.waive`, `node.abandon` and `node.unblock`.** The four rows of `docs/proposal/api/outcome.md:11-14` stay `stubbed`, at phase 2 and phase 3. No route of this block writes `discarded` at any level.
- **No per-node graph write.** EPIC 017 owns `node.create`, `node.update` and `node.delete`.
- **No claim, no heartbeat and no release.** EPIC 018 owns the three routes, the lease service, the execution service and the sweep. This epic consumes them.
- **No readiness derivation.** EPIC 016 owns `pending → ready` and the closed `PlanStore` mutation API. Every node state write of this epic runs through `setNodeState`.
- **No migration.** This epic adds no column and no table. The object id lands in the existing nullable `head_oid` of `run` and of `attempt`, which `018-claim-and-lease.md:57` reserves for it, and the `outcome` `CHECK` of `docs/proposal/database/attempt.md:15-16` already admits the four values this route accepts.
- **No registry-wide completeness sweep and no P1B scenario.** EPIC 020 owns the sweep over every operation of the block and the inventory assertion over the whole command set. **This epic binds and registers everything it adds, and defers no wiring to EPIC 020.**
- **No lease field on a node view.** `110-scheduler-leases-and-the-general-worker.md:14` gives the lease field to EPIC 111. This epic adds two objective fields to `node.show` only, and it adds no field to `node.list`.

## Decisions

These are settled here. No story revisits one.

- **One route, and the node kind decides the behaviour.** `node.report` is one operation on one path. A task report applies the reported outcome. An objective report attests an object id or closes the gate. An initiative is `400 invalid-request` with `details.refusal = "initiative-not-reportable"`, which follows the `initiative-not-claimable` refusal of `018-claim-and-lease.md:37`. This is the idiom of `docs/proposal/api/outcome.md:16`: the client cannot pick the wrong operation for the node it names. Two routes were refused because the client would then carry the kind rule that the daemon already holds.
- **The objective result is attested, and it is never inferred.** The object id of the last task to finish is not an objective result. `018-claim-and-lease.md` admits many sibling task claims by one actor, and the daemon runs no git, so it cannot relate one task object to another. An objective therefore reaches `awaiting_approval` only through an explicit objective report that carries the combined object id its actor attests. Report order decides nothing.
- **Aggregation computes the projection, and it never transitions an objective.** When every task of an objective is terminal, the daemon computes `done` or `partial` and offers it through `node.show` and through the task report response. The objective stays `running` until somebody attests. An objective whose tasks are all terminal and which nobody attested stays `running`, and that state is legible rather than defective.
- **The drive mode of an objective is pinned at its first claim.** The pin holds while the objective is non-terminal. An internal worker cannot claim an objective that holds an external run in its history, and an external harness cannot claim an objective that holds an internal run. **EPIC 014 declares the pin as contract data, and EPIC 018 enforces it inside `claimNode`.** The pin removes sequential driver mixing, so no close path depends on which driver finished last. **EPIC 018's claim-side run reuse must reject an active run whose driver is not the driver of the claim.** A blind adoption would open an external attempt under an internal run, which the composite driver foreign key of `018-claim-and-lease.md:57` refuses at the database.
- **The separation from `112-objective-gate-and-mr` rests on the pin.** EPIC 112's freeze path checks state, tasks, workspace, lease and run input, and its approval path checks state, candidate, workspace, checks and leases. **Neither path holds a `run.driver` guard.** `closeObjective` of this epic keeps its own `driver = 'external'` assertion as a cheap defence, and the pin is the mechanism that makes the two paths disjoint.
- **The body carries the lease fence, and authentication carries the owner.** `018-claim-and-lease.md:45` states the requirement and names the code. **The request body carries no `owner` field.** The command derives the owner from the authenticated actor id, and it requires one identity: the authenticated actor id equals the lease owner. A body-supplied owner would let a second authenticated actor report another actor's work from a known owner and fence.
- **A live lease means a matching owner, a matching fence and an unexpired row.** The command captures one `now` and refuses a lease whose `expires_at` is at or before that `now`, even when the owner and the fence match. Recovery is claim-driven per `018-claim-and-lease.md:43`, so an expired row keeps its owner and its fence until some claim sweeps it. Without the expiry check a harness whose authority ended at the TTL still reports. Every refusal of this rule is `409 lease-held` and writes nothing.
- **Per-branch actor policy, and the route admits both kinds.** `allowedActors` is per operation, and `node.report` admits `human` and `harness`. The task branch and the attestation branch admit `harness` only, because the transition rows they write carry `actorKind: "harness"`. The close branch admits `human` only, because `015-actor-identity.md:50` reserves an approval decision for a human. Each refused kind is `403 actor-forbidden` from inside the command, with the same code the registry gate raises.
- **Four task report outcomes, and `timed-out` is not one of them.** A timeout is a daemon fact about an internal attempt with a `timeout_ms` budget, and `014-external-drive-contract.md:28` makes `timeout_ms` null for every external attempt. The task variants admit `accepted`, `rejected`, `failed` and `cancelled` only, so `timed-out` is `400 invalid-request`.
- **Attempt accounting takes `MAX(attempt_no)` over the surviving attempts of the active task run.** `docs/proposal/database/attempt.md:24` and `accountAttempts` at `src/domain/attempt-accounting.ts:59-82` derive the counter from that maximum and never from a row count. **A gap is supported**, so a deleted or an absent number never lowers the counter. `attempt` carries `UNIQUE (run_id, attempt_no)`, so the number is unique inside its run. No node column and no run column holds a count. A report increments nothing; it closes the row that the claim opened, and the next claim mints the next number.
- **A rejected, a failed and a cancelled report each keep the task run active under the limit.** The run is what carries the attempt count, so a run that ended on every rejection would reset the counter and the limit would never be reached. The run ends only when the task leaves `running` for a state that is not `ready`: outcome `done` on an accepted report, and outcome `blocked` at the attempt limit. This is the one way a `cancelled` report differs from `node.release`, which ends the run per `018-claim-and-lease.md:98`.
- **Every closed attempt spends a try, whatever its outcome.** `accountAttempts` at `src/domain/attempt-accounting.ts:71-74` marks the run exhausted only when the newest attempt ended `rejected`. A harness that reports `failed` for ever, or `cancelled` for ever, would then never block. **Three cancellations under limit three reach the limit and block the task.** The widened rule is one clause: the run is exhausted when the counter is at or above the limit and the attempt at the counter has ended. This epic amends `docs/proposal/phase-1/state-machine.md:118` and the prose of `docs/proposal/database/attempt.md:24` with the same clause.
- **`attemptsRemaining` is `Math.max(0, run.attempt_limit - accounting.counter)`.** The value clamps at zero, so it is never negative when a limit edit lowers `settings.attemptLimit` under a counter that already passed it.
- **The limit compared is the limit of the run.** `run.attempt_limit` is stamped when the run opens, per `018-claim-and-lease.md:83`. A configuration edit therefore never rewrites the limit of work already in flight, which is the rule `docs/proposal/api/execution.md` already applies to the resolved worker.
- **The three levels do not share one aggregation rule, and this epic reads the table at `docs/proposal/phase-1/state-machine.md:37-41` rather than restating it.** `aggregate` at `src/domain/aggregation.ts:17`, `objectiveOutcome` at `src/domain/outcome.ts:17` and `initiativeOutcome` at `src/domain/outcome.ts:25` already hold that table as code, and no production file imports one of them today. This epic is their first consumer, and it writes no second projection.
- **The initiative rule is the table, and the table has three outcomes.** `aggregate("initiative", states)` returns `done` when every objective is `done`, `discarded` when every objective is `discarded`, and `partial` in every other terminal mixture. A single `partial` objective therefore makes the initiative `partial`, and an all-discarded initiative is `discarded` and never `partial`. `initiativeOutcome(projected, "not-applicable")` returns that projection unchanged, because `docs/proposal/phase-1/state-machine.md:43` records MVP end-to-end detection as `not-applicable`. The roll-up runs when every objective of the initiative is terminal, and it writes nothing otherwise.
- **`aggregateInitiative` carries all three write paths, and one of them is unreachable in this block.** The `discarded` path ships because `initiativeOutcome` returns `discarded` and a command with no write path for a value its own function returns is incomplete. No route of this block writes a `discarded` objective, so the path is reachable only from a fixture that writes objective states directly. A later discard route needs no second change.
- **Aggregation was deferred from EPIC 016 to here, and the reason was the route.** `016-readiness-applied.md:18` states it: no route wrote a terminal child until this epic, so an aggregation story in EPIC 016 would have shipped a rule that nothing could reach. `node.report` is that route.
- **An object id is 40 or 64 lowercase hexadecimal characters.** `src/domain/column.ts:6` declares `objectId` over that union, and `docs/proposal/database/README.md:43` states the same rule. Every schema of this epic reuses `objectId` and hard-codes no length.
- **The close derives its state and never reads it from the request.** The close request carries `acknowledgePartial` and nothing else. The daemon computes `done` or `partial` from the task states. A derived `partial` with no acknowledgement is `409 acknowledgement-required`, which is the meaning that code carries at `docs/proposal/api/README.md:180` and the rule at `docs/proposal/phase-1/state-machine.md:96`. A request that names a state would be a state field on a route, and `docs/proposal/api/graph.md:9` refuses that.
- **A task report frees the task lease and never the objective lease.** `018-claim-and-lease.md:30` publishes it and this epic obeys it. The objective lease is acquired at the first task claim and is held through every task claim, every task release and every task report of its owner. `reportOutcome` therefore calls `lease.release` on the task subject alone. Three consequences are load-bearing. The attestation that follows the last task report meets a live objective lease, so `reportObjective` answers `200` rather than `409 lease-held`. Two sequential sibling tasks stay with one harness, because no window opens between two reports. A harness that abandons the objective loses it at the expiry sweep of `018-claim-and-lease.md:31`, so the objective is never stuck.
- **The attestation frees the objective lease, so the close carries no fence.** The attestation runs under a live objective lease and releases it in the same transaction. No lease is live at `awaiting_approval`, so the state check is the whole guard of the close.
- **The objective run ends at the close, not at the attestation.** The lease and the run are separate rows. The run stays active from the claim to the close, so it carries the attested object id while the human reads it, and `activeRun: true` holds for the `object-reported`, `human-close` and `human-close-partial` rows of `014-external-drive-contract.md:33`.
- **The reason of a rejected or a failed report lives in the event payload.** `attempt` holds no reason column, and this epic adds no migration. The `outcome.reported` event carries it, and the story below fixes every payload key by name, because a payload left to build time breaks the determinism rule.
- **The event payload is a published contract, and this epic owns it.** `src/http/contract/event.ts:26` declares `payload: z.unknown()`, so every payload of the block is asserted inside its producer and published to no client. This epic is the last producer of the block, so it lands the typed schemas for **every** event type the daemon writes, its own included. A partial map is worse than none: a client cannot tell an undeclared type from an untyped one, and no honesty test is total over a partial map. **The schemas are published as named OpenAPI components, and `eventView.payload` stays `z.unknown()`.** A closed union of the current shapes cannot parse a payload an earlier build wrote, so a typed `eventView.payload` would fail `event.list` on exactly the history `eventView.type` stays `z.string()` to serve. A named component per type is what makes the shape public; the route's runtime parse never was.
- **`eventTypes` is append-only, and a payload schema widens and never narrows.** An `event` row is durable, so a type a build no longer writes still sits in a migrated database. A member is therefore never removed from `eventTypes`, and a key is never removed from a payload schema; a later epic adds an optional key instead. Without that rule `event.list` fails on the history it exists to serve. **Append-only means no removal, not appended at the end**: a new member takes its bytewise position in the tuple. **An append-only registry therefore never equals a scan of the current source tree.** A retired producer leaves a member no scan can find, so the honesty mechanism asserts two subset relations plus a named `retiredEventTypes` difference, and never a bare set equality.
- **The report writes one `outcome.reported` event plus one event per transition.** The attestation and the close each write one event per transition and no extra event: the transition event names the actor, the target state and the object id, so a second event would record nothing new.

The function reads no clock, mints no identity and holds no state pair of its own: each branch names an `ExternalTriggerId`, and the caller reads the pair from `externalTransitions`. `nodeState` and `trigger` are two representations of one destination, so the test asserts they agree row by row.

- **`services/execution` gains two methods** — `src/services/execution/index.ts` and `src/services/execution/sqlite.ts` of `018-claim-and-lease.md:83`. `stampRunHead(transaction, input)` writes `head_oid` on an active run and moves no other column. No second capability is added, so `src/domain/layout.test.ts` needs no edit in this epic.

- **`reportOutcome`, the command** — `src/commands/outcome/report-outcome.ts`, dependencies `{ storage, plan, lease, execution, events, clock, reportObjective, closeObjective, instanceId }`, input `{ nodeId, actorId, actorKind, body }`. `reportObjective` and `closeObjective` arrive injected, because `commands/` never imports `commands/`; `018-claim-and-lease.md:104` sets that precedent for `sweepExpiredExternalLeases`. One transaction, one `now` from `clock.now()`, in this exact order. It loads the node; an unknown node is `404 not-found`, and an initiative is the `400` of the Decisions. A `report` value that does not match the node kind is `400 invalid-request` with `details.refusal = "body-kind-mismatch"`. An objective with `report: "attested"` delegates to `reportObjective`, an objective with `report: "closed"` delegates to `closeObjective`, each with the same transaction, and it returns that result. For a task it refuses a `human` actor with `403 actor-forbidden`, then asserts the node is `running`, and any other state is `409 illegal-transition` naming the current state. It reads the live task lease and refuses `409 lease-held` on three conditions: an owner other than the authenticated actor id, a fence other than the current one, and an `expires_at` at or before the captured `now`. It reads the active task run, closes the open attempt with the reported outcome and the reported object id through `closeAttempt`, reads the attempts back, calls `accountAttempts` with `run.attempt_limit`, and calls `taskReportEffect`. It writes the task state through `plan.setNodeState`, under the trigger `taskReportEffect` returns — `outcome-accepted`, `attempt-rejected`, `attempt-failed`, `report-cancelled` or `attempt-limit-reached` — stamps `head_oid` and ends the task run when the effect names a run end, and releases the **task** lease through `lease.release`. **It never touches the objective lease and never ends the objective run.** `018-claim-and-lease.md:30` is the rule: the objective lease is held from the first task claim until `reportObjective` attests, so the attestation always meets the live lease it requires, and no second actor takes a sibling task between two reports of one harness. A report that released the objective lease would answer the following attestation `409 lease-held` and would make the claim-to-close journey impossible. It then reads the sibling task states and computes the objective projection, and it writes no objective state. The response carries `nodeId`, `kind`, `state`, `blockReason`, `attemptId`, `attemptNo`, `attemptsRemaining`, `objectId`, `objectiveState` and `objectiveProjection`. `objectiveProjection` is `done` or `partial` when every sibling task is terminal, and null otherwise, so the harness reads its own attestation cue from the response that made the last task terminal.

- **The `outcome.reported` event payload, fixed key by key** — the same command. The event type is `outcome.reported`, `subjectKind` is `node`, `subjectId` is the task identity, `actorKind` is `harness` and `actorId` is the authenticated actor id. The payload holds exactly these keys, in this order: `runId`, `attemptId`, `attemptNo`, `outcome`, `reason`, `objectId`, `attemptsRemaining`, `fromState` and `toState`. `reason` is the request reason or null. `objectId` is the accepted object id or null. This is the durable home of a rejected or a failed reason, because `attempt` holds no reason column and this epic adds no migration.

- **`reportObjective`, the attestation command** — `src/commands/outcome/report-objective.ts`, exported as `reportObjective(dependencies, transaction, input)`, dependencies `{ plan, lease, execution, events, clock, instanceId }`. It refuses a `human` actor with `403 actor-forbidden`. It refuses a node that is not `running` with `409 illegal-transition`. It applies the same three-condition lease guard as the task branch, on the objective lease, with `409 lease-held`. It reads every task of the objective through `PlanStore.readAllNodes`, which costs one full-graph read at the bound `018-claim-and-lease.md:47` accepts, and it refuses `409 illegal-transition` while any task is non-terminal. It calls `aggregate("objective", states)` of `src/domain/aggregation.ts:17` and `objectiveOutcome` of `src/domain/outcome.ts:17`, and it refuses a `discarded` projection with `409 illegal-transition`, because `awaiting_approval` needs at least one `done` task. It writes the objective state through `plan.setNodeState` under trigger `object-reported`, stamps the attested object id on the active objective run through `stampRunHead`, releases the objective lease, and ends no run. The event is `node.awaitingApproval`, attributed to the attesting harness, with the payload `from`, `to`, `reason: "object-attested"`, `objectId`, `projection` and `objectiveRunId`.

- **`closeObjective`** — `src/commands/outcome/close-objective.ts`, exported as `closeObjective(dependencies, transaction, input)`, dependencies `{ plan, execution, events, clock, aggregateInitiative, instanceId }`. It refuses a `harness` actor with `403 actor-forbidden`. It refuses a node that is not in `awaiting_approval` with `409 illegal-transition`. It reads the active objective run and refuses `driver = 'internal'` with `409 illegal-transition`; the drive-mode pin of EPIC 014 is what makes that case unreachable, and this assertion is the cheap defence. It refuses a run whose `head_oid` is null with `409 illegal-transition`, because `014-external-drive-contract.md:33` makes the reported object id required on both close rows. It derives `done` or `partial` from the task states through `aggregate` and answers `409 acknowledgement-required` when the derived state is `partial` and the request omits `acknowledgePartial`.
