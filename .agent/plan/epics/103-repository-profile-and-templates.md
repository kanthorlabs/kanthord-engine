# EPIC 103 — Repository profile and templates

Status: **blocked**. EPIC 015 of the external-drive block removes the configured `actor` binding from every handler, and it adds one error code before this epic adds its own. This epic becomes ready when EPIC 015 closes.

## Goal

A repository carries one `kanthord.profile/v1` profile in SQLite: the frontmatter contract, the role-headed body, the `checks` map, and the template provenance. `src/domain/profile-document.ts`, `src/domain/profile-check.ts`, `src/domain/profile-render.ts` and `src/domain/profile-parse.ts` hold the pure rules, and they reuse the canonical serialization of `docs/proposal/phase-1/plan-format.md` through `quoteScalar` and `comparePaths` rather than a second format. `src/domain/profile-template.ts` ships the one `nodejs` template with its id, version and canonical payload. `src/services/profile/` reads and writes the `profile` row of `src/services/storage/migration-0001-core-entities.ts`, `src/commands/profile/` writes it, and `src/queries/profile/export-profile.ts` reads it. `profile.instantiate`, `profile.export` and `profile.import` move from `stubbed` to `routed` in `src/http/contract/instruction.ts`. An export and a re-import round-trip byte-identically, and a check that cannot fail is rejected with its name.

## Non-goals

- No per-objective profile pin. EPIC 110 records `workspace.profile_blob` when the objective workspace is created.
- No `profile.verify`, no gate A and no gate B. EPIC 109 owns both gates and the `profile-gate` check results.
- No channel composition and no `instructions.resolve`. EPIC 104 consumes the `checks` map and the role body as one channel.
- No check execution. EPIC 107 runs a declared check. This epic validates a declaration statically and runs no process.
- No CLI command. EPIC 114 drives `profile instantiate` through onboarding.
- No template catalogue route. `template.list` and `template.show` stay `stubbed`, because phase 2 ships one template and the human names it. `docs/proposal/phase-2/instructions-and-profiles.md` defers detection and the wider library.
- No onboarding detection. The client supplies the template id.

## Stories

- **The `kanthord.profile/v1` schema** — `src/domain/profile-document.ts` holds the zod contract of the document, and it imports `zod` only. The frontmatter carries exactly three keys: `schema`, which must equal the literal `kanthord.profile/v1`; `template`, a map of `id`, `version` and `digest`, where `digest` matches `/^sha256:[0-9a-f]{64}$/` like `blobHash` of `src/domain/blob.ts`; and `checks`, the map of story two. An extra frontmatter key is a finding, because the frontmatter holds only what the daemon runs or routes on. The body is a list of role sections, each keyed by one role of `agentKinds` in `src/domain/agent.ts`. `src/domain/profile-finding.ts` holds the closed finding code list `body-preamble-unexpected`, `check-cannot-fail`, `check-missing`, `check-name-invalid`, `check-run-empty`, `check-run-invalid`, `check-timeout-invalid`, `document-unparsable`, `frontmatter-invalid`, `role-heading-duplicated`, `role-heading-unknown`, `schema-unknown`, `template-digest-mismatch`, `template-unknown` and `template-version-unknown`, the shape `{ code, locator: string | null, message }`, and one sorter. `locator` names the check name or the role heading. The sorter orders by `code` through `comparePaths` of `src/domain/plan-path.ts`, then by `locator`, and a `null` locator sorts first. It copies the shape of `src/domain/plan-finding.ts` and shares no code list with it, because a plan finding and a profile finding never appear in one report.
- **The `checks` map, and the vacuous-command lint** — `src/domain/profile-check.ts` validates one entry. A check name is `unit` or `e2e`, and no other name is legal, because `docs/proposal/phase-2/instructions-and-profiles.md` states that the frontmatter holds only what the daemon runs or routes on. Any other name is `check-name-invalid` with the name as the locator. The name `unit` is required, and an absent `unit` is `check-missing` with locator `unit`. The name `e2e` is optional: the same file states that a repository with no end-to-end suite declares no `e2e` command. An entry carries `run`, a non-empty sequence of strings, and `timeout`, a string matching `/^[1-9][0-9]*m$/`. Canonical serialization re-emits the declared token, so a closed token form keeps an export byte-identical and keeps the millisecond parse deterministic. The minute is the one unit, and it is the unit of the example in `docs/proposal/phase-2/instructions-and-profiles.md`. An empty `run` is `check-run-empty`. A non-string element, an empty element and an element holding a NUL byte are `check-run-invalid`. A timeout outside the pattern is `check-timeout-invalid`. A pure `timeoutMilliseconds` parse converts the token, and the renderer emits the token the document declared.

  **The vacuous-command lint is a conservative static rule over a closed set of command forms, and no process runs.** Take `program`, the last `/`-separated segment of `run[0]`. The lint returns `check-cannot-fail` when:

  - `program` is `true` or `:`;
  - `program` is one of `sh`, `bash`, `zsh` or `dash`, and the element after the first `-c`, trimmed of leading and trailing whitespace, equals `true`, `:` or `exit 0`, or ends with `|| true`, `|| :`, `; true` or `|| exit 0`.

  Nothing else is rejected. `echo` and `printf` stay accepted, because a write error makes each one fail. `["exit", "0"]` stays accepted, because `exit` names no executable and the spawn fails. The lint is static, so it is deterministic and it needs no workspace. It catches a spelling, never a meaning: `["env", "true"]`, `["sh", "-c", "exit 0 # ok"]` and `["node", "-e", "process.exit(0)"]` all pass it. `docs/proposal/phase-2/gates-and-approval.md` states that import cannot prove a check is runnable or meaningful. EPIC 109 owns the real proof: gate B runs the check at an exact commit and applies the negative control.

- **The canonical render, and the profile hash** — `src/domain/profile-render.ts` renders one document, and the byte order is fixed here. Frontmatter key order is `schema`, `template`, `checks`. `template` renders as a block map with key order `id`, `version`, `digest`. `checks` renders its entries sorted bytewise by check name through `comparePaths`, and each entry renders `run` then `timeout`. `run` renders as a block sequence in the declared order, never sorted, because the order is the argument vector. Every scalar is double-quoted through `quoteScalar` of `src/domain/plan-render.ts`, so the escaping rule is the one rule the plan format already carries. No flow collection appears in the output, although the example of `docs/proposal/phase-2/instructions-and-profiles.md` uses one and import accepts it. The body renders the role sections in the order of `agentKinds` in `src/domain/agent.ts`: `general@1`, `swe@1`, `te@1`, `re@1`. An absent role is omitted. A section is the line `## <role>`, one blank line, then the section text. One blank line separates two sections, and the document ends with exactly one LF. Output is UTF-8 and LF only. The profile content hash is `BlobStore.hash` of `src/services/blob/index.ts` over those bytes, so it equals the `content_blob` of `docs/proposal/database/profile.md` by construction. A command computes it, never `domain/`, because `domain/` imports `zod` only. Two hashes exist, and they cover different bytes: the profile content hash covers the whole rendered profile document, and the template digest of story five covers the canonical template payload. `docs/proposal/phase-2/instructions-and-profiles.md` and `docs/proposal/api/instruction.md` name both.
- **Markdown import with its findings** — `src/domain/profile-parse.ts` takes one already-read frontmatter value and one body string, and it returns a parsed profile or a finding list. It reads no document itself, so it stays pure. The command calls `DocumentReader.read` of `src/services/document/index.ts`, catches `DocumentError`, and builds the `document-unparsable` finding, because `DocumentError` belongs to a service and `domain/` imports `domain/` and `zod` only. The body normalizes through `normalizeBody` of `src/domain/plan-body.ts`, so CRLF and a lone CR become LF and the body ends with exactly one LF. The parser splits the body on a line that begins `## `. Text before the first role heading is `body-preamble-unexpected`. A heading that names no role of `agentKinds` is `role-heading-unknown` with the heading text as the locator. A repeated role is `role-heading-duplicated`. **Validation collects every finding and stops at none**, like `validateDocuments` of `src/domain/plan-validate.ts`, because a human who edits a profile by hand wants one round trip. The returned list is sorted by the sorter of story one.
- **The `nodejs` template** — `src/domain/profile-template.ts` holds the one template as data, with id `nodejs` and version `1.0.0`. Its `checks` map declares `unit` only, with `run` of `["npm", "test"]` and `timeout` of `10m`; it declares no `e2e`. Its body holds one section per role, in the `agentKinds` order, with exactly this prose: `general@1` — `Change the smallest number of files that satisfies the task.`; `swe@1` — `Keep every module inside the import boundaries the repository declares.`; `te@1` — `Write one test per behaviour, and assert an exact value.`; `re@1` — `Judge only the acceptance criteria of the task.`. The module exports `canonicalTemplatePayload`, the bytes of the template document rendered through story three with the frontmatter keys `schema`, `template` and `checks`, where the `template` map carries `id` and `version` only. **The payload omits `digest`, so the digest is never defined over bytes that hold it.** The template digest is `BlobStore.hash` over that payload, and a command computes it, because `domain/` runs no hash. An instantiated profile document adds `digest` to its `template` map, so the profile document differs from the payload the digest covers. An instantiated profile records the template id, version and digest, so a later template change is a diff the human reads. A template id that is not `nodejs` is `template-unknown`, a version that is not `1.0.0` is `template-version-unknown`, and a digest that does not equal the digest the command computed over `canonicalTemplatePayload` is `template-digest-mismatch`. The command produces those three findings, because the digest comparison needs the hash capability.
- **The profile store** — `src/services/profile/index.ts` declares `ProfileStore` with `read(transaction, repositoryId)` returning the row of `src/domain/profile.ts` or `null`, and `upsert(transaction, row)`. `src/services/profile/sqlite.ts` implements it against the `profile` table, and the `repository_id` unique constraint of `src/services/storage/migration-0001-core-entities.ts` keeps one profile per repository. The interface names `Transaction` of `src/services/storage/index.ts`, because the write of story seven persists inside the caller's transaction. It copies the shape of `src/services/plan/index.ts`. The capability directory is new, so the directory list of `src/domain/layout.test.ts` gains `profile` between `plan` and `storage`, and the count in its suite name grows by one, on top of the names EPIC 102 and every earlier epic add.
- **Instantiate and import, each in one storage transaction** — `src/commands/profile/instantiate-profile.ts` takes `storage`, `profiles`, `blobs`, `ids`, `clock` and `events`, and it takes the repository id, the template id, the confirmed fields and `actor`. The confirmed fields are a `checks` map holding `unit`, `e2e` or both, and each supplied entry replaces the whole template entry for that name. The command validates the merged map through `src/domain/profile-check.ts`, so a confirmed field passes the same rules and the same vacuous-command lint as an imported one, and it throws with every finding when the list is not empty. It then computes the template digest, renders the merged document, hashes it, and inside **one** `storage.transact` writes the blob through `BlobStore.put`, mints the id through `ids.mint("profile")`, writes the row with `updated_at` from `clock.now()`, and appends the `profile.instantiated` event. The row write and its event append therefore commit together. It refuses a repository that already holds a profile with `illegal-transition`, and it names the existing content hash. `src/commands/profile/import-profile.ts` takes the same dependencies plus `reader`, and it takes the document text, `fromHash` and `actor`. It reads the frontmatter, validates the schema, the `checks` map and the role headings through `src/domain/profile-parse.ts`, compares the template triple, and throws with every finding, sorted by the sorter of story one, when the list is not empty. It then opens one transaction, compares `fromHash` against the stored `content_blob`, refuses a mismatch with `stale-revision`, re-renders the accepted document canonically, writes the new blob, moves the pointer, and appends `profile.imported` in that same transaction. `fromHash` is `null` for the first import of a repository. The old blob stays under its own hash, so anything that cited it keeps its meaning. Neither command reads a working tree, because the database is canonical.
- **The two events** — both events carry subject kind `repository` and the repository id as `subjectId`, because the profile row is one per repository and the human reads the repository history. Both carry `actorKind: "human"` and `actorId` from the `actor` input, and **the handler supplies the authenticated actor, never a configured name**. `015-actor-identity.md:70` drops every `actor: settings.actor` binding of `src/main.ts`, and `015-actor-identity.md:58` puts the resolved actor on `HandlerContext` of `src/http/server/app.ts`, so each handler reads the actor from its handler context and passes its id. Both routes admit `human` only, per the authorization rule of `015-actor-identity.md:62`, so `actorKind` stays `human`. `profile.instantiated` carries the payload `{ profileId, contentBlob, templateId, templateVersion, templateDigest }`. `profile.imported` carries the payload `{ profileId, contentBlob, fromBlob }`, where `fromBlob` is `null` for the first import. Every payload field is a value the command already holds, so no payload holds a timestamp and a snapshot stays deterministic.
- **Export** — `src/queries/profile/export-profile.ts` takes `storage`, `profiles` and `blobs`, reads the row, decodes the blob and returns the document text with its content hash. It renders nothing, because the stored blob is already canonical, so export is a byte copy and the round trip cannot drift. It refuses an absent profile with `not-found`, which `src/http/contract/errors.ts` already declares at status `404`. This epic adds no code for that refusal.
- **The three routes move from `stubbed` to `routed`** — `src/http/contract/instruction.ts` sets `status: "routed"` on `profile.instantiate`, `profile.export` and `profile.import`, and declares a request, a response, the errors and the examples of each. `agent.list`, `template.list`, `template.show`, `profile.verify` and `instructions.resolve` keep `status: "stubbed"`. `profile.instantiate` keeps `idempotency: "memory"` and `replayable: [200]`. The `profile.instantiate` request carries `templateId` and the optional `checks`, the fields the human confirmed, which `docs/proposal/api/instruction.md` requires. `checks` is a map whose keys are `unit` and `e2e` only, and whose value is an object with `run`, a non-empty array of strings, and `timeout`, a string. An absent `checks` key keeps the template entry, and a supplied key replaces it. The request carries no template version and no digest; the daemon records the version and the digest it ships, so no client can claim a version. A confirmed field that fails the rules of story two answers `422 profile-invalid` with the same finding list as an import. EPIC 114 drives this route through onboarding, so the field set is closed here and onboarding adds none. The `profile.import` request carries `document` and `fromHash`. Both responses carry the document text and the content hash, which `docs/proposal/api/instruction.md` requires. The matching rows of the table in `docs/proposal/api/instruction.md` change to `routed`, because `src/http/contract/parity.test.ts` compares the registry against that table. A new error code `profile-invalid` with status `422` is added to `errorStatuses` of `src/http/contract/errors.ts`, immediately after `credential-rejected`, with the same row position in the code table of `docs/proposal/api/README.md`. `src/http/contract/errors.test.ts` asserts the exact ordered key list of `errorStatuses`, which `015-actor-identity.md:64` puts in place of the two pinned counts. This epic adds `profile-invalid` to that ordered list in the same position, immediately after `credential-rejected`, and it states no count. Its `details` carry the sorted finding list, so the offending check name reaches the client in `locator`. `src/http/server/profile/instantiate-profile.ts`, `export-profile.ts` and `import-profile.ts` parse the request, call exactly one command or query, and format the response. None branches on a domain rule. `src/main.ts` constructs `SqliteProfileStore`, binds the three handlers, and the fixture map of `src/main.test.ts` gains the three operation ids.

Hermetic coverage required beyond the Proof:

- `canonicalTemplatePayload` of the `nodejs` template holds no `digest` key, asserted by `Buffer.includes` of the bytes `digest` returning `false`, and the digest the command records matches `/^sha256:[0-9a-f]{64}$/`.
- An instantiated `nodejs` profile exports the exact expected document, asserted whole with `Buffer.compare(actual, expected) === 0`.
- `profile.instantiate` with `checks.unit.run` of `["npm", "run", "test:ci"]` and `timeout` of `5m` exports `run` of `["npm", "run", "test:ci"]` and `timeout` of `5m`, and not the template values `["npm", "test"]` and `10m`.
- `profile.instantiate` with `checks.unit.run` of `["true"]` answers `422 profile-invalid`, `details.findings[0].code` equals `check-cannot-fail`, and the `profile` table holds zero rows.
- Export, then import of those same bytes with the matching `fromHash`, then export again returns identical bytes, `Buffer.compare` equals `0`, and `content_blob` is unchanged.
- A profile declaring `unit` and `e2e` exports `e2e` before `unit`, because `e` sorts before `u` bytewise.
- `run` of `["npm", "run", "test:unit"]` exports in that order, and the order is not sorted.
- `checks.unit.run` of `["true"]` returns exactly one finding, `check-cannot-fail` with locator `unit`, and the `profile` row is unchanged.
- `["bash", "-c", "npm test || true"]` returns `check-cannot-fail` with locator `unit`, and `["npm", "test"]` returns no finding.
- `["echo", "ok"]`, `["printf", "ok"]`, `["exit", "0"]` and `["env", "true"]` each return no finding, because the lint rejects only the closed set of story two.
- A profile with no `unit` check returns `check-missing` with locator `unit`.
- A check named `lint` returns `check-name-invalid` with locator `lint`.
- A document with an unknown template id and a `true` unit command returns both findings, in the order `check-cannot-fail` then `template-unknown`, because the sorter of story one orders by `code` first and `check-cannot-fail` sorts before `template-unknown`.
- `timeout` of `10s` returns `check-timeout-invalid`, and `10m` parses to `600000` milliseconds.
- A body listing `re@1` before `general@1` exports them in the order `general@1` then `re@1`.
- A body heading `## swe@2` returns `role-heading-unknown` with locator `swe@2`.
- A body with prose before the first role heading returns `body-preamble-unexpected`.
- Non-ASCII role prose survives the round trip byte for byte, asserted with `Buffer.compare`.
- `instantiate-profile` commits the blob, the `profile` row and the `profile.instantiated` event together: a failure injected after the row write leaves zero `blob` rows, zero `profile` rows and zero `event` rows for that repository.
- `import-profile` commits the new blob, the moved pointer and the `profile.imported` event together. Inject a failure after the pointer moves and before the transaction commits. Then `content_blob` still equals the exact hash `instantiate-profile` returned, the `blob` table holds zero rows for the hash of the new document, the `event` table holds zero rows of type `profile.imported`, and the old blob still holds the exact bytes of the instantiated document, asserted with `Buffer.compare` equal to `0`, under that same unchanged hash.
- `profile.import` with a stale `fromHash` answers `409 stale-revision`, and `content_blob` is unchanged.
- `profile.instantiate` on a repository that already holds a profile answers `409 illegal-transition`, and a replay of the same idempotency key answers `200` with the original document.
- `profile.export` on a repository with no profile answers `404 not-found`.
- `profile.import` with a `true` unit command answers `422 profile-invalid`, and `details.findings[0].locator` equals `unit`.
- The registry declares `profile.instantiate`, `profile.export` and `profile.import` as `routed`, and `agent.list`, `template.list`, `template.show`, `profile.verify` and `instructions.resolve` as `stubbed`.
- The `profile` row of an instantiated profile holds `updated_at` equal to `1700000000000`, the exact value the fake clock returns.
- The `profile.instantiated` event holds `subjectKind` `repository`, `subjectId` equal to the repository id, `actorKind` `human`, `actorId` equal to the id of the authenticated actor the test calls with, and a payload whose `templateId` is `nodejs`, `templateVersion` is `1.0.0` and `contentBlob` equals the exported content hash.
