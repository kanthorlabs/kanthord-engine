# EPIC 010.6 — Idempotent POST

Status: **draft**.

## Goal

A client retries a `POST` without repeating its effect. An operation declares its idempotency policy
as registry data, a middleware enforces the policy, and a duplicate under the same key replays the
first answer rather than acting twice.

## Why this epic exists

A dropped response leaves a client unable to tell a committed command from a rejected one. Today one
operation solves that and every other one cannot: `plan.import` carries a client-minted `importId`
with a durable fingerprint, and nothing else has a mechanism. So the Flutter client retries `GET`
only, and a human who loses a response to `repository.register` or `run.start` has to read state back
to find out what happened.

It sits after EPIC 010 because a policy per operation is registry data, and the registry is complete
there. It sits with EPIC 010.5 because `Idempotency-Key` must reach a browser client through the
preflight allow list.

## What this guarantees, and what it does not

The guarantee is **bounded, same-process duplicate suppression**. It is not exactly-once execution.

A restart empties the cache. A command whose effect reaches a git remote or a forge can succeed
outside the daemon and fail inside it. A `POST` that runs longer than the retention window outlives
its own record. Each of those stays the responsibility of the operation, and the story that adds a
policy to an operation states which case it does not cover.

**The naming rule for every document and every message this epic writes:** never call a keyed `POST`
"safe to retry". Call it "a duplicate is suppressed for the retention window, in this process".

## Non-goals

- **No replacement of `importId`.** The durable mechanism stays exactly as `phase-1/plan-format.md`
  and `docs/proposal/api/README.md` define it. A memory cache cannot carry it: the accepted document
  exists only in the response, a crash after the commit is the case the mechanism exists for, a
  restart is what follows a crash, and the human who re-runs the import does it long after any
  retention window. `importId` also has no expiry, because the revision it names has none.
- **No mandatory key.** A `POST` with no key executes as it does today. A mandatory header would break
  the CLI on the day it ships and would fail every request a human makes by hand.
- **No key on `GET`, `PUT` or `DELETE`.** The scope is `POST`. This is a scope decision, not a claim
  that the other methods are idempotent: repeating a `PUT` may append another event or trigger
  external work, and HTTP method semantics prove nothing about an implementation.
- **No distributed cache and no persistence.** One process, one human.

## Stories

- **The policy in the registry** — `Operation` gains `idempotency`, one of `none`, `memory` or
  `durable`. `durable` belongs to `plan.import` and to nothing else. A `GET` declaring anything but
  `none` is a registry fault, alongside the faults `registryFaults` already reports. The default is
  `none`, so an operation that says nothing keeps today's behaviour.
- **The cacheable outcome, declared per operation** — an operation names which outcomes may be
  replayed. **Never infer it from the status class.** A `409 lease-held`, a `409 stale-revision`, a
  `409 binding-in-use` and a `404 not-found` are all temporary domain state, and caching one for the
  retention window turns a lease that has since expired into an artificial outage. A `500` is worse
  than uncacheable: a command that committed and then failed while formatting its response is
  indeterminate, and neither replaying it nor re-running it is safe, so the record marks the key
  indeterminate and a duplicate answers the same indeterminate result rather than acting again.
- **The key and its fingerprint** — the header is `Idempotency-Key`. The story fixes the maximum
  length and the accepted character set, refuses a repeated header, and refuses a key that fails
  either check with `400 invalid-request`. The record is scoped to the `operationId` and the concrete
  path parameters, so one key under two operations is two records. The fingerprint covers the method,
  the rendered path, **the query string** and the raw request body bytes. The query string is in it
  because a command may read one. Raw-byte preservation is configured on the body parser explicitly
  and asserted, because parsing JSON does not inherently keep the original bytes.
- **The reservation and the join** — the reservation is inserted **synchronously, before the first
  `await`**, or two concurrent duplicates both miss. A duplicate that arrives while the first is
  in flight **joins the same promise** and receives the same answer. It does not get a new error code:
  a code would force the client to poll and would widen the public contract for nothing. The wait is
  bounded, and a client that disconnects never cancels the underlying operation.
- **The retention and the bounds** — the cache is bounded by entry count **and** by retained bytes,
  because a stored response may hold a document. The TTL starts when the request **completes**, not
  when it starts, and defaults to 5 minutes. **An in-flight record never expires and is never
  evicted**: expiry or eviction of a reservation lets a duplicate miss and both commands run, which
  destroys the only guarantee this epic makes. When every record is in flight and the bound is
  reached, a new keyed request meets backpressure rather than evicting a reservation. Completed
  records evict by a deterministic policy. The clock is injected, never the wall clock.
- **The response capture** — replaying an answer needs the final answer, and today `dispatch` throws
  and the outer `envelope` middleware materializes the error. So envelope materialization moves into a
  shared function that both the envelope middleware and this middleware call, and the record stores
  the status, the body and the response headers that belong to the answer. Storing a status and a body
  alone would replay a `blob.show`-shaped answer without its `ETag`.
- **`plan.import` under the durable policy** — the middleware validates the header, then **bypasses the
  cache entirely** and lets the durable mechanism own the lookup, the fingerprint and the replay. A
  supplied `Idempotency-Key` must equal the body's `importId`, and a mismatch is
  `400 invalid-request`. The header is not refused outright, so one SDK rule covers every keyed
  `POST`; and the durable fingerprint keeps normalizing and sorting the documents, so a reordered
  array stays a retry where the raw-byte fingerprint would have called it a mismatch.
- **The configuration** — `http.idempotency.ttl` in seconds, default `300`, env
  `KANTHORD_HTTP_IDEMPOTENCY_TTL`. `http.idempotency.maxEntries` and `http.idempotency.maxBytes`, both
  with defaults. A zero TTL disables the memory policy and is a legal configuration.

## Verification gate

Gates: `npm run verify`

Proof:

```bash
node --test src/http/server/idempotency.test.ts src/http/contract/registry.test.ts && echo "PASS EPIC-010.6"
```

Hermetic coverage required beyond the Proof:

- Two identical keyed `POST`s run the command once, asserted by a handler call counter, and both
  answers are byte-identical including the response headers.
- The same key with a different body is `409 idempotency-mismatch`, and the command never runs.
- The same key with a different query string is `409 idempotency-mismatch`.
- One key sent to two different operations records two entries and runs both commands.
- Two concurrent duplicates, dispatched with no `await` between them, run the command once and both
  receive the same answer. The second joins rather than erroring.
- A duplicate whose original is still in flight does not cancel the original when it disconnects,
  asserted by observing the original complete.
- An in-flight reservation survives a TTL sweep and survives a capacity eviction pass. Asserted by
  advancing the injected clock past the TTL while a command is still running, then dispatching the
  duplicate and observing one command run.
- With every record in flight at the entry bound, a new keyed request meets backpressure and no
  reservation is dropped.
- The TTL starts at completion: a command that runs longer than the TTL still replays afterwards.
- A `409 lease-held` is not cached, and the second request runs the command again.
- A handler that throws after its transaction commits marks the key indeterminate, and the duplicate
  receives the same indeterminate answer rather than running the command a second time.
- A key that is too long, that carries an illegal character, or that arrives twice in the headers, is
  `400 invalid-request` and the command never runs.
- A `POST` with no key runs exactly as it does before this epic, asserted against the same route.
- `plan.import` with a header equal to its `importId` reaches the durable path, and the memory cache
  holds no record for it. With a header that differs from `importId` it is `400 invalid-request`.
- `plan.import` retried with the documents in a different array order is a retry, not a mismatch,
  proving the durable fingerprint is in force rather than the raw-byte one.
- A registry entry declaring `memory` on a `GET` is a registry fault.
