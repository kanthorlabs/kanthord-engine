# EPIC 111 — Inspection and manual controls

Status: **ready**.

## Goal

A blocked task is diagnosable from another machine, and a stuck node clears by hand. `node.attempts`, `attempt.show`, `node.checks` and `worker.list` move from `stubbed` to `routed` in `src/http/contract/execution.ts`, and `node.abandon` moves in `src/http/contract/outcome.ts`. One read returns, per attempt of one task, the rendered prompt with per-block provenance, the tool trace, the diff, the verification output, the `re@1` reason per criterion, and the pinned provider and model, exactly as `docs/proposal/phase-2/agents-and-workers.md` requires. Every large payload travels as a blob hash, per `docs/proposal/api/new-decisions.md`, `blob.show` serves the bytes, and `kanthord blob show` prints them. `node.attempts` scopes to the active task run of the node, and to the newest ended task run when none is active, per `docs/proposal/api/execution.md`; `?run=<runId>` selects an earlier one, so the P2-E2 oracle of "exactly three attempts" survives an abandon and a rerun. Every credential is redacted before the evidence is stored, which EPIC 110 owns, and this epic asserts that no inline field and no referenced blob of a record holds credential material. `node.unblock` is already `routed` from `019-outcome-report.md` for the reason `attempt-limit`, and this epic widens it to clear exactly the four reasons `docs/proposal/phase-1/state-machine.md` names. `node.abandon` is refused on a live lease; on an expired or released lease it advances the lease fence, resets the workspace to the recorded base, ends every affected active run with outcome `abandoned`, moves a task to `blocked` with reason `abandoned`, and cascades an objective to every task that is not `discarded`. The earlier task commits survive, because the reset uses the base object id of that task's own run. The node view of `src/queries/node/show-node.ts` gains the `lease` field that `docs/proposal/api/execution.md` declares for a node, and `system.status` names a `running` node whose lease expired as stale. Every state transition and its event append sit in one storage transaction.

## Non-goals

- No worker loop, no attempt write, no check write. EPIC 110 owns `run.start`, `run.cancel`, `run.list`, `run.show`, the attempt lifecycle, every `attempt`, `agent_invocation` and `check_result` row, the run field of the lease, and the redaction of every credential before the evidence is stored. This epic reads those rows and writes none of them. **One run write is this epic's own**: an abandon ends every affected active run through `ExecutionStore.closeRun` of EPIC 110, because `docs/proposal/database/run.md` states that an abandon ends the run.
- No lease field on a run. EPIC 110 owns it, and this epic owns the node field only, per its own non-goal.
- No `agent.list`. EPIC 106 routes it and owns `agentToolAllowLists` and `deferredAgentRoles`. This epic reads neither.
- No approval, no candidate freeze, no merge and no `invalidated_at` write. EPIC 112 owns all four, and this epic reports `invalidatedAt` as a stored value.
- No publish. EPIC 113 owns `repository.publish`.
- No startup reconciliation, no `dirty-recovery` block and no automatic recovery. Phase 3 owns all three, per `docs/proposal/phase-3/recovery.md`. The human clears every stuck node by hand in this phase.
- No `node.discard` and no `node.waive`. Both are `introducedIn: "phase-3"` in `src/http/contract/outcome.ts` and both keep `status: "stubbed"`. A `dependency-discarded` block therefore stays blocked here, because `docs/proposal/api/outcome.md` gives it to `waive`.
- No journal row. The one git write of this epic is `Git.resetWorkspace` inside the disposable objective workspace, and it moves no ref of the bare home. The second write rule of `.agent/plan/epics/100-phase-2-overview.md` states that exemption, and EPIC 108, EPIC 112 and EPIC 113 own the `sync`, `merge` and `publish` rows.
- No new table and no new migration. Every row this epic reads exists in `src/services/storage/migration-0003-execution-and-journal.ts`, and EPIC 110 adds migration `9`. The external-drive block takes `0005`, `0006` and `0007`, and EPIC 105 takes `0008`.
- No lease reaper. Nothing in this epic expires a lease by itself. An expired holding stays in the row until a human abandons the node or a later `run.start` of EPIC 110 claims it.
- No paging on `node.attempts`. The attempt count of one task run is bounded by `attempt_limit`, so a cursor buys nothing.

## Stories

- **The five operations move from `stubbed` to `routed`** — `src/http/contract/execution.ts` sets `status: "routed"` on `node.attempts`, `attempt.show`, `node.checks` and `worker.list`, and `src/http/contract/outcome.ts` sets it on `node.abandon`. **`node.unblock` is already `routed`**: `019-outcome-report.md` routed it for the reason `attempt-limit`, so this epic widens its reason set rather than flipping its lifecycle, and it declares no trigger for it, because the state pair is unchanged. Every method, path, `introducedIn`, `idempotency` and `replayable` value stays unchanged, and `node.discard` and `node.waive` stay `stubbed`. The five matching status cells of the tables in `docs/proposal/api/execution.md` and `docs/proposal/api/outcome.md` change to `routed`, because `src/http/contract/parity.test.ts` compares the registry against those tables. Each of the five declares a request schema where it takes input, a response schema, `errors` and an example set, because `src/http/contract/coverage.test.ts` requires all four of a routed operation and exempts `blob.show` alone. `nodeAttemptsRequest` is `z.strictObject({ run: z.string().min(1).optional() })`; `nodeChecksRequest` is `cursorRequest` of `src/http/contract/cursor.ts`; `attempt.show`, `worker.list`, `node.unblock` and `node.abandon` take no body and no query, because the actor comes from configuration, per `docs/proposal/api/new-decisions.md`. `nodeAttemptsResponse` is `z.strictObject({ run: z.string().nullable(), attempts: z.array(attemptRecordView) })`; `attemptShowResponse` is `z.strictObject({ attempt: attemptRecordView })`; `nodeChecksResponse` is `z.strictObject({ checks: z.array(checkRecordView) })`; `workerListResponse` is `z.strictObject({ workers: z.array(z.strictObject({ worker: workerKind, agents: z.array(z.string()) })) })`; `nodeUnblockResponse` already exists with that shape from EPIC 019; and `nodeAbandonResponse` is `z.strictObject({ node: nodeShowResponse, blocked: z.array(z.string()), resetOid: objectId })`. `errorStatuses` of `src/http/contract/errors.ts` gains no code, and the count pinned in `src/http/contract/errors.test.ts` is unchanged.
- **The attempt record is a pure projection with a closed field list** — `src/domain/attempt-record.ts` is pure, imports `zod` only, and holds the whole shape decision, so one file decides what a human reads and no handler formats a row. `attemptUsage` is `z.strictObject({ inputTokens: z.int(), outputTokens: z.int(), cacheReadTokens: z.int(), cacheWriteTokens: z.int(), totalTokens: z.int() })`. `attemptSourcesView` is `z.strictObject({ channels: z.array(z.strictObject({ channel: z.string(), blob: blobHash, bytes: z.int(), from: z.string() })), budget: z.strictObject({ limit: z.int(), used: z.int() }), dropped: z.array(z.string()) })`, which is the `sources_json` document EPIC 110 writes, re-validated on read. **The inline fields and the hash fields are decided here, and no implementer chooses at build time.** An attempt carries inline `id`, `runId`, `nodeId`, `attemptNo`, `providerId`, `providerModel`, `timeoutMs`, `baseOid`, `headOid`, `outcome` and `endedAt`, which is the list of `docs/proposal/api/execution.md`. An invocation carries inline `id`, `agent`, `adapterVersion`, `verdict`, `sources`, `usage`, `criteria` and `endedAt`, with `sources` of `attemptSourcesView.nullable()` and `usage` of `attemptUsage.nullable()`, and it carries `promptBlob`, `toolDefinitionsBlob`, `toolTraceBlob`, `diffBlob`, `reasonBlob` and `errorBlob` as hashes. `criteria` is the `re@1` reason per criterion, inline, one entry of `{ index, criterion, verdict, reason }` per line of `reason_blob`, and it is null on an implementer row. **The reason is inline and the prompt, the trace and the diff are hashes**, because `docs/proposal/api/execution.md` lists the verdict and its reason per criterion beside each other and lists the other four among the hashes, and because the P2-E2 oracle reads the reviewer reason per criterion out of the record itself. `docs/proposal/api/new-decisions.md` names a prompt, a trace, a diff, a check log, an evidence document and a plan document as the payloads that travel as hashes, and it names no reason. A check carries inline `id`, `subjectKind`, `subjectId`, `nodeId`, `runId`, `commitOid`, `checkName`, `command`, `cwd`, `envIdentity`, `toolchainVersion`, `timeoutMs`, `authoritative`, `result`, `exitCode`, `profileBlob`, `conventionVersion`, `invalidatedAt` and `endedAt`, and it carries `outputBlob` as a hash. `command` is the parsed `command_json` array, declared `z.array(z.string()).nullable()`, because an argv is small and a human reads it. `buildAttemptRecord(input)` takes the decoded rows and returns the record, and it takes no row type that names a ciphertext column. **The three parsed documents are declared nullable, so a degraded field parses.** A `sources_json`, a `usage_json` or a `command_json` value that fails its schema yields null for that field and never throws, so one malformed row cannot hide the other attempts of a blocked task, and the strict view schema admits that null by declaration.
- **The `re@1` reason is parsed, and a bad blob degrades** — `src/domain/agent-review.ts` of EPIC 106 gains one pure export, `parseReviewNdjson(bytes: Uint8Array): readonly ReviewCriterionVerdict[] | null`. It splits on LF, ignores one trailing empty line, parses each line with the `ReviewCriterionVerdict` schema, and returns null when any line fails, so a malformed blob reports `criteria: null` with `reasonBlob` still set and the client fetches the bytes through `blob.show`. It is the inverse of `renderReview`, and it lives beside it because that file owns the review shape. The parse is byte-exact: a non-ASCII reason survives, and no text is truncated.
- **No inline field and no referenced blob holds credential material** — `docs/proposal/api/execution.md` states that credentials are redacted **before** the evidence is stored, so an inline payload and a `blob.show` payload are both clean, and a hash of secret-bearing bytes is indirection rather than redaction. **EPIC 110 owns that redaction at write time**, because it writes every `attempt`, `agent_invocation` and `check_result` row and every blob they cite. This epic asserts the property it can assert over stored rows, in three parts. **One:** `src/domain/attempt-record.ts` declares the field list of every record as a strict schema, and no field of the `provider` table other than `providerId` reaches it. No record holds a name, a payload, an initialization vector, a tag or a key version. **Two:** no query of this epic admits a credential reader. `ListAttemptsDependencies`, `ShowAttemptDependencies` and `ListChecksDependencies` name `Storage`, `PlanStore`, `ExecutionStore`, `CheckStore` and `BlobStore` and nothing else, asserted at compile time in the style of EPIC 104: the test declares `type Assert<T extends true> = T` and asserts `"credentials" extends keyof ListAttemptsDependencies ? false : true`, and the same for `"crypto"`. `src/services/credential/index.ts` stays the one reader of `payload_ciphertext`, which EPIC 108 already made true. **Three:** a source assertion reads every file under `src/queries/` and `src/commands/` and reports the files containing `payloadCiphertext`, `payload_ciphertext` or `apiKey`; the list deep-equals `[]`. The projection therefore adds no credential surface of its own, and the stored bytes it serves are already redacted.
- **`node.attempts` scopes to the active task run, and to the newest ended run when none is active** — `src/queries/node/list-attempts.ts` exports `listAttempts(dependencies, input)`, with the input `Readonly<{ nodeId: string; run: string | null }>`. It reads the node, and a node whose kind is not `task` raises `AttemptQueryError("node-kind-invalid")`, because an attempt belongs to a task run and `docs/proposal/api/execution.md` scopes the operation to a task run. **The default scope is the active task run of that node, and the newest ended task run when no run is active**, which `docs/proposal/api/execution.md` states. `ExecutionStore.activeRun` answers the first case, and `newestRun` of kind `task` answers the second, ordered by `id` bytewise descending. A blocked task holds no active run, and P2-E2 reads exactly that ended record. A `run` input names an earlier run: an unknown id raises `AttemptQueryError("not-found")`, and a run whose `node_id` is another node raises `AttemptQueryError("run-node-mismatch")`, so a client cannot read the attempts of one node under another node's path. **A task that never ran answers `run` of null and `attempts` of the empty list**, per the same file, and it is not an error. The attempts order by `attempt_no` ascending, which the query sorts explicitly and never inherits from the row order, and the invocations of each attempt order by `id` bytewise ascending, so the implementer row precedes the `re@1` row, as EPIC 110 mints them. Each attempt carries the diagnostic rows whose `subject_id` is that attempt, ordered by `id` bytewise ascending, so the verification output of the try sits inside the try. The query writes nothing and opens one transaction.
- **`attempt.show` returns one attempt with its invocations** — `src/queries/attempt/show-attempt.ts` exports `showAttempt(dependencies, input)`, with the input `Readonly<{ id: string }>`. It reads the attempt, its run, its invocations and its diagnostic rows, and it returns the identical `AttemptRecord` that `node.attempts` returns for that attempt, because both call `buildAttemptRecord`. An unknown id returns null and the handler answers `404 not-found`. There is no invocations subresource, per `docs/proposal/api/new-decisions.md`.
- **`node.checks` returns every result attributed to the node** — `src/queries/node/list-checks.ts` exports `listChecks(dependencies, input)`, with the input `Readonly<{ nodeId: string; after: string | null; limit: number }>`. It accepts any node kind, because `docs/proposal/api/outcome.md` and `docs/proposal/api/execution.md` attribute a per-task diagnostic to a task and a candidate or merge result to an objective. It returns every `check_result` row whose `node_id` is that node, ordered by `id` bytewise ascending, with `after` exclusive, which is the paging shape EPIC 110 uses for `run.list`. An absent node raises `not-found`, and a node with no result answers `200` with an empty list. A `profile-gate` row belongs to no node and therefore never appears, which `docs/proposal/api/execution.md` requires. **This epic proves the projection over seeded rows only.** EPIC 112 owns the candidate check, the merge check and every `invalidated_at` write, so a `candidate` row, a `merge` row and a non-null `invalidatedAt` reach this test as fixture data, and **EPIC 112 owns the end-to-end proof** that the daemon produces them.
- **`worker.list` publishes the composition of the one implemented worker kind** — `src/domain/worker-composition.ts` is pure and exports `workerCompositions`, a frozen record holding exactly one entry: `general@1` is `{ agents: ["general@1", "re@1"] }`. `docs/proposal/api/execution.md` states that the route returns the worker kinds the daemon implements and that the MVP returns `general@1` only, so `tdd@1` and `git@1` have no entry. `docs/proposal/phase-2/agents-and-workers.md` fixes the value: the MVP worker composes the `general@1` agent and `re@1`. The agent list is stored sorted, so a comparison never sorts. `src/queries/worker/list-workers.ts` exports `listWorkers()`, which takes no dependency and no input, because the answer is code data, and it returns one row per implemented kind ordered by `worker` with `Buffer.compare`. A client therefore tells a valid `worker` frontmatter value from a rejected one before it imports a plan.
- **The node view carries its lease, and the stale verdict is pure** — `src/domain/lease.ts` gains the pure `isLeaseStale(input: Readonly<{ owner: string | null; expiresAt: number | null; now: number }>): boolean`, which is true when `owner` is not null and `expiresAt` is not null and `expiresAt` is at or before `now`. **The verdict reads no wall clock**: every caller passes `clock.now()`, and a test uses the mock clock of `test/helpers/clock.ts` and advances it by the exact value the case names. `src/queries/node/show-node.ts` gains `leases: Lease` and `clock: Clock` in its dependencies, and `NodeView` gains `lease`, of `Readonly<{ owner: string | null; expiresAt: number | null; stale: boolean }>` or null, read through `Lease.read` of EPIC 110. **The field reports the lease row whose subject is that node, and null when no row exists**, so an objective reports its own holding and a task reports null, because the lease subject of a task's execution is its parent objective. `docs/proposal/api/execution.md` states that a lease has no route and appears as a field of a node and of a run, and EPIC 110 owns the run field. `nodeShowResponse` of `src/http/contract/graph.ts` gains the same field, and `nodeListItem` does not, because a list of nodes is a graph view and `node.show` is the node the human is diagnosing.
- **`status` names the stale node** — `src/queries/system/read-status.ts` keeps its lease query and its filter, and `ExpiredLeaseLine` gains `stale: boolean` from `isLeaseStale` and `nodeState: NodeState | null`, read from the `node` row when `subject_kind` is `node` and null for a `repository` subject. `docs/proposal/phase-2/agents-and-workers.md` requires that `status` reports a `running` node whose lease expired as stale, and the state is what makes the line actionable: a `running` node with `stale: true` is the node `node.abandon` clears. The lease line of `systemStatusResponse` in `src/http/contract/system.ts` gains both fields, and its example gains both values. The order stays `subject_kind` then `subject_id` ascending, so identical state produces identical bytes.
- **`node.unblock` widens from one reason to four** — `src/commands/node/unblock-node.ts` already exists from `019-outcome-report.md`, with the dependencies `Readonly<{ storage: Storage; plan: PlanStore; events: EventLog; clock: Clock }>` and one transaction that writes the state and appends the event. This epic replaces its single `attempt-limit` comparison with the frozen tuple `unblockableReasons` of `["abandoned", "attempt-limit", "dirty-recovery", "stale-base"]`, sorted, which `src/domain/state.ts` gains and which is exactly the list of the `blocked` to `pending` row of `docs/proposal/phase-1/state-machine.md`. It writes no new command, no new handler, no new route and no new CLI command. A node that is not `blocked` raises `UnblockError("not-blocked")`. A `block_reason` of `dependency-discarded` raises `UnblockError("block-reason-not-clearable")`, because readiness needs every dependency terminal and successful and `docs/proposal/api/outcome.md` gives that reason to `waive`. A `block_reason` of `e2e-failed` raises the same code, because `docs/proposal/phase-1/state-machine.md` clears it when the repair objective imports. The write itself does not change: one transaction calls `PlanStore.setNodeState` from `blocked` to `pending` under trigger `manual-unblock` with `blockReason` of null, and appends `node.unblocked`. `setNodeState` validates the pair and applies readiness inside that transaction, per `016-readiness-applied.md:49`, so the scheduler of EPIC 110 re-derives nothing for this write. **It resets no workspace and reads no lease**, per `docs/proposal/api/outcome.md`: a block that holds commits needs `node.abandon` first.
- **`node.abandon` on a task: the refusals, then the fence, then the reset, then one transaction** — `src/commands/node/abandon-node.ts` exports `abandonNode(dependencies, input)`, with the input `Readonly<{ nodeId: string; actor: string }>` and the dependencies `Readonly<{ storage: Storage; plan: PlanStore; execution: ExecutionStore; workspaces: WorkspaceStore; leases: Lease; events: EventLog; git: Git; clock: Clock }>`. **Every refusal is decided before the fence advance, and the order is fixed.** An absent node raises `AbandonError("not-found")`. A node of kind `initiative` raises `AbandonError("node-kind-invalid")`, because `docs/proposal/api/new-decisions.md` makes this one route for a task and an objective and the node kind decides the behaviour. A task whose state is `discarded` or `partial` raises `AbandonError("state-not-abandonable")`, because `src/domain/transition.ts` admits no target from either. A task whose parent objective is `done` or `partial` raises `AbandonError("integrated")`, which is the refusal after integration of `docs/proposal/api/outcome.md`. A live lease raises `LeaseError("lease-held")`: the command reads the lease of the **parent objective** through `Lease.read` and refuses when `owner` is not null and `expiresAt` is after `clock.now()`. **An expired or released holding is accepted**, which is the manual stale-lease clearing of `docs/proposal/phase-2/agents-and-workers.md`. A task whose commits are not at the tip raises `AbandonError("commits-above")`, and the details name the tasks that sit above: the blockers are every other task of the objective whose newest task run holds a non-null `head_oid` and an `id` greater than the newest task run of this task, ordered by node id with `comparePaths` of `src/domain/plan-path.ts`. `docs/proposal/api/outcome.md` requires that refusal and that list. An objective with no `workspace` row raises `AbandonError("workspace-missing")`, because a reset needs a clone and a phase-3 recovery owns a `running` node with none. **A task with no task run at all raises `AbandonError("run-missing")`**, because an abandon resets to a recorded base and a task that never ran has none; that case is reachable, because an objective abandon cascades a `pending` task to `blocked` with reason `abandoned` and leaves it with no run, and the human clears such a task with `node.unblock`. `resetOid` is therefore never null. The fence advance of the next story runs next. The reset then runs: `Git.resetWorkspace` of EPIC 110, with `oid` of the `base_oid` of the newest task run of that task, which `docs/proposal/database/run.md` names the base an abandon resets to. **The reset precedes the transaction**, because git and SQLite share no transaction, and a task whose reason is `abandoned` must never be read beside a dirty tree that no attempt owns. One transaction then ends the active task run of that task, if one is active, with `ExecutionStore.closeRun`, `outcome: "abandoned"`, `headOid` of null and `endedAt` of `clock.now()`; blocks the task; and appends its event, and nothing else. `docs/proposal/database/run.md` states that an abandon ends the run, and the `run_one_active` index of EPIC 110 admits one active run per node, so a run left `active` would block every later execution of that node. The holding is released after that transaction. A `GitError` from the reset raises `AbandonError("reset-failed")`, writes no row, and releases the holding, so the human retries the same call.
- **`node.abandon` on an objective cascades to every task** — an objective abandon takes the same refusal order, and it reads the lease of the objective itself. It resets the workspace to the **clone base**, which is the `base_oid` of the newest objective run of that node, per `docs/proposal/api/outcome.md`. An objective with no objective run raises `AbandonError("run-missing")`, for the reason the task path gives. It skips the `commits-above` check, because the whole objective is parked. One transaction then ends **every active run of the objective and of its cascaded tasks** with `ExecutionStore.closeRun`, `outcome: "abandoned"`, `headOid` of null and `endedAt` of `clock.now()`, blocks the objective and **every task of that objective whose state is not `discarded`**, and appends one event per node, all in that one transaction. `ExecutionStore.activeRun` names the run of each node, and a node with no active run closes nothing. A `discarded` task is skipped, because a discard carries a human reason and `src/domain/transition.ts` admits no transition out of `discarded`. An objective whose state is `done` or `partial` raises `AbandonError("integrated")`, and an objective whose state is `discarded` raises `AbandonError("state-not-abandonable")`. An objective in `awaiting_approval` is accepted, because `src/domain/transition.ts` admits `awaiting_approval` to `blocked` for an objective with reason `abandoned`. The response lists every blocked node id, ordered by `comparePaths`, and the object id the workspace was reset to.
- **A block that re-stamps a reason writes no transition** — **`transitionNode` of EPIC 110 performs every abandon that changes state**, and this epic adds no second guarded state write. `canTransition` of `src/domain/transition.ts` returns false when `from` equals `to`, so the one case `transitionNode` cannot serve is a task already `blocked` that keeps `blocked` with a new reason. `docs/proposal/phase-2/README.md` requires exactly that case: the P2-E2 task is `blocked` with `attempt-limit`, and `abandon task` then moves it to `blocked` with reason `abandoned`. `src/services/plan/index.ts` therefore gains one narrow method beside `transitionNode`, `restampBlockReason(transaction, input: Readonly<{ id: string; blockReason: BlockReason; updatedAt: number }>): number`, whose statement is `UPDATE node SET block_reason = ?, updated_at = ? WHERE id = ? AND state = 'blocked'` and which returns the changed row count, so a node no longer `blocked` changes zero rows and the caller raises `illegal-transition`. **It writes no `state` column**, so it cannot serve as a second transition path. `abandonNode` is its one caller, and it calls the method only when the stored state is already `blocked`; on every other state it calls `transitionNode` from that state to `blocked` with reason `abandoned`. **The transition rule stays in `domain/`**, and the store performs one write.
- **The fence advances before the workspace is touched** — one transaction calls `Lease.acquire` for `subjectKind: "node"` and the objective id, with `owner` of `` `abandon:${actor}` `` and `ttlMs` of `OBJECTIVE_LEASE_MARGIN_MS` of `src/domain/lease.ts`, and it writes nothing else. **That acquisition precedes `Git.resetWorkspace`.** `docs/proposal/database/lease.md` states that the fence increments on every acquisition and that every durable write of a holder carries the fence it acquired, so an expired worker loop of EPIC 110 that wakes during the reset fails its `Lease.assertHeld` and writes nothing. An acquisition after the reset would leave that window open. The `ttlMs` is stated rather than chosen: EPIC 110 declares `OBJECTIVE_LEASE_MARGIN_MS` of `300_000` as the margin that covers one git call plus the transaction that follows it, which is exactly the work this holding covers. An acquisition that raises `LeaseError("lease-held")` is the live-lease refusal, so the guard and the fence advance are one mechanism and the check cannot be skipped. `Lease.release` runs on the returned fence in its own transaction, after the transaction that closes the runs, updates the nodes and appends the events, and on the `reset-failed` path too, so no abandon leaves a holding behind.
- **Every transition, its run close and its event sit in one storage transaction** — `Storage.transact` is synchronous, so the `Git.resetWorkspace` call sits between the fence transaction and the write transaction, and never inside one. Every run close of an abandon sits in the same transaction as the node update and the event of that abandon, so no reader sees a `blocked` node beside an `active` run. The transitions of this epic, each with its event, its subject and its payload:

  | Transition                                       | Event type       | Subject       | Payload                                               |
  | ------------------------------------------------ | ---------------- | ------------- | ----------------------------------------------------- |
  | node `blocked` to `pending`                      | `node.unblocked` | the node      | `{ clearedReason }`                                   |
  | task to `blocked`, reason `abandoned`            | `node.abandoned` | the task      | `{ runId, fromState, resetOid, fence }`               |
  | objective to `blocked`, reason `abandoned`       | `node.abandoned` | the objective | `{ runId, fromState, resetOid, fence, tasks }`        |
  | a cascaded task to `blocked`, reason `abandoned` | `node.abandoned` | the task      | `{ runId, fromState, resetOid, fence, cascadedFrom }` |

  Every actor is `actorKind: "human"` and `actorId` of the configured actor, because a human called the route and `docs/proposal/api/new-decisions.md` stamps the actor from configuration. No payload holds a timestamp, so every snapshot stays deterministic.
