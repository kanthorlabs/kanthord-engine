# EPIC 110 — Scheduler, leases and the `general@1` worker

Status: **blocked**. The external-drive block of EPICs 013 to 021 took the `services/execution` capability, the `services/lease` implementation, the closed `PlanStore` mutation API and migrations 0005 to 0007. This epic becomes ready when EPIC 018 has landed, so its `Execution` and `Lease` interfaces, its `driver` column and its lease hierarchy rule exist to be consumed.

## Goal

The daemon does work. `run.start`, `run.cancel`, `run.list` and `run.show` move from `stubbed` to `routed` in `src/http/contract/execution.ts`. **The daemon runs one internally driven objective run at a time, over every project**, and a unique partial index of migration `9` enforces it, per `docs/proposal/api/execution.md`. One `run.start` pass claims one objective under an objective lease, and it takes the `lease` row **before** it touches the file system or git, per `docs/proposal/database/lease.md`. That lease row is the one EPIC 018 writes, so a harness holding an objective and the worker holding one arbitrate through one mechanism. It then runs the freshness pass of EPIC 108, clones the bare home into `<home>/workspaces/<objectiveId>`, pins the profile hash and the frozen ambient file on the `workspace` row, opens the objective `run` row, and submits one worker loop to the in-process dispatcher. The loop walks the tasks of that objective in topological order, and for each task it opens a task `run` row and runs attempts. One attempt pins one registration, one `provider_model` and one deadline, renders the `general@1` prompt from the pinned profile, calls the `general@1` agent of EPIC 106, commits nothing yet, runs the objective's `unit` check as a diagnostic over the produced diff, renders the reduced `re@1` prompt, and calls `re@1` over the diff and that verification output. An acceptance commits the work as one commit and moves the task to `done`. A rejection routes back to the `general@1` agent and opens the next attempt. The attempt limit of `settings.attemptLimit`, default `3`, resets the workspace and moves the task to `blocked` with reason `attempt-limit`. Every attempt persists its evidence — the rendered messages, every source blob by content address, the tool trace, the diff, the provider usage, the adapter version and the tool definitions — from the bytes EPIC 106 returns. Every diagnostic result is recorded against its task with `authoritative = 0`, and it gates nothing. The last task leaves the objective `running`, because the move to `awaiting_approval` records a candidate and EPIC 112 owns that operation. Every state transition and its event append sit in one storage transaction. Every `run` row and every `attempt` row this epic writes carries `driver: "internal"`. `src/services/check/` and `src/services/dispatcher/` are the two new capabilities, and `src/services/execution/` of EPIC 018 gains the methods the internal driver needs.

## Non-goals

- No objective gate, no candidate freeze and no approval. EPIC 112 owns the frozen candidate, the authoritative `unit` check against it, the merge-commit re-run, `invalidated_at` and every `merge` journal row. **This epic never enters `awaiting_approval`**: `docs/proposal/phase-2/gates-and-approval.md` records a candidate revision when the objective enters that state, so EPIC 112 owns the transition and its event in one operation.
- No publish. EPIC 113 owns `repository.publish` and the `publish` journal row.
- No inspection route and no manual control. EPIC 111 owns `node.attempts`, `attempt.show`, `node.checks`, `worker.list` and `node.abandon`, and each of them reads a row this epic writes. All five keep `status: "stubbed"` here. `node.unblock` is already `routed`, by `019-outcome-report.md`, and EPIC 111 widens its reason set; this epic changes neither.
- No lease field on a node view. `docs/proposal/api/execution.md` puts a lease on a node and on a run, and **EPIC 111 owns the node field**, because `status` and the node views are its surface. This epic owns the run field alone.
- No startup recovery of an interrupted run. Phase 3 owns it, per `docs/proposal/phase-3/recovery.md`. A `running` node whose lease expired stays `running` until a human clears it with the controls of EPIC 111.
- No `tdd@1`, no `git@1`, no `te@1` and no `swe@1`. `docs/proposal/phase-2/agents-and-workers.md` defers all four. A resolved worker kind other than `general@1` refuses the pass.
- No agent adapter and no check runner. EPIC 106 returns the agent evidence, EPIC 107 returns the `CheckOutput`, and this epic persists both.
- No prompt compiler. EPIC 104 owns the channels, the precedence, the render, the provenance and the per-channel budget. This epic supplies the channel values of a real attempt and calls the compiler.
- No ambient reader. EPIC 105 owns the git read, the host switch and the freeze command. This epic opens the transaction the freeze writes in.
- No freshness classification and no reconcile. EPIC 108 owns both. This epic owns the one call site of `ensureFreshBase` and the proof that no clone reaches git without it.
- No journal row. Every git write of this epic happens inside the disposable objective workspace, and it moves no ref of the bare home. The second write rule of `.agent/plan/epics/100-phase-2-overview.md` states that exemption: the journal covers a durable write to the bare home, a mutation inside a disposable objective workspace carries no row, and **phase 3 owns the recovery of that workspace**. EPIC 108 owns `sync`, EPIC 112 owns `merge` and EPIC 113 owns `publish`.
- No concurrency. One worker loop runs at a time over the whole daemon, per `docs/proposal/api/execution.md`, which defers concurrency between objectives. A second `run.start` while any objective run is active answers `409 lease-held` and names that run, whatever project it belongs to.
- No new table and no new column. `src/services/storage/migration-0003-execution-and-journal.ts` holds `run`, `attempt`, `agent_invocation`, `check_result`, `lease` and `workspace`, and migration 0007 of EPIC 018 adds the `driver` column of `run` and `attempt` and the `owner_kind` column of `lease`. This epic adds migration `9`, one index and no column. EPIC 015 owns `0005`, EPIC 017 owns `0006`, EPIC 018 owns `0007` and EPIC 105 owns `0008`. **It also owns no lease service and no execution capability**: EPIC 018 owns `services/lease` with its hierarchy rule and `ownerKind`, and it owns `services/execution` with `Execution` and `SqliteExecution`. This epic consumes both, and it extends the execution interface with the methods the internal driver needs.
- No provider chain and no failover across attempts. `docs/proposal/phase-2/providers-and-credentials.md` defers both. The MVP resolves the one global default.

## Stories

- **The dispatcher runs one loop, and a cancel awaits it** — `src/services/dispatcher/index.ts` declares the capability, and it names no vendor package and no `node:` module. `DispatchedWork` is `(signal: AbortSignal) => Promise<void>`. `Dispatcher` holds exactly three methods, `submit(key: string, work: DispatchedWork): void`, `cancel(key: string): Promise<boolean>` and `cancelAll(): Promise<void>`, because `main.ts` awaits its shutdown through `cancelAll` and no production path polls for quiescence. `DispatcherErrorCode` is exactly `"dispatcher-key-active"`, and `DispatcherError` carries `code` alone. `src/services/dispatcher/in-process.ts` exports `class InProcessDispatcher implements Dispatcher`. Its one dependency is `onFailure: (key: string, error: unknown) => void`, so a rejection reaches the log and never an unhandled rejection. `submit` raises `DispatcherError("dispatcher-key-active")` on a key already in flight, mints one `AbortController` per key, and starts the work. `cancel` aborts the controller of that key and awaits the settlement of that work, returning `true`; an unknown key returns `false` and awaits nothing. `cancelAll` aborts every key and awaits all of them. **The dispatcher decides nothing about the domain**: it holds no lease, reads no row and knows no state, so every write of a cancelled run happens in the loop's own path. `settings` gains no key, because one loop needs no pool size.
- **One internal objective run daemon-wide, and the database enforces it** — `src/services/storage/migration-0009-one-objective-run.ts` exports `migration0009OneObjectiveRun`, version `9`, name `0009-one-objective-run`, one statement, `CREATE UNIQUE INDEX run_one_active_objective ON run (kind) WHERE kind = 'objective' AND state = 'active' AND driver = 'internal'`, and `src/services/storage/migrations.ts` appends it, so `migrations` holds nine entries. **The index keys on `kind` alone and names no project**, so two projects cannot hold two active internal objective runs, which is what `docs/proposal/api/execution.md` requires while it defers concurrency between objectives. **The `driver` predicate is required**: without it one long-lived external objective run of EPIC 018 blocks the internal worker over the whole daemon, and the two drivers are arbitrated by the lease hierarchy rule and by the drive-mode pin, never by this index. The insert of the objective `run` row is therefore the atomic gate for the internal driver. Two racing passes both read no active run, both open a transaction, and the second insert violates the index; `SqliteExecution.openRun` translates that violation to `ExecutionError("run-active")`, and `ExecutionErrorCode` is exactly `"run-active"`, so no caller reads a SQLite message. `Execution.activeObjectiveRun(transaction)` returns the active internal objective run or null, so the refusal of story four names the holder even when another project owns it. `src/domain/execution-contract.ts` exports `OBJECTIVE_LOOP_KEY` of `"objective-loop"`, the one dispatcher key of the daemon, so `submit` refuses a second loop with `DispatcherError("dispatcher-key-active")` and `cancelRun` cancels by that key and never by a run id.
- **`run.start` is the only trigger, and it claims exactly one objective** — `src/commands/run/start-run.ts` exports `startRun(dependencies, input)`. The input is `Readonly<{ projectId: string; actor: string }>`. The dependencies are `Readonly<{ storage: Storage; plan: PlanStore; execution: Execution; profiles: ProfileStore; credentials: CredentialStore; leases: Lease; clock: Clock; dispatcher: Dispatcher; claimObjective: (input: ClaimObjectiveInput) => Promise<ClaimObjectiveResult>; executeObjective: (input: ExecuteObjectiveInput, signal: AbortSignal) => Promise<void> }>`. **`claimObjective` and `executeObjective` are bound commands of this epic**, because `AGENTS.md` forbids a command importing a command, and `startRun` therefore holds no `Git`, no `IdGenerator`, no `Lease` owner, no workspace root and no freshness function of its own. `startRun` reads and refuses, and every git call, every lease acquisition and every write of the claim belong to `claimObjective`. The pass reads the project and its nodes in one transaction, refuses `run-active` when `Execution.activeObjectiveRun` returns a row, and builds the candidate list: every objective of the project whose `state` is `ready`, plus every objective whose `state` is `running` and whose `lease` row holds a null `owner` or an `expires_at` at or before `clock.now()`. **A live lease of any owner kind excludes the objective**, so an objective a harness of EPIC 018 holds is never a candidate, and the hierarchy rule refuses the claim in any case. **The candidate list orders by node id with `comparePaths` of `src/domain/plan-path.ts`, and the first candidate is claimed.** That function is the domain's bytewise comparator, and `src/domain/plan-path.test.ts` already asserts it agrees with `Buffer.compare`, so the command consumes a domain decision and imports no `node:buffer`. A `ready` objective whose dependencies are not all satisfied by `isReady` of `src/domain/readiness.ts` is not a candidate. An empty candidate list returns `{ run: null }`, and the route answers `200`, because a pass with nothing to do is not an error. `startRun` then awaits `claimObjective`, which takes the lease and returns the claim, and then calls `dispatcher.submit(OBJECTIVE_LOOP_KEY, (signal) => executeObjective(<the claim>, signal))` and returns the run view. It returns before the loop finishes, because a worker loop outlives an HTTP request.
- **The refusals are decided before any row is written** — `StartRunError` carries the closed code list `"not-found" | "run-active" | "worker-unsupported" | "profile-missing" | "provider-missing" | "freshness-refused"`, and the `freshness-refused` member carries the `FreshBaseVerdict` refusal. The order is fixed, and each refusal writes nothing except what EPIC 108 already writes in its own pass: an absent project raises `not-found`; an active objective run of any project raises `run-active` and names it; a resolved worker kind other than `general@1` raises `worker-unsupported`; a repository with no `profile` row raises `profile-missing`; an absent default `llm` registration raises `provider-missing`; and a freshness verdict of `clone: false` raises `freshness-refused`. The provider check runs here so a missing registration refuses the request rather than failing a background loop, and it stores nothing, because story eleven pins the registration per attempt. **The `run-active` refusal is a read and never the whole guard**: the index of story two refuses the loser of a race after both passes read no active run.
- **The claim: the lease first, then freshness, then the clone, then one transaction** — `src/commands/run/claim-objective.ts` exports `claimObjective(dependencies, input)`. The input is `Readonly<{ projectId: string; objectiveId: string; nodeState: "ready" | "running"; worker: WorkerKind; actor: string }>`, and the dependencies are `Readonly<{ storage: Storage; plan: PlanStore; execution: Execution; workspaces: WorkspaceStore; profiles: ProfileStore; blobs: BlobStore; leases: Lease; events: EventLog; git: Git; ids: IdGenerator; clock: Clock; ensureFreshBase: (input: EnsureFreshBaseInput) => Promise<FreshBaseVerdict>; freezeAmbient: (input: FreezeAmbientInput) => FreezeAmbientOutcome; attemptBudgetMs: number; workspaceRoot: string; leaseOwner: string }>`. **It takes no precomputed authorization**, because `ensureFreshBase` is a command of EPIC 108 and only `main.ts` binds it into this one. `ClaimObjectiveResult` carries the run row, the workspace row, the acquired owner and the acquired fence. **The lease comes first, and it is the lease of EPIC 018.** One transaction acquires it and writes nothing else: `Lease.acquire` for `subjectKind: "node"` and the objective id, with `owner` of `leaseOwner`, `ownerKind: "daemon"`, `now` of `clock.now()` and `ttlMs` of `objectiveLeaseTtlMs(attemptBudgetMs)` of story seven. The call answers `AcquireLeaseResult`, and the claim reads `record` for the fence and ignores `acquired`, because the worker never reuses a holding of its own. **The hierarchy rule of `018-claim-and-lease.md:73` is what refuses**: `liveLeaseRefusal` raises `LeaseError("lease-held")` when another owner holds a live lease on the objective itself or on **any task of it**, and the reverse refusal stops a harness task claim under an objective this worker holds. **That transaction performs no file-system call and no git call**, so a second concurrent start refuses before any directory is read, created or removed, and `docs/proposal/database/lease.md` holds: the worker takes the row before it clones, and holds it for the whole objective. Every later step of the claim runs on the acquired fence. A `nodeState` of `running` takes the resume of story six. A `nodeState` of `ready` continues, in this fixed order. `ensureFreshBase` runs, with `nodeId` of the objective and `runId` of null, because the run row does not exist yet. Then the command reads the `profile` row through `ProfileStore.read` and decodes `content_blob` through `BlobStore.get`. Then it reads the ambient source through `Git.readAmbientSource` of EPIC 105, with `gitDir` of `repository.homePath` and `commitOid` of the clone base. Then it removes a leftover directory at the target path when no `workspace` row cites it, and calls `Git.clone` with `sourceGitDir` of `repository.homePath`, `targetDir` of `join(workspaceRoot, objectiveId)` and `ref` of `repository.landingBranch`. `src/domain/fresh-base.ts` defines `CloneAuthorization` as `Extract<FreshBaseVerdict, { clone: true }>` and exports the pure `resolveCloneBase(authorization: CloneAuthorization): Readonly<{ cloneBaseOid: string; upstreamOidAtClone: string }>`, and the clone arguments and both recorded object ids come from that call, so **no clone can be issued without a `clone: true` verdict, by the signature**. `cloneBaseOid` is `authorization.upstreamOid` when `authorization.fastForwarded` is true, and `authorization.landingOid` otherwise; `upstreamOidAtClone` is always `authorization.upstreamOid`. **The clone runs before any `workspace` row and any `run` row is written**, so a crash between the two leaves an orphan directory, no `workspace` row and a held `lease` row whose `expires_at` lapses; the next pass removes the directory, and phase 3 owns the recovery of the holding. One transaction then does all of the following and nothing else: `Lease.assertHeld` on the acquired owner and fence; a re-read of the node, which raises `illegal-transition` when the state is no longer `ready`; `WorkspaceStore.insert` with `profileBlob` of the stored `content_blob`, `conventionVersion` of `CONVENTION_VERSION` of `src/domain/instruction-contract.ts`, `state` of `"ready"` and `updatedAt` of `clock.now()`; the injected `freezeAmbient` with that same `Transaction`; `Execution.openRun` for the objective run with `driver: "internal"`, which raises `ExecutionError("run-active")` when the index of story two already holds an active internal objective run; `PlanStore.setNodeState` from `ready` to `running` with `trigger` of `worker-objective-started`; and the two events of story sixteen. `workspaceStates` becomes the frozen tuple `["ready"]` in `src/domain/workspace.ts`, and `workspaceRow.state` narrows to it, because phase 2 writes exactly one workspace state and an unknown value must be a defect. Phase 3 adds the recovery values.
- **The resume opens a new run and writes no transition** — the resume is the second branch of `claimObjective`, so it also takes the lease first. An objective already `running` whose lease is released or expired keeps its workspace, its pinned profile and its frozen ambient blob, so a resume runs **no freshness pass and no clone**. `docs/proposal/database/run.md` states that a node holds several runs and that the old row stays as history, and `docs/proposal/api/execution.md` depends on it for `?run=<runId>`. After the lease transaction the command reads the workspace head through `Git.workspaceHead`, then one transaction asserts the fence, opens the objective run with `driver: "internal"` and `base_oid` of that head, and appends `run.resumed`. It writes no `node` row, because `running` to `running` is not a transition and `src/domain/transition.ts` admits none. A resume of an objective whose `workspace` row is absent raises `StartRunError("not-found")`, because a `running` objective with no clone is a phase-3 recovery case.
- **The objective lease: its TTL, its renewal, its release and its fence** — the row is the `lease` row of EPIC 018, on `subject_kind = 'node'` and the objective identity, and this epic writes `owner_kind = 'daemon'` where a harness holding writes `owner_kind = 'actor'`. `src/domain/lease.ts` gains `OBJECTIVE_LEASE_MARGIN_MS` of `300_000` and the pure `objectiveLeaseTtlMs(budgetMs: number): number`, which returns `budgetMs + OBJECTIVE_LEASE_MARGIN_MS`, beside the two constants EPIC 108 added. **The TTL derives from the budget, and the margin is stated here**: `300_000` covers the git call, the diagnostic close and the transaction that follows a bounded phase, so no implementer picks a number at build time. The claim of story five uses `objectiveLeaseTtlMs(settings.agent.timeoutMs)`, which is `1_200_000` under the default `900_000` of EPIC 106, so an attempt that runs to its own deadline cannot expire the lease that authorizes its writes. **The lease is renewed between the bounded phases**, and not only at open and close: the transaction that opens an attempt, the transaction that persists each `agent_invocation` row, the transaction that closes the diagnostic, and the transaction that closes the attempt each call `Lease.renew` on the acquired fence with `ttlMs` of `objectiveLeaseTtlMs(<the remaining budget of story eleven>)`, so a long objective never looks stale while it progresses and no holding outlives the attempt deadline by more than the margin. Every closing transaction of the loop calls `Lease.assertHeld` with the acquired owner and fence **before** it writes anything, per `docs/proposal/database/lease.md`, and a `LeaseError("lease-fenced")` ends the run at once and writes nothing. The loop releases the lease in a `finally` on the owner and the fence it acquired, which is what `ReleaseLeaseInput` of EPIC 018 requires, on every path: a completed objective, a blocked task, a cancellation and a thrown error alike. **A daemon that stops cleanly releases it**, because `main.ts` awaits `dispatcher.cancelAll()` and the cancel path of story eighteen runs. **A daemon killed without a shutdown leaves the holding in place**, and the row keeps its `owner` and its `expires_at` until they expire; the fence then refuses the write of a zombie holder, and `system.status` of EPIC 111 reports the node stale. Nothing in this epic reaps an expired lease, and the claim-driven sweep of EPIC 018 reaps an **external** lease only, so a `daemon` holding is never swept behind the worker's back.
- **The task order, and the tie-break** — `src/commands/run/execute-objective.ts` exports `executeObjective(dependencies, input, signal)`. It reads the tasks and the containment edges of the objective in one transaction and calls `taskOrder` of `src/domain/task-order.ts`, which walks topologically and breaks a tie by the ULID part of the task id, because two task ids share the `task_` prefix. **The order is computed once per objective run**, so a state change during the run cannot reorder the walk. The loop then visits each task in that order and skips a task whose state is `done`, `discarded` or `blocked`, and a task whose dependencies are not all `done` or `partial` by `isReady`. A visited task takes the task run of story nine. The loop stops early only on a cancellation, on a run-ending error of story nineteen, or on a `lease-fenced` refusal. After the walk it takes the objective closing of story seventeen.
- **One task run per execution of one task** — the loop reads the workspace head through `Git.workspaceHead` and opens the task run in one transaction: `Execution.openRun` with `driver: "internal"`, `kind: "task"`, `parentRunId` of the objective run, `workspaceId` of the objective workspace, `worker` of the resolved kind, `leaseFence` of the acquired fence, `attemptLimit` of `settings.attemptLimit`, `baseOid` of that head and `state: "active"`; `PlanStore.setNodeState` from `ready` to `running` with `trigger` of `worker-task-started`; and the two events of story sixteen. **The three internal-only columns are all present**, which is what the `CHECK ((driver = 'internal') = (workspace_id IS NOT NULL))` clause of migration 0007 and its two siblings require. `docs/proposal/database/run.md` makes that head the base a later abandon resets to, which is why no separate table holds it. The task run closes through `Execution.endRun` in one transaction with `headOid` of the commit an acceptance produced, or null, `outcome` of `"done"`, `"blocked"`, `"abandoned"` or `"failed"`, `endedAt` of `clock.now()` and `state: "ended"`. The `run_one_active` partial index gives one active run per node, so a second task run of the same task cannot open while the first is active.
- **The attempt loop, and the three ways it ends** — `src/commands/run/execute-task.ts` exports `executeTask(dependencies, input)`. It reads the attempts of the active task run through `Execution.attemptsOfRun` and calls `accountAttempts` of `src/domain/attempt-accounting.ts` with the limit of the run. **A try ends the task in exactly one of three ways.** An accepted attempt commits the work, moves the task from `running` to `done` with `trigger` of `worker-task-accepted`, and ends the task run with `outcome: "done"`. A rejected attempt appends `attempt.rejected` and opens the next attempt, and `accounting.counter` of the limit value stops the loop. A `failed`, `timed-out` or `cancelled` attempt consumes one try in the same way, so a persistent adapter fault parks the task rather than retrying without bound. When `accounting.counter` reaches the limit and no attempt was accepted, the task takes the exhaustion sequence of story fifteen. `attemptVerdict` of `src/domain/attempt-accounting.ts` supplies the `attempt-limit` reason, and `blockReasons` of `src/domain/state.ts` holds no other value for an exhausted try, so an exhaustion whose last outcome is not `rejected` records the same reason.
- **One attempt pins one registration, one `provider_model` and one deadline** — the attempt opens in one transaction: `CredentialStore.readDefaultLlm` resolves the registration and its `defaultModel`; `ids.mint("attempt")` mints the id; `Execution.openAttempt` writes `driver: "internal"`, `runId`, `attemptNo` of `accounting.nextAttemptNo`, `providerId`, `providerModel`, `timeoutMs` of `settings.agent.timeoutMs`, `baseOid` of the task run base and `outcome` of null; `Lease.renew` runs on the acquired owner and fence; and `attempt.started` is appended. **The four internal-only columns are all present**, and the composite `FOREIGN KEY (run_id, driver) REFERENCES run(id, driver)` of migration 0007 makes an internal attempt under an external run impossible to record. `src/services/credential/index.ts` gains one method, `readDefaultLlm(transaction): Readonly<{ registration: ProviderRow; defaultModel: string }>`, which raises `CredentialError("credential-not-found")` when no `kind = 'llm'` row carries a non-null `set_default_at`, and picks the row with the greatest `set_default_at`, tie-broken by `id` bytewise with `Buffer.compare`. **One decryption path stays**, because EPIC 108 already made that store the only reader of `payload_ciphertext`, and the method returns the sealed row plus the model id and never the credential. **The attempt holds one deadline, and every bounded phase spends the same budget.** `docs/proposal/database/attempt.md` calls `timeout_ms` the wall-clock budget of the attempt, so the row records `settings.agent.timeoutMs` once, the opening transaction captures `startedAt` of `clock.now()`, and the deadline is `startedAt + timeoutMs`. `src/domain/execution-contract.ts` exports the pure `remainingBudgetMs(input: Readonly<{ deadline: number; now: number }>): number`, which returns `deadline - now` clamped at `0`. Each bounded phase receives its own `timeoutMs` of `remainingBudgetMs({ deadline, now: clock.now() })`: the `general@1` call, then the diagnostic of story twenty, then the `re@1` call. The diagnostic takes `Math.min(<the declared profile timeout>, <the remaining budget>)`, so a declared check timeout never extends the attempt. A remaining budget of `0` before a phase starts ends the attempt with `outcome: "timed-out"` and reason `timed-out`, runs no further call, and calls no agent. **Two calls therefore cannot each spend the whole timeout.** Both `AgentRequest` values of the attempt — the implementer call and the reviewer call — carry that same `registration` and a `providerModel` of the pinned value, never null, so `docs/proposal/phase-2/providers-and-credentials.md` holds by construction. A `CredentialError` inside a started attempt ends the attempt as `failed` with reason `provider-unreadable`, and it never switches the registration mid-attempt.
- **The prompt of a real attempt renders from the pinned profile** — `src/domain/attempt-prompt.ts` is pure and exports `composeAttemptPrompt(input)`. It takes the role, the decoded pinned profile document, the decoded task instruction and acceptance text, the ambient sources, the project id, the node id, the revision, the attempt id and the runtime evidence, and it returns the block list, the provenance, the budget accounting, the dropped channels and one source byte sequence per provenance entry. It builds exactly one contribution per channel of EPIC 104, calls `resolveInstruction`, `renderPrompt` and `applyBudget`, and adds no channel and no field. **The profile reaches it as a document value and never as a row**, so `ExecuteTaskDependencies` names no `ProfileStore`, and an edit of the profile during the run cannot change the instruction: every render decodes `workspace.profile_blob` through `BlobStore.get`. `docs/proposal/phase-2/instructions-and-profiles.md` requires that pin, and EPIC 103 and EPIC 104 both leave it here. The ambient contribution comes from `composeAmbientChannel` of `src/domain/ambient-compose.ts` over the frozen `workspace.ambient_blob` and the host sources of `HostAmbientReader`, so a later edit of the repository file inside the clone reaches no later attempt of that objective. The `runtime-evidence` contribution of a `general@1` attempt after a rejection is the `reason_blob` NDJSON of the previous attempt's `re@1` invocation, and it is empty on attempt one. The `runtime-evidence` contribution of the `re@1` call is the diff of that attempt's implementer invocation, followed by the captured output of **that same attempt's diagnostic**, read through `BlobStore.get` over the `output_blob` of the row story twenty closed. That output always exists, because the diagnostic runs before the reviewer call. `re@1` therefore reads the criteria, the diff and the verification output of the tree it judges, which is the reduced render `docs/proposal/phase-2/instructions-and-profiles.md` requires and the order `docs/proposal/phase-2/gates-and-approval.md` fixes.
- **The reviewer's diff is bounded twice, and each bound has one outcome** — the diff comes from `Git.diffWorkspace` of EPIC 106, whose output cap is `DEFAULT_OUTPUT_LIMIT_BYTES` of `1_048_576`; a diff over it raises `AgentError("diff-too-large")` and ends the attempt as `failed` with reason `diff-too-large`. The rendered `runtime-evidence` block is bounded by `channelBudgets["runtime-evidence"]` of `262_144`; a block over it makes `applyBudget` refuse, and the attempt ends as `failed` with reason `channel-over-budget` and the channel name in its event payload. **Neither bound is a rejection**, because a truncated diff would make `re@1` judge partial work, and `docs/proposal/phase-2/instructions-and-profiles.md` forbids truncated instruction. The `ambient-context` channel is the one channel `applyBudget` drops, and story twenty-one records that drop.
