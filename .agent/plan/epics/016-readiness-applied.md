# EPIC 016 — Readiness applied

Status: **draft**.

## Goal

`plan.import` leaves a project with a `ready` frontier instead of every node in `pending`. The daemon derives readiness from the dependency edges and writes each `pending → ready` and each `ready → pending` transition inside the transaction of the write that changed eligibility. `node.list` and `node.show` return `ready` for every eligible `pending` node, and every derived transition carries one event attributed to the daemon instance, `node.ready` on a promotion and `node.pending` on a demotion. Every node state write goes through one store method that takes a required `trigger` from the closed union of EPIC 014, so a write states its reason and no test infers one from a literal state pair. One application fixture drives `plan.import`, then `node.list`, `node.show` and `event.list` against one migrated database, and asserts the exact frontier and the exact events. No scheduler exists, no timer runs, and no background loop exists.

## The defect this epic closes

`src/domain/readiness.ts:12` defines `isReady`. No production file outside `src/domain/` imports it. `src/services/plan/sqlite.ts:25` writes the literal `'pending'` on every node insert, and its `ON CONFLICT` clause never updates `state`. `src/commands/plan/import-plan.ts:418` is the only caller. `src/commands/startup/recover-expired-leases.ts:147` writes `ready`, but only from `running`. An imported plan therefore holds every node in `pending` for ever, and nothing is claimable. `docs/proposal/phase-1/state-machine.md:63` says the scheduler writes the transition, and `013-external-drive-overview.md:98` refuses a scheduler.

## Decisions

These are settled here. No story revisits one.

- **A node with no dependency is `ready`.** The rule is a universal quantifier over an empty set.
- **The rule is identical at all three levels.** `docs/proposal/phase-1/state-machine.md:63` marks `pending → ready` valid at task, objective and initiative. Only sibling dependency edges feed the rule. Containment feeds nothing: a parent never waits for a child, because a parent leaves `pending` through the child start cascade of EPIC 018.
- **A waived edge satisfies its dependency.** `StoredEdge.waivedAt` at `src/domain/plan-graph.ts:25` is the input, and `isReady` at `src/domain/readiness.ts:12` already honours it.
- **Derivation reads and writes the pair `{pending, ready}` only.** A `running`, `blocked`, `awaiting_approval`, `done`, `partial` or `discarded` node is never read as a subject and never written.
- **The direction is two way.** Derivation yields `pending → ready` for a `pending` node whose dependencies are all satisfied, and `ready → pending` for a `ready` node with one unsatisfied dependency. It yields no other pair. EPIC 014 makes both cells legal and makes a structural edit legal at `ready`, so the reverse cell has a writer from this epic on.
- **One pass is a fixed point, in both directions.** Neither `pending` nor `ready` satisfies a dependency. A promotion and a demotion each turn one non-satisfying state into another non-satisfying state, so neither one changes the eligibility of a second node. One pass over the node set is final, and no loop exists.
- **The reverse direction ships here, and EPIC 017 is its routine consumer.** `plan.import` reaches the reverse case on one path only: a re-import that adds an unsatisfied dependency to a node an earlier import made `ready`. The per-node topology write of EPIC 017 reaches it on every added dependency, which `014-external-drive-contract.md:23` states. The derivation is one function, so it ships whole here rather than in two halves.
- **The invariant covers eligibility, not dependencies.** Every write that can alter eligibility applies readiness in its own transaction. A dependency edge change, a node state change and a node insert all qualify. `unblock` writes `blocked → pending` and touches no dependency, and it still qualifies. The mutation boundary below makes the invariant structural rather than a review habit.
- **The actor of a derived transition is the daemon instance.** `docs/proposal/api/event.md:26` binds a configured actor to a **human decision**. A derived transition is not a decision. `actorKind` is the constant `daemon`, and `actorId` is the daemon instance identity injected at composition. Neither value is an input, so a `human` or a `harness` caller of `plan.import` cannot be credited with a transition it did not request.
- **The event carries its cause.** `docs/proposal/database/event.md:12` says `actor_id` names which daemon instance. Attribution alone does not say why. The payload therefore holds `revision` and `importId`, so an audit reader reaches the import that caused the transition.
- **Readiness events precede the import events.** Readiness applies inside the mutation, and the mutation precedes the `node.imported` appends at `src/commands/plan/import-plan.ts:471`. Position carries no meaning; the payload cause does.
- **Order is bytewise by node identity.** A transition list sorts through `Buffer.compare` on the identity, so the event order of one import is reproducible.
- **A state write names its trigger, and the trigger is required.** `setNodeState` takes `trigger` over `NodeTriggerId` of `014-external-drive-contract.md`, and the member is not optional. A caller cannot write a state without stating why it writes it. That is what makes a source scan over `src/commands/` unnecessary: intent is a declared value, and no test infers it from a literal state pair.
- **`mutateGraph` takes no trigger, and each transition carries its own.** One `mutateGraph` call writes both directions in one readiness pass, so one trigger for the call cannot describe the call. `deriveReadiness` therefore stamps each transition it returns: a `pending → ready` transition carries `readiness-promoted`, and a `ready → pending` transition carries `readiness-demoted`. The store passes the transition's own trigger into its update. A `mutateGraph` input member would be a second source for the same fact.

## Stories

- **The proposal amendment** — `docs/proposal/phase-1/state-machine.md` loses the scheduler in three notes. Line 63 reads that the daemon derives the transition inside the transaction of the write that changed eligibility. Line 85 and line 86 lose "the scheduler re-derives readiness" and "the scheduler re-derives eligibility" for the same daemon wording. Line 117 keeps the rule and names the daemon. `src/domain/transition.ts:20`, `:196` and `:204` carry those notes as strings, and each string changes with the document. No cell flips, and `allowedPairs` gains no pair, because EPIC 014 owns the matrix.
- **`deriveReadiness` in `domain/`** — a pure function beside `isReady` in `src/domain/readiness.ts`. It takes the node set with each state and the edge set with each `waivedAt`, and it returns the ordered transitions. Each transition carries `nodeId`, `from`, `to` and `trigger`. A node in `pending` whose dependencies are all satisfied yields one `pending → ready` transition with trigger `readiness-promoted`. A node in `ready` with one unsatisfied dependency yields one `ready → pending` transition with trigger `readiness-demoted`. Every other node yields nothing, and no node yields two transitions. The result sorts by node identity through `Buffer.compare`. The function reads no clock and mints no identity.
- **`services/readiness`** — a new capability. `src/services/readiness/index.ts` declares `Readiness.apply(transaction, input): readonly ReadinessTransition[]`, where `input` carries `projectId`, the node snapshot, the edge snapshot, `at`, `instanceId` and `cause`. `src/services/readiness/dependency.ts` exports `DependencyReadiness`, which implements it over the `EventLog` interface. It calls `deriveReadiness`, appends one event per transition, and returns the ordered transitions to its caller, which writes the states. Each returned transition carries its own trigger, so the caller writes no trigger of its own and reads no direction. It holds no `PlanStore`, so composition has no cycle. The capability is a service and not a second command, because the import matrix forbids `commands/` from importing `commands/`, and the transaction context must cross the call. `src/domain/layout.test.ts:101` pins the capability inventory as an exact fifteen-name list; this epic adds `readiness` to that list and to the name in the test title.
- **The closed mutation API on `PlanStore`** — `src/services/plan/index.ts` loses `upsertNode`, `insertEdge` and `deleteEdge`, and gains exactly two mutation methods. `mutateGraph(transaction, input)` takes `projectId`, the node upserts, the edge inserts, the edge deletes, `at` and `cause`. `setNodeState(transaction, input)` takes `id`, `from`, `to`, `trigger`, `blockReason`, `at` and `cause`. `trigger` is required and it is typed `NodeTriggerId` of `014-external-drive-contract.md`. `mutateGraph` takes no trigger, under the Decisions. Both run their SQL, then read the project graph back, then call `readiness.apply`, then write each returned transition with `UPDATE node SET state = ?, updated_at = ? WHERE id = ? AND state = ?`, binding `to` and `from` from the transition. One statement serves both directions, because the guard is the `from` of the transition and never a literal. A caller cannot skip readiness, because no other mutation entry exists. `SqlitePlanStore` takes `Readiness` through its constructor, which the import matrix permits: an implementation imports any service interface.
- **`setNodeState` validates the pair and the trigger** — it calls `triggerTransition` from `src/domain/node-trigger.ts` and throws when the declared `from`, the declared `to` or the declared `levels` list of the trigger disagrees with the input `from`, the input `to` or the node kind. It then calls `canTransition` from `src/domain/transition.ts:468` with the node kind, `from` and `to`, and it throws when the pair is not in the matrix. **The trigger check is the replacement for the deleted source scan of `014-external-drive-contract.md`**: a declaration and its write cannot disagree, because every write reads the declaration. The `AND state = ?` guard on `from` stays as well, so a concurrent write that moved the node makes the update a no-op and the store appends no event. Validation through `canTransition` ships, and a hand-listed pair set does not, because a hand-listed set drifts from the matrix that EPIC 002 already asserts as data.
- **The eslint rule** — `no-restricted-syntax` over `src/**/*.ts` forbids a string literal or template literal that matches `/\b(insert\s+into|update|delete\s+from)\s+["'`\[]?(node|edge)\b/i`. The rule block sets `ignores: ["src/services/plan/sqlite.ts"]`, so that file is the only place a node or edge write exists. `src/services/plan/sqlite.ts:25`keeps its`INSERT_NODE`constant, its`'pending'`literal and its`ON CONFLICT`clause, because insertion order inside one import puts a node in the table before its edges exist. - **`plan.import` writes through the mutation API** — `src/commands/plan/import-plan.ts` replaces the `upsertNode` loop at line 418, the `deleteEdge` loop at line 452 and the `insertEdge` loop at line 464 with one `mutateGraph` call placed at line 469, after the edge reconciliation and before the event appends at line 471. The call therefore carries the accepted node set and the accepted edge set together. `cause` holds the new `revision` and `input.importId`. The retry path at `src/commands/plan/import-plan.ts:152` returns before any write and calls nothing, because a retry changes no row. `ImportPlanDependencies` gains no new member, because readiness reaches the command through the plan store.
- **`recover-expired-leases` writes through the mutation API** — `src/commands/startup/recover-expired-leases.ts:147` replaces its raw `UPDATE node` with `plan.setNodeState`, and `RecoverExpiredLeasesDependencies` gains `plan`. - **The event** — `DependencyReadiness` appends one event per applied transition.
