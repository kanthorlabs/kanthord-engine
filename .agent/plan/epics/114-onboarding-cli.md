# EPIC 114 — Onboarding CLI

Status: **blocked**. The external-drive block of EPICs 013 to 025 adds seventeen CLI commands, the five actor commands of EPIC 015 included, and it invalidates every scalar CLI total this file pinned. This epic becomes ready when EPIC 020 has landed, so the block's command set is final and this file asserts names against it.

## Goal

One command onboards a human from nothing. `kanthord onboard`, in `src/cli/onboard/onboard.ts`, drives the sequence the proposal names: register the git credential, register the repository, register one llm provider with its default model, stamp that provider as the default, create a project, bind the repository to it, and instantiate the profile. `docs/proposal/phase-2/providers-and-credentials.md` requires the provider and its stamp, `docs/proposal/api/credential.md` states that onboarding calls `provider.setDefault`, `docs/proposal/api/project.md` names onboarding as the source of `project.create`, and `docs/proposal/phase-2/instructions-and-profiles.md` states that onboarding instantiates one named template. It calls `provider.list`, `repository.list`, `project.list`, `provider.register`, `repository.inspect`, `repository.register`, `provider.setDefault`, `project.create`, `project.repositories`, `profile.export` and `profile.instantiate` over HTTP through `DaemonClient` of `src/cli/client.ts`, so it imports no command and no query, per `docs/proposal/phase-1/transport.md` and the import matrix of `AGENTS.md`. Each step of the sequence is one callable action, and the four existing commands plus the new `kanthord profile instantiate` call the same actions, so no wording and no refusal exists twice. It refuses to start when it has no way to reach an llm provider, and it names the flags that fix that. Every step is drivable by flag, so a scripted run needs no terminal. Every step re-reads the daemon first, reports `skipped` for work that already exists, and refuses when an existing name denotes a different thing.

- No template detection and no template catalogue read. `docs/proposal/after-the-mvp.md` defers detection, `template.list` and `template.show` stay `stubbed`, and onboarding asks the human for the template id.
- No `profile export`, `profile import` or `profile verify` command. EPIC 109 owns `profile verify` and states that it is manual.
- No run, no lease and no attempt. EPIC 110 owns work.
- No actor command and no route of the external-drive block. EPIC 015 authors the five actor commands and their `src/cli/inventory.ts` rows, EPICs 017, 018 and 019 author the node commands, and EPIC 020 authors `event list` and asserts the block's own set. This epic carries every one of them in its inventory reasoning and writes none of them.

## Stories

- **One command, and why it is one** — `src/cli/onboard/onboard.ts` exports `registerOnboard`, and `src/cli/program.ts` calls it, so `onboard` is a top-level leaf beside `run` and `status`. It is one command rather than seven, because the order, the skip rule and the provider stop rule are the product here: the existing commands already ship, and a human who runs them by hand can finish with no provider and no profile. `RegisterOnboardInput` takes `program`, `client`, `confirm`, `readFile`, `stdout`, `stderr`, `fail` and `exit`, the shape `src/cli/repository/register.ts` and `src/cli/plan/import.ts` already take. `ProgramDependencies` carries no `client`: `buildProgram` builds the one `client` at line 87 of `src/cli/program.ts` and passes it, exactly as it does to `registerRepositoryRegister`. Onboard parses every response with the contract schema of that route, as every other CLI command does.
- **The six steps, in one fixed order** — the step names are `git-credential`, `repository`, `llm-credential`, `project`, `binding` and `profile`, and no step runs before the step above it. The call order of a full fresh run is `provider.list`, `repository.list`, `project.list`, `provider.register` for the git kind, `repository.inspect`, `repository.register`, `provider.register` for the llm kind, `provider.setDefault`, `project.create`, `project.repositories`, `profile.export`, `profile.instantiate`. The git credential comes first because `repository.register` carries a mandatory `credentialId` of `kind = 'git'`, which `docs/proposal/api/credential.md` states. The binding comes before the profile because `docs/proposal/api/project.md` names onboarding as the source of `project.create`, and a plan import later refuses an objective whose repository is not bound. `profile.export` runs after the repository step, because that route carries the repository id in its path.
- **The preflight, the three reads and the provider stop rule** — onboard validates its flags, then calls `provider.list`, then evaluates the stop rule, then calls `repository.list` and `project.list`. No write and no file read happens before those three reads. The llm step needs one of two things: a row of `kind = 'llm'` whose `name` equals `--provider-credential`, or the three flags `--provider`, `--model` and `--api-key-file`. When it has neither, onboard writes exactly `kanthord: onboarding-incomplete: no llm provider is registered; pass --provider-credential, --provider, --model and --api-key-file\n` to stderr, calls `exit(LOCAL_REFUSAL)`, and performs no further call. Onboarding does not finish without a provider, and it stops before it changes anything, so a second run starts from the same state.
- **`provider.setDefault` runs unconditionally** — after the llm step selects an existing row or creates a new one, onboard calls `provider.setDefault` with the parameter `provider` equal to that row id, and it prints `kanthord: llm default <name>\n` from the returned view. It never reads `setDefaultAt` to decide. `docs/proposal/api/credential.md` states that onboarding calls that route for the first registration, and EPIC 101 makes the call idempotent: the row that already holds the stamp answers `200`, writes nothing and appends no event. One unconditional call therefore has one oracle. A second `llm` row that already holds the stamp refuses with `default-already-set`, which EPIC 101 owns, and onboard reports that refusal through the daemon channel and stops.
- **The skip rule, and the refusal when a name denotes a different thing** — a step whose work already exists prints `kanthord: skipped <step-name>\n` and calls nothing. The read that decides each skip is fixed: the `provider.list` rows matched by `name` for `git-credential` and `llm-credential`; the `repository.list` rows matched by `name` for `repository`; the `project.list` rows matched by `name` for `project`; the `repositories` array of the matched project view, which holds repository ids, for `binding`; and `profile.export` for `profile`, where `404 not-found` means absent and every other failure is a refusal. A matched row that denotes a different thing is a local refusal, never a skip, and each refusal names both values: a credential of the wrong kind gives `kanthord: invalid-request: the credential <name> is of kind <kind>\n`, the wording `src/cli/repository/register.ts` uses at line 78; a repository whose `remoteUrl` differs gives `kanthord: invalid-request: the repository <name> names remote url <stored>, not <given>\n`; a repository whose `credential.name` differs gives `kanthord: invalid-request: the repository <name> binds credential <stored>, not <given>\n`; a repository whose `upstreamBranch` differs from a supplied `--upstream` gives `kanthord: invalid-request: the repository <name> tracks upstream <stored>, not <given>\n`, and no comparison happens when `--upstream` is absent, because the suggestion then comes from the daemon; a repository id inside the `repositories` of another project gives `kanthord: invalid-request: the repository <name> is bound to project <other-name>\n`; a project whose `repositories` holds one other id gives `kanthord: invalid-request: the project <name> binds repository <stored>, not <given>\n`, because `docs/proposal/api/project.md` binds one repository per project in the MVP and `PUT` replaces the whole list; and an existing profile whose `template.id` differs gives `kanthord: invalid-request: the repository profile names template <stored>, not <given>\n`, read through `parseProfileDocument` of `src/domain/profile-parse.ts`, which EPIC 103 owns and which `cli/` may import because `domain/` is pure. A skipped step still yields the id the next step needs, so the sequence never re-registers a row to learn its id. The human continues a failed run by running `kanthord onboard` again with the same flags, and nothing else. Onboard sends no idempotency key: `profile.instantiate` carries `idempotency: "memory"`, a memory key does not survive a daemon restart, and the read is the guard that does.
- **Every secret arrives as a file path** — the three secret flags are `--git-token-file`, `--git-private-key-file` and `--api-key-file`, and onboard declares no flag that takes a secret value. So no secret enters a shell history and no secret appears in the argument vector that `ps` prints. `src/cli/credential/payload.ts` holds the reader-independent part: it exports `trimSingleTrailingNewline`, which moves out of `src/cli/credential/register.ts` unchanged, plus `gitHttpBasicPayload({ forge, username, token })`, `gitSshPayload({ privateKey })` and `llmPayload({ provider, apiKey, defaultModel, baseUrl })`. Each returns the exact object literal `src/cli/credential/register.ts` builds today at lines 118, 132 and 153, with the same field names and the same `?? ""` and `?? null` defaults. The module also exports `readSecretFile(readFile, flagName, path)`, which returns `{ ok: true, value }` or `{ ok: false, message }` and never puts file content in a message. Its five outcomes are exact: a `code` of `ENOENT` gives `kanthord: invalid-request: <flag> names no file: <path>\n`; `EISDIR` gives `kanthord: invalid-request: <flag> names a directory: <path>\n`; `EACCES` and every other thrown error give `kanthord: invalid-request: <flag> cannot be read: <path>\n`; and content that is empty after `trimSingleTrailingNewline` gives `kanthord: invalid-request: <flag> names an empty file: <path>\n`. Each is a local refusal, and onboard reads every secret file it needs after the three preflight reads and before the first write, so a bad path costs no write. Onboard prints no payload field and no projection field. `src/cli/credential/register.ts` calls the three payload builders, keeps its direct `readFile` call, and its stdout lines, its stderr lines and its request body change by nothing: `readSecretFile` is not adopted there, because that would change an exit path EPIC 009 already pinned.
- **One callable action per step** — each step is a function that takes its dependencies first and its input second, returns `{ ok: true, view }` or `{ ok: false, code, message }`, and holds the request building, the response parsing and the printing of that step. The commander command and onboard are both thin callers, so a wording and an error mapping exist once. `src/cli/credential/registration.ts` exports `runCredentialRegistration(dependencies, { name, kind, payload })`, which calls `provider.register`, parses `providerRegisterResponse`, and writes the `registered`, `transport` and `forge` lines of `src/cli/credential/register.ts` lines 173 to 183 unchanged. `src/cli/repository/registration.ts` exports `resolveGitCredential(providers, name)`, which returns the matched id or the two refusals of lines 71 and 78, and `runRepositoryRegistration(dependencies, input)`, which holds lines 50 to 177 with the `provider.list` call and the name resolution removed. Its input is `url`, `credentialId`, `name`, `upstream`, `landing`, `publishRef`, `hostFingerprint` and `publishOnApproval`, so it calls only `repository.inspect` and `repository.register`, and the sequence of story two holds one `provider.list`. It keeps the url transport check, the three informational lines and the six view lines, and it owns the `landing` default of `upstream`, the `publishRef` default of `refs/heads/<upstream>` and the two confirmations. `src/cli/project/creation.ts` exports `runProjectCreation(dependencies, { name })`, and `src/cli/project/binding.ts` exports `resolveRepositoryIds(repositories, names)` and `runProjectBinding(dependencies, { id, repositories })`, which sends the full list and prints `printProjectView`. `src/cli/profile/instantiation.ts` exports `runProfileInstantiation(dependencies, { repositoryId, templateId })`, which calls `profile.instantiate`, parses the EPIC 103 response, and prints `kanthord: profile <template-id> <content-hash>\n` from its `contentHash` field. `src/cli/credential/register.ts`, `src/cli/repository/register.ts`, `src/cli/project/create.ts` and `src/cli/project/repository.ts` keep their command names, their flags, their local refusals and their output.
- **`kanthord profile instantiate` ships here** — EPIC 109 states that this epic adds `instantiate` to the `profile` group, and onboarding needs the same action, so one code path serves both. `src/cli/profile/index.ts` exports `profileCommand`, which creates the `profile` group or returns the existing one, copying `src/cli/repository/index.ts`; EPIC 109 declares the same file, and whichever epic lands first writes it. `src/cli/profile/instantiate.ts` exports `registerProfileInstantiate`, registers `instantiate` with the required options `--repository <id>` and `--template <id>`, and calls `runProfileInstantiation`. - **Exactly three prompts, and a flag for each** — `--upstream <branch>` asks `upstream branch?` with the `defaultBranch` of `repository.inspect` as the suggestion. `--host-fingerprint <value>` asks `host key fingerprint?` with the inspected fingerprint as the suggestion, and only when `remoteTransport` of `src/cli/repository/transport.ts` returns `ssh`. `--template <id>` asks `template id?` with the suggestion `null`, so onboarding never guesses a template. All three go through `confirmValue` of `src/cli/confirm.ts`, so a supplied flag skips the question and a missing flag with no terminal throws `ConfirmationRequiredError`, which onboard reports as `kanthord: confirmation-required: <message>\n` and exit code `1`. A skipped repository step asks neither of its two questions, because it calls `repository.inspect` zero times. No other prompt exists. Onboard never asks a yes-or-no question, so a scripted run needs no answer file.
- **The full flag set, and the order of the local refusals** — required: `--git-credential <name>`, `--git-transport <transport>` with the values `http-basic` and `ssh`, `--repository <name>`, `--url <url>`, `--project <name>`, and `--provider-credential <name>`. Prompted: `--upstream <branch>`, `--host-fingerprint <value>`, `--template <id>`. `--base-url` and `--token` are program options that `registerClientOptions` already declares, so onboard declares neither. - **Two exit-code channels** — a local refusal calls `exit(LOCAL_REFUSAL)` of `src/cli/exit-code.ts`. Onboard never continues after a refusal, so a step never runs against a state an earlier step failed to write.
