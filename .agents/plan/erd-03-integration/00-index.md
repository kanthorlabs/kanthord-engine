# Plan 00: Index

## Scope

ERD 3 ("External integration") covers the tables `intake_inbound`, `intake_inbound_event` and `intake_outbound_request` (`docs/reference/erd/03-integration.md:50–84`), together with the operations, collaborations, CLI commands and fixtures that make them usable end-to-end: the Intake Service module and its service identity; the outbound record with its repeat rules and its human operations; the configured repository actions `github.pull_request` and `git.merge_push`, the pull-request read and the check of a request evidence; the presigned storage grants and `s3.delete_object`; the inbound with its credential release; the webhook and the poll acquisition of GitHub; delivery admission; the handoff with the human event operations; the inbound resource healthcheck; and the OpenAPI and CLI of all of these.

ERD 3 replaces every ERD 2 seam that ERD 2 decision D6 left `unwired` (decision D6):

- `IntakeCheck.check`, `IntakeActions.perform`, `IntakeActions.read`: plan 03.
- `IntakeStorage.put`, `check`, `get`, `executionGet`, `delete`: plan 04.

The out-of-scope boundary is decision D5: the CLI transport and every CLI write, Slack, Telegram and Jira, the native push send, the inbound request contract (POSTPONED), acceptance as a human act and the account mapping, the cross-process identity contract (POSTPONED), the MCP server and its read tools, every B9 item and the stored telemetry of ERD 4. A task that meets an open HANDOFF item implements the page as written and states the gap in one line (decision D1).

The decisions D1 to D24 that the plans cite are in [decisions.md](decisions.md).

**Rationale for order.**
The foundation (01) creates the tables, the service identity and the `service` policy that every later plan needs. The outbound record (02) is the write path of every outbound operation, so it precedes the repository actions (03) and the object delete (04). Plan 03 generalizes the protected facility, which plans 04 and 05 extend. The inbound store (05) precedes the webhook (06) and the poll (07), which insert events; the event reads sit in plan 06, so the first writer of `intake_inbound_event` proves its rows through a CLI read (ERD 1 decision D13). Delivery admission (08) needs the check of plan 03, and it precedes the handoff (09), which calls it (decision D5). Plan 10 assembles what crosses plans.

**Collaboration-type contract rule.**
ERD 2 `00-index.md` "Collaboration-type contract rule" stands: a service declares the types of its collaborations inline in its own `contract.ts`, and the composition root is the only file that wires cross-service types (`engine/src/apps/server/index.ts:74–319`; `architecture.impl.md:592–623`).

## Blockers

Each blocker below is a real gap or conflict of the pages under decision D1. A task that a blocker affects waits for the ruling of Ulrich and its publication on the owning page (decision D1). Each plan names the recommendation and the task that implements it after the ruling.

- B1 — `architecture.impl.md:698–699` admits only reads before `caller.commit` and runs the asynchronous work first. Three ruled mechanisms write outside that rule in a handler: the `pending` insert of an outbound request before its call (`intake-service.impl.md:164`); every custody release before a platform call, which pins under an execution identity and drains under every identity (`custody.impl.md:163`, `:168–169`); and the `failed` state of an outbound request whose operation answers an error, which the handler writes in its own transaction before it throws (`intake-service.impl.md:168`; `mission-service.impl.md:358`). The affected handlers are `intake.action.perform`, `intake.action.read`, `intake.action.check`, the five storage operations, and the inbound create and delete that call a platform (decision D3). Recommendation: one sentence in `architecture.impl.md:698` that admits a write that the owning sibling rules before the asynchronous call or before an error answer, with the three mechanisms named. Plans 02, 03, 04, 06, 07.
- B2 — The health report keys a project-scoped entry by the project name inside one inventory transaction (`gateway-service.impl.md:358`, `:365`, `:376`). The Intake Service reaches a peer through an operation only, declares one collaboration, and shares no atomic invariant with another service (`intake-service.md:32–34`), and a Kind 2 collaboration serves only an atomic invariant (`architecture.impl.md:594`). No page gives the Intake inventory the project name. Recommendation: the Intake inventory answers each entry with its `projectId`, and the composition root resolves the name through a Project-owned read in the collection transaction; `gateway-service.impl.md:376` names that resolution, and the Intake boundary stays unchanged. Alternative: a Project read collaboration of the Intake inventory, which needs `intake-service.md:32–34` and the collaboration list of `architecture.impl.md:599–603` to name it. Plan 10.
- B3 — A registered webhook needs the absolute public URL of `/hooks/<inbound id>` (`intake-service.impl.md:40`), and no page names the origin of the ingress (`gateway-service.impl.md:481–500`). Recommendation: the proposed contract of decision D18 in `intake-service.impl.md` and the field index of `architecture.impl.md:308–327`. Plan 06.
- B4 — The liveness answer names the closed set of component maps (`gateway-service.impl.md:316`, `:325`, `:328`), and a new service registers its own probe (`architecture.impl.md:910`; `engine/AGENTS.md` "Add a service" step 5). Recommendation: the map `intake` with the component `events`, which reports the dispatcher of the running service, on those three lines. This map is apart from the ruled `services.intake` owner of the resource report (`gateway-service.impl.md:354`). Plan 01.
- B5 — `engine/docs/cli/intake.md:411–419` names two API operations and no route. No page names the routes of `intake.action.perform`, `intake.action.read`, `intake.storage.put`, `intake.storage.check`, `intake.storage.get`, `intake.execution.storage.get` and `intake.storage.delete`, or the operation identity of the receipt, whose route `POST /hooks/<inbound id>` stands (`engine/docs/cli/intake.md:389`). The `service` operations `intake.action.check` and `mission.delivery.admit` take no route and no OpenAPI entry (`architecture.impl.md:665–666`). A `client` route of `intake.storage.put` lets its caller select a fresh asset identity, so the Mission Service no longer allocates the destination (`intake-service.impl.md:142`; decision D8). Recommendation: the routes of plans 03, 04 and 06 in the section "Routes without a command" of `engine/docs/cli/intake.md`, and a ruling on the allocation authority of the PUT; the whole PUT contract of plan 04 waits for it. Plans 03, 04, 06, 10. The `human` route of `intake.storage.delete` also lets a human delete the object of a live evidence without the `force`, the reason and the mission version of `mission.evidence.asset.delete` (`mission-service.impl.md:350–354`); the recommendation is that the route takes the Mission deletion admission, with `expectedMissionVersion`, `force` and `reason` forwarded through the seam.
- B6 — `docs/reference/erd/03-integration.md:24` states that the peers reach the Intake Service through `service`-policy operations alone, and `intake-service.impl.md:120–127` declares `client` and `human` operations that forward the caller identity (`intake-service.md:39–40`). Recommendation: a repair of the ERD sentence to the policies of the owning sibling; the plans follow `intake-service.impl.md:120–127`, which declares the operations (`intake-service.md:140`). Plans 03, 04.
- B7 — Every mutation handler is idempotent by a natural key of its own, except an evidence submission (`architecture.impl.md:506`, `:722`; `gateway-service.impl.md:411`). `intake.inbound.create` has no natural key, because a duplicate inbound serves a rotation (`engine/docs/cli/intake.md:222–224`; `docs/reference/erd/03-integration.md:126`). `architecture.impl.md:506` repeats the rule. Recommendation: name the inbound create as the second exception on the three lines. No configuration index and no request record (root `AGENTS.md` "Rejected proposals"). Plan 05.
- B9 — Each remote call of an inbound takes its own release (`intake-service.md:36`; `intake-service.impl.md:19`), and a consumed grant authorizes no second operation (`custody.impl.md:100–101`). `intake-service.impl.md:33` deregisters after a refused insert with the material of the `webhook-register` grant, and a sibling never overrides its page (`intake-service.impl.md:8–9`). Recommendation: the compensation takes its own `webhook-deregister` grant; when the credential is gone, the create answers the refusal and a human removes the registration at the platform, as `intake-service.md:65` rules for a crash; the ruling also reconciles the test of `intake-service.impl.md:219`, which asserts that no registration remains. Plan 06.
- B8 — A registered webhook registers "the events that `configuration` names" (`intake-service.impl.md:40`), and the configuration holds no field beyond `resource` until HANDOFF lands (`engine/docs/cli/intake.md:198`; `docs/brainstorm/HANDOFF.md:48`). Recommendation: the fixed event list `pull_request` and `push` of decision D14 in `intake-service.impl.md:40`. Plan 06.
- B10 — The read-back of `github.pull_request` finds an open pull request of the node branch (`intake-service.impl.md:176`; `repository.impl.md:39`), and the request key of a pull request holds no snapshot (`worker-service.impl.md:434`; `intake-service.vocabulary.md:67–71`). A reuse of a pull request pushes the snapshot (`intake-service.impl.md:122`), so the open pull request that existed before proves no push, and a failed push turns `succeeded` at the repeat. Recommendation: a reuse appends the snapshot commit to its request key, and its read-back checks that the node branch contains the snapshot (`landedOn`). Plan 03.
- B11 — Delivery admission "writes only ERD 2 rows: `end_state` of a request evidence and the landed-commit evidence" (`docs/reference/erd/03-integration.md:155`), and the end state moves the node `External.Requested -> External.Success` or `External.Failed` and closes the attempt (`mission-service.md:604–611`; `engine/src/mission/node-check.ts:141–166`). Recommendation: the ERD sentence admits the node transitions and the attempt closure that the Mission Service rules for the end state. Plan 08.
