# EPIC 051.1 — The candidate and the git primitives

Status: **draft**. It follows EPIC 051 by sequence order, and it runs before EPIC 051.2. It consumes EPIC 006's `Git` service and loopback fixture, EPIC 050's run and fence, and EPIC 050.1's expiry pass.

**Dispatch prerequisite.** EPICs 050.2, 050.3, 050.4, 050.5 and 051 ship before this one. Story 5 appends `"051.1"` to `shippedEpics`, and `test/sequence/conformance.test.ts:264` requires that list to stay a prefix of `authoredEpics`. Story 4 appends `"051.1"` to `authoredEpics` after `"051"`, and `test/sequence/conformance.test.ts:41` throws for a listed epic whose story directory is absent, so EPIC 051's story tree exists before this epic is implemented.

It carries a decimal number for the reason EPIC 051 states. It needs neither EPIC 050.6 nor the re-authored EPIC 107: no story here runs a declared command.

## Goal

A worker's candidate is a pinned ref the daemon owns, and the daemon can read, judge and reap it:

- a worker pushes its candidate to `refs/kanthord/candidate/<runId>/<attemptNo>`, and that ref is the pin;
- `ingest.candidate` resolves the ref and refuses `candidate-unreachable` when the reported oid is not reachable from it;
- `candidate.discard` deletes one candidate ref, and it is the only site that calls `git.deleteRef:candidate`;
- `candidate.sweep` lists the namespace and deletes every ref whose run is not `active`, at startup;
- `Git` gains the six read and write primitives the family needs;
- the three acceptance verdicts exist as pure functions with no caller yet.

## Non-goals

- **No `acceptExecution`.** The ordered gate that calls these units is EPIC 051.4. The units here carry their own tests and no caller, which is what lets EPIC 051.4 draw one composed path per refusal.
- **No command execution.** `commands.run` is EPIC 051.2, and it is the one story of the family that needs a working `Verify`.
- **No land, and no checkpoint.** EPIC 051.3 owns both.
- **No wire change.** `node.report` is untouched here; EPIC 051.4 carries every contract edit of the family.
- **No candidate table.** The shipped `candidate` table stays unused. EPIC 057 drops it.

- **No runtime candidate sweep.** The reaper runs at startup and nowhere else. `expireRuns` runs inside `claimNode`'s transaction (`src/commands/node/claim-node.ts:147`) and the daemon holds no periodic driver, so a post-expiry deletion needs `ClaimNodeResult` to carry the runs the pass ended and the `node.claim` binding at `src/main.ts:553` to become asynchronous. **EPIC 051.5 owns that targeted cleanup**, and it is targeted rather than a second global sweep because the runs it acts on are already committed as `ended`, which is what makes it race-free. This epic ships the startup half and states the residue: a candidate ref of a run that expires mid-session survives until the next start.

## Decisions

- **A worker delivers its candidate to a pinned ref, and the daemon never fetches from a worker.** `docs/workflow/worker.md:423` — section 8 step 2 — states the mechanism outright: the daemon owns the bare home, the worker pushes its candidate to `refs/kanthord/candidate/<runId>/<attemptNo>` before it reports, that ref **is** the pin, a report naming an oid the ref does not reach is refused, and the daemon deletes the ref on acceptance, on rejection and on contention. This epic implements that sentence; it derives nothing. An internal worker's attempt workspace has the bare home as its origin, and an external client is given the same path at claim. The refusal code is `candidate-unreachable`, which the source does not name and this epic chooses.

- **The pin is created by the worker and owned by the daemon.** The daemon deletes the candidate ref on acceptance, on rejection and on contention. A ref left behind would keep a rejected object alive and let a later report name it.

- **A run that ends without a report leaves its ref behind, so the daemon sweeps the namespace.** The three deletions above each sit on a path a report reached. An expiry reaches none of them, and so does an operator handoff. `.agents/plan/stories/050.1-the-claim/02-the-expiry-pass.md:98-100` states the gap and delegates the fourth deletion here. The daemon therefore holds one reaper: it lists `refs/kanthord/candidate/`, and it deletes every ref whose run is not `active`. **The sweep runs at startup, and this epic wires no other call site.** The runtime half of EPIC 050.1's delegation resolves to EPIC 051.5, not here. One mechanism still discharges both orphans, because neither the expiry nor an operator handoff knows the attempt number, and the reaper needs none.

- **The sweep is not a call inside `expireRuns`, and the signature is why.** `ExpireRunsDependencies` is `{ events, instanceId }` at `.agents/plan/stories/050.1-the-claim/02-the-expiry-pass.md:47-50`. It names no `Git`, it takes the caller's transaction, and it is synchronous. A ref delete is git I/O, and `AGENTS.md` forbids git I/O inside a storage transaction. `expireRuns` also returns `{ runId, nodeId, fence }` and no attempt number, so a caller holding its result still cannot name `refs/kanthord/candidate/<runId>/<attemptNo>`. The seam trace of `expiry-pass-one-due` therefore does not move, and this epic supersedes no EPIC 050.1 diagram. The sweep is its own command, and at the startup call site of this epic it runs against a quiescent daemon.

- **A candidate deletion is a git write that opens no journal row, and the exemption is stated by crash consistency.** `AGENTS.md` makes a command that writes git a journaled write with exactly two transactions. `candidate.discard` writes a ref inside no transaction and `candidate.sweep` writes refs after one, and neither carries a journal row. That is legal here because all six conditions hold, and a git write that fails any of them stays a journaled write:

  1. the deletion has no database mutation or event that must be atomic with it;
  2. product correctness does not depend on the deletion happening immediately;
  3. eligibility comes from committed, monotonic state — a run already `ended`, or a run id no row carries;
  4. a failure leaves a ref, which is a safely retryable remnant and never a corrupt one;
  5. startup is guaranteed to retry it, because the reaper is a startup step;
  6. the caller settles its logical outcome before it attempts the deletion.

  Ownership and idempotence are **not** the criterion. They say a repeated deletion is harmless and say nothing about a crash between a database decision and the write. **This criterion is carried in `AGENTS.md` `### Rules the import matrix cannot express`, beside the journaled-write rule**, and that bullet is the normative form. EPIC 051.4 and EPIC 054 audit their own deletions against the six conditions; a deletion whose success must sequence with a database effect is journaled.

- **`sweepRemnants` is grandfathered by name, and it is not the precedent for the rule above.** `src/commands/startup/sweep-remnants.ts:33` and `:63` open two storage transactions around filesystem I/O with no journal row, so a crash between them loses the durable record of a removal. It removes `.lock` files, staging directories and key material — not valid refs through the ref-update protocol — so it neither justifies nor is justified by the candidate exemption. It is named here so a reader does not read the exemption as written to cover it. Repairing it belongs to whichever epic next touches startup recovery.

- **The sweep reads the ref namespace, so `Git` gains a listing method.** No shipped method lists refs under a prefix: `src/services/git/index.ts` declares `resolveRef` and `refUpdate` and nothing that enumerates. The sweep is the only caller that cannot name its refs in advance, and a reaper that cannot enumerate is not a reaper.

- **The candidate ref is a convention, and the epic does not pretend it is a boundary.** `refs/kanthord/candidate/<runId>/<attemptNo>` is where a worker writes, with the run id and the attempt number taken from its own active run. Nothing enforces it. The fetch-confinement rule of EPIC 006 is the refspec `+refs/heads/*:refs/remotes/origin/*` on the daemon's **own fetch**, and it restricts no worker, so this epic makes no claim on it.

- **A worker that writes another ref is not detected, and `worker.md` section 11 records that.** A worker holds file system access to the bare home, so it could write `refs/heads/<objectiveId>` and skip every check of section 8. No hook stops that: a hook binds a push, and a worker with a local path can write a ref directly. The daemon's defence is that it reads no such ref. It accepts the candidate the report names, it verifies ancestry from the recorded base, and it moves the objective branch itself by compare and swap. The assertion that proves it belongs to EPIC 051.4, where the whole route exists.

- **The worktree lifecycle belongs to `Git`, both halves of it.** An earlier draft of this epic gave `checkout` a caller-supplied `targetDir` and declared no disposal at all. Both were defects, and EPIC 051.2 is what exposed them: its `commands.run` is a command under `src/commands/`, where `eslint.config.js:342` bans `node:fs`, so it can neither allocate a directory atomically nor remove one. `checkout` therefore mints its own with `mkdtempSync` and returns the path, and `removeWorktree` disposes of it. Creation and disposal of a git worktree are one capability's concern, and splitting them left the only caller unable to hold either end.

- **A crash between a `checkout` and its `removeWorktree` leaks a directory, and reclaiming it is a stated non-goal of this epic.** Measured on git 2.48.1, `git worktree prune --expire=now` removes only an administrative entry whose working tree is **missing** — Story 1's case 14 asserts exactly that — so a crash that left the directory in place keeps both the directory and its entry, and the prune this epic adds to `sweepHome` does not reach them. The residue is bounded by one directory per interrupted command and it is inert: `mkdtemp` never reallocates an occupied path, so it corrupts nothing. **The sweeper belongs to the epic that owns startup recovery for the acceptance gate, which is EPIC 051.4**, and it needs a rule this epic cannot state — which live worktrees a running daemon still holds. Do not add a sweep to `sweepHome` for it: `sweepHome` runs at startup against boundaries it enumerates from the registry, and it cannot tell an in-flight worktree from an abandoned one.

- **`git.deleteRef` is a separate method and not a widening of `RefUpdateInput.nextOid` to `string | null`.** `git update-ref -d` is a different invocation, and a null would force conditional argv construction inside `ref-update.ts`.

- **`git.isAncestor` carries no label, and it is `isAncestor` and not `isDescendant`.** The reachability call sits inside `ingest.candidate`, which is a nested unit, and the ancestry call of EPIC 051.4 sits in `acceptExecution`. The two are therefore in different diagrams, and `.agents/plan/authoring.md` forbids a repeated token only inside one diagram, so nothing needs separating. A `:candidate` or `:ancestry` label would also name the call site rather than an argument, which `.agents/plan/authoring.md:188` refuses: a projection names a value the call actually receives. The predicate reads naturally in both places — the reported oid is an ancestor of the ref tip, and the run base is an ancestor of the candidate head.

- **`candidate.discard` is a nested unit so `git.deleteRef:candidate` appears in one diagram only.** Every refusal that has an existing candidate ref draws `candidate.discard` as one step; the missing-ref path does not, because the ref never existed.

- **The declared-path check compares exact file paths, and it names every violation.** A `verify.paths` entry matches a changed file path bytewise; it is not a directory prefix. A rename counts as two changed paths, the old and the new, and both must be declared. The refusal lists every undeclared path, sorted with `comparePaths`, so a worker sees the whole gap in one report rather than one path per attempt.

- **An empty `paths` list refuses every change.** A node that declares no path declares no write set. `worker.md` section 2 states an empty `commands` list asserts nothing, and it states nothing of the kind about `paths`. The two lists are not symmetric: an execution node whose `verify.paths` is empty and whose diff is non-empty refuses `path-undeclared`, and an empty diff passes.

- **An execution run holds exactly one base row, and `repositoryVerdict` compares against it.** EPIC 050 sets the upper bound at "at most one" and states that this family raises the lower bound, so `runRow`'s refine at `src/domain/run.ts:34-45` tightens to exactly one for `execution`. **That does not make `multi-repository-unsupported` unreachable, because the refusal never compared two stored rows.** `repositoryVerdict` compares the repository the report names against the single stored `run_base` row, and refuses when they differ. A two-row base set was never producible — `src/services/storage/migration-0002-graph-and-plan.ts:33` gives an objective exactly one `repository_id`, the `run_base` primary key `(run_id, repository_id)` forbids a duplicate, and the claim writes one row — so a fixture built on two rows would have proved a refusal over a state no code path reaches.

- **The refine states the invariant and enforces nothing, and the epic says so.** `runRow` is imported only into the `rows` registry at `src/domain/rows.ts:43`, and no production file calls `parse` or `safeParse` on it. Tightening it is a documentation change. What enforces the cardinality is the claim of EPIC 051, which writes exactly one row inside its own transaction.

- **A zero-row execution run is an invariant violation, never a refusal.** The claim inserts the base row atomically with the run, so no execution run reaches acceptance without one. Before EPIC 051 every run has no base row, and startup blocks such a node with `recovery-inputs-missing`; that path is EPIC 050.5's and it is unchanged.

- **The pure verdicts read no git.** `ancestryVerdict`, `repositoryVerdict` and `declaredPathVerdict` receive values. The two git reads that feed them are added to `acceptExecution` by EPIC 051.4, which is where a call site exists to hold them.

### Seam keys this epic introduces

- `ingest.candidate` — nested unit injected into `AcceptExecutionDependencies`; encapsulates the ref-resolve and reachability check, and exposes the candidate ref for later deletion.
- `git.resolveRef` — present since EPIC 006; `:candidate` labels the call that reads the candidate ref.
- `git.isAncestor(input: { gitDir, ancestorOid, descendantOid }): Promise<boolean>` — new method on `Git`, over `git merge-base --is-ancestor`. Exit `0` is `true`, exit `1` is `false`, and any other exit throws. Equality is an ancestor, so a report that exactly matches the ref tip passes.
- `git.changedPaths(input: { gitDir, baseOid, headOid }): Promise<string[]>` — new method on `Git`, over `git diff --name-status`. A status beginning `R` or `C` emits both the old and the new path, because `docs/proposal` makes both sides of a rename load-bearing here. Every other status emits one path. The result is deduplicated.
- `git.checkout(input: { gitDir, oid }): Promise<string>` — new method on `Git`, over `git worktree add --detach <allocated> <oid>`. A bare repository holds no index, so a `--work-tree` checkout would need an injected `GIT_INDEX_FILE` per command; `worktree add` needs none. **It allocates its own directory with `mkdtempSync` under a new `GitPaths.worktreeDirectory` and returns the created path.** It takes no `targetDir`: every caller of it is a command under `src/commands/`, `eslint.config.js:342` bans `node:fs` there, and a caller-derived name is not atomically fresh — a crash leaves the derived path occupied and `git worktree add` then refuses it. A failed `worktree add` removes the directory it allocated before it throws, because a path that never became a registered worktree cannot be removed by `git worktree remove`.

- `git.removeWorktree(input: { gitDir, targetDir }): Promise<void>` — new method on `Git`, over `git worktree remove --force <targetDir>`. **`--force` is required**: a declared command of EPIC 051.2 runs arbitrary shell in that tree, and `git worktree remove` refuses a dirty one. Measured on git 2.48.1, one invocation deletes the directory **and** removes the `${gitDir}/worktrees` entry, so a caller disposes of both halves with one call. It is **not** idempotent — a second call on the same path exits `128` — so it runs once per `checkout` and no caller retries it.
- `git.deleteRef(input: { gitDir, ref }): Promise<void>` — new method on `Git`, over `git update-ref -d`, unconditional and with no compare-and-swap.
- `git.listRefs(input: { gitDir, prefix }): Promise<string[]>` — new method on `Git`, over `git for-each-ref --format=%(refname) --sort=refname`, returning full ref names and an empty array for a prefix with no ref.
- `candidate.discard` — nested unit injected into `AcceptExecutionDependencies`; calls `git.deleteRef:candidate` on the candidate ref that `ingest.candidate` resolved.
- `candidate.sweep` — the reaper command. It lists `refs/kanthord/candidate/`, reads the run state of each ref it finds, and calls **`candidate.discard`** for every ref whose run is not `active`. It never calls `git.deleteRef` itself: `candidate.discard` is the only site that does, which is what keeps `git.deleteRef:candidate` in one diagram of the family. It opens one transaction for the read and holds none across the deletes.

## Stories

Each entry is a name and the output it contributes. The story file holds the change, the tasks and the diagrams, and it declares its kind.

1. **The six git primitives.** Extend the `Git` interface at `src/services/git/index.ts` and add one implementation file each, matching the conventions of `ref-read.ts`, `ref-update.ts` and `worktree.ts`: `isAncestor` in `is-ancestor.ts`, `changedPaths` in `changed-paths.ts`, `checkout` in `checkout.ts`, `removeWorktree` in `remove-worktree.ts`, `deleteRef` in `delete-ref.ts`, `listRefs` in `list-refs.ts`. Add `worktreeDirectory` to `GitPaths` and create it in `buildGitPaths`. Extend startup's `sweepHome` path with `git worktree prune --expire=now`. This is one story because six methods extend one interface, and six stories would spend most of the epic's budget on primitives. Its file stem stays `01-the-five-git-primitives`, because EPIC 051.2's stories cite it and a stem is an address. `story-foundation`.

2. **The candidate ref is missing.** Add `src/commands/checkpoint/ingest-candidate.ts` and draw `ingest-candidate-missing-ref`: `git.resolveRef:candidate` returns null and the command refuses `candidate-unreachable` immediately, with no reachability call and no deletion. `story-implement`.

3. **The candidate ref does not reach the reported oid.** Draws `ingest-candidate-unreachable`: the ref resolves, `git.isAncestor({ ancestorOid: reportedOid, descendantOid: refTip })` is false, `candidate.discard` deletes the ref, and the command refuses `candidate-unreachable`. It adds the false branch alone; Story 7 adds the check and the path that still succeeds. `story-implement`.

4. **The candidate ref is deleted.** Add `src/commands/checkpoint/discard-candidate.ts` and draw `discard-candidate`, one `git.deleteRef:candidate` call. Drawing it as its own nested unit is what keeps that token in exactly one diagram of the family. `story-implement`.

5. **The reaper deletes a stale ref.** Draws `sweep-candidates`: the enumeration of Story 8 finds a ref whose run is not `active`, and `candidate.discard` deletes it. Call the command from `src/commands/startup/` alone. It discharges the startup half of the obligation `.agents/plan/stories/050.1-the-claim/02-the-expiry-pass.md:98-100` delegates here, and it supersedes no EPIC 050.1 diagram, because `expireRuns` gains no seam call. It is last in dispatch order, because it appends `"051.1"` to `shippedEpics`. File stem `05-the-candidate-namespace-has-a-reaper`. `story-implement`.

6. **The acceptance verdicts.** Add `src/domain/execution-acceptance.ts` with `ancestryVerdict`, `repositoryVerdict` and `declaredPathVerdict`, each pure and each reading no git. Tighten the `runRow` refine at `src/domain/run.ts:34-45` to exactly one base row for `execution`. `story-foundation`.

7. **The candidate ref reaches the reported oid.** Draws `ingest-candidate-reachable`: the ref resolves, `git.isAncestor` is true, and the command returns ok having deleted nothing. It adds the reachability check itself, so Story 3 adds only the false branch and its deletion. The two paths hold **different seam sets** — the refusal reaches `candidate.discard` and this one does not — so `.agents/plan/authoring.md` draws both, and a `story-implement` draws one. File stem `07-the-candidate-ref-reaches-the-reported-oid`. `story-implement`.

8. **The candidate namespace is enumerated.** Add `src/commands/checkpoint/sweep-candidates.ts` and draw `sweep-candidates-no-stale-ref`: one transaction reads the repository homes and the active run ids, `git.listRefs:candidate` enumerates each bare home, every ref belongs to an active run, and the command returns ok having deleted nothing. Story 5 adds the deletion. Same reason as Story 7: a sweep that deletes nothing never reaches `candidate.discard`, which is a different seam set. File stem `08-the-candidate-namespace-is-enumerated`. `story-implement`.
