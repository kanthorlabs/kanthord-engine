# EPIC 050.6 — The process capability

Status: **draft**. It follows EPIC 050.5 by sequence order, and it runs before a re-authored
EPIC 107 and before EPIC 051.2, the one epic of the EPIC 051 family that needs a working `Verify`.
It consumes nothing that EPIC 050.5 does not already leave in the tree.

## Goal

- `src/services/process/` exists as a capability of its own. It holds the launcher, the one
  **spawned-child** supervision machine and its TERM-then-KILL cancel path, and it is the only
  place under `src/` that creates a process.
- `src/services/git/` runs on that machine. `run.ts`, `probe.ts`, `host-key.ts` and `child.ts` hold
  no launcher import, and no second copy of the timeout, the output cap, the group signal or the
  launcher exit codes **for a child the daemon spawned and still holds a handle to**.
- **Journal recovery is a separate path and stays in `src/services/git/child.ts`.** `stopChild`
  signals a pid it read from a journal, holds no child handle, and keeps its own signal sequence and
  poll loop. It is not a second copy of the machine, because the machine supervises a handle it owns.
- `assertSignallable` and `requireSignallable` are pure pid checks in `src/domain/pid.ts`.
- Nothing else moves. The epic ships no agent, no model call, no route and no configuration key, and
  it changes no command and no query.

## Non-goals

- **No agent work of any kind.** No evidence contract, no allow list, no resources, no model bridge,
  no agent shell, no tool trace, no rendered messages, no `re@1` verdict and no `PiCodingAgent`.
  EPIC 106 owns every one of them.
- **No `agent.list` route change.** `src/http/contract/instruction.ts` keeps `agent.list` as
  `stubbed`, and EPIC 106 moves it.
- **No `src/services/git/diff.ts` and no `diffWorkspace`.** EPIC 106 owns the temporary-index diff.
- **No canonical JSON.** `src/domain/canonical-json.ts` is EPIC 106's.
- **No configuration key.** `agent.timeoutMs` and `agent.path` are EPIC 106's; `check.path` is
  EPIC 107's. This epic touches no file under `src/services/config/`.
- **No check contract and no `SupervisedVerify`.** EPIC 107 owns `src/services/verify/`, and it is
  re-authored against the tree this epic leaves.
- **No new runner semantics.** Every constant, every outcome and every signal sequence is EPIC 006's
  shipped behaviour relocated, and `docs/proposal/phase-1/git-foundation.md:273` owns that sequence.
  **This is not a claim that no caller changes**: `## Decisions` names exactly two caller-visible
  changes, the grace for two callers and the output bound for three, and no third one exists.
- **No harness run.** `scripts/e2e/007/run.ts` runs under `pnpm run e2e:007` when a human runs it,
  and EPIC 011 owns the acceptance run. This epic repairs those call sites and proves them with
  `pnpm run typecheck` only.

## Decisions

- **This epic depends on nothing in EPIC 101 to EPIC 105, and that is why it can precede them.**
  Every symbol it moves already ships: `src/services/git/launcher.ts:1` — `node:child_process`,
  `src/services/git/run.ts:14` — `DEFAULT_TIMEOUT_MS`, `src/services/git/run.ts:15` —
  `DEFAULT_OUTPUT_LIMIT_BYTES`, `src/services/git/run.ts:16` — `TERMINATION_GRACE_MS`,
  `src/services/git/run.ts:36` — `ScheduledTimer` and `src/services/git/run.ts:38` — `Schedule`. The
  capability names no vendor package, takes no `Model`, no `Deadline`, no `Ambient` and no
  `Workspace`, and imports nothing that EPIC 050.5 does not leave behind. Gate row 16 asserts it over
  the import graph, so the claim is machine-checked and not prose.

- **The extraction cannot ship alone, so the git repairs are in this epic.**
  `src/services/git/run.ts:11` — `launcher.ts`, `src/services/git/child.ts:17` —
  `assertSignallable`, `src/services/git/probe.ts:12` — `spawnSupervised`,
  `src/services/git/host-key.ts:12` — `spawnSupervised` and `src/services/git/child.test.ts:23` —
  `spawnSupervised` all import `./launcher.ts`. `.agents/plan/authoring.md` makes a change and the
  repairs it forces one epic, and that rule outranks the story count.

- **`createGitRunner` takes the runner as a required second parameter, and the default is deleted.**
  `src/services/git/run.ts:51` — `schedule` is defaulted to `systemSchedule` today. A default of
  `createSupervisedRunner(systemSchedule)` would make `src/services/git/run.ts` import
  `src/services/process/supervisor.ts`, which is one capability's implementation importing another
  capability's, refused by the import matrix of `AGENTS.md` and proven refused by
  `src/domain/layout.test.ts:232` — `SqliteHomeLock`. The parameter is therefore required, and every
  call site passes a runner. The closure is `src/main.ts:233` — `createGitRunner`, thirteen suites
  under `src/services/git/`, and seven files under `scripts/e2e/`; `src/services/git/run.test.ts:126`
  — `systemSchedule` asserts the deleted default and is rewritten at the supervisor.

- **The blast radius stops at `src/services/git/binary.ts`, so no command and no query changes.**
  `src/services/git/index.ts:159` — `scanHostKeys`, `:160` — `confirmHostKey`, `:185` —
  `inspectChild` and `:186` — `stopChild` keep their exact signatures, because the runner is bound at
  construction. `BinaryGitDependencies` gains `runSupervised`, and `src/services/git/binary.ts:33` —
  `scanHostKeys` passes it. No file under `src/commands/` or `src/queries/` changes, and no `Git`
  fake in their tests changes. **The number of commands, queries and nested commands whose seam trace
  moves is zero**, which is why this epic holds no `story-implement` entry.

- **`confirmHostKey` is in the repair set, and `stopChild` is not.**
  `src/services/git/host-key.ts:129` — `scanHostKeys` calls the scan, so `confirmHostKey` takes the
  runner and forwards it. `src/services/git/child.ts:233` — `stopChild` spawns nothing:
  `src/services/git/child.ts:237` — `process.kill` signals a pid read from a journal, so it takes no
  runner and keeps its own poll loop. Inside `child.ts` only
  `src/services/git/child.ts:167` — `readProcessStartSeconds` spawns, so `inspectChild` takes the
  runner and passes it down.

- **All three pid predicates move to `src/domain/pid.ts`, and exactly two of them are exported.**
  `src/services/git/launcher.ts:50` — `assertSignallable`, `:56` — `isSignallable` and `:60` —
  `requireSignallable` are pure integer checks over a pid. Splitting them would leave the launcher a
  second copy, and the launcher may import `domain/` under the import matrix of `AGENTS.md`.
  `src/domain/pid.ts` exports `assertSignallable`, because
  `src/services/git/child.ts:119` calls it, and `requireSignallable`, because
  `src/services/git/launcher.ts:117` calls it. `isSignallable` stays private to `pid.ts`, so
  **no test asserts it directly** and gate row 2 proves it only through the two exported callers. The
  file imports nothing, so `eslint.config.js:311` — `node:*` and the purity cases at
  `src/domain/layout.test.ts:59` — `Date.now` both hold with no exemption.

- **The pid file has one owner, that owner decides its lifetime, and the supervisor never removes
  one.** `ProcessRunRequest.pidFile` is a required `string`, which carries no supplied-versus-minted
  bit, so a supervisor cannot decide the question at all. The rule is therefore ownership, not
  minting: **a scratch owner removes its file in a `finally`; a journal owner keeps it until
  reconciliation; the runner removes nothing.** `src/services/git/probe.ts:206` — `rmSync`,
  `src/services/git/host-key.ts:277` — `rmSync` and `src/services/git/child.ts:229` — `rmSync`
  already remove their own scratch file in a `finally`, and `src/services/git/run.ts` removes only
  the file it minted because `src/commands/repository/register-repository.ts:219` — `pidFile`
  supplies a journaled path whose removal `src/commands/startup/reap-orphans.ts:187` —
  `removePidFile` owns. A supervisor that removed every pid file would destroy that token before
  reconciliation reads it. `src/services/git/run.test.ts:413` — `minted` therefore stays a git case.
  **Every later caller inherits the obligation**: EPIC 107 and EPIC 106 each mint a pid file and
  neither states a removal today, so each leaks one per run until its re-authoring adds the
  `finally`. This epic reports that, and gate row 12 pins the runner half of the rule.

- **Two callers gain the grace, and that is one of exactly two caller-visible behaviour changes.**
  `src/services/git/probe.ts:165` — `signalGroup` and the timeout of
  `src/services/git/child.ts:167` — `readProcessStartSeconds` send `SIGKILL` with no `SIGTERM` first.
  `src/services/git/run.ts:100` — `signalGroup` and `src/services/git/host-key.ts:227` —
  `signalGroup` already send `SIGTERM` then `SIGKILL` after `TERMINATION_GRACE_MS`, so neither
  changes. One machine has one sequence, and `docs/proposal/phase-1/git-foundation.md:273` states
  that sequence as the contract. **The bound is on the signal, not on the exit**: `SIGKILL` is
  requested `2_000` ms after `SIGTERM`, and the runner then awaits the child, for which no
  completion deadline exists — a child in uninterruptible sleep still delays the settle. The claim
  is that the daemon signals on time, never that the child dies on time.

- **The three callers that captured output without a bound gain the bound, and map its refusal to
  the degraded result they already return.** `src/services/git/probe.ts:176` — `chunks`,
  `src/services/git/host-key.ts:198` — `stdoutChunks` and `src/services/git/child.ts:210` — `chunks`
  accumulate with no cap today. **That is the second caller-visible change**: three paths can now end
  early on an output-bound refusal. Each passes `DEFAULT_OUTPUT_LIMIT_BYTES`, and an
  `output-exceeded` outcome maps to the value that caller already returns when its child produces
  nothing readable — `ToolProbeError("tool-unreadable")` for `probeTools`, exactly
  `{ scanned: false, failure: "host-key-unavailable", detail: "" }` for `scanHostKeys`, whose
  `ScanOutcome` failure variant at `src/services/git/host-key.ts:33` — `detail` carries a third
  field, and `null` for `readProcessStartSeconds`, which surfaces as the `liveness-unknown` finding.
  No new error code and no new outcome name enters the git service.

- **`onStdout` and `onStderr` never receive the chunk that crosses the cap.**
  `.agents/plan/epics/107-verify-service.md:29` already pins the truncation rule — the runner drops
  the crossing chunk, keeps the whole chunks before it, and reports `output-exceeded`. The callbacks
  observe exactly what `stdout` and `stderr` retain, so a streaming caller and a buffering caller see
  the same bytes. Leaving this open would force EPIC 106 to re-open the interface's behaviour, which
  is the cost this extraction exists to avoid.

- **`Schedule` is injected everywhere, so no supervised run reads a raw timer.**
  `src/services/git/probe.ts:162` — `setTimeout`, `src/services/git/host-key.ts:225` — `setTimeout`
  and `src/services/git/child.ts:196` — `setTimeout` arm a raw timer today. After the move the timer
  is the injected `Schedule` of `src/services/process/index.ts`, which is what makes
  `src/services/process/supervisor.test.ts` hermetic under `AGENTS.md` — no wall-clock dependency.

- **`onStdout`, `onStderr` and `signal` ship with a proof and no production caller.** No caller of
  this epic streams or cancels; `.agents/plan/epics/107-verify-service.md:58` passes `onStdout` null
  and `onStderr` null and `.agents/plan/epics/106-agents-on-pi-coding-agent.md:24` streams the agent
  shell, so removing the fields would force both epics to re-open the interface.
  `docs/proposal/phase-2/agents-and-workers.md:107` requires the cancel path. Gate rows 8 and 9 prove
  all three at the supervisor, so nothing ships unproven.

  `src/services/process/supervisor.ts` and `src/services/process/index.ts` keeps only the `Schedule`

  `src/main.ts:191` — `systemSchedule` is a different, unrelated value; the alias survives the move
