# EPIC 010.5 — Browser access

Status: **ready**.

## Goal

A browser client reaches the daemon when, and only when, a human names its exact origin in
configuration. `docs/proposal/phase-1/transport.md` holds the policy. An empty origin list keeps the
behaviour EPIC 004 shipped, byte for byte.

## Why this epic exists

EPIC 004 rejects every request that carries an `Origin` header. That is correct for a CLI and it makes
a browser client impossible, because a browser attaches `Origin` and a page cannot suppress it. The
product needs a browser client, so the total rejection becomes an allow list that is empty by default.

It sits after EPIC 010 because a browser client reads real routes, and a preflight over a registry
that still answers `501` everywhere proves nothing about the mode. It sits before EPIC 011 because an
end-to-end scenario must drive the browser path.

## Non-goals

- **No certificate handling.** The daemon still serves plain HTTP. A deployment that needs an HTTPS
  page puts a reverse proxy in front. `docs/proposal/phase-1/transport.md` names that topology and the
  daemon takes no part in it.
- **No cookie authentication and no `Access-Control-Allow-Credentials`.** The client authenticates
  with an `Authorization` header. Allowing credentials would admit cookie-bearing cross-origin
  requests and buy nothing.
- **No relaxation of the `Host` allow list.** It stays mandatory and exact on every request that
  reaches a route. It is the DNS rebind defence and this epic does not touch it.
- **No `OPTIONS` in the route registry.** A preflight is answered by the transport, not by an
  operation. The registry keeps its four methods, and `renderPath` keeps its grammar.

## Stories

- **The origin configuration** — `http.allowedOrigins`, env `KANTHORD_HTTP_ALLOWED_ORIGINS`, comma
  separated, default empty. Each entry is canonicalized on load through the URL parser and stored as
  the browser's own serialization, so a host case difference, an internationalized name, an IPv6
  literal and a default port all match. The loader refuses a scheme other than `http` or `https`, a
  wildcard, a suffix pattern, a path, a trailing slash, embedded credentials, and the literal `null`.
  A refusal names the offending entry.
- **The startup refusal** — a non-empty origin list with no `http.token` refuses to start, and the
  message names `http.token`. This joins the existing refusal in `src/services/config/refusals.ts` on
  a non-loopback bind with no token. A browser-reachable daemon with no token is the worst
  configuration this product can hold.
- **The origin decision** — `originMiddleware` becomes an allow list. No `Origin` header passes
  through untouched, so a CLI and a native client are unchanged. An `Origin` against an empty list is
  `403 origin-forbidden`. An `Origin` outside a non-empty list is `403 origin-forbidden`. An `Origin`
  inside the list sets `Access-Control-Allow-Origin` to the exact received origin and appends `Origin`
  to `Vary`. **Appends**: a `Vary` value already set by another middleware is merged, never replaced.
- **The preflight answer** — an `OPTIONS` request from an allowed origin answers `204` and terminates.
  It names `DELETE, GET, POST, PUT` as the allowed methods and `authorization, content-type,
idempotency-key, if-none-match, x-kanthord-client` as the allowed headers, and it sets
  `Access-Control-Max-Age`. `if-none-match` is in the list because `blob.show` sets an `ETag` and a
  browser revalidates with it. `idempotency-key` is in it because EPIC 010.6 adds that header, and a
  header absent from this list is a header a browser refuses to send.
  The answer is a constant and it never consults the registry, so a path that exists and a path that
  does not are indistinguishable. The story states the disclosure this accepts, from
  `docs/proposal/phase-1/transport.md`.
- **The middleware order** — envelope, origin decision, host, preflight termination, auth, route. The
  preflight is answered before the bearer check, because a browser sends no token on it. It is
  answered **after** the `Host` check, because no request may skip that control. The order is asserted
  rather than assumed.
- **The exposed response headers** — a non-preflight request from an allowed origin carries
  `Access-Control-Expose-Headers` naming `etag`, `accept-ranges` and `content-range`, so a browser
  client can read what `blob.show` returns. Without it a script sees the body and none of the caching
  or range metadata.

## Verification Gate

Gates: `npm run verify`

Proof:

```bash
node --test src/domain/origin.test.ts src/services/config/refusals.test.ts \
  src/services/config/convict.test.ts src/http/server/origin.test.ts \
  src/http/server/preflight.test.ts src/http/server/app.test.ts && echo "PASS EPIC-010.5"
```

Hermetic coverage required beyond the Proof:

- With an empty origin list, every request carrying any `Origin` value answers `403 origin-forbidden`,
  and a request carrying no `Origin` answers exactly what it answered before this epic. One assertion
  covers a routed route, a stubbed route and `system.health`.
- With `http://localhost:8080` configured, that exact origin passes and each of these answers
  `403 origin-forbidden`: `http://localhost:8081`, `https://localhost:8080`,
  `http://localhost.evil.test:8080`, `http://evil.test`, and the literal `null`.
- A configured `http://LOCALHOST:80` matches a received `http://localhost`, proving the default port
  and the host case are canonicalized on load.
- Each refused configuration value fails to load and names itself: `*`, `http://*.test`,
  `http://a.test/`, `http://a.test/path`, `ftp://a.test`, `http://user:pw@a.test`, `null`.
- A non-empty origin list with an empty token refuses startup and the message names `http.token`.
- A preflight from an allowed origin answers `204` with no bearer token, and the identical preflight
  to a path that matches no operation answers the identical `204`, byte for byte.
- A preflight from an allowed origin with a `Host` outside the allow list answers
  `403 host-forbidden`, proving the host check runs first.
- A preflight from an origin outside the list answers `403 origin-forbidden` and carries no
  `Access-Control-Allow-Origin` header.
- A `GET` from an allowed origin with no bearer token still answers `401 unauthenticated`, and it
  carries `Access-Control-Allow-Origin`, so a browser can read the `401` rather than see an opaque
  failure.
- A response that already carries a `Vary` value keeps it, and `Origin` is appended.
- `Access-Control-Allow-Credentials` appears on no response, asserted by construction.
- A `GET /v1/blob/:hash` from an allowed origin carries `Access-Control-Expose-Headers` naming `etag`,
  `accept-ranges` and `content-range`.
