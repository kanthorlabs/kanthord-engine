# EPIC 053.2 — The objective review attestation

Status: **draft**. It follows EPIC 053.1 by sequence order, and it runs before EPIC 054. It consumes EPIC 053.1's `acceptReview`, its three read seams and its `review` report member, EPIC 051.3's `checkpoint` table and its `objective-land-accepted` precedent, EPIC 050.4's unconditional attempt, and EPIC 053's parent-objective aggregation, which this epic's path never calls.

It carries a decimal number because EPIC 054 and every whole number after it are already authored.

**Dispatch prerequisite.** EPIC 053.1 ships before this one. Story 1 inserts `"053.2"` into `scripts/epic-sequence-range.ts:1` — `authoredEpics` after `"053.1"`, and Story 4 appends it to `shippedEpics`, which `test/sequence/conformance.test.ts:254` — `shippedEpics` requires to stay a prefix of `authoredEpics`. Story 4 is therefore last in dispatch order.

**It holds four stories, and two of them draw.** `src/domain/node-pair.ts:43` — `review` legalises `(objective, review)` with the state owner `attestation-then-human`, and two paths carry it: the claim and the accepted attestation. Every refusal of EPIC 053.1 decides this branch at the step it already decides the task branch, so no refusal path moves.

## Goal

An atomic objective delivers a verdict, and a human closes it:

- an `(objective, review)` claim is admitted, and `review-head-unavailable` is raised by no claim path;
- the claim and the report are admitted in one story, so the pair is never half-admitted;
- an accepted review attestation moves an atomic objective from `running` to `awaiting_approval` under its own trigger;
- the attestation writes one `review` checkpoint whose `node_id` is the objective, closes the attempt, ends the run and rolls no parent up;
- the verdict decides no state on the objective branch, exactly as on the task branch;
- `acceptReview` widens by one arm, and no second command joins `src/commands/checkpoint/`.

## Non-goals

- **No close.** `.agents/plan/epics/056.1-the-close-and-the-human-boundary.md:36` owns the human close, and `../docs/workflow/worker.md:371` states an objective reaches a terminal state when a human closes it. This epic moves an atomic objective to `awaiting_approval` and stops there.
- **No parent objective review.** `../docs/workflow/worker.md:92` states an objective that declares an execution deliverable is an atomic objective, and `docs/proposal/phase-2/deliverables-and-pairs.md:19` — `attestation-then-human` fixes the `(objective, review)` shape as `atomic`. A parent objective declares `expansion`, so no parent objective ever holds a review checkpoint, and the graph validator enforces the shape at `docs/proposal/phase-2/deliverables-and-pairs.md:30`.
- **No aggregation.** EPIC 053 owns every parent transition. `awaiting_approval` is not in `src/domain/state.ts:20` — `terminalStates`, so nothing rolls up from this path, and `src/commands/outcome/aggregate-objective.ts` of EPIC 053 takes an objective id this node's parent may not be.
- **No new refusal and no new error code.** The five refusals of EPIC 053.1 and their fixed order at `.agents/plan/epics/053.1-the-review-checkpoint.md:64` — `The refusal order is fixed` decide this branch unchanged. The wire gains nothing, so no story edits `src/http/contract/errors.ts`, `src/cli/exit-code.ts` or `docs/proposal/api/README.md`'s error matrix.
- **No `review-head-unavailable` retirement.** `docs/proposal/api/README.md:110` states "a removal of any kind is still forbidden" inside `/v1`, so the code keeps its `409` row at `docs/proposal/api/README.md:264`, its entry in `node.claim`'s `errors` record, its `ClaimRefusal` member at `src/commands/node/claim-node.ts:39` — `review-head-unavailable` and its branch in `src/http/server/node/refusals.ts:153`. This epic deletes the throw alone, and the code becomes unreachable — which is the ruling `.agents/plan/epics/053.1-the-review-checkpoint.md:38` already took for the task half.
- **No event type and no payload variant.** `src/domain/event-type.ts` gains nothing and `src/http/contract/event-payload.ts` gains nothing. The Decisions state why the transition rides `outcome.reported`.
- **No approval evidence bundle.** `node.approvalEvidence` stays `stubbed`. EPIC 112 owns it.
- **No `attested` member change.** `src/commands/outcome/report-objective.ts:51` — `reportObjective` keeps its path, its trigger and its one event. It serves a parent objective an external harness attests, it closes no attempt and it ends no run, and this epic changes no line of it. It gains one test as a control.

## Decisions

- **`acceptReview` widens by one arm, and its input gains the node kind.** `AcceptReviewInput` gains `nodeKind: "task" | "objective"`, and the one call site — the review arm of `.agents/plan/stories/053.1-the-review-checkpoint/10-the-report-route-carries-a-verdict.md:128` — `accept.review` — passes `node.kind`. The input that story constructs carries `nodeId`, `parentId`, `revision`, `runId`, `runFence`, `attemptId`, `attempts`, `attemptLimit`, `actorId`, `at`, `verdict`, `judgedCheckpointId` and `reason`, and none of them says what kind of node reported. A second command would restate the five refusals, their fixed order and the three reads that decide them, and `.agents/plan/authoring.md` gives a required field and every site that constructs the type to one epic, so the field and the call site land in one story.

- **The state and the trigger are a two-row table in the command, copied from the accepted settle.** `.agents/plan/stories/051.3-the-checkpoint-and-the-land/04-the-accepted-settle.md:212` — `node.kind` holds the identical table for the land — `task` gives `done` under `outcome-accepted`, `objective` gives `awaiting_approval` under `objective-land-accepted` — and this command takes the same shape with its own objective trigger. **The task row is not rewritten**: it keeps `effect.nodeState` and `effect.trigger` from `taskReportEffect`, which `.agents/plan/stories/053.1-the-review-checkpoint/07-the-attestation-with-a-reason.md:265` — `taskReportEffect` requires, so no `"outcome-accepted"` literal enters this command. **The objective row is a literal pair**, `"awaiting_approval"` and `"objective-review-accepted"`, because no domain function can supply it: `.agents/plan/stories/051.3-the-checkpoint-and-the-land/04-the-accepted-settle.md:227` — `objectiveOutcome` states that `objectiveOutcome` takes a `TerminalState` projected from children an atomic objective does not have, and `.agents/plan/epics/053-node-state-ownership.md:52` — `the one new rule` refuses a third expression of the state-owner rule. `taskReportEffect` still supplies `attemptOutcome` and `runEnd` on both arms, because an attempt outcome and a run end are the same on both.

- **One new external trigger, `objective-review-accepted`, and `object-reported` is not reused.** `src/domain/external-transition.ts:4` — `externalTriggerIds` gains it, and `externalTransitions` gains its row with `level: "objective"`, `from: "running"`, `to: "awaiting_approval"` and the precondition `{ runDriver: "external", activeRun: true, leaseFence: "valid", actorKind: "harness", attemptLimit: "under", reportedObjectId: "absent", childAggregation: "not-applicable" }`. Two fields of `src/domain/external-transition.ts:90` — `object-reported` make it unusable here: `childAggregation: "every-task-terminal-one-done"`, and an atomic objective holds no child; and `reportedObjectId: "required"`, while `.agents/plan/epics/053.1-the-review-checkpoint.md:44` states the review member carries no `objectId`. `reportedObjectId` is therefore `absent`, which `src/domain/external-transition.ts:24` — `reportedObjectId` admits. `src/domain/node-trigger.ts:135` — `triggerTransition` resolves a trigger to the first row naming it, so one id carries one level and `outcome-accepted` cannot gain an objective row. `src/domain/transition.ts:152` already admits an objective `running` to `awaiting_approval`, so the legality table does not change, and neither does its note.

- **The consumer registry names the command, and `objective-land-accepted` is the precedent.** `src/domain/external-transition.ts:215` — `externalTriggerConsumer` gains a key for `objective-review-accepted` naming `src/commands/checkpoint/accept-review.ts` alone, and the objective row of the table above is what puts that trigger id in the file as a double-quoted literal, which is what `src/domain/external-transition.test.ts` — `every consumer file holds its own trigger id as a literal` reads. **`"outcome-accepted"` gains no entry for that file, and the omission is deliberate.** `acceptReview` writes that trigger through `effect.trigger` and holds no literal of it, so naming the file under `outcome-accepted` would fail the same case; `.agents/plan/stories/019-outcome-report/12-consumer-on-disk-assertion.md:20` states that no source scan over `src/commands/` exists and forbids adding one, so the map names the files that carry the literal and nothing else. `"object-reported"` is not touched, so its pinned value holds. The three shipped counts that `src/domain/external-transition.test.ts:181`, `:201` and `:520` pin each move by one.

- **The transition rides `outcome.reported`, and no `node.awaitingApproval` event is appended.** `.agents/plan/stories/051.3-the-checkpoint-and-the-land/04-the-accepted-settle.md:231` appends `outcome.reported` with `toState` set to the objective's new state and `run.ended` beside it, for the same atomic-objective transition, and appends no third event. **The payload is what forces it**: `src/http/contract/event-payload.ts:161` — `outcome.reported` requires `attemptId`, `attemptNo` and `attemptsRemaining`, and `src/commands/outcome/report-objective.ts:195` returns `null` for all three, which is why the shipped attestation appends `node.awaitingApproval` instead — it holds no attempt. A review attestation holds one, closes it, and therefore has the payload the type requires. The two events carry `subjectKind` `node` on the objective id and `subjectKind` `run` on the run id, with `actorKind: "harness"` and `actorId` the authenticated principal, exactly as the task arm appends them in the same transaction.

- **`attemptsRemaining` is a number in the payload and `null` in the result, and the two schemas force the split.** `src/http/contract/event-payload.ts:168` — `attemptsRemaining` is `z.number().int()` and admits no null, so the payload carries `Math.max(0, attemptLimit - accounting.counter)` over the list the route already read, which is the value `.agents/plan/stories/051.3-the-checkpoint-and-the-land/04-the-accepted-settle.md:233` computes. `src/http/contract/outcome.ts:62` — `attemptsRemaining` is nullable, and the run ends in this transaction so no further attempt of it can open, which is why the result carries `null`. `.agents/plan/epics/054-attempt-classification-and-the-supervisor.md:93` keeps both types unchanged, so no later epic widens the payload.

- **The run ends, because a worker holds no active run while a human decides.** `../docs/workflow/worker.md:304` states "An accepted report ends the run" and "A worker holds no active run while a human decides", and `:552` states the human then closes the objective against the accepted checkpoint. The objective arm therefore keeps the task arm's `execution.closeAttempt` and `execution.endRun`, and it calls no `execution.stampRunHead`: a review pins no oid, which is the ruling `.agents/plan/epics/053.1-the-review-checkpoint.md:48` took for the task arm.

- **The objective arm reaches neither `objective.aggregate` nor `plan.readAllNodes`, and that is the whole token difference from the task arm.** `awaiting_approval` is not terminal, so `src/commands/outcome/aggregate-initiative.ts:39` would return early on the parent anyway; and EPIC 053's `aggregateObjective` takes an objective id, while an atomic objective's parent may be an initiative, so the call is not merely useless but wrong at the level. `.agents/plan/stories/053.1-the-review-checkpoint/07-the-attestation-with-a-reason.md:70` — `Step 12 is what fills the result` reads `plan.readAllNodes` only to read the parent's post-aggregation state; with no aggregation there is nothing to read, and the node's own new state is the value the result needs.

- **The result names the node's own state, and its projection is `null`.** The objective arm returns `kind: "objective"`, `state` and `objectiveState` both `awaiting_approval`, `objectId: null`, `attemptsRemaining: null` and `objectiveProjection: null`. `src/commands/outcome/report-objective.ts:200` returns an aggregate projection because a parent objective has children to project; an atomic objective has none. The human supplies the outcome instead: `.agents/plan/epics/056.1-the-close-and-the-human-boundary.md:52` gives the atomic close member `checkpointId` and `outcome`, so no projection is derived for this shape and `docs/proposal/phase-2/gates-and-approval.md:74`'s projected-outcome rule stays with the candidate it was written for.

- **Every judged rule of EPIC 053.1 applies unchanged, so this epic draws no refusal path.** `../docs/workflow/worker.md:447` states a review node is atomic, holds no child, and connects a verdict to its subject through `depends_on` — a sentence about a review node of either kind. `plan.readDependencies(transaction, nodeId)` and `execution.newestExecutionCheckpoint(transaction, nodeId)` of `.agents/plan/epics/053.1-the-review-checkpoint.md:60` are keyed by node id, and the byte cap is pure over the request value. The five refusals therefore fire at the same step, in the same order, for both node kinds, and the four refusal diagrams of EPIC 053.1 keep their traces.

- **The checkpoint records the objective and the kind `review`.** `checkpoint.node_id` is the objective's id, `kind` is `review`, `run_id` and `attempt_id` name the objective's own run and its one open attempt, and `fence` is the pre-raise run fence. `.agents/plan/stories/051.3-the-checkpoint-and-the-land/04-the-accepted-settle.md:411` asserts the same `node_id` rule for the atomic objective land. The attempt exists because `.agents/plan/epics/050.4-the-node-lease-removal.md:62` — `openAttempt` makes an admitted run of any kind open exactly one, which the composite `FOREIGN KEY (attempt_id, run_id)` of `.agents/plan/stories/051.3-the-checkpoint-and-the-land/01-migration-14.md:49` — `attempt_id` requires.

- **The claim gate and the report gate fall in one story, because either alone is a half-admitted pair.** `.agents/plan/stories/053.1-the-review-checkpoint/10-the-report-route-carries-a-verdict.md:125` states the two terms go together. A claim admitted alone opens a run whose only exit is expiry, and a report admitted alone reaches the task arm, which writes `to: "done"` under `outcome-accepted` — a trigger whose row is `level: "task"`, so `src/services/plan/sqlite.ts:521` throws on the node kind. Story 2 lands the arm the pair needs before Story 3 admits the pair, so no story boundary leaves a reachable throw.

- **The claim is a second path because three tokens differ, and the difference comes from conditions the shipped command already carries.** Measured against `claim-success-review` of `.agents/plan/stories/053.1-the-review-checkpoint/02-a-review-claim-is-admitted.md:15` — `Seams`: the objective claim reaches `execution.runDriversUnderObjective` with its own id, because `src/commands/node/claim-node.ts:262` gates that read on `node.kind !== "initiative"` and `:560` — `objectiveScopeId` returns the node's own id above a task; it takes one cascade write and one cascade event where the task path takes two, because `src/commands/node/claim-node.ts:599` — the ancestor chain of an objective is its initiative alone; and it reuses one lease record for both result fields until EPIC 050.4 deletes them. No guard is added and none is moved.

- **`review-head-unavailable` loses its last producer, and the throw is deleted whole.** `src/commands/node/claim-node.ts:208` — `runKind` is narrowed by EPIC 053.1 to `runKind === "review" && node.kind !== "task"`, and the surviving term names the pair this epic admits. `(initiative, review)` is illegal at `src/domain/node-pair.ts:29`, so it refuses `pair-illegal` at `src/commands/node/claim-node.ts:164` before the run kind is derived, and no third review pair exists. The refusal order of what remains does not move: deleting a throw removes a code, and it reorders none.
