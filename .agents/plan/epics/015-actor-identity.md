# EPIC 015 — Actor identity and authorization

Status: **draft**.

## Goal

The daemon holds an `actor` table. A `human` registers a `harness` through a bound `POST /v1/actor`, and the response discloses that harness token once. The harness authenticates with that token and reaches `GET /v1/node`, and the resolved actor arrives in the handler. The same token on `GET /v1/provider` is `403 actor-forbidden` before the handler runs, because every operation in `src/http/contract/` declares the actor kinds it admits. A `human` replaces a lost harness token through `POST /v1/actor/:id/rotate`, and the replaced token then answers `401` on every route. The configured bearer token of `docs/proposal/phase-1/transport.md:17` keeps working, and it resolves to the bootstrap `human` actor, so every phase-1 deployment authenticates unchanged. The daemon also derives `http.allowedHosts` from its bind address when the key is omitted, and it refuses to start on a wildcard bind that names no explicit list.

## Non-goals

- No harness write and no harness-caused event. Every operation this epic admits for a `harness` is a read. EPIC 017 is the first epic where a harness writes, and it owns the assertion that every event names the real actor.
- No claim, no lease and no owner kind. EPIC 018 owns them. This epic decides the revocation policy for a lease, and EPIC 018 implements it.
- No per-node write route. EPIC 017 owns it.
- No outcome report. EPIC 019 owns it.
- No run driver column and no transition row. EPIC 014 owns the vocabulary, and it amends `docs/proposal/phase-1/transport.md:19` and `docs/proposal/api/README.md:144-148`.
- **No token delivery.** This epic owns issuance, rotation and the one-time disclosure, and it owns nothing that moves a token to a second machine. Delivery is an operator responsibility: ssh over the internal network, or a password manager. The deployment is an internal network or a VPN, and the daemon terminates no TLS (`013-external-drive-overview.md:169`), so a token that leaves that network without an operator-supplied tunnel travels in cleartext. **No epic of this block proves delivery.** EPIC 020 captures each token through the `--token-file` option of this epic, which is the product path and never a transfer mechanism. Phase 3 proves the deployment environment once.
- **No token expiry, and rotation is no longer post-mvp.** An earlier draft of this file assigned rotation to `docs/proposal/after-the-mvp.md`. **This epic reverses that decision and ships rotation.** An actor name is unique and a revoked row stays listed, so revoke-then-register forces a renamed replacement actor or an unstated name-reuse rule. `docs/proposal/after-the-mvp.md` keeps expiry, a scope and an automated distribution.
- **No harness integration.** A harness plugin is a separate deliverable outside this block, and no story here builds one.
- No permission model finer than the actor kind. A scope, a role and a per-project grant are post-mvp.
- No agent-role binding. `agent.list`, `instructions.resolve` and every `profile.*` route stay `stubbed`.
- No composition-root completeness sweep. EPIC 020 owns it. The five actor handlers are bound in this epic, because an unbound route is a defect of the epic that declared it.

## Decisions

These decisions are contract. A story below implements one of them, and no story reopens one.

- **Token dispatch compares the configured token first.** `resolveActor` compares the presented token against the configured token before it attempts any parse. Only a failed comparison starts actor-token parsing. `src/services/config/convict.ts:161` accepts the configured token as an unrestricted `String`, so a configured token that holds a `.` is legal today. A parse-first rule breaks that deployment.
- **Registration is refused while the configured token is empty.** `src/http/server/auth.ts:39` trusts every caller when the token is empty. A local process must not mint a credential that outlives that mode. `actor.register` answers `400 invalid-request` with `details.refusal = "no-configured-token"`, and it writes nothing. `actor.rotate` answers the same refusal, because it mints the same class of credential. `actor.list`, `actor.show` and `actor.revoke` stay available, so an operator inspects and revokes before the daemon is exposed.
- **An actor id is public by construction, and that disclosure is accepted.** A token carries its own actor id, and `actor.list` returns every id. An unknown id still runs a fixed dummy digest compare, so an unknown id and a wrong secret take the same path. The accepted disclosure is membership, not the secret.
- **Revocation is linearized at authentication.** A revocation affects a request authenticated after it commits. A command does not recheck actor activity inside its transaction. The exposure window is one in-flight request. A per-transaction recheck couples every command to the `actor` table and still cannot stop a commit already in flight, so it buys no guarantee for its cost.
- **Revocation fences the actor's live leases in the same transaction.** Waiting for expiry is wrong, because a revoked harness holds its task out of the pool for the whole lease term. Refusing the revocation with `409 lease-held` is wrong, because it lets a compromised actor block its own revocation. An open execution record is not cancelled and not rewritten: its next report fails authentication. EPIC 018 implements the fence when `lease.owner_kind` exists; until then no actor owns a lease, so the rule has no rows to act on.
- **Registration creates a `harness` and nothing else.** `actor.register` carries `{ name }` and no `kind` field. The table `kind` `CHECK` still admits `human`, because the bootstrap row is `human`. A second human is a post-mvp decision.
- **A registered actor name is `^[a-z0-9][a-z0-9-]{0,62}$`.** One to sixty-three characters, lowercase letters, digits and the hyphen, and the first character is not a hyphen. The bootstrap row is exempt and stores `settings.actor` verbatim, so an existing configured name never fails startup.
- **`actor.list` orders by `id` ascending, compared bytewise.** An actor id embeds a ULID, so the order is registration order. The bootstrap id is `actor_` and twenty-six zero characters, so it sorts first. A revoked row is listed, and the view carries `revokedAt`.
- **All three POST routes declare `idempotency: "memory"` and `replayable: [200]`.** `docs/proposal/api/README.md:122-126` gives every `POST` except `plan.import` the `memory` policy, and `src/http/contract/registry.test.ts:639-644` asserts `[200]` on every `memory` entry. "Disclosed once" means one command execution mints one secret and returns it once. A replay under the same `Idempotency-Key` returns the stored response of that execution, so it returns the same token and mints nothing. A lost response with no key strands nothing: a second `actor.register` with the same name is `400 invalid-request` with `details.refusal = "name-taken"`, and a second `actor.rotate` mints a replacement token and invalidates the undisclosed intermediate one.
- **A lost token is recovered by `actor list` then `actor rotate`, and never by revoke-then-register.** `actor.list` names every actor and its id, and `actor.rotate` replaces the secret of that id. Revocation stays the operation that retires an actor and fences its leases. Revoke-then-register is refused as a recovery path, because `name` is `UNIQUE` and a revoked row stays listed, so the replacement actor carries a second name for one identity.
- **Rotation replaces the secret and preserves the identity.** `actor.rotate` admits a `human` caller only, and it targets a registered `harness` row. The bootstrap actor is refused with `400 invalid-request` and `details.refusal = "bootstrap-actor"`, because its secret lives in configuration and the daemon persists no digest for it. A revoked actor is refused with `400 invalid-request` and `details.refusal = "actor-revoked"`, because a rotation is not an undo. It writes a new `token_sha256` in one transaction, and it preserves `id`, `name`, `kind`, `registered_by`, `created_at`, every event already appended, and every live lease. A lease is not fenced, because the actor is the same actor. The replaced secret authenticates no request that arrives after the commit, which is the linearization rule above applied to a digest change rather than to `revoked_at`.
- **The CLI writes a token to a file, and never to stdout.** `kanthord actor register --name <name> --token-file <path>` and `kanthord actor rotate --id <id> --token-file <path>` both take a required `--token-file`. The CLI creates that file exclusively with mode `0600` **before** it issues the request, so an existing path fails before a secret exists. It prints the actor id and a redacted confirmation. A `--print-token` option is refused: one disclosure path is auditable, and two are not.
- **EPIC 020 inherits the capture path and owes two inventory rows.** `020-wiring-and-scenarios.md:39` decides that the harness token never enters the runner process, and it builds that from a `captureToken` mode inside `scripts/e2e/podman/bin/e2e-request.mjs` plus a `registerActor(role, name)` driver member. **The `--token-file` option of this epic replaces that mode.** `registerActor` runs `cliAs(role, ["actor", "register", "--name", name, "--token-file", path])` and returns `{ actorId, tokenFile }`, so `e2e-request.mjs` gains no capture mode and `assertNoDisclosure` at `scripts/e2e/lib/disclosure.ts:92-104` passes by construction, because the CLI prints no secret. EPIC 020 also adds `actor.rotate` to the authorization inventory of `src/http/contract/authorization.test.ts` with `["human"]`, adds `actor rotate` to the CLI inventory and the reachability rows, and raises its own two block totals: twelve `routed` operations rather than eleven, and sixteen CLI commands rather than fifteen. The sixteen-name harness set at `020-wiring-and-scenarios.md:48` is unchanged, because `actor.rotate` admits `human` only.
- **A wildcard bind with no `http.allowedHosts` refuses startup, and every other bind derives the list.** `http.allowedHosts` keeps `default: null` (`src/services/config/convict.ts:167-171`), and the key is optional. When it is omitted, the daemon derives the list from the bind address and the configured port. When the operator supplies an empty array, the `hostList` validator at `src/services/config/convict.ts:18-27` still answers `config-invalid`, because an empty list admits no client at all. Exact authority matching is unchanged: `src/http/server/host.ts:16-20` compares the whole lower-cased `Host` value, which is the DNS-rebind defence of `docs/proposal/phase-1/transport.md:35`. **A wildcard is not added and the port is not stripped.**
- **The derivation is one pure function with three cases.** A loopback bind derives `127.0.0.1:<port>` and `localhost:<port>`, and an IPv6 loopback bind derives `[::1]:<port>` in addition. A concrete non-wildcard bind derives exactly one entry, `<bind-authority>:<port>`, with an IPv6 literal in brackets. A bind of `0.0.0.0` or `::` derives nothing and refuses startup, because a wildcard bind carries no evidence of the authority a client sends. A configured port of `0` refuses on the same rule, because the listening port is unknown when the allow list is built. The order of a derived list is fixed, so two loads of one configuration produce one list.
- **An operator who uses a DNS alias names that alias.** The daemon reads the `Host` header and never resolves a name, so it cannot infer the alias a client sends. There is therefore no zero-configuration remote mode, and this trade-off is accepted. `013-external-drive-overview.md:170` and `025-external-drive-acceptance-run.md:98` each state that `http.allowedHosts` has no usable default. That statement becomes true for a wildcard bind only, and both epics inherit the corrected behaviour.
- **`kanthord config generate` writes a consistent local configuration.** It binds `127.0.0.1` rather than `0.0.0.0` (`src/cli/config/generate.ts:38-46`), because the file it writes today binds every interface and admits two loopback authorities only. It takes `--bind <address>` once and `--allowed-host <authority>` repeatably. It is not named a VPN mode and it verifies no network: the generator writes a file and reaches nothing.
- **The memory idempotency cache stays process-local and in-memory.** A daemon restart empties it, so a retried `POST` re-executes. That is the guarantee `docs/proposal/api/README.md:134` already documents, and this epic does not change it. Actor scoping narrows the key namespace only.
- **This epic owns the actor-kind widening, and the widening is one change.** EPIC 014 keeps `src/domain/event.ts:6` at two members and assigns the widening here (`014-external-drive-contract.md:13`), and `013-external-drive-overview.md:17` agrees. Five artefacts move in one commit: the domain enum, `ActorKind` at `src/services/event/index.ts:3`, the `actor_kind` `CHECK` of migration 0005, `docs/proposal/database/event.md`, and both `enum=human,daemon` pins at `src/http/contract/field-decisions.fixture.ts:8,16`. A split fails `npm run typecheck` or the field-decision parity assertion, so no partial landing exists.
- **The event migration preserves legacy attribution.** No `event.actor_id` value is rewritten. The two rejected alternatives: a deterministic legacy actor row invents an identity no human registered, and it forces the token-hash `CHECK` open for a row that can never authenticate; a legacy attribution column widens the event row, the event contract and every reader, for a fact `actor_id` already holds.

## Stories

- **Actor vocabulary in `domain/`** — `identityKinds` and `identityPrefixes` gain `actor` with the prefix `actor`, at `src/domain/identity.ts:3-43`. A new `src/domain/actor.ts` holds `registeredActorKinds = ["human", "harness"]`, the actor row schema, the actor name pattern, the bootstrap actor id constant, and the token grammar. `src/domain/event.ts:6` holds the event enum. This epic widens it to `["human", "daemon", "harness"]`, and it renames it from `actorKinds` to `eventActorKinds`. Two exports named `actorKinds` with different members invite a wrong import. The rename has two call sites: `src/http/contract/event.ts:3,15,24`. The token grammar is a pure parser and a pure renderer: a token is `<actorId>.<secret>`, the separator is the first `.`, and `secret` is 43 base64url characters. `domain/` mints nothing, so the secret arrives from a service. The same change edits both `enum=human,daemon` pins at `src/http/contract/field-decisions.fixture.ts:8,16` to `enum=human,daemon,harness`, because `event.list` declares `actorKind` on its query and on its response item. EPIC 014 lands neither pin (`014-external-drive-contract.md:13`).

- **The `secret` service capability** — a new `src/services/secret/index.ts` declares the interface, and `src/services/secret/node-crypto.ts` exports the `NodeCryptoSecret` implementation. The interface holds three methods: `generate(): string` returns 32 bytes from `node:crypto` as 43 base64url characters; `digest(secret: string): Uint8Array` returns the 32-byte SHA-256; `matches(expected: Uint8Array, presented: Uint8Array): boolean` compares with `timingSafeEqual`. `services/crypto` is not extended: it is envelope encryption for a stored provider credential, and `Crypto` at `src/services/crypto/index.ts:20-23` exposes `seal` and `open` only. One capability holds one responsibility. `tokensMatch` at `src/http/server/auth.ts:6-10` is deleted, because `resolveActor` now performs every comparison and a query cannot import `http/server/`. Its constant-time assertion moves from `src/http/server/auth.test.ts` to `src/services/secret/node-crypto.test.ts` unchanged in substance. A fast hash is correct here, because the secret is 256 random bits rather than a password, so no key-derivation dependency enters.

- **Migration 0005, the actor table and the event widening** — one new file `src/services/storage/migration-0005-actor.ts`, registered in `src/services/storage/migrations.ts:7-12`. It creates `actor (id, kind, name, token_sha256, registered_by, created_at, revoked_at, revoked_by)`, `STRICT`. `id TEXT PRIMARY KEY`; `kind TEXT NOT NULL CHECK (kind IN ('human', 'harness'))`; `name TEXT NOT NULL UNIQUE`; `token_sha256 BLOB` with `CHECK (length(token_sha256) = 32)` and `CHECK ((token_sha256 IS NULL) = (id = <bootstrap id>))`; `registered_by TEXT REFERENCES actor(id)` with `CHECK ((registered_by IS NULL) = (id = <bootstrap id>))`; `created_at INTEGER NOT NULL`; `revoked_at INTEGER`; `revoked_by TEXT REFERENCES actor(id)` with `CHECK ((revoked_at IS NULL) = (revoked_by IS NULL))`. It inserts the bootstrap row: id `actor_` followed by twenty-six zero characters, kind `human`, name `bootstrap`, `token_sha256` null, `registered_by` null, `created_at` 0. The bootstrap row stores no hash, because the configured token lives in configuration and the daemon never persists it. The same migration rebuilds `event` (`src/services/storage/migration-0003-execution-and-journal.ts:146-154`): a new table with `actor_kind IN ('human', 'daemon', 'harness')` and `CHECK (actor_kind <> 'harness' OR actor_id LIKE 'actor\_%' ESCAPE '\')`, an `INSERT ... SELECT` that copies every column verbatim, a drop, a rename, and the three indexes of `src/services/storage/migration-0004-event-indexes.ts:6-10` recreated. SQLite cannot alter a `CHECK`, so the rebuild is the only mechanism. No legacy `actor_id` changes, so a phase-1 human name such as `ulrich` survives byte-identically, and a database whose configured name changed over its life keeps both names. The `CHECK` binds `harness` only, and there is no legacy `harness` row, so every copied row passes. `docs/proposal/database/actor.md` is authored with the same DDL in one `sql` fence, and `docs/proposal/database/event.md:10` gains the `harness` member in this same change, so `proposalStatements` compares both.

- **`resolveActor`, the one authentication query** — `src/queries/actor/resolve-actor.ts`, dependencies `{ storage, secret, configuredToken }`, input the presented token, result the actor row or `null`. It imports `domain/` and two service interfaces only, which is what `AGENTS.md` admits for a query. Step one: when `configuredToken` is not empty, compare the whole presented token against it through `secret.matches` over both digests, and resolve the bootstrap row on a match. Step two only runs when step one fails: parse the token, load the row by id, and compare `secret.digest(secret)` against `token_sha256` through `secret.matches`. An unrecognized shape, an unknown id, a revoked row and a wrong secret each return `null`. The unknown-id path runs `secret.matches` against a fixed 32-byte zero digest, so the two failure paths do the same work.

- **The auth path keeps its refusals and gains an actor** — `authMiddleware` in `src/http/server/auth.ts:35-52` takes `{ token, resolveActor }`. It still refuses a missing bearer token with `401 unauthenticated`, and it now refuses an unresolved token with the same code and the same message. It writes the resolved actor to `context.state`, and `HandlerContext` at `src/http/server/app.ts:25-32` gains a required `actor` field, so a handler reads a fact rather than a claim. The empty-token branch at `src/http/server/auth.ts:39` is kept and it resolves to the bootstrap actor, so a loopback daemon with no configured token behaves as it did, and the registration refusal above closes the credential-persistence hole that mode would otherwise open. A database that holds no actor row cannot be served: migration 0005 inserts the bootstrap row, and the migration gate of EPIC 004 refuses to listen against an unapplied migration.

- **The bootstrap actor and the startup order** — a new `src/commands/startup/ensure-bootstrap-actor.ts` writes `settings.actor` into the bootstrap row's `name`. It runs after the migration gate and before `recoverHome` at `src/main.ts:167`, because the transport must never listen against a bootstrap row that names the wrong human. It refuses to start when `settings.actor` names a different actor row, because `name` is unique and a silent collision attributes two identities to one name. The refusal names the conflicting actor id.

- **Authorization as registry data, under one rule** — `Operation` at `src/http/contract/operation.ts:32-47` gains a required `allowedActors: readonly RegisteredActorKind[]`. It is required rather than optional, so a new operation cannot omit the declaration. **The rule: an operation admits `harness` when a harness performs it on its own work — reading the graph it executes, fetching a blob a read returned, claiming a task, or reporting an outcome. An operation admits `human` only when it changes daemon configuration, manages an actor, or takes an approval decision. Every operation admits `human`.** This epic decides the rule and the rows for the operations that exist today. EPICs 017, 018 and 019 each add their own `allowedActors` rows under this rule for the routes they introduce; they do not reopen the rule and they do not invent a policy at build time. Each of the three also adds its own ids to the named assertion this epic writes, so the assertion grows and never breaks. Under the rule exactly nine existing operations admit `harness`: `system.health`, `project.list`, `project.show`, `project.status`, `node.list`, `node.show`, `edge.list`, `plan.export`, `blob.show`. `blob.show` is included because `node.show` returns the instruction and acceptance blob hashes, and a harness that cannot dereference them cannot read its own work. `system.health` is included because it returns a liveness verdict and a dependency list only (`src/http/contract/system.ts:18-26`), which a harness polls before it works. `system.status` is excluded: it returns `bind`, the repository divergence set and every live lease (`src/http/contract/system.ts:38-73`), which is operator detail. `event.list` is excluded: it has no per-actor restriction, so it discloses every human decision to a harness. **A harness operates inside a project a human provisioned, and that is the boundary the human-only rows draw.** Project and repository lifecycle, and whole-document plan submission and validation, are control-plane operations reserved to a human, so `project.create`, every `repository.*` row, `plan.import` and `plan.validate` declare `["human"]`. A harness changes the graph through the per-node operations of EPIC 017 instead. `plan.revisions` declares `["human"]` for the disclosure reason rather than the boundary: `planRevisionEntry` at `src/http/contract/graph.ts:39-46` carries `submittedBlob` and `choicesBlob`, and `blob.show` dereferences both, so admitting it would hand a harness every superseded submission and every human import choice, which is the disclosure the `event.list` exclusion refuses. A harness that needs the project revision reads it from `plan.export`, per `017-per-node-graph-write.md`. Every other operation of the 59 rows declares `["human"]`, the 27 `stubbed` rows included. A new `src/http/server/authorize.ts` runs after `routeMiddleware` and before the body parser in `src/http/server/app.ts:78-88`, so a refusal precedes any parse and any idempotency reservation. A stubbed route therefore answers `403` to a disallowed actor and `501` otherwise, and it still writes nothing.

- **`403 actor-forbidden`** — no code in the table at `docs/proposal/api/README.md:169-193` fits. `401 unauthenticated` is wrong, because the caller authenticated. `origin-forbidden` and `host-forbidden` are browser defences. A later epic that adds a code edits the ordered list in its own stated position, so no sibling epic copies a scalar. **EPIC 014 must not add this code.** 014 amends vocabulary, and an error code added there would be an amendment with no mechanism behind it, which is a defect this story names instead of inheriting.

- **The actor routes** — a new `docs/proposal/api/actor.md` gains the five rows, and `docs/proposal/api/README.md:27-39` gains its line in the domain table. `test/helpers/proposal.ts:54-58` reads every `.md` of that directory except two, so the new file enters parity with no helper change. The rows are `actor.register` `POST /v1/actor`, `actor.list` `GET /v1/actor`, `actor.show` `GET /v1/actor/:id`, `actor.revoke` `POST /v1/actor/:id/revoke` and `actor.rotate` `POST /v1/actor/:id/rotate`, each `phase-1`, `routed`. All five declare `allowedActors: ["human"]`: a harness never manages an actor, and a harness never rotates its own token. The three `POST` rows declare `idempotency: "memory"`, `replayable: [200]` and the default success status 200. `src/http/contract/actor.ts` holds the schemas: the `actor.register` request is `{ name }` and carries no `kind`; the `actor.register` response and the `actor.rotate` response each carry `token` once; the `actor.rotate` request body is empty, because the id is the only input; `actor.list` and `actor.show` return the view with no token field, which is the rule `provider` already follows at `.agents/plan/epics/003-storage.md:22`. `registry.ts:24-37` gains the module.

- **The actor commands and handlers** — `src/commands/actor/register-actor.ts` mints the id and the secret through `ids` and `secret`, stores `secret.digest(...)`, sets `registered_by` to the calling actor, and appends the `actor.registered` event in the same transaction with the payload `{ actorId, kind, name, registeredBy }`. The payload holds neither the secret nor its digest. `src/commands/actor/revoke-actor.ts` stamps `revoked_at` and `revoked_by`, fences every live lease the actor owns, and appends the `actor.revoked` event in the same transaction with the payload `{ actorId, kind, name, revokedBy, revokedAt, leasesFenced }`. A revocation without an event loses who performed it, so the append is not optional. A second revoke of the same actor returns the same view with `200`, so a retry is not an error. A revoke of the bootstrap actor is `400 invalid-request` with `details.refusal = "bootstrap-actor"`, a duplicate name is `400 invalid-request` with `details.refusal = "name-taken"`, and a registration under an empty configured token is `400 invalid-request` with `details.refusal = "no-configured-token"`, which follows `src/http/server/credential/refusals.ts:14-18`. `src/commands/actor/rotate-actor-token.ts` mints one new secret through `secret`, writes `secret.digest(...)` over the existing `token_sha256`, and appends the `actor.tokenRotated` event in the same transaction with the payload `{ actorId, kind, name, rotatedBy, rotatedAt }`. The payload holds neither the token nor the digest, which is the rule `actor.registered` already follows. It writes no other column, so the id, the name, the audit history and every live lease survive. A rotation of the bootstrap actor is `400 invalid-request` with `details.refusal = "bootstrap-actor"`, and a rotation of a revoked actor is `400 invalid-request` with `details.refusal = "actor-revoked"`. `src/queries/actor/list-actor.ts` and `src/queries/actor/show-actor.ts` serve the two reads.

- **Event attribution through the authenticated actor** — `src/services/event/index.ts:3` reads `export type ActorKind = "human" | "daemon"` and gains `harness`, so a harness event is representable at the service interface and not only in `domain/` and the database. A handler stops taking `actor: string` from configuration and reads the resolved actor from its handler context. `src/main.ts:234-335` drops every `actor: settings.actor` binding, and `settings.actor` keeps exactly one job: the bootstrap row's name. The eight `{ actor: "daemon" }` bindings at `src/main.ts:179-194` are unchanged. `event.actor_id` then holds an actor id for a `human` decision taken after this epic, the legacy configured name for a row written before it, and `daemon` for a daemon row. EPIC 017 owns the assertion that a harness-caused event names its actor, because this epic admits no harness write.
