# EPIC 054.2 — The execution accept pays its attempt

## Goal

Every daemon rejection of the execution gate charges a semantic attempt, and a contended land charges none:

- each of the five gate refusals settles a `daemon-rejected` termination in one transaction of its own;
- a contended land settles a `contended` termination inside the journal transaction it already owns;
- the accepted land closes its attempt through the same command, so the close has one caller and every close appends one event;
- a rejection is a returned disposition at the accept boundary, so the settlement commits before the refusal is raised;
- the order is settle, discard, refuse, and no discard precedes the write it depends on;
- the execution arm opens one transaction on a rejection and two on an acceptance, and never three.

## Non-goals

- **No new refusal code, and no changed verdict.** The five refusals of EPIC 051.4 keep their codes, their order and their contract mapping. `src/http/server/node/refusals.ts` maps the same error class, because `reportOutcome` still raises it.
- **No report member, and no structural or review arm.** EPIC 054.3 owns the worker's own failure member and the two other accept arms.
- **No change to the report route.** `report-checkpoint-reap` of EPIC 051.6 Story 3 (`03-the-report-reaps-on-every-settled-terminal`) stays as drawn, and so does `report-execution-checkpoint` of EPIC 051.4 Story 7 (`07-the-gate-accepts-and-writes-the-checkpoint`): the accepted close is inside `land.settle:accepted`, which both hold as one token. **The accepted settle itself does change**, per the Decisions.
- **`report-refusal-contended` does not move.** `.agents/plan/epics/051.4-the-acceptance-gate-and-the-report-route.md:83` — `report-refusal-contended` draws the land steps as nested units, so the settlement this epic adds is inside `land.settle:contended` and changes no token of that diagram.
- **No journal row for the discard.** The audit below establishes the six conditions of `AGENTS.md` `### Rules the import matrix cannot express` for every discard this epic sequences.

## Decisions

- **A rejection settles in a transaction its own arm already owns, and no command opens a new one beyond the ceiling.** Three constraints close this: a daemon rejection is `semantic` and must be recorded — `docs/workflow/worker.md:467` — `A daemon rejection`; `reportOutcome` opens one transaction that commits before the git-bearing accept runs — `.agents/plan/epics/051.4-the-acceptance-gate-and-the-report-route.md:40` — `reportOutcome`; and `acceptExecution` opens exactly two on an acceptance and may not open a third — `.agents/plan/epics/051.4-the-acceptance-gate-and-the-report-route.md:36` — `acceptExecution`. `AGENTS.md` also names the two-unjournaled-transactions shape a defect it intends to repair, so a second `reportOutcome` transaction is refused. **The rejection arm reaches no transaction today**, so it opens exactly one, and the acceptance arm is unchanged at two.

- **A rejection is a returned disposition at the accept boundary, never a throw, and this covers all six refusals.** A throw inside `storage.transact` rolls the settlement back with it. `.agents/plan/epics/051.6-the-post-expiry-reap-on-the-run-operations.md:64` — `disposition` already records that a returned disposition and a thrown refusal are both legal shapes here. `acceptExecution` therefore returns the rejection, and `reportOutcome` raises the refusal after the settlement has committed. The error class the handler maps is unchanged: `src/http/server/node/refusals.ts:67` — `reportOutcomeRefusal` maps a `ReportOutcomeError`, and `reportOutcome` still raises one.

- **The `contended` arm returns the same shape, and `AcceptExecutionError` is deleted.** Its transaction has already committed when it refuses, so it is not the rollback case the rule above exists for — but a command that answers a refusal two ways is one every caller and every reader must know twice. **One command, one refusal protocol.** `test/helpers/sequence-conformance.ts:310` — `value.ok === false` derives `refuse:contended` from the returned shape exactly as it derives it from a thrown one, so `report-refusal-contended` of EPIC 051.4 Story 6 (`06-the-gate-refuses-a-contended-land`) keeps its nine steps and its terminal, and no diagram of this epic or of EPIC 051.4 moves. With no throwing site left, `AcceptExecutionError` has no producer and no consumer, and the `try`/`catch` of `.agents/plan/stories/051.6-the-post-expiry-reap-on-the-run-operations/03-the-report-reaps-on-every-settled-terminal.md:173` — `settled` collapses to a straight-line disposition test. **An untyped throw still reaches no reap**, because it propagates out of `reportOutcome` instead of being captured, which is what condition 6 of the six-condition rule requires. The amendments below carry the asks this creates.

- **The order is settle, discard, refuse, and it is stated here rather than left to the implementer.** `docs/workflow/worker.md:423` — `deletes the ref` requires the discard on a rejection, and a discard before the termination write would break condition 6 of the six-condition rule. Every refusal that holds a candidate ref therefore keeps `candidate.discard` as its last step, after the settlement transaction commits.

- **`candidate.discard` is renumbered and not moved.** `.agents/plan/authoring.md:289` — `renumbered` states that inserting a step renumbers every later ordinal and moves nothing, so the discard token stays context on the four diagrams that already hold it, and no story declares it.

- **The unreachable-candidate refusal reaches no discard, and it still settles.** `.agents/plan/epics/051.4-the-acceptance-gate-and-the-report-route.md:28` — `candidate.discard` states the missing-ref path performs none, because the ref never existed. The attempt is still paid, because the rejection is the daemon's own verdict on the report.

- **A contended land is `infrastructure`, and it settles inside the journal transaction.** `land.settle:contended` of EPIC 051.3 Story 5 (`05-the-contended-settle`) already owns a transaction that records the contended outcome, and the termination joins it. The land is a journaled write, so its two transactions are legal by `AGENTS.md`, and this epic adds none.

- **The six conditions hold for every discard this epic sequences.** Condition 1: the settlement transaction commits before the deletion runs, so no database mutation and no event ride with it. Condition 2: correctness does not need the deletion immediate. Condition 3: the candidate ref is attempt-scoped, and a closed attempt never reopens, so eligibility is the committed close. Condition 4: a failure leaves an inert ref. Condition 5: `candidate.sweep` **deletes** every ref of that namespace whose run is not `active`, at startup — `.agents/plan/epics/051.1-the-candidate-and-the-git-primitives.md:16` — `candidate.sweep`, and the deletion is the `candidate.discard` call of `.agents/plan/stories/051.1-the-candidate-and-the-git-primitives/08-the-candidate-namespace-is-enumerated.md:140` — `candidate.discard`, not the finding beside it. **The sweep's eligibility is a run that is not `active`, which is narrower than condition 3's**, so a remnant this epic leaves is swept after the run ends rather than at the next start; the run always ends, by the expiry pass or by a release, so the retry is guaranteed and only its timing is later. Condition 6: the order above settles the outcome first.

- **The accepted land closes through `end-attempt`, and it carries no termination.** `.agents/plan/epics/053-node-state-ownership.md:98` — `land-settle-aggregate` is the live diagram of the accepted settle, and its `execution.closeAttempt:A` step becomes `attempt.end:A`. **The token carries a key, because `endAttempt:A` is not one**: `test/helpers/sequence-conformance.ts:259` — `callMatch` requires `<key>.<method>`, and `test/helpers/sequence-conformance.ts:113` — `typeof capability !== "object"` records nothing for a function-valued dependency, so the command is injected as an object-valued `attempt` key with the method `end`, after `objective.aggregate`. Story 1 (`01-the-unreachable-candidate-pays-its-attempt`) owns its projection. The accepted member of the input carries `headOid` and no evidence, so the row keeps a null `termination` and the event records the acceptance. EPIC 054 rules why an acceptance appends the event: a vocabulary whose `attempt.ended` excluded the commonest ending would make the type filter of `src/http/contract/event.ts:14` — `type` unusable. **This epic reverses no rule of EPIC 053**: the aggregation step and its order are untouched, and only the close token moves.

- **A gate refusal writes no node state and ends no run, and only the expiry recovers the node.** `endAttempt` closes the attempt and appends the event and does nothing else — `.agents/plan/epics/054.1-the-end-attempt-command.md:15` — `endAttempt` names its whole effect — and `src/commands/outcome/report-outcome.ts:247` — `taskReportEffect` is the only chooser of `ready` or `blocked`, on a worker-report body that a refused `accepted` body never reaches. **A refused report therefore leaves the run `active`, the node `running` and no open attempt**, and the worker can do nothing further with that run. It cannot report again — `src/commands/outcome/report-outcome.ts:222` — `no open attempt` refuses it — and **it cannot release either**: `src/commands/node/release-node.ts:16` — `no-open-attempt` refuses a release of a run that holds none. **The one path that recovers the node is the expiry pass**, which touches no attempt at all — `src/commands/run/expire-runs.ts:30` — `expireDueRuns` ends the due runs and appends `run.expired`, and nothing in it reads the attempt table — so a closed attempt does not obstruct it and the node becomes claimable at the run's deadline. **Adding a node transition to the refusal was rejected**: it would put `plan.setNodeState` and `execution.endRun` on all five refusal diagrams, which the two-step claim below forbids, and it would give the daemon a second writer of a terminal the report path does not own. **Whether a worker should be able to hand back a run it can no longer report on is a product question this epic does not settle**, and the story tree records it as an open ruling rather than inventing a write.

- **Every superseded diagram keeps its fixture.** The gate's git-dependent checks run outside every transaction, exactly as they do today, so no fixture of EPIC 051.4 changes and each new diagram is the old one plus two steps.
