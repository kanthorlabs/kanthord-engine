## Goal

A candidate ref of a run that a run operation **expires** is deleted by that same operation:

- `renew`, `release` and `report` each call `candidate.reap` once, after their own last transaction commits and after the git write of that terminal completes;
- the call is unconditional, so no operation branches on the list length;
- a report that refuses inside `accept.execution` with a typed refusal reaps before it raises, because its prelude already committed the expiry;
- an operation whose expiry rolls back, and an operation whose journaled outcome is left unsettled, reap nothing;
- the run the caller presents is never in the reaped set, on any of the three;
- the **expiry** residue EPIC 051.1 and EPIC 051.5 state narrows to one case — a run that expires while no claim, renew, release or report arrives. The residue of a run an operation **ends deliberately** does not narrow, and the next Non-goal names its owner.

## Non-goals

- **No reap of a run this operation itself ends.** A task release ends the presented run, and `releaseObjective` and `closeObjective` end every active child run inside their own transaction. None of those runs is in the list `expiry.expireRuns` returned, so none is reaped here, and each leaves a candidate ref until startup. `.agents/plan/epics/051.1-the-candidate-and-the-git-primitives.md:36` — `refs/kanthord/candidate/` states that a run that ends without a report leaves its ref behind and gives `candidate.sweep` that whole class. Widening the reaped set to "every run this transaction ended" is a different rule with a different eligibility proof, and this epic does not take it.
- **No reap on `renew-refusal-lifetime-exceeded`.** `.agents/plan/epics/050.2-the-run-renew-release-and-report.md:36` — `expiry.expireRuns` states that a command that expires a run and then refuses rolls the expiry back with everything else. `.agents/plan/stories/050.2-the-run-renew-release-and-report/04-the-lifetime-refusal.md:11` — `renew-refusal-lifetime-exceeded` raises inside the command's one `storage.transact`, so it commits no expiry and there is nothing to reap. That diagram does not move, and this is a stated non-path rather than a path with a zero count. Gate row 4 asserts it.
- **No reap on the prelude refusals of the other two.** The same rule covers every refusal `assertRunAuthority` raises on `release` and on `report`: each is thrown inside the one transaction the command opens, so the expiry rolls back with it. Gate row 13 asserts the `report` case, which is the one whose transaction is followed by more work.
- **No reap after an unsettled journaled outcome.** An untyped throw out of `accept.execution` may leave a `land` journal row `open`, and `AGENTS.md:106` — `six conditions` requires the caller to settle its logical outcome before it attempts a deletion. Such a throw therefore propagates with no reap, and startup reconciles the row and sweeps the ref. Gate row 12 carries it as the control of the typed-refusal case.
- **No reap on the objective attestation.** `.agents/plan/stories/050.4-the-node-lease-removal/07-the-objective-attestation-drops-the-lease.md:7` — `attest-lease-free` draws no `expiry.expireRuns` step, because `reportObjective` receives the transaction its caller opened and runs no expiry pass of its own. The objective arm of `node.report` reaps through `reportOutcome`, which is where the expiry pass is; `attest-lease-free` and `baseline-report-objective` are unchanged by this epic.
- **No second reap command.** `src/commands/checkpoint/reap-run-candidates.ts` of EPIC 051.5 Story 3 is the one implementation, and this epic adds no file under `src/commands/`. `execution.runBaseHomes` and `candidateRunPrefix` are read inside it and are not reached from these three commands, so neither moves.
- **No change to EPIC 051.5's interior diagrams.** `reap-candidates-no-expired-run`, `reap-candidates-no-ref` and `reap-candidates-one-ref` describe `reapRunCandidates`, whose signature and seam trace this epic does not touch. An empty list from any of the three callers reaches the first of them unchanged.
- **No reap inside `acceptExecution`.** `candidate.discard` of EPIC 051.4 deletes the reported run's own ref on the acceptance, rejection and contention paths. This epic adds a call in `reportOutcome`, one level above, and changes none of EPIC 051.4's seven diagrams.
- **No periodic driver.** The daemon still holds none. `candidate.sweep` at startup stays the last resort.
- **No attempt termination.** `attempt.termination` and the class an expiry charges are EPIC 054. This epic writes no attempt row.

## Decisions

- **A typed refusal from `accept.execution` arms the reap; a prelude refusal and an untyped throw do not. One reap statement serves both arms, and the `catch` only captures.** `.agents/plan/stories/051.4-the-acceptance-gate-and-the-report-route/08-the-report-route-enforces-the-gate.md:103` — `before step 9` puts the expiry pass of `src/commands/outcome/report-outcome.ts:107` — `transact` on the committed side of every terminal that reaches `accept.execution`. `.agents/plan/stories/051.2-the-command-gate/index.md:98` — `finally` rules in this repository that a `finally` discards the exception it wrapped, so a reap that rejects inside one would replace the refusal the worker must see with a cleanup fault. The shape is therefore a capture, one reap, then the raise or the return:

  ```ts
  const decided =
    dependencies.storage.transact(
      /* the prelude and every in-transaction arm */
    );
  let settled:
    | Readonly<{ kind: "ok"; result: ReportOutcomeResult }>
    | Readonly<{ kind: "refused"; error: AcceptExecutionError }>;
  try {
    settled = {
      kind: "ok",
      result:
        decided.kind === "accept"
          ? await dependencies.accept.execution(decided.input)
          : decided.result,
    };
  } catch (error) {
    if (!(error instanceof AcceptExecutionError)) throw error;
    settled = { kind: "refused", error };
  }
  await dependencies.candidate.reap(decided.expired);
  if (settled.kind === "refused") throw settled.error;
  return settled.result;
  ```

  **One statement is the point, and it is what makes three properties structural instead of asserted twice**: the argument is the same `decided.expired` on both arms, the call happens exactly once, and it starts only after `accept.execution` settles. A second reap site inside the `catch` would make each of the three a per-arm claim, and gate row 15 would have to prove the ordering twice. A prelude refusal throws before `decided` exists, so it reaches no reap at all, and an untyped throw leaves through the `throw error` of the `catch`, which is what the Non-goal on an unsettled journaled outcome requires. The drawn path still reaches `candidate.reap` once, which is what `.agents/plan/authoring.md:178` — `No two steps of one diagram` requires.

  **The shape now matches the claim, and one line still differs.** `.agents/plan/stories/051-the-workspace-branch/07-the-loser-of-two-first-claims-refuses.md:55` — `ClaimNodeError` states that `claimSettle` raises nothing and `claimNode` throws `objective-busy` from a returned value, so EPIC 051.5 reads a `disposition` field where this command reads a caught error. Both then reap once and raise. That difference is real and it is not erased: `claimSettle` reports a disposition, and `acceptExecution` refuses, so `.agents/plan/stories/051.2-the-command-gate/index.md:100` — `throws a typed error carrying` requires it to throw. The local union above is a variable inside `report-outcome.ts` and never a command's result, so that rule holds. `src/commands/outcome/report-outcome.ts:107` — `transact` already holds EPIC 051.4 Story 8's `decided` in the same idiom, so this adds no new pattern to the file.

- **`candidate.reap` is total, and that contract — not a caller's catch — is what protects every terminal.** `.agents/plan/epics/051.5-the-targeted-post-expiry-candidate-cleanup.md:59` — `findings` makes `reapRunCandidates` return four finding buckets and throw in none of them. This epic chooses that one policy for all three commands: no caller wraps the reap in a rejection handler, no test injects a throwing reap, and a reap that throws is a defect in `reapRunCandidates` proven by EPIC 051.5's own case set. The reap statement sits **outside** the `try` of the decision above, so a reap that rejects on the refusing arm would mask the refusal exactly as a `finally` would — and that is the reason the contract is total rather than the reason a caller should catch. The alternative — every caller tolerating a rejection — needs an explicit suppression at four sites and buys nothing the contract does not already give.

- **The refusing arm of `report` is not a diagram, because its seam set and its seam order do not differ.** `.agents/plan/authoring.md:152` — `Draw a path only when its seam set or its seam order differs from a path already drawn` is the rule. `test/helpers/sequence-conformance.ts:132` — `tokens.push` pushes the token before `Reflect.apply`, so a call that throws is recorded; `accept.execution` is one step whether it returns or throws, and the refusing arm's trace is steps 1 to 9 of `report-checkpoint-gate` followed by `candidate.reap` at the same ordinal as the accepting arm. Only the terminal differs. `.agents/plan/authoring.md:200` — `A refusal path is its own diagram` fixes the id of a refusal that **is** drawn; it does not compel drawing one whose set and order match, and `.agents/plan/authoring.md:327` — `It does not prove the behaviour a guard adds` names the case as the instrument. **EPIC 051.5 reaches the same conclusion on the claim, and it is the sibling precedent rather than the counter-example.** Its Story 9 draws no diagram for the contended cut, because the reap sits before the raise and that arm reaches the same steps in the same order — the ruling `.agents/plan/stories/051-the-workspace-branch/06-the-first-execution-claim.md:22` — `same eighteen steps in the same order` first made for the undrawn refusing arm of the composed claim. Gate row 12 carries this epic's arm the same way.

- **No diagram proves that the reap starts after the git write completes, so a case does.** `.agents/plan/authoring.md:27` — `An asynchronous seam needs begin and end records` says an asynchronous seam drawn as one step records invocation only. `accept.execution` and `candidate.reap` are both asynchronous, so `await accept.execution(…)` followed by the reap and a **missing** `await` produce the identical token list, and `report-checkpoint-reap` cannot tell them apart. The epic does not introduce begin and end records for one call: it states the limit and proves the ordering behaviourally. Gate row 15 resolves `accept.execution` from a deferred promise and asserts no `candidate.reap` call is recorded until that promise settles, and it asserts the same for the `storage.transact` span on `renew` and `release`.

- **`renew` and `release` need no `try`, because no refusal is raised after their transaction.** Each is one `storage.transact` at `src/commands/node/heartbeat-node.ts:64` — `storage.transact` and `src/commands/node/release-node.ts:62` — `storage.transact`, and every refusal of each is thrown inside the callback. The reap is therefore a plain statement after the transaction returns. The difference from `report` is stated rather than harmonised: a `finally` here would mask a **success** exactly as it masks a refusal there, and the totality of `reapRunCandidates` is what makes the plain statement safe.

- **The run the caller presents is never in the reaped set.** On all three commands the expiry pass runs at step 3 and `execution.runById` reads the presented run at step 4 or 5, so a run the pass just ended reaches `assertRunAuthority` already `ended` and refuses `run-ended` inside the transaction — which rolls the expiry back and reaps nothing. This proves the deletion is targeted and it carries condition 3 of the six; it is **not** what carries condition 6, which the arming rule above carries. Gate rows 5, 8 and 17 assert it, one per command.

- **The other five conditions hold on all three sites, unchanged from EPIC 051.5.** `AGENTS.md:106` — `six conditions` fixes the check per deletion, so this epic re-checks rather than inheriting the verdict. The deletion carries no database mutation and no event; correctness does not depend on its immediacy; eligibility is the committed `state = 'ended'` the expiry pass wrote, read back through `run_base`; a failure leaves a ref, which is retryable and never corrupt; and `candidate.sweep` at startup is guaranteed to retry it.

- **Each of the three commands tightens its own `Expiry`, and EPIC 051.5's tightening does not reach them.** `.agents/plan/stories/051.2-the-command-gate/index.md:102` — `Expiry` rules that a nested unit narrows the service interface it needs and does not export the narrowing, and `eslint.config.js:221` — `command` forbids a command importing another command, so `src/commands/node/claim-node.ts:75` — `Expiry` is the claim's own type and EPIC 051.5 Story 1 tightens that one declaration. `src/domain/run.ts` cannot own the signature, because it names `Transaction` and `AGENTS.md` keeps `domain/` pure; a service interface must not own it either, because `expireRuns` is a command and declaring it there classifies an injected command as a service capability. EPIC 050.2 gives `renew`, `release` and `report` an `expiry` key each, and each copies the shipped `readonly unknown[]` at `src/commands/node/claim-node.ts:79` — `readonly unknown[]`. A command cannot read `runId` off `unknown`, so each of the three declares `expireRuns(...): readonly ExpiredRun[]` over the `src/domain/run.ts` type, in the story that adds its reap. Three tightenings, one per command, and `src/main.ts:84` — `Expiry` keeps passing one object to all four.

- **`candidate` is a locally declared seam key on each of the three, in the shape the claim uses.** The same narrowing rule applies: `reapRunCandidates` is a command, so no command imports it. Each of the three declares

  ```ts
  candidate: Readonly<{ reap(runs: readonly ExpiredRun[]): Promise<unknown> }>;
  ```

  and `src/main.ts` binds the one callable EPIC 051.5 already constructs for the claim. The return is `unknown` because every caller discards it: `.agents/plan/epics/051.5-the-targeted-post-expiry-candidate-cleanup.md:59` — `findings` states the value exists so each bucket is asserted by value in `reapRunCandidates`' own test, not by a caller.

- **The call is unconditional, so the empty list is a value and not a branch.** `.agents/plan/epics/051.5-the-targeted-post-expiry-candidate-cleanup.md:61` — `reap-candidates-no-expired-run` makes `reapRunCandidates` return before `storage.transact` on an empty list, which is where the zero-work decision belongs. A caller that guarded the call on `expired.length > 0` would duplicate that decision and give the conformance runner two traces for one path. Gate rows 10 and 17 assert the empty-list call by value.

- **`renewRun` and `releaseNode` become `async`; `reportOutcome` already is.** `.agents/plan/epics/051.1-the-candidate-and-the-git-primitives.md:95` — `git.listRefs` returns `Promise<string[]>`, so `reapRunCandidates` is asynchronous and a caller after its own transaction must await it. `src/commands/node/heartbeat-node.ts:63` — `HeartbeatNodeResult` and `src/commands/node/release-node.ts:61` — `ReleaseNodeResult` become `Promise<…>`. `src/http/server/node/heartbeat-node.ts:15` — `async` and `src/http/server/node/release-node.ts:15` — `async` are already asynchronous handlers and gain one `await` each. `cli/` reaches the daemon over HTTP and does not change. EPIC 051.4 Story 8 already made `reportOutcome` return a promise.

- **The transaction callback returns the expired-run list beside its result, and that is not a seam change.** `expiry.expireRuns` already returns the list at `src/commands/node/claim-node.ts:147` — `expireRuns`, and every shipped caller discards it. Binding the value changes no call, no argument and no order, so each ship diagram declares `+candidate.reap` and nothing else. On `renew` and `release` the callback returns `{ result, expired }`. On `report` it returns EPIC 051.4 Story 8's discriminated value with `expired` added to both arms, so `src/commands/outcome/report-outcome.ts:122` — `objective` and every task arm carry it identically.

- **The reap appends no event.** `run.expired` already records each ending inside the expiry transaction. A ref deletion is not domain state, and an event appended after the transaction commits would sit in a second transaction with no journal row. Gate row 14 asserts the event count on the arms that reap.

- **The per-diagram supersession this epic's three-story swap needs is EPIC 051.5's, and this epic adds no harness story.** Under the shipped harness, `test/sequence/conformance.test.ts:85` — `has` treats a diagram as due when its epic is in `shippedEpics` and no **shipped** epic supersedes it, `test/sequence/conformance.test.ts:126` — `scenario files` requires exactly one scenario file per due diagram, and `test/sequence/conformance.test.ts:270` — `every due scenario conforms` replays each against the real command — so no ordering of three superseding stories is green at every boundary. `.agents/plan/epics/051.5-the-targeted-post-expiry-candidate-cleanup.md:69` — `Supersession and dueness` rules both facts per diagram and keys them on the superseding scenario file, and EPIC 051.5 Story 10 (`10-the-conformance-harness-admits-an-incremental-supersession`) ships it. Each of this epic's three stories therefore swaps one scenario and stays green: while `renew-reap.ts` exists and `"051.6"` is authored, `renew-lease-free` is superseded and needs no scenario, while `release-lease-free` is still due and keeps its own.
