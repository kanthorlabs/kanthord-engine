# EPIC 050.3 — The plan-write guard

Status: **draft**. It follows EPIC 050.2 by sequence order, and it runs before EPIC 050.4. It consumes EPIC 050's run row and its `subtree-busy` refusal.

It carries a decimal number because EPIC 051 through EPIC 057 are authored and numbered, and renumbering them to insert a whole-number epic would break every cross-reference between them.

## Goal

A human editing the plan cannot write under a worker's feet:

- a plan write refuses while an active run covers the affected graph, and the affected graph is stated per command;
- the guarded set is the seed the command names, plus every ancestor of it, plus every descendant where the mutation reaches one;
- the refusal is `subtree-busy`, the same code and the same details a claim raises for the same condition;
- the two lease-derived reads on a plan write stop being read, so EPIC 050.4 can delete the mechanism without dropping a guard.

**This epic changes no run command.** The claim, the renew, the release and the report keep every lease call EPIC 050 and EPIC 050.2 left them.

## Non-goals

- **No lease removal.** EPIC 050.4 deletes `src/domain/lease-hierarchy.ts`, narrows the `Lease` interface to the repository subject, and lands migration `13`. This epic leaves every row, every column and every call site of the lease intact.
- **No run-command change.** `claim-node.ts`, `renew-run.ts`, `release-node.ts` and `report-outcome.ts` are untouched. `lease-held` stays on all four operations, because all four still take a lease.
- **No new error code.** `subtree-busy` is registered by EPIC 050 as a 409 precondition with the details `{ relation, nodeId, runId, expiresAt }`. This epic adds it to five error unions and defines nothing.
- **No wire generation, and one additive contract change.** No request field, response field, event type, operation id or capability name changes. Five operations do gain a declared error, `subtree-busy`, so the generated OpenAPI documents change. That change is **adding a member to an enum**, which `docs/proposal/api/README.md:96` permits inside `/v1`, and the same document requires a client to tolerate an unknown enum member. The code, its status and its details schema are EPIC 050's and are unchanged, so nothing here changes what an error code means or the status it maps to, which is what the closed list forbids at `:105`. `KANTHORD_VERSION` therefore moves by patch, and no capability is retired.

  This epic is **not** invisible to a document reader; it is invisible to a client that already handles `subtree-busy`. The policy amendment EPIC 050.2 wrote — a change outside the closed list needs a human ruling and a capability retirement — is not reached, because this change is inside the list.

- **No `binding-in-use` change.** The shipped blocker list of `update-node` and `delete-node` keeps its shape, its code and its details. This epic removes one member of one list and adds no other.

## What the shipped guard actually is

The epic that preceded this one claimed five commands refuse a plan write on a leased node. The source says otherwise, and the correction is the reason this epic is scoped the way it is. `leaseHeld` at `src/services/plan/sqlite.ts:558` is **private**, and it reaches a command through exactly two products:

| product                                                                  | consumer                                                                                                             | effect                                              |
| ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| `ContainmentFacts.lease` (`sqlite.ts:276` and `:306`)                    | `update-node.ts:187`                                                                                                 | pushes a `lease` blocker, refusing `binding-in-use` |
| `ContainmentFacts.lease`                                                 | `containmentMovable` at `src/domain/plan-containment.ts:9`, reached by `update-node.ts:184` and `import-plan.ts:316` | makes a containment move illegal                    |
| the `lease` blocker of `readSubtreeExecutionFacts` (`sqlite.ts:349-353`) | `delete-node.ts:105`                                                                                                 | refuses `binding-in-use`                            |

`create-node.ts` and `unblock-node.ts` hold **no** lease guard at all — neither names the lease and neither reads a containment fact. `grep -n "lease" src/commands/node/*.ts src/commands/plan/import-plan.ts` returns one line, `update-node.ts:187`.

Two consequences, and the epic states both rather than letting an implementing agent discover them:

- **Wiring the guard into `create-node` and `unblock-node` adds a refusal those commands never had.** It is new behaviour, not a replacement. It is still correct — a run over an ancestor covers the whole subtree, so appending a child under a claimed objective is exactly the write the guard exists to refuse — but no test regresses to prove it, because nothing refused it before.
- **No plan operation declares `lease-held`.** `grep -rn '"lease-held"' src/http/contract/` binds it to `node.claim`, `node.heartbeat`, `node.release` and `node.report` and to nothing else. This epic therefore **adds** `subtree-busy` to five operations and **removes** no code from any of them. `lease-held` leaves the four run operations in EPIC 050.4, with the mechanism that raises it.

## Decisions

- **`runCoversNode` is a read on the plan store, it expands the set itself, and it runs in the caller's transaction.** The signature is `runCoversNode(transaction, seedIds: readonly string[], now: number)`, returning one `subtree-busy` refusal or `null`. The store walks to every ancestor of the seed and every descendant of it in SQL — the same recursive walk `readSubtreeContainmentFacts` already uses at `sqlite.ts:300` — and reads every run over the closure whose `state` is `active` and whose `expires_at` is greater than `now`.

  The command passes the seed, never the closure. A command that computed ancestors itself would need a graph read before the guard, and `create-node` reads the graph only at `:128`, after two blob writes. Expanding inside the store keeps the guard ahead of every write in all five commands, which is the property the epic is for.

- **It runs inside the caller's transaction, and that is what closes the race.** `services/storage` opens `BEGIN IMMEDIATE` at `src/services/storage/connection.ts:35`, so a claim that opens a run and a plan write that reads coverage serialise, and neither sees a half-written graph. A read in a separate transaction would admit a write against a run opened a microsecond later. The lease closed this race with a row; the run closes it with the isolation level.

- **It is deterministic.** When several runs cover the closure, it returns the one whose node id sorts first bytewise, breaking a further tie by run id, exactly as `subtreeExclusion` does. One input always names the same run, so a refusal message is reproducible and a test can assert it by value.

- **The liveness boundary is the boundary of `subtreeExclusion` and of `assertRunAuthority`.** `expires_at <= now` is expired, and the caller passes the same `now` it read once at the top of its transaction. A write admitted at that instant is safe because the same instant refuses the stale worker: EPIC 050.2 states that `assertRunAuthority` refuses an expired run, and this epic admits the plan write at exactly the same `now`. The two halves are asserted together.

- **The closure is symmetric for every command, and only the seed differs.** A run over an ancestor covers the whole subtree by EPIC 050's rule, and a run under a node means that node's subtree is busy — a human editing an objective while a task under it executes is exactly the write this guard exists to refuse. Making the direction depend on the command would give one condition two meanings and would make `runCoversNode` take a mode argument whose two values no test could distinguish from a bug.

  The consequence is stated rather than discovered: a run on an existing child of a parent refuses a `create-node` under that parent, and a run on a descendant refuses an `unblock-node`. Both are new refusals, both are correct, and each is asserted by its story.

- **When several seeds match, `self` beats `ancestor` beats `descendant`.** With a multi-id seed one covering node can be `self` for one member and `ancestor` of another, so the bytewise tie-break alone does not determine `relation`. The rule is evaluated over the seed set as a whole: a covering node inside the seed is `self`; otherwise a covering node above any seed member is `ancestor`; otherwise it is `descendant`. Only `import-plan` passes more than one id today, and the rule is asserted against it.

- **The guarded set is the seed, and the seed is stated per command.** The closure adds ancestors and descendants; the seed names what the mutation touches.

  | command        | seed                                                   | why                                                                  |
  | -------------- | ------------------------------------------------------ | -------------------------------------------------------------------- |
  | `create-node`  | the parent id                                          | the new node has no id yet, and the parent is what the write changes |
  | `update-node`  | the node id                                            | a field write touches one node                                       |
  | `delete-node`  | the node id                                            | the closure supplies the subtree the delete removes                  |
  | `unblock-node` | the node id                                            | a state write touches one node                                       |
  | `import-plan`  | every id in the submitted set, and every id it deletes | an import is a graph rewrite, and both halves are affected           |

  `import-plan` is the one command whose seed is not available at the top of its transaction: the ids it deletes are the project's nodes no submitted document names, and that set needs the graph. Its guard therefore sits **after** `plan.readGraph` at `:190` and before the first write at `:408`, and its story draws that ordinal. Placing it earlier would force the seed to drop the deletions, which is the half of an import that removes a subtree a worker may hold.

  A descendant is covered by the closure wherever the mutation reaches one, and an ancestor is covered everywhere, because a run over an ancestor covers the whole subtree by EPIC 050's rule. `create-node` seeds the parent and not the new node, because a run over the parent is the condition to refuse and the new node cannot be covered by anything.

- **The guard sits after the cheap identity and revision refusals and before the first write.** In every one of the five it follows the not-found and stale-revision checks, which cost one read each and name a cause the caller can act on first, and it precedes the first `blobs.put`, `ids.mint`, `revision.record`, `plan.mutateGraph`, `plan.setNodeState` or `events.append`. A refusal writes nothing, and every refusal test asserts it by comparing database bytes.

  The exact insertion point per command is drawn by that command's story, and the drawn ordinal is the contract.

- **The refusal is `subtree-busy`, and no new error code is added.** The plan write and the claim answer the same question about the same graph — is an active run over this node — so they carry the same code and the same details. Adding a `node-busy` that differed only in which operation raised it would put two codes on one condition, and `errorStatuses` would then owe two entries and two details schemas for one meaning.

- **`binding-in-use` keeps its shape, and it is not the run guard.** `update-node` and `delete-node` refuse `binding-in-use` with a `blockers` list when a node is bound to execution state. That list keeps `workspace`, `attempt-commit` and `retained-commit`; `update-node` loses the `lease` member and gains none. The run guard fires earlier and carries a different code, because it answers a different question: `binding-in-use` says a node is referenced, and `subtree-busy` says a worker holds it now.

- **`delete-node` keeps the `lease` blocker of `readSubtreeExecutionFacts` for one epic.** That blocker sits in the store's closed `executionBlockers` list, EPIC 050.4 swaps it for the run blocker with the rest of the mechanism, and removing it here would leave the list half-migrated across two epics. Until then `delete-node` refuses on a stale lease row as well as on an active run — a superset of the guard, never a gap.

- **Nothing reads `ContainmentFacts.lease` when this epic ends, and the field survives to EPIC 050.4.** `update-node.ts:187` stops pushing the blocker and `containmentMovable` stops testing `facts.lease`. The field is still produced by `readContainmentFacts` and `readSubtreeContainmentFacts`, unread, until EPIC 050.4 deletes the producer with `leaseHeld`. Deleting the field here would force the store change into this epic and split one mechanism removal across two.

  A test asserts the field is read by no production file, so the dead producer is a stated interval and not a leak.

- **`containmentMovable` drops one conjunct and keeps its signature.** It becomes `!facts.workspace && !facts.attemptCommit && !facts.retainedCommit`. Its callers pass the same `ContainmentFacts`, and the run guard is a separate refusal ahead of it, so no caller changes shape. A movable-containment rule that also consulted a run would answer two questions with one boolean and would lose the run id the refusal must name.

- **`KANTHORD_VERSION` moves to `28.0.1`.** No wire shape changes; the bump records the build. The compatibility record gains no row, and `declaredCapabilities` is unchanged.

## Sequence

**A pair here draws the path that still succeeds.** Each of the five commands gains a refusal, and the
diagram of a guarded command draws the fixture with no active run — the path whose seam order this
epic changes. The refusal itself is a branch of a different fixture, and drawing it would give the
story a second live diagram, which the sizing rule forbids. What proves the refusal is the refusal
test and the byte-identical database comparison, and each story names the case that carries it.

This epic draws no diagram. A path is drawn by the story that changes it, under
`.agents/plan/authoring.md`, and the story list below names the pair each story carries. Five
stories carry a pair; four draw nothing.

## Stories

Each entry is a name and the output it contributes. The story file holds the change, the tasks and
the diagrams, and it declares its kind. A `story-foundation` draws nothing; a `story-implement` draws
one baseline and one ship diagram. `.agents/plan/authoring.md` is the standard.

1. **The run-covers-node rule** — `runCoversNode` on `src/services/plan/index.ts` and `src/services/plan/sqlite.ts`, expanding the seed to its ancestors and descendants and returning the `subtree-busy` refusal or `null` with the bytewise tie-break. `story-foundation`.

2. **The create-node guard** — `create-node` refuses while a run covers the parent or an ancestor of it, before it mints an id or writes a blob.

   Diagrams: create-node-guard

   Baselines: create-node-guard <- baseline-create-node

   Seams: create-node-guard: +plan.runCoversNode

3. **The update-node guard** — `update-node` refuses while a run covers the node or an ancestor of it, and it stops pushing the `lease` blocker.

   Diagrams: update-node-guard

   Baselines: update-node-guard <- baseline-update-node

   Seams: update-node-guard: +plan.runCoversNode

4. **The delete-node guard** — `delete-node` refuses while a run covers the node, an ancestor of it or anything in its subtree.

   Diagrams: delete-node-guard

   Baselines: delete-node-guard <- baseline-delete-node

   Seams: delete-node-guard: +plan.runCoversNode

5. **The unblock-node guard** — `unblock-node` refuses while a run covers the node or an ancestor of it, before it appends its event.

   Diagrams: unblock-node-guard

   Baselines: unblock-node-guard <- baseline-unblock-node

   Seams: unblock-node-guard: +plan.runCoversNode

6. **The import-plan guard** — `import-plan` refuses while a run covers any submitted node, any node the import deletes, or an ancestor of either, and the command's single clock read moves to the top of its transaction.

   Diagrams: import-plan-guard

   Baselines: import-plan-guard <- baseline-import-plan

   Seams: import-plan-guard: +plan.runCoversNode, ~clock.now @src/commands/plan/import-plan.ts:390

7. **Containment stops reading the lease** — `containmentMovable` drops its `!facts.lease` conjunct, and `update-node` drops the `lease` member of its blocker list. `story-foundation`.

8. **`subtree-busy` joins the five plan operations** — the code on the `errors` record of `plan.import`, `node.create`, `node.update`, `node.delete` and `node.unblock`, and in `operationAdditions`. `story-foundation`.

9. **The proposal records one guard** — `docs/proposal/phase-2/runs-and-exclusion.md` gains the run-covers-node rule, the seed per command and the `subtree-busy` refusal on a plan write. `KANTHORD_VERSION` moves to `28.0.1`. `story-foundation`.

Gates: `pnpm run verify`

Proof:

```bash
node --test \
  src/services/plan/sqlite.test.ts \
  src/domain/plan-containment.test.ts \
  src/commands/node/create-node.test.ts \
  src/commands/node/update-node.test.ts \
  src/commands/node/delete-node.test.ts \

  src/commands/plan/import-plan.test.ts \

```

Hermetic coverage required beyond the Proof:

- A plan write on a node covered by an active run refuses `subtree-busy`, and the details name the covering node, its run id and its `expires_at`. One case per command, five commands.
- The closure is proven per command, against real SQLite: a run on an **ancestor** refuses each of the five, a run on a **descendant** refuses each of the five, and a run on an **unrelated** node refuses none. Fifteen cases. The descendant row is the one a seed-only guard would miss, and the unrelated row is the one an over-wide closure would fail.
- The `relation` precedence is asserted against a multi-id seed: one covering node that is `self` for one member and `ancestor` of another reports `self`. Only `import-plan` passes such a seed today.
- `create-node` seeds the parent, asserted by a run on the parent refusing and a run on a sibling of the parent admitting.
- A plan write on a node covered by an **expired** run succeeds, and on a node whose run has **ended** succeeds. Both boundaries asserted.
- `runCoversNode` and `assertRunAuthority` share one liveness boundary. For `expires_at` of `now - 1`, `now` and `now + 1`, a test asserts the plan write is admitted exactly when the worker's write is refused. Three iterations, both sides in one case. **Story 1 owns this case**, because it is a property of the read and not of any one command.
- `runCoversNode` returns the bytewise-first covering node, and breaks a further tie by run id. Asserted with two runs seeded in both insertion orders, so the result cannot depend on row order.
- Two seed arrays holding the same ids in different orders give a deep-equal result.
- A claim and a plan write on the same node, issued concurrently against one real database, produce no interleaved state and an outcome equal to one of the two serial orders: either the claim commits and the plan write refuses `subtree-busy`, or the plan write commits and the claim then opens its run over the written graph. `BEGIN IMMEDIATE` serialises the two writers; it does not make one of them lose, and an oracle demanding exactly one winner would fail on a legal execution.
- A node left `running` behind an expired run still admits a plan write, and the worker that held it is refused at the same instant. Both halves in one case, **owned by Story 1**. Coverage is a property of the run, not of the node state; a rule keyed on `node.state = 'running'` would block edits behind a dead worker until the daemon restarted.
- Every assertion in this gate is owned by exactly one story, and each story's Verify section names the case. An assertion that appears here and in no story is a gate nobody implements.
- Every `subtree-busy` refusal leaves the database byte-identical, asserted for all five commands. `create-node` is the case that matters most: it refuses after two shipped blob writes today unless the guard moves ahead of them.
- `create-node` and `unblock-node` gain a refusal they never had, asserted as a new case each and named as an addition in the story. No existing case regresses, because none existed.
- `update-node` no longer pushes a `lease` blocker: a node holding a live node lease and no run is asserted to accept a containment move. This is the one behaviour this epic deliberately relaxes, and EPIC 050.4 makes the lease unreachable a epic later.
- `containmentMovable` returns `true` for `{ lease: true, workspace: false, attemptCommit: false, retainedCommit: false }`, asserted by value, and still returns `false` for each of the other three flags. Four cases, so the drop is exactly one conjunct.
- `ContainmentFacts.lease` is read by no production file, asserted by enumerating the tree for the identifier rather than by one grep of one file. The producer survives on purpose, and the assertion is what makes that interval safe.
- `delete-node` still refuses on the `lease` blocker of `readSubtreeExecutionFacts`, asserted by one case, so the superset guard is deliberate and EPIC 050.4 inherits a known state.
- `subtree-busy` is a declared error on all five plan operations, asserted against the registry, and `lease-held` is declared on none of them, asserted the same way — because it never was.
- `declaredCapabilities` is **unchanged** by this epic, asserted by value against EPIC 050.2's names. No capability is retired and none is declared.
- The five operations' declared error sets each grow by exactly one member, asserted by comparing the shipped set with the new one per operation. The generated OpenAPI documents change, and `pnpm run verify` emits and validates every one of them.
- The change to each operation is exactly one added enum member and nothing else: the status map, the details schema and the meaning of `subtree-busy` are asserted equal to the values EPIC 050 registered. That is what puts this epic inside the closed list of `docs/proposal/api/README.md:96` rather than outside it at `:105`.
- `KANTHORD_VERSION` is `28.0.1`, and the compatibility record gains no row.
- Every diagram of every story of this epic is replayed against the real command over real SQLite, and the recorded token list equals the drawn list by `deepStrictEqual`.
- Every story of this epic owns at most one live diagram, and every story that changes a shipped command declares a baseline. Both asserted by the gate.
- This epic's own text holds no mermaid block, asserted by the gate over `.agents/plan/epics/`.
