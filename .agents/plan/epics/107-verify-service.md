# EPIC 107 — Verify service

Status: **ready**.

## Goal

A declared check runs inside a workspace under the operational limits of `docs/proposal/phase-2/gates-and-approval.md`: a timeout, a process-tree kill so a test server the command started cannot survive, an output size cap, and a filtered environment. `src/services/verify/index.ts` is rewritten into the result contract, and `src/services/verify/supervised.ts` holds the one implementation, `SupervisedVerify`. It runs on the `SupervisedRunner` of `src/services/process/`, which EPIC 106 extracts in its story **The process capability**, so the timeout, the `SIGTERM`-then-`SIGKILL` group signal, the per-stream output cap and the launcher exit codes have one implementation for git, for a tool call and for a check. `src/services/verify/environment.ts` pins the ten-entry check environment, builds the check paths and computes the environment identity, and `src/services/verify/toolchain.ts` renders the recorded toolchain identity. `SupervisedVerify.run` **returns** one `CheckOutput` carrying the command, the working directory, the environment identity, the toolchain version, the two timestamps, the timeout, the exit status, the error reason and the captured output, which is every field of `docs/proposal/phase-2/gates-and-approval.md` that a subprocess can report. It writes no row, opens no storage transaction and takes no `Storage`. `src/main.ts` constructs the implementation and builds its `CheckPaths`, because only `main.ts` may name an implementation and an implementation the composition root cannot instantiate is not shippable. `src/services/verify/not-implemented.ts` is deleted, because the real implementation exists.

## Non-goals

- No persistence. EPIC 110 writes the `task-diagnostic` row of `docs/proposal/database/check_result.md` with `authoritative = 0`, and EPIC 112 writes the `candidate` and `merge` rows with `authoritative = 1`. Each stores the output blob, the `profile_blob`, the `commit_oid`, the `node_id` and the `run_id`, and each mints the `checkResult` id, whose ULID is the start time. This epic returns a value and opens no transaction.
- No per-task diagnostic run and no attribution. EPIC 110 owns the call after each task, and it owns the rule that a diagnostic gates nothing.
- No candidate freeze and no objective gate. EPIC 112 owns the frozen candidate, the run against a clean checkout of that exact commit, the merge-commit re-run and `invalidated_at`.
- No gate A and no gate B. EPIC 109 owns `profile.verify`, the negative control, and the report that separates a wrong declaration from a red baseline. It is the first caller of this service.
- No reconciliation. EPIC 108 owns the `reconcile` check against the merge commit and its `sync` and `merge` journal rows.
- No initiative end-to-end run. `docs/proposal/phase-2/gates-and-approval.md` defers it, and an MVP initiative records `not-applicable`. The service outcome set holds no `not-applicable`; the caller records that value without running anything.
- No check declaration and no lint. EPIC 103 owns the `checks` map, the `unit` and `e2e` names, the `timeout` token, the `timeoutMilliseconds` parse and the vacuous-command lint. This service runs the argv it receives and validates no declaration.
- No route and no CLI command. `profile.verify` stays `stubbed` in `src/http/contract/instruction.ts`, and EPIC 109 moves it. No operation id changes lifecycle in this epic.
- No hash implementation. `src/services/blob/index.ts` already exposes `hash`, and EPIC 103 reuses it for the profile hash and the template digest. This epic injects that capability and spells `sha256:<hex>` nowhere.
- No toolchain probe. The daemon executes exactly the declared command and no second command, because a probe of its own is undeclared work with side effects, and for `sh -c "npm test"` it reports the shell.
- No new machinery. This epic copies no launcher, no cancel path and no output accounting. A second copy of the supervised run is a defect, and EPIC 106 already reduced four copies to one.
- No migration. `docs/proposal/database/check_result.md` closes the `result` column over `running`, `passed`, `failed`, `error`, `timed-out`, `cancelled` and `not-applicable`, so this epic adds no outcome name and changes no schema.

## Stories

- **The check contract** — `src/services/verify/index.ts` is rewritten, and it names no vendor package and no `node:` module. `CheckOutcome` is exactly `"passed" | "failed" | "error" | "timed-out" | "cancelled"`, the subset of the `result` column of `docs/proposal/database/check_result.md` that one subprocess run can report: `running` is the row the caller opens before the call, and `not-applicable` is the value the caller records when it runs nothing. `CheckErrorReason` is exactly `"not-started" | "pid-file-failed" | "orphaned" | "output-exceeded"`, the four faults that leave no exit code and that `check_result` has no column for; the caller carries it in its refusal event. `CheckRequest` is `Readonly<{ command: readonly string[]; cwd: string; timeoutMs: number; signal: AbortSignal | null }>`. It carries **no** `env`, so no caller can inject a variable and every recorded identity is the one this service pins. It carries **no** `outputLimitBytes`, so every result of the daemon is comparable under one cap. It carries **no** `checkName`: the service decides nothing from the name, and EPIC 110 writes `check_name` from the `checks` map key it already holds. It keeps `timeoutMs`, because EPIC 103 makes the timeout a declared field of the profile. `CheckOutput` is `Readonly<{ result: CheckOutcome; command: readonly string[]; cwd: string; envIdentity: string; toolchainVersion: string; timeoutMs: number; exitCode: number | null; errorReason: CheckErrorReason | null; output: string; startedAt: number; endedAt: number }>`, which is the record of `docs/proposal/phase-2/gates-and-approval.md` reduced to what one subprocess run knows: the commit, the manifest and the profile hash belong to the caller, which pins them. `errorReason` is null for every result other than `error`, and null for an `error` that carries an exit code. `CHECK_OUTPUT_LIMIT_BYTES` is `4_194_304`, exported from this file beside the interface, as EPIC 106 exports `DEFAULT_TIMEOUT_MS` from `src/services/process/index.ts`. The cap is four times the `DEFAULT_OUTPUT_LIMIT_BYTES` of `1_048_576` that git carries, because a check log is evidence a human reads and `npm test` output passes one mebibyte in a normal repository, and it is still bounded, so one check cannot fill the `blob` table. `VerifyErrorCode` is exactly `"request-invalid"`, and `VerifyError` keeps its two-argument constructor and its `name` of `VerifyError`. **The code is the whole contract of a refusal, and no test reads a refusal message.** No captured output and no environment value reaches a refusal message. The interface is `Verify`, with one method, `run(request: CheckRequest): Promise<CheckOutput>`. `src/services/verify/not-implemented.ts` and `src/services/verify/not-implemented.test.ts` are deleted, and the `not-implemented.ts` case of `src/domain/layout.test.ts` names `lease` only, with its suite name changed to match.
- **The pinned environment, its paths, and its identity** — `src/services/verify/environment.ts` exports `CheckPaths` as `Readonly<{ path: string; home: string; tmpDir: string; runDirectory: string }>` and `checkEnvironment(paths)`, which returns exactly `{ PATH: paths.path, HOME: paths.home, TMPDIR: paths.tmpDir, LC_ALL: "C", LANG: "C", TERM: "dumb", GIT_TERMINAL_PROMPT: "0", GIT_CONFIG_GLOBAL: "/dev/null", GIT_CONFIG_SYSTEM: "/dev/null", GIT_CONFIG_NOSYSTEM: "1" }` and nothing else. It accepts no extra entry, so the child inherits nothing and no provider credential, no `KANTHORD_MASTER_KEY` and no operator variable reaches a check. **The environment is filtered and never mutated**, which is what `docs/proposal/phase-2/gates-and-approval.md` requires: the ten entries are the ten of `agentEnvironment` in EPIC 106, and this epic adds none. It sets no `CI` and no `NO_COLOR`, because `CI` changes what a test runner executes and a recorded pass must be the pass the human reproduces. The same file exports `buildCheckPaths({ home, path })`, which returns `{ path, home: join(home, "check", "home"), tmpDir: join(home, "check", "tmp"), runDirectory: join(home, "check", "run") }` and creates the three directories with `mkdirSync`, `recursive: true` and mode `0o700`, exactly as `buildGitPaths` of `src/services/git/probe.ts` does. It also exports `renderEnvironment(env)` and `environmentIdentity(hash, env)`. **The rendering is injective, because the name grammar is closed.** A name matches `/^[A-Z_][A-Z0-9_]*$/`, the POSIX form, so a name holds no `=` and is never empty; a value holds no LF and no NUL byte. `renderEnvironment` raises `VerifyError("request-invalid")` on a name or a value that breaks those rules, sorts the entry names with `comparePaths` of `src/domain/plan-path.ts`, emits one line `<name>=<value>` per entry with one LF after each, and returns the UTF-8 bytes. `{ "A=B": "C" }` is therefore refused rather than rendered, so no two maps render to the same bytes. `environmentIdentity` takes `hash` of type `BlobStore["hash"]` from `src/services/blob/index.ts` and returns `hash(renderEnvironment(env))`, so the `sha256:<hex>` spelling has one implementation in the daemon and EPIC 103 already reuses the same one. The identity is a pure function of the ten entries, so two runs on one host produce one identity and a moved home produces a different one, which is what `env_identity` of `docs/proposal/database/check_result.md` records for.
- **The recorded toolchain identity** — `src/services/verify/toolchain.ts` exports `CheckToolchain` as `Readonly<{ nodeVersion: string; gitVersion: string }>`, `programName(argv0)` and `renderToolchainVersion(program, toolchain)`. **A declared check is an arbitrary argv, so the daemon names no language and executes no second command.** `toolchain_version` of `docs/proposal/database/check_result.md` therefore holds the program the daemon ran plus the daemon's own toolchain identity, and nothing else: `renderToolchainVersion` returns exactly `` `${program} node@${toolchain.nodeVersion} git@${toolchain.gitVersion}` ``. `programName` returns the last `/`-separated segment of `command[0]`, so `["npm", "test"]` records `npm node@24.4.0 git@2.47.1` and `["/bin/sh", "-c", "npm test"]` records `sh node@24.4.0 git@2.47.1`. The two versions are injected, not read from the host inside the service: `main.ts` passes `process.version` without its leading `v` and the `gitVersion` that `probeTools` of `src/services/git/probe.ts` already measured at startup. The field is the identity of the daemon that ran the check, and it is not the version of the test framework the command invokes; a reproduction needs the recorded command and the recorded commit for that.
- **The supervised check run** — `src/services/verify/supervised.ts` exports `class SupervisedVerify implements Verify`. Its dependencies are `Readonly<{ runSupervised: SupervisedRunner; clock: Clock; blobs: BlobStore; toolchain: CheckToolchain; paths: CheckPaths }>`, every one an interface of `src/services/process/index.ts`, `src/services/clock/index.ts` and `src/services/blob/index.ts`, and it takes no `Storage`. A service implementation may depend on another service interface, so the hash reaches it through `blobs.hash`. `run` validates the request first and raises `VerifyError("request-invalid")` on an empty `command`, on an element that is empty or holds a NUL byte, on a `cwd` that is not an absolute path, and on a `timeoutMs` that is not a positive integer. **That refusal is the only throw of this service, and it happens before anything starts.** Every attempted check returns a `CheckOutput`, because `docs/proposal/database/check_result.md` opens the row as `running` before the call and EPIC 108 opens a journal row with it, so a throw after the start strands both. `run` reads `startedAt` from `clock.now()` before the spawn, and `endedAt` from `clock.now()` after the child settles. A `request.signal` that is already aborted returns `result: "cancelled"` with `exitCode` null, `errorReason` null, `output` the empty string, and it spawns nothing. Otherwise it mints the pid file `join(paths.runDirectory, "check-" + randomUUID() + ".pid")`, exactly as `src/services/git/run.ts` does, and calls `runSupervised` **exactly once** with `command: request.command[0]`, `args: request.command.slice(1)`, `env: checkEnvironment(paths)`, `cwd: request.cwd`, that pid file, `timeoutMs: request.timeoutMs`, `outputLimitBytes: CHECK_OUTPUT_LIMIT_BYTES`, `signal: request.signal`, and `onStdout` and `onStderr` both null. One `run` therefore makes one runner call, or none when it refuses or when the signal is already aborted. `output` is the runner `stdout` followed by the runner `stderr`, with nothing between them, because two streams have no reproducible interleaving. **The outcome mapping is a table and not a judgement, because `docs/proposal/database/check_result.md` states that `result` is explicit and never inferred from `exit_code`.** An outcome of `exited` maps by code: `0` is `passed`; `126` and `127` are `error` with `errorReason` null, because `/bin/sh` reports those two when it cannot execute the program, so the check decided nothing and EPIC 109 gate B needs that case separated from a red baseline; every other code is `failed`. `timed-out` is the distinct outcome `timed-out` with `exitCode` null, never `failed`, because a budget expiry and a red suite are different facts. `cancelled` is `cancelled` with `exitCode` null. The three daemon faults `not-started`, `pid-file-failed` and `orphaned` are each `error` with `exitCode` null and `errorReason` equal to that outcome name, so the caller closes its `running` row and names the fault. `output-exceeded` is `error` with `exitCode` null and `errorReason` of `"output-exceeded"`, because the runner already killed the process tree and the `result` column admits no `output-exceeded` value. **The truncation rule belongs to the runner: it drops the chunk that crosses the cap, keeps the whole chunks before it and reports `output-exceeded`.** This service returns that captured prefix unchanged and counts nothing, so it exposes no byte total that an operating-system chunk boundary would make irreproducible. EPIC 106 asserts the cap at the runner; this epic asserts the mapping. The process-tree kill, the grace of `TERMINATION_GRACE_MS` and the ignored `ESRCH` and `EPERM` all live in the runner, so this file holds no signal call and no timer.
- **Configuration** — `src/services/config/convict.ts` gains one key, `check.path`, format `nonEmptyString`, default `/usr/local/bin:/usr/bin:/bin`, env `KANTHORD_CHECK_PATH`, and the env mapping list gains `["KANTHORD_CHECK_PATH", "check.path"]` beside the existing entries. `src/services/config/index.ts` gains `CheckSettings` as `Readonly<{ path: string }>` and adds `check: CheckSettings` to `Settings`, beside `attemptLimit`. It is the `PATH` the launcher resolves `command[0]` against, so a check reaches `npm` without inheriting the operator shell. No timeout key exists, because EPIC 103 makes the timeout a declared field per check and a second source would contradict the profile. No output-cap key exists, because a per-host cap would make two recorded results incomparable.
- **The composition root constructs it** — `src/main.ts` calls `buildCheckPaths({ home: settings.home, path: settings.check.path })` and constructs `const verify: Verify = new SupervisedVerify({ runSupervised, clock, blobs, toolchain: { nodeVersion: process.version.slice(1), gitVersion: probed.gitVersion }, paths: checkPaths });` after `const blobs = new SqliteBlobStore(...)`, so every dependency it names already exists at that point. `runSupervised` is the one `createSupervisedRunner(systemSchedule)` value that EPIC 106 builds before `probeTools`. **No route reaches a bare check run in this epic.** `profile.verify` stays `stubbed`, no handler and no command takes `verify`, and EPIC 109 is the first caller: it passes this same value into `verifyProfile`. `reporters` of the health check gains no entry, because a probe that runs no check would report the capability healthy without proving it. The composition is proved instead by its one observable effect: a started daemon holds `check/home`, `check/tmp` and `check/run` under its home, at mode `0o700`, and no route creates them.

## Verification gate

Gates: `npm run verify`

Proof:

```bash
node --test src/services/verify/*.test.ts src/services/config/convict.test.ts src/domain/layout.test.ts src/main.test.ts && echo "PASS EPIC-107"
```

**No route reaches a bare check run, so the close proof is the hermetic suite below plus the composition assertion of `src/main.test.ts`.** The suite has two parts, and the split is explicit. The **deterministic** part drives `SupervisedVerify` through a mock `SupervisedRunner`, a hand-written object that returns the exact `ProcessRunResult` the case names and records the request it received, so every outcome mapping, every call count and every recorded field is an exact value. The **integration** part is exactly one case, and it runs one real subprocess to prove the process-tree kill against the operating system.
