# EPIC 011.2 — The deployment scenarios move to phase 3

Status: **ready**.

## Goal

`docs/proposal/README.md` now states that every `deployment` scenario belongs to phase 3. Routing,
binding across two machines and token distribution are one subject, and phase 3 proves it once.
Phase 1 keeps the assertion a fixture cannot make: the product onboards a real repository from a real
git forge, on one machine.

P1-E3 therefore leaves phase 1 and becomes P3-E6, and phase 1 gains P1-E5 in its place. The runner
already carries every mechanism this needs; the change is which scenario id declares what.

## Non-goals

- **No new oracle.** P1-E5 runs the P1-E1 journey against the real profile. Every assertion it makes
  is an assertion P1-E1 already makes, against a different origin and a different credential.
- **No ssh deletion.** `scripts/e2e/lib/driver/ssh.ts` stays. P3-E6 consumes it in phase 3, and a
  driver deleted now is a driver rewritten later.
- **No phase-3 scenario implementation.** P3-E6 and P3-E7 are declared in the proposal and they are
  implemented in phase 3. This epic removes their phase-1 declaration and keeps their code reachable.
- **No change to P1-E4.** The container pair keeps the fixture profile and the two-namespace topology.

## Stories

- **P1-E3 becomes P1-E5** — `scripts/e2e/lib/tag.ts` declares the scenario id union, and
  `scripts/e2e/lib/record/verdict.ts` declares the set the scenario axis requires. Replace `P1-E3`
  with `P1-E5` in both, and rename `scripts/e2e/lib/scenario/p1-e3.ts` and its test to `p1-e5.ts`.
  `scripts/e2e/lib/scenario/index.ts` declares the new entry: mode `integration`, driver `local`,
  profile real. The verdict then requires a P1-E5 bundle where it required a P1-E3 bundle, and the
  phase exits by pointing at that bundle.

- **The mode is part of the declaration** — `ScenarioDeclaration` carries `mode`, and the bundle
  records it. Add `integration` to the mode union, and assert that exactly one phase-1 scenario
  declares it. `deployment` stays in the union with no phase-1 member, because phase 3 uses it.

- **The local driver serves the real profile** — P1-E3 built the real profile behind the ssh driver.
  P1-E5 runs on one machine, so `createLocalDriver` serves it. The driver delivers the plan directory
  and the token file exactly as it does for the fixture profile, and the token file is mode `0600`,
  written by the runner and removed by the ledger. `createRealProfile` needs no change: it takes the
  origin, the credential arguments and the default branch as input, and the caller supplies them.

- **P1-E5 takes its inputs from `.env.e2e`** — `loadE2eEnv` in `scripts/e2e/env.ts` already reads
  `E2E_GH_REPO`, `E2E_GH_BASE_BRANCH` and `E2E_GH_TOKEN`. P1-E5 derives the origin from `E2E_GH_REPO`,
  the default branch from `E2E_GH_BASE_BRANCH`, and writes `E2E_GH_TOKEN` to a mode `0600` file it
  removes at the end. The plan path and the expected objective and task counts stay explicit options,
  because a real plan is authored per run. An absent or incomplete `.env.e2e` raises `unavailable`
  and names each missing key. `--daemon-host` and `--client-host` are refused for P1-E5, because it
  runs on one machine.

- **The run leaves the forge unchanged** — no phase-1 operation writes a ref on the remote, and P1-E5
  runs against a repository Ulrich owns. Assert it: read the remote ref advertisement before the
  journey and after it, and compare the two sets exactly. A difference fails the scenario. This is
  the assertion that makes a real-forge run safe to repeat.

- **The documents name P1-E5** — `.agents/plan/epics/012-phase-1-acceptance-run.md` and
  `.claude/commands/e2e.md` name the four phase-1 scenario ids and the exit bundle. Both are amended
  ahead of this epic. `.agents/plan/epics/011-end-to-end-scenarios.md` and
  `.agents/plan/epics/011.1-acceptance-run-preconditions.md` are complete and they are not rewritten:
  a closed epic records what it did, and this epic records what changed after it.

## Verification Gate

Gates: `npm run verify`

Proof:

```bash
TAG=$(node scripts/e2e/run.mjs --mint-tag) \
  && node scripts/e2e/run.mjs P1-E5 --tag "$TAG" \
  && node scripts/e2e/run.mjs --verdict "$TAG" --scenarios-only; test $? -eq 3 \
  && echo "PASS EPIC-011.2"
```

The verdict exits `3` here, because P1-E1, P1-E2 and P1-E4 hold no bundle under this tag and no
verify record exists. An absent artifact is exit `3`, and the first failing condition sets the
status; `.claude/commands/e2e.md` holds the one exit-code table. P1-E5 itself exits zero against
the `.env.e2e` repository. That is the assertion: an incomplete run is not a pass.

Coverage required beyond the Proof:

- `P1-E3` is not a known scenario id, and the runner names `P1-E5` in its refusal.
- The verdict requires a P1-E5 bundle, and a run missing it exits non-zero on the scenario axis.
- Exactly one phase-1 scenario declares mode `integration`, and no phase-1 scenario declares mode
  `deployment`.
- `--daemon-host` or `--client-host` with P1-E5 is an argument fault.
- P1-E5 raises `unavailable`, and names each missing key, when `.env.e2e` is absent or incomplete.
- The real token appears in no printed command, no bundle and no log, and its file is absent after
  the run.
- The remote ref advertisement is identical before and after the run.
- `scripts/e2e/lib/driver/ssh.ts` still typechecks and still satisfies the driver interface test, so
  phase 3 inherits a working driver.
