# EPIC 020 — Wiring, CLI and the external-drive scenarios

Status: **draft**.

## Goal

The block is assembled, and three mechanisms prove it. One assertion names every operation of the registry with the actor kinds it admits. One assertion drives every `routed` operation of the block against a daemon started from the real composition root, so no operation answers `501` there. One assertion runs every declared CLI leaf against a recording client and compares the operation ids it issues with the ids its inventory row declares. Three scenarios then run through `scripts/e2e/run.mjs`, against the packaged `dist/main.js`: a single harness completes the claim-to-close loop, two harness clients in two network namespaces drive one daemon in one run, and a stale harness loses its claim to a second one. `P1B-E2` is the block's exit criterion, and it executes the whole journey `013-external-drive-overview.md:13` states.

**What this epic does not catch.** A handler bound to the wrong implementation, which returns the status the fixture expects, passes every assertion here. A `node.delete` handler bound to a no-op `404` passes a missing-node fixture. That defect belongs to the functional test of the owning epic, and this epic proves reach rather than effect. The three mechanisms catch an unbound operation, an unregistered command, a registered command that reaches no operation, and a missing `allowedActors` row.

**This epic implements no domain behaviour.** EPICs 015, 017, 018 and 019 each own their own `src/main.ts` binding and their own `src/cli/program.ts` registration, and each says so. EPIC 016 owns no CLI command at all. This epic owns only the seams that no vertical epic owns. **A hole this epic finds is a defect returned to the epic that owed it, and never a fix made here.**

## Non-goals

- **No route, no handler and no migration.** EPIC 015 owns the actor routes, EPIC 017 the per-node write routes, EPIC 018 the claim routes and EPIC 019 the report route. Each one binds and registers what it adds. `kanthord event list` calls the `event.list` route that phase 1 already ships, so it adds no route and no handler.
- **No authorization rule and no `allowedActors` row.** EPIC 015 owns the rule and its own rows. EPICs 017, 018 and 019 each own the rows they add. This epic asserts the complete set and decides nothing.
- **One new CLI command, and one only.** This epic ships `kanthord event list`, and it is the single exception to the rule that a vertical epic owns every command. **It also normalizes the option grammar of five commands it does not own** — `node claim`, `node heartbeat`, `node release` and `node show` from a positional `<id>` to `--id <id>`, and `node unblock` from `--node <id>` to `--id <id>` — because the scenarios of this epic are the first caller to compose those argv programmatically and the three grammars disagreed. It adds no command and changes no behaviour there. `018-claim-and-lease/16-cli-commands.md`, `019-outcome-report/19a-node-unblock.md` and `111-inspection-and-manual-controls.md` are amended in the same change. `docs/proposal/open-items.md` defers the remaining grammar questions. The block claims that a human answers "who did what" across several harnesses, `event.list` is the only read that answers it, and no other epic of the block owes that command. EPICs 015, 017, 018 and 019 author every other command of the block and add their own `src/cli/inventory.ts` rows. This epic asserts the whole inventory.
- **No registry total and no proposal row total.** `src/http/contract/parity.test.ts:16,25` and `src/http/contract/registry.test.ts:20,25` hold the scalar counts, and each vertical epic raises them by its own row count. This epic states no total, because six epics editing one number is how a correct branch goes stale at integration. EPIC 015 already pins totals at `015-actor-identity.md:127`, so a claim that no earlier epic states one is false.
- **No environment proof.** The Podman gate proves the two-host **logic** and never the environment. It proves no routing, no VPN, no TLS and no token distribution. `docs/proposal/README.md:102-106` puts every `deployment` scenario in phase 3, and `011-end-to-end-scenarios.md:13,71` says a container pair never substitutes for one. **The daemon terminates no TLS at all**, per `docs/proposal/phase-1/transport.md:29`, so a bearer token travels in cleartext. Phase 3 proves the environment once, through `P3-E6`.
- **No live mode and no provider account.** The three scenarios are `deterministic`. `011.2-the-deployment-scenarios-move-to-phase-3.md` keeps `P1-E5` as the one `integration` scenario, and this epic adds none.
- **No acceptance run and no verdict.** EPIC 025 runs the scenarios in order and writes the verdict, exactly as EPIC 012 does for phase 1.
- **No git and no integration.** No scenario of this epic drives a merge. The harness reports an object id and the daemon records it.
- **No assertion that restates a `node:test` case.** A scenario asserts a rule against the packaged binary and a running daemon, which is a different subject. `011-end-to-end-scenarios.md:11` sets that rule.

## Decisions

These are settled here. No story revisits one.

- **The block reaches thirteen `routed` operations of its own and adds no `stubbed` one.** Five from EPIC 015, three from EPIC 017, three from EPIC 018 and two from EPIC 019. The fifth of EPIC 015 is `actor.rotate`, which `015-actor-identity.md:66` declares with the other four actor rows and `:127` counts in its parity raise. `015-actor-identity.md:39` instructs this epic to carry twelve rather than eleven. **Twelve of the thirteen are new entries, and the thirteenth is a lifecycle flip**: `node.unblock` already exists as a `stubbed` entry, and `019-outcome-report.md` sets it `routed` for the reason `attempt-limit`, so the registry row count rises by twelve while thirteen operations answer a command. Every assertion of this epic that walks the block's routed set walks all thirteen.
- **Seventeen operations admit `harness`, and this epic names all seventeen.** Nine from EPIC 015, seven added by EPICs 017, 018 and 019, and `project.nodes` added by EPIC 022. Every operation admits `human`. The assertion names the set and states no count of the whole registry.
- **The block adds seventeen CLI commands.** Five from EPIC 015, three from EPIC 017, five from EPIC 018, three from EPIC 019 and `event list` from this epic. `node attest` is one of the three of EPIC 019, per `019-outcome-report.md:85`. The fifth of EPIC 015 is `actor rotate`, which `015-actor-identity.md:39` adds after this count was first written.
- **The CLI covers every declared command and not every route, and this epic names the gap.** `src/cli/reachability.test.ts` proves that every entry of `declaredCommands` reaches its operation. It proves no converse, and **"a CLI for every route" is false for the assembled application**. Eight `routed` operations carry no CLI command after the block closes: `blob.show`, `edge.list`, `project.status`, `system.health`, `provider.show`, `provider.rename`, `provider.remove` and `provider.setDefault`. Each is acceptable for a stated reason, and no epic of this block owes a command for one. **`event.list` left that set, because this epic ships `kanthord event list`**: it is the one audit read the block's human value depends on, and the acceptance checklist of EPIC 025 now drives it through the CLI. `blob.show` and `edge.list` are dereference reads that `node show` and `node list` already summarise for a human. `project.status` and `system.health` are covered for a human by `kanthord status`, which calls `system.status`. The four remaining `provider.*` operations are phase-1 credential management that `114-onboarding-cli` owns. **This epic adds no command for any of the eight**, because a command with no caller is inventory that the parity assertion then has to carry.
- **Two test paths, and neither is the packaged artifact.** `src/http/contract/authorization.test.ts` holds the inventory, and `src/cli/reachability.test.ts` holds the CLI reach proof. A named path that does not exist makes `node --test` exit non-zero, so the Proof fails before this epic is built.
- **The scenarios run the packaged artifact, and `src/main.test.ts` does not.** `scripts/e2e/podman/product.Containerfile:3` links `dist/main.js` as `kanthord`, and the local driver packs and installs the tarball at `scripts/e2e/lib/driver/local.ts:41-69`. `launchDaemon` at `test/helpers/daemon.ts` spawns `src/main.ts`, so every `src/main.test.ts` claim says **the real composition root** and never the packaged binary.
- **A scenario drives the CLI and direct HTTP only.** It opens no database, imports no service and calls no internal function, per `docs/proposal/README.md:110`.
- **The three scenario ids are `P1B-E1`, `P1B-E2` and `P1B-E3`.** `scripts/e2e/lib/main.ts:44-48` recognises a scenario id through `knownScenarioIds`, and the pattern at `:56` validates `--tag` only. Each new id is added to both lists.
- **`P1B-E1` takes the `local` driver, and `P1B-E2` and `P1B-E3` take the `podman` driver.** A single harness needs one host, and two harness clients need two network identities. All three take the `fixture` profile and the mode `deterministic`.
- **`deterministic` is the runner mode axis, and it is not clock control.** The daemon exposes no clock API, so `P1B-E3` waits on wall clock. `P1B-E3` polls `node claim` at **250 ms** to a deadline of **60000 ms**, under `leaseTtlMs` of **2000**. The deadline is thirty times the lease term, which absorbs CI and container scheduling variance.
- **The harness token never enters the runner process, and the CLI is what keeps it out.** `runCommand` keeps stdout in the raw `CommandRecord` of `scripts/e2e/lib/command.ts:5-12`, and `assertNoDisclosure` reads `record.stdout` at `scripts/e2e/lib/disclosure.ts:92-104` before serialization redacts anything, so a printed token would leak. `015-actor-identity.md:39` settles the mechanism: `kanthord actor register --name <name> --token-file <path>` creates the file exclusively at mode `0600` before it issues the request, prints the actor id with a redacted confirmation, and prints no secret. **`scripts/e2e/podman/bin/e2e-request.mjs` therefore gains no `captureToken` mode and no redaction of its own**; it is edited only to accept a `tokenFile` field and read the bearer token from that path inside the container. The runner holds no harness token, so it discloses none, and `assertNoDisclosure` passes by construction.
- **The second client is cross-cutting infrastructure.** Nine named places assume one client, and each one is work in the story below. `013-external-drive-overview.md:15` calls it one topology change, and that is an understatement rather than a plan.
- **A caller-selected header needs direct HTTP.** `src/cli/client.ts:61-73` builds a fixed header set and admits no arbitrary header, so no CLI command sends a caller-chosen `Idempotency-Key`. The driver gains `issueAs(role, request)` for that, and `cliAs(role, argv)` keeps the CLI path.
- **The idempotency oracle is a same-node claim replay.** Two report calls under one key on two different node ids prove nothing: `docs/proposal/api/README.md` keys an idempotency record by route parameters, so the two requests are separate even with no actor scoping. Two actors claiming **one** node id under **one** key is the assertion that needs actor scoping, per `015-actor-identity.md:74`.
- **The block needs a third objective, and it needs a dependency between objectives.** `test/e2e/fixtures/two-objective/plan/journey/alpha/objective.md` and `.../beta/objective.md` declare no `depends_on`, so no objective of that fixture becomes ready through another. A new fixture carries the edge.
- **Sequential requests, and one race.** The runner issues one request at a time, so `P1B-E2` proves two identities, two namespaces and server-side arbitration in one daemon run. It does not prove two requests in flight, except in the one phase that drives them in flight on purpose.

- **`P1B-E1` also proves the harness authors its own tasks, and it is the one scenario that does** — the same `scripts/e2e/lib/scenario/p1b-e1.ts`. `017-per-node-graph-write.md` calls graph editing the harness capability this block exists for, and no other scenario of the block writes a node, so the assembled-binary proof of that capability lives here or nowhere.   **Both authored nodes go under the alpha objective, and that placement is load-bearing.** Alpha is the one objective this scenario claims, attests and closes, so an authored task under alpha travels the whole loop and the attestation covers it.   **The transient node covers all three write routes.** `node create` adds one task under the alpha objective with **no** `dependsOn` entry, using the `revision` of `plan export` as `fromRevision`. `node update` renames it, sending the node revision. `node delete` removes it, sending the `revision` the update returned.   **The durable node then travels the whole loop.** `node create` adds a second task under alpha, again with no `dependsOn`, so readiness promotes it to `ready` in the transaction of the write and it is claimable at once. The assertion is scoped to the harness-signed requests by design: the human `plan import` of the phase-1 journey issues one `plan.revisions` call of its own, per `008-project-and-plan.md:70`, so an absolute claim over the whole run would be false.

  **This scenario exercises no stale revision, and it claims none.** Its writes are sequential and each one carries the token the previous response returned, so no `409 stale-revision` arises and none is asserted. The concurrent revision race is proved hermetically by the concurrency assertions of `017-per-node-graph-write.md`, and no scenario of this block asserts it. `P1B-E3` races a **lease**, not a revision, so it is not that proof either.

- **`P1B-E2` — the two-client exit journey** — a new `scripts/e2e/lib/scenario/p1b-e2.ts`, driver `podman`, profile `fixture`, plan `three-objective`, mode `deterministic`. **It executes the complete journey of `013-external-drive-overview.md:13`, and it combines no fact from `P1B-E1`.** It builds the two-client topology, runs the journey from the first client, and registers **two** harness actors through the configured token, one per client container, each token captured inside its own container.
