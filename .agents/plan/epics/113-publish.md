# EPIC 113 — Publish

Status: **ready**.

## Goal

The landing branch reaches remote origin against an expected object id, or it is refused with a classified reason. `src/commands/repository/publish-repository.ts` takes the repository lease of EPIC 108, asserts that `refs/heads/<branch>` equals the `landingOid` the caller reviewed, reads the remote `publishRef` with `git ls-remote`, and pushes that object id to that ref through `src/services/git/push.ts`. The push never carries `--force`, `--force-with-lease` or a leading `+` in its refspec, so remote origin accepts a fast-forward and arbitrates every other case itself. `expectedRemoteOid` is advisory freshness rather than a remote compare-and-swap, and a null value means the ref must not exist yet, exactly as `docs/proposal/phase-1/git-foundation.md` states. A rejection is classified from object ids in `src/domain/publish.ts`, recorded in `git_operation.detail_blob` as the daemon received the server message, less the url userinfo and bounded, and never resolved: the daemon runs no fetch, no merge and no retry after a refusal. One `publish` journal row brackets the push, opened before the child spawns and named by its pid file, per `docs/proposal/database/git_operation.md`. `repository.publish` moves from `stubbed` to `routed` in `src/http/contract/integration.ts`, `kanthord repository publish` calls it, and an approval whose candidate carries `publish_requested` of `1` chains one publish through a function `src/main.ts` injects into `approveNode` of EPIC 112. The per-repository default is the shipped `repository.publish_on_approval` column, which EPIC 112 already records on the candidate.

## Non-goals

- No reconciliation and no freshness pass. EPIC 108 owns `ensureFreshBase`, `reconcileRepository`, the `sync` row, `classifyAncestry`, `isAncestor`, `SqliteLease`, `SqliteCredentialStore` and the `intents` filter of the outside-writer diagnostic. This epic calls each one and reimplements none.
- No objective merge and no candidate. EPIC 112 owns `freezeCandidate`, `approveNode`, the `merge` rows, the candidate table and `publish_requested`. This epic adds one injected function to `approveNode` and writes no candidate column.
- No local ref write. This epic writes exactly one ref, and that ref lives on remote origin. It never calls `Git.refUpdate`, so it moves no `refs/heads/*`.
- No fetch. `docs/proposal/phase-2/integration-and-publish.md` forbids a fetch, a merge and a retry after a rejection, and this epic runs `git ls-remote` only, which transfers no object and writes no ref.
- No force push and no remote repair. `docs/proposal/phase-1/git-foundation.md` makes repairing a remote by force a human operation with the `git` CLI, and no story ships a force flag.
- No `pr@1` and no hosted review. `docs/proposal/phase-2/integration-and-publish.md` defers both, so no story pushes an objective branch and no story opens a pull request.
- No startup recovery of an incomplete `publish` row. Phase 3 owns the remote reconcile, per `docs/proposal/phase-3/recovery.md`. EPIC 007.5 already marks such a row `awaiting-remote-reconcile` and makes the repository refuse new work, and this epic depends on that behaviour rather than changing it.
- No `gitOperation.list`. It stays `stubbed`, because `docs/proposal/api/integration.md` gives it `introducedIn: phase-3`.
- No landing-branch operation. EPIC 029 removed it from the registry, so there is no such route, and no other operation changes lifecycle here.
- No `revert` intent. This epic writes `publish` rows only.
- No new error code. `errorStatuses` of `src/http/contract/errors.ts` gains nothing, because `docs/proposal/api/README.md` names a publish rejection class as a value that travels in `details` rather than as a code of its own.
- No repository state transition. A publish changes no `repository` column, so this epic claims no state transition; the atomic pairing it owns is the journal close together with its event.

## Stories

- **The publish classification, and it stays pure** — `src/domain/publish.ts` imports `zod` and `ancestryRelations` of `src/domain/repository.ts`, and nothing else. It exports `publishRejections`, the frozen tuple `["non-fast-forward", "policy-rejected", "auth-failed", "transport-failed"]`, and `publishOutcomes`, the frozen tuple `["fast-forward", ...publishRejections]`, which are the `outcome` values `docs/proposal/database/git_operation.md` names for this intent. It exports `publishTransportFailures`, the frozen tuple `["auth-failed", "transport-failed"]`, so the domain names its own closed set and never imports `GitFailure`. It exports `classifyPushRejection(input: Readonly<{ transportFailure: PublishTransportFailure | null; relation: AncestryRelation | null }>): PublishRejection`, which decides in this fixed order: a `transportFailure` returns that same value; a null `relation` returns `"policy-rejected"`, because an absent remote ref cannot make a create a non-fast-forward; a `relation` of `"upstream-advanced"` or `"diverged"` returns `"non-fast-forward"`, because the reviewed commit does not contain the value the ref holds; and a `relation` of `"synchronized"` or `"local-ahead"` returns `"policy-rejected"`, because a fast-forward was available and the server refused it for a reason of its own. **The classification reads object ids and never a git message.** `docs/proposal/phase-1/git-foundation.md` forbids message parsing for a decision, and the four `remote:` wordings of a protected branch, a required check, a signature rule and a server hook are the forge's text rather than a contract. The file also exports `remoteReport(report: string): string`, the extraction rule of the server message: it splits the report on `"\n"`, keeps every line that begins with the exact prefix `"remote: "`, removes that prefix from each kept line, removes one trailing `"\r"` from each, and joins the kept lines with `"\n"`. **The extraction is required, because the whole report is not the server message.** Git prefixes remote output with `remote: `, and `--porcelain` adds its own per-ref status lines, so a test that compared the whole report against the hook sentence could never pass. The file also exports `PUBLISH_DETAIL_LIMIT_BYTES` of `8_192` and `boundDetail(text: string): Readonly<{ detail: string; truncated: boolean }>`, which encodes the text as UTF-8, keeps the **first** `PUBLISH_DETAIL_LIMIT_BYTES` bytes, because the server sends its reason before its summary, decodes them with a non-fatal UTF-8 decoder so a split sequence becomes one `U+FFFD`, and sets `truncated` when the input exceeded the limit. **This is what `docs/proposal/phase-2/integration-and-publish.md` names exactly**: the remote-sent payload, in the order the server sent it, with the url userinfo already removed by `stripUserinfo` of `src/services/git/redact.ts`, bounded at 8192 bytes, and nothing else rewritten. The daemon never matches on that text to decide a class. The file also exports `PublishError`, the error class of this epic, with `code` from the frozen tuple `publishRefusals`, and the callable contract of the chained publish: `PublishChainInput`, `PublishChainResult` and `PublishChain`, the function type over the two. **The callable contract lives in `domain/` for the reason EPIC 112 puts `CandidateFreeze` there**: `src/commands/node/approve-node.ts` may not import a command, and both sides need one type. `PublishError` lives beside it, because the same file catches it and `src/http/server/repository/refusals.ts` maps it.
- **One push, one remote read each side, and one object probe** — `src/services/git/push.ts` exports `push(runner, paths, input: PushRemoteInput)`, where `PushRemoteInput` is `Readonly<{ gitDir: string; remoteUrl: string; publishRef: string; proposedOid: string; credential: GitCredential; pidFile: string }>`. The transport guard is **extracted rather than copied**: `src/services/git/preflight.ts` exports `assertPushTransport(input: Readonly<{ remoteUrl: string; credential: GitCredential }>): void`, which holds the two `GitError("url-refused")` raises that `canPush` already implements, `canPush` calls it in place of those lines and keeps its behaviour, and `push` calls it first. `push` imports `preflight.ts`, which is one implementation reaching another in the **same** capability, so the import matrix allows it. It runs through `runAuthenticated` of `src/services/git/authenticated.ts` with the argument vector `["--git-dir=<gitDir>", "push", "--porcelain", "--", <remoteUrl>, "<proposedOid>:<publishRef>"]` and the supplied `pidFile`, so the child is supervised and the journal row names it. **The vector holds no `--force`, no `--force-with-lease`, no `--mirror` and no `+` prefix**, and a test asserts that over the recorded vector rather than over one message. `--porcelain` is present because it makes the recorded per-ref status tabular for the human who reads `detail_blob`, and no story parses it. The result is `Readonly<{ pushed: true; report: string }>` on exit code `0`, and `Readonly<{ pushed: false; failure: GitFailure; report: string }>` otherwise, where `failure` comes from `classifyFailure` of `src/services/git/credential.ts` and `report` is `stripUserinfo(stdout)` followed by `stripUserinfo(stderr)`, concatenated in that order and never interleaved. `remoteRefValue` of `src/services/git/preflight.ts` reaches the `Git` interface unchanged, because the command must read the remote ref before and after the push and `docs/proposal/database/git_operation.md` makes `result_head_oid` the value `git ls-remote` observed afterwards. `src/services/git/ancestry.ts` gains `hasObject(runner, input: Readonly<{ gitDir: string; oid: string }>)`, which runs `git --git-dir=<gitDir> cat-file -e <oid>^{commit}` and returns true on exit code `0` and false on any other code. It is required: a remote that moved to a commit the daemon never fetched makes `isAncestor` raise `GitError("unknown")`, and the epic forbids a fetch, so an absent object is answered as two false ancestor flags, which `classifyAncestry` reads as `"diverged"`. `push` and `hasObject` reach `Git` in `src/services/git/index.ts` and bind in `src/services/git/binary.ts`.
- **The journal records the rejection, and only the rejection** — `DiscardJournalRowInput` of `src/services/git/index.ts` gains `detailBlob: string | null`, and the discard statement of `src/services/git/journal.ts` sets `detail_blob = ?` from it. `docs/proposal/database/git_operation.md` gives that column the rejection of a publish, and no shipped method could write it. `CompleteJournalRowInput` gains nothing, because that same line names the rejection alone and no requirement stores a report for an accepted push. Every shipped discard call site passes `detailBlob: null` and changes nothing else: the `settle` branches of `src/commands/startup/reconcile-journal.ts`, and every existing case of `src/services/git/journal.test.ts`, which keeps each asserted value. `markPublishPending` and `clearChildToken` are untouched, because EPIC 007.5 owns them and a recovery path writes no detail.
- **The publish lease TTL** — `src/domain/lease.ts` gains `PUBLISH_LEASE_TTL_MS` of `600_000`, beside `FRESHNESS_LEASE_TTL_MS` and `RECONCILE_LEASE_MARGIN_MS` of EPIC 108. The value is five times `DEFAULT_TIMEOUT_MS` of `src/services/process/index.ts`, where EPIC 106 moved it, and bounds the three network commands one publish runs: one `ls-remote` read before the push, the push, and one `ls-remote` read after it. The descent test of the expectation reads no remote, because it runs on `Git.hasObject` and `Git.isAncestor` in the bare home. The TTL bounds nothing at run time. It is what `system.status` reads to call a holding stale.
- **Publish refuses before it touches the remote** — `src/commands/repository/publish-repository.ts` exports `publishRepository(dependencies, input)`. The dependencies are `Readonly<{ storage: Storage; git: Git; journal: GitJournal; leases: Lease; blobs: BlobStore; credentials: CredentialStore; events: EventLog; ids: IdGenerator; clock: Clock; acceptsWork: (transaction: Transaction, repositoryId: string) => RepositoryWorkVerdict; runDirectory: string; leaseOwner: string }>`, every one a service interface or a pure function. The input is `PublishChainInput` of `src/domain/publish.ts`, which is `Readonly<{ repositoryId: string; landingOid: string; expectation: Readonly<{ asserted: true; remoteOid: string | null }> | Readonly<{ asserted: false }>; nodeId: string | null; runId: string | null; candidateId: string | null; actorKind: "human" | "daemon"; actor: string }>`. The result is `PublishChainResult` of that same file, which is `Readonly<{ ref: string; landingOid: string; expectedRemoteOid: string | null; resultHeadOid: string; outcome: "fast-forward"; gitOperationId: string }>`. The command reads its own `repository` row with its own statement, because that read serves this operation alone. `PublishError` of `src/domain/publish.ts` carries the closed code list `publishRefusals`, the frozen tuple `["not-found", "publish-reconcile-pending", "needs-reconcile", "stale-oid", "outside-writer", "expectation-not-ancestor", "remote-ref-exists", "remote-ahead", "non-fast-forward", "policy-rejected", "auth-failed", "transport-failed"]`. **The sequence is fixed: read, accepts-work, state check, acquire.** One transaction reads the `repository` row and calls `acceptsWork`, and it claims no lease: an absent repository raises `not-found`; a repository the `acceptsWork` verdict of EPIC 108 refuses raises `publish-reconcile-pending` carrying the open row id, so two publishes never overlap and an unreconciled push blocks the next one; and a repository in `needs-reconcile` raises `needs-reconcile` carrying both diverged object ids, because a landing tip that does not contain the fetched upstream is not a thing to publish. A second transaction then acquires the lease, and every later check runs under it, because `docs/proposal/phase-2/integration-and-publish.md` takes the repository lock **before** it asserts the landing ref: a `refs/heads/<branch>` that differs from `input.landingOid` raises `stale-oid` carrying the expected and the current value, which is the precondition `docs/proposal/api/integration.md` names; and an outside-writer mismatch raises `outside-writer` carrying both object ids. **Every refusal before the row opens writes no `git_operation` row**, and the `finally` releases the lease on each one. The diagnostic call is `Git.checkOutsideWriter` with `gitDir` of the bare home, `ref` of `refs/heads/<branch>` and `intents` of `["merge", "sync"]`, the array EPIC 108 introduced, and it appends `repository.outsideWriter` with the payload `{ ref, expectedOid, observedOid }` in one transaction before it raises. The landing ref is local, so the baseline is a local intent; `publish` is never in that array. The lease is claimed with `ttlMs` of `PUBLISH_LEASE_TTL_MS`, held until after the closing transaction, and released in a `finally` on the fence it acquired; `LeaseError("lease-held")` propagates, because a second holder is the caller's problem.
- **The expectation is advisory, and a predictable rejection needs no round trip** — after the local refusals the command resolves the credential through `CredentialStore.readGit` and reads the remote `publishRef` with `Git.remoteRefValue`, which yields `R`. It then classifies `R` against `landingOid` through `Git.hasObject`, `Git.isAncestor` twice, skipped when the two object ids are equal, and `classifyAncestry` of EPIC 108, with `landingOid` as the landing tip and `R` as the upstream tip; `R` of null makes the relation null. **Two different tests use that classification, and they are not the same test.** When `input.expectation.asserted` is true and `remoteOid` is not null, the command asserts that `landingOid` descends from `remoteOid`, through `hasObject` and `isAncestor` on that value, and raises `expectation-not-ancestor` carrying both object ids when it does not: the caller reviewed a commit that does not contain the value it believed the remote held. An `asserted` expectation whose value differs from `R` is **not** a refusal on its own, because `docs/proposal/phase-1/git-foundation.md` states that a stale expectation whose value is already an ancestor of `landingOid` must publish. An `asserted` `remoteOid` of null **asserts that the ref does not exist**, the meaning `docs/proposal/phase-1/git-foundation.md` and `docs/proposal/phase-2/integration-and-publish.md` both give it, so an `R` that is not null raises `remote-ref-exists` carrying `landingOid` and `R`: the caller published a first publication and the ref appeared under it. The one case that still succeeds is the race, where the ref appears after this read and inside the push; the push carries no force, so remote origin accepts it when the new value is already an ancestor and rejects it otherwise. `docs/proposal/database/git_operation.md` states that exact case, and the daemon enforces nothing at push time. A pre-push failure is classified as a publish class rather than as a bare git failure: a `GitError` raised by `Git.remoteRefValue` maps `auth-failed` to `PublishError("auth-failed")` and every other failure to `PublishError("transport-failed")`, because `docs/proposal/api/integration.md` requires a dead token to read `auth-failed` and the read happens before any row exists. Then the prediction: a relation of `"upstream-advanced"` or `"diverged"` raises `remote-ahead` carrying the relation, `landingOid` and `R`, and **no row opens and no push runs**, which is the rejection `docs/proposal/phase-1/git-foundation.md` says the daemon predicts without a round trip. A relation of `"synchronized"`, `"local-ahead"` or null continues. `expectation.asserted` of false skips the descent test alone and keeps the prediction, and the chained publish of the approval is its only caller.
- **The `publish` row opens before the child spawns, and closes on every path** — one transaction mints `gitOperationId` through `ids.mint("gitOperation")` and opens the row through `GitJournal.open` with `intent: "publish"`, `ref` of `publishRefOf(repository.branch)`, `baseOid` of `landingOid`, `proposedHeadOid` of `landingOid`, `expectedRemoteOid` of `R`, `leaseFence` of the acquired fence, `nodeId`, `runId` and `candidateId` from the input, and `childToken` of `join(runDirectory, \`gitop-${gitOperationId}.pid\`)`, which matches `GITOP_PID_PATTERN`of`src/domain/recovery.ts`so the reap of EPIC 007.5 attributes the child.`docs/proposal/database/git_operation.md`fixes each of those five values for this intent, including that`base_oid`is the reviewed`landingOid`and`expected_remote_oid`is the value the remote ref held when it was checked. **The row commits before the spawn**, because a process id cannot be recorded before the process exists. Then`Git.push`runs once with that pid file. On`pushed: true`the command reads the remote ref again with`Git.remoteRefValue`, and one transaction calls `Lease.assertHeld`with the acquired owner and fence **before** it writes anything, completes the row with`resultHeadOid`of the second observed value and`outcome`of`"fast-forward"`, and appends `repository.published`with`subjectKind: "repository"`, `subjectId`of the repository id,`actorKind`and`actorId`from the input, and the payload`{ ref, landingOid, expectedRemoteOid, resultHeadOid, gitOperationId, nodeId, candidateId }`. The pid file is removed after that transaction commits, per `docs/proposal/database/git_operation.md`. **A push that succeeds and a row that cannot be closed leave the row `open`, and that is the designed outcome, not a gap.** A `lease-fenced`close writes nothing, and any other failure of the closing transaction rolls it back; in both cases the pid file stays,`assertRepositoryAcceptsWork`refuses every later publish, approval and freshness pass of that repository, and the next startup marks the row`awaiting-remote-reconcile`through the shipped`GitJournal.markPublishPending`of EPIC 007.5. The command performs no second push and no compensating write, because the push already landed and a repeat is not a repair. A`GitError`thrown by the push itself — a timeout, an exceeded output cap — leaves the row`open`for the same reason: the daemon does not know whether the remote applied it, and`docs/proposal/database/git_operation.md` makes that exact row the reason the table exists.
- **A rejection is classified, recorded and never resolved** — on `pushed: false` the command maps `failure` onto the domain set: `"auth-failed"` becomes `"auth-failed"`; `"host-key-mismatch"` and `"transport-failed"` become `"transport-failed"`; and `"permission-denied"`, `"unknown"` and every other value become null, so a `permission-denied` reading of a protected-branch message never skips the object-id test that decides the class. A null transport failure reads the remote ref once more with `Git.remoteRefValue` and classifies it against `landingOid` exactly as the prediction did, which is the freshness classification of EPIC 108 applied to the remote ref; a transport failure skips that read, because a second call would fail the same way, and its relation is null. `classifyPushRejection` then returns the class. One transaction calls `Lease.assertHeld` before it writes, puts the `detail` of `boundDetail(remoteReport(report))` through `BlobStore.put` as UTF-8 bytes, discards the row with `outcome` of that class and `detailBlob` of that hash and `resultHeadOid` of null, and appends `repository.publishRejected` with the payload `{ ref, landingOid, expectedRemoteOid, rejection, relation, observedRemoteOid, detailBlob, truncated, gitOperationId }`. The pid file is removed after the commit. The command then raises `PublishError(<class>)` carrying `relation`, `landingOid`, `observedRemoteOid`, `detailBlob` and `truncated`. **The server message travels as one representation, the blob hash**, because `docs/proposal/api/README.md` makes an error detail a blob the client fetches through `blob.show`; `truncated` travels beside it, because a bound the client cannot see is a bound it reads as the whole message. **The daemon takes no further action on any class.** It runs no fetch, no merge, no second push and no state transition, because `docs/proposal/phase-2/integration-and-publish.md` states that fetching, merging and retrying would turn a publish into an unapproved source integration, and because origin can move again immediately after any retry. The repository stays `ready`, and a publish rejection never sets `needs-reconcile`, which names a landing-to-upstream divergence and nothing else.
