# EPIC 051.3 — The checkpoint schema and the land

Status: **draft**. It follows EPIC 051.2 by sequence order, and it runs before EPIC 051.4. It consumes EPIC 051's `workspace_branch` and its `plan.setWorkspaceBranchHead`, EPIC 051.1's git primitives, and EPIC 050's run, attempt and fence.

It carries a decimal number for the reason EPIC 051 states.

## Goal

An accepted commit becomes the checkpoint of an execution run:

- migration `14` creates the whole `checkpoint` table, and only the `execution` kind has a writer;
- the land is a compare and swap on the objective branch, bracketed by a `merge` journal row;
- a successful land writes the checkpoint, advances `workspace_branch.head_oid`, closes the attempt, ends the run and records the node transition and its two events in one transaction;
- a failed swap is `contended`: it consumes no attempt, ends the run, raises the fence and returns the node to `ready`;
- a crash between the ref move and the transaction is reconciled at startup, which writes the checkpoint the land owed.

## Non-goals

- **No acceptance gate, no composition and no route.** `land.begin` and `land.settle` are nested units with no caller here. EPIC 051.4's `acceptExecution` injects them, orders them around the compare and swap, and draws the composed paths. There is no `land.execute` command: a command whose only work is to sequence three calls its one caller could sequence itself has no second reason to exist. Nothing here reads `node.report`.
- **No structural or review checkpoint.** EPIC 052 and EPIC 053 own them. This epic creates the whole table, and only the `execution` kind has a writer.
- **No parent-objective state, and no aggregation.** An accepted checkpoint on a task gives its own terminal state, and on an atomic objective it gives `awaiting_approval`. It does **not** reach that state through `objectiveOutcome` at `src/domain/outcome.ts:17`: that function projects a `TerminalState` from the objective's children, and an atomic objective has none, so the land writes the constant under its own trigger. EPIC 053 adds the pair-driven dispatch, the aggregation and the precedence.
- **No cross-repository landing.** An execution run records exactly one base row, and this epic lands one repository per objective.
- **No publish.** The landing is on the objective branch inside the bare home. Remote origin is EPIC 113.
- **No candidate removal.** The shipped `candidate` table stays unused. EPIC 057 drops it.
- **No `caller` and no `subject`.** Both columns are nullable here and a checkpoint written by this epic keeps them null.

## Decisions

- **The `checkpoint` table is enumerated here, and every column is stated.** Migration `14` creates it. `kind` in `('execution', 'structural', 'review')`. Binding columns `NOT NULL`: `id`, `node_id`, `run_id`, `attempt_id`, `fence`, `created_at`. **`caller` and `subject` are nullable here, and EPIC 054 fills them.** `worker.md` section 8 step 4 names all five bindings, but neither concept has a source yet: `.agents/plan/epics/054-attempt-classification-and-the-supervisor.md:26` adds `attempt.caller` and `attempt.subject` nullable in its migration, and `:13` owns the rule that derives both from authenticated state. A `NOT NULL` column three epics before its derivation exists is not implementable, and inventing a value would manufacture audit evidence. Execution columns: `repository_id`, `base_oid`, `accepted_oid`, `landed_oid`. Structural columns: `graph_revision`, `patch_blob`. Review columns: `verdict`, `judged_checkpoint_id`, `judged_oid`, `reason_blob`, **created here and not by EPIC 053**. A review CHECK cannot exist without them, SQLite cannot widen a CHECK in place, and a `kind` set admitting `'review'` with no review CHECK admits an all-null review row until EPIC 053 lands. EPIC 053 therefore adds a writer and no column. **Every CHECK is named**, so a test asserts it by name and EPIC 053 can cite one it did not create. The clauses are one per group, and the review group takes two: `checkpoint_execution_accepted_oid` is `(kind = 'execution') = (accepted_oid IS NOT NULL)`, `checkpoint_execution_repository` is `(kind = 'execution') = (repository_id IS NOT NULL)`, `checkpoint_structural_patch` is `(kind = 'structural') = (patch_blob IS NOT NULL)`, `checkpoint_review_verdict` is `(kind = 'review') = (verdict IS NOT NULL)` and `checkpoint_review_judged` is `(kind = 'review') = (judged_checkpoint_id IS NOT NULL)`. `verdict` alone would admit an execution row carrying `judged_checkpoint_id`. `checkpoint_review_verdict` is a biconditional, so it also refuses an execution row carrying a verdict and EPIC 053 needs no separate `checkpoint_execution_no_verdict`. `FOREIGN KEY (attempt_id, run_id) REFERENCES attempt(id, run_id)` ties the attempt to the run.

- **That composite reference needs a unique index, and migration `14` creates it first.** SQLite accepts a composite foreign key only against a PRIMARY KEY or a UNIQUE index on the parent columns. `attempt` at `migration-0007-external-execution.ts:34-53` holds `id TEXT PRIMARY KEY` and `UNIQUE (run_id, attempt_no)`, and no key on `(id, run_id)`. The superseded draft cited `:52` as the pattern to mirror, but that line references `run(id, driver)`, and `run` carries `UNIQUE (id, driver)` — the target had the key and `attempt` does not. **The defect does not surface at DDL.** `CREATE TABLE checkpoint` succeeds, and the first `INSERT` fails with `foreign key mismatch - "checkpoint" referencing "attempt"`, because `src/services/storage/connection.ts:8` sets `PRAGMA foreign_keys = ON` at every open. Migration `14` therefore runs `CREATE UNIQUE INDEX attempt_id_run_id ON attempt (id, run_id)` before it creates `checkpoint`. `id` is the primary key, so the pair is unique for every row and the index constrains nothing new; it exists to satisfy the reference. **EPIC 057 must re-create it**, because its migration makes `attempt.caller` and `attempt.subject` `NOT NULL`, SQLite cannot alter a column to `NOT NULL`, and a table rebuild drops a standalone index. `src/services/storage/migration-0007-external-execution.test.ts:1104` is the precedent for asserting an index survives a rebuild.

- **Migration `14` also creates the `workspace_branch` delete trigger, which migration `13` could not.** EPIC 051's Decisions state the trigger refuses a `DELETE` of a `workspace_branch` row referenced by a `checkpoint` row, and a trigger naming an absent table is not creatable. The trigger therefore lands with the table it names.

- **Migration `14` is additive and rebuilds nothing.** It creates one index and one table and one trigger. No shipped column changes nullability, no shipped table is rebuilt, and it declares no `rebuild` flag. EPIC 051's migration `13` is the one that rebuilds, and it rebuilds `git_operation` alone.

- **A checkpoint binds five facts as columns, not as a blob.** `worker.md` section 8 step 4 names the run, the attempt, the caller, the subject and the fence. The audit trail is exactly this tuple, and a blob makes it unqueryable.

- **The land is a compare and swap on the objective branch, with three named fields.** `ref` is the objective branch, `expected` is the run's recorded base for that repository, and `next` is the pinned and verified head. The `refUpdate` primitive of EPIC 006 performs it, bracketed by a `merge` journal row.

- **A successful land completes the run lifecycle, and it does so in the settle.** `land.settle:accepted` closes the attempt as `accepted`, stamps the run head, ends the run with outcome `done` and raises the fence, beside the checkpoint and the branch head. The alternative is a third transaction after the land, and `AGENTS.md` gives a journaled write two and never more, so no caller may open one. The checkpoint records the **pre-raise** fence, which is the value its input carries. A task would otherwise reach `done` holding an active run and an open attempt.

- **The settle owns the node transition, so it owns the event that describes it.** `land.settle:accepted` appends the shipped `outcome.reported` on the node and `run.ended` on the run, and this epic registers **no new event type**. An event that describes a transition sits in the transaction of that transition. A third event for the checkpoint itself has no requirement behind it: a consumer reads `outcome.reported.objectId` and joins the `checkpoint` table. EPIC 051.4 removes those writes from `reportOutcome`'s own path when it wires the route.

- **This epic adds three external triggers, and it reuses none for a meaning it does not have.** `objective-land-accepted` carries an atomic objective from `running` to `awaiting_approval`; `land-contended` and `objective-land-contended` carry a task and an atomic objective from `running` to `ready`. `object-reported` at `src/domain/external-transition.ts:90` carries `childAggregation: "every-task-terminal-one-done"` and `report-cancelled` at `:180` is `actorKind: "harness"`, so borrowing either would make the audit log claim an aggregation or a report that never happened. `triggerTransition` at `src/domain/node-trigger.ts:135` resolves one trigger to one row, which is why the objective needs its own ids. The `running` to `ready` legality row at `src/domain/transition.ts:136` gains its `objective` column with them: a contended atomic objective must be claimable again, and only these triggers name that row for an objective.

- **The settle takes its actor, and that is what distinguishes a recovered land.** `reportOutcome` passes the authenticated harness actor and the startup reconcile passes `actorKind: "daemon"` with the startup actor, so both events record which one wrote them. The reconcile therefore appends no `recovery.journalReconciled` on the landed row; the other five verdicts keep it.

- **A successful land advances `workspace_branch.head_oid` in the same transaction as the checkpoint.** `worker.md` section 7 states `head` records the current branch head, and section 8 step 7 states the next task starts from the accepted head. The workspace update, the checkpoint insert, the node transition and the event are one storage transaction. A separate update would let the next claim take a stale base.

- **For an internal run the branch record duplicates two facts, and one command owns the agreement.** `origin_oid` repeats `workspace.clone_base_oid`, and `head_oid` is derivable from the objective ref in the bare home. SQLite cannot constrain agreement across two tables, so the land is where the invariant lives and the gate asserts it. Deriving both instead would make every read of a moving head a git call inside a transaction, which `AGENTS.md` forbids.

- **Contention ends the run, and the node repeats under a new claim.** `worker.md` section 8 states a failed swap discards the candidate, repeats the node from the new head, and consumes no attempt. A run's `base` is immutable, so the same run cannot retry against a moved head. The daemon therefore records `outcome = 'cancelled'` on the attempt, ends the run, raises the fence, and returns the node to `ready`. The next claim opens a new run whose `run_base` is the new `workspace_branch.head_oid`. The candidate ref is deleted by `candidate.discard` in the outer command of EPIC 051.4, not here.

- **The contended settle always completes, and the contended outcome is expressed in the outer terminal.** `land.settle:contended` returns ok, and EPIC 051.4's `report-refusal-contended` carries the refusal. A settle that refused would leave the outer with no way to distinguish a failed settle from a lost swap.

- **A crash between the ref move and the transaction is reconciled at startup, not ignored.** The journal row is `open` with its `proposed_head_oid`. `src/commands/startup/reconcile-journal.ts` reads every `open` `merge` row, compares the ref to `proposed_head_oid`, and either completes the row and applies the pending transition, or marks it `discarded`. **The shipped command applies no transition at all** — it completes and discards rows and writes nothing else — so this is new work rather than a parameter change.

- **The journal row carries no checkpoint bindings, and startup derives them rather than storing them.** `git_operation` at `migration-0003-execution-and-journal.ts:127-144` holds no `attempt_id` and no `fence`, and this epic adds no column to it: the table is polymorphic, and a `cut`, `sync` or `publish` row has no run, no attempt and no caller to put in one. `node_id` and `run_id` are already columns, but `listOpen` does not project them, so `src/services/git/journal.ts:58-60` and `OpenJournalRow` gain both. `attempt_id` is the open attempt of the run. **`fence` is `run.fence` read at reconcile time, and that is equal to its value at `land.begin`**: the reconcile runs **because** the settle did not — that is the crash it repairs — so the run is still `active` and its fence still holds the value `land.begin` saw, even though a completed settle would have ended the run and raised it. `src/commands/startup/recover-home.ts:19-22` orders the passes reap, sweep, reconcile, leases, so the one other pass that ends a run runs after reconcile. `lease_fence` on the same row is not this fence; it is the external-drive precondition mode.

- **The `attempt_id` derivation rests on one open attempt per run, and the schema does not enforce it.** `attempt` carries `UNIQUE (run_id, attempt_no)` and no constraint on open attempts, so the guarantee is protocol, not schema. The epic states it rather than assuming it, and the recovery test asserts the derivation picks the attempt the crashed land opened.

## Sequence

This epic draws no diagram. A path is drawn by the story that changes it, under `.agents/plan/authoring.md`. The three land paths are written from nothing, so each ship diagram stands alone with an empty prior set. The composed order is not drawn here, because EPIC 051.4 decides it. The startup reconciliation changes the `merge` path of a shipped command that no epic has drawn, so its story draws the pair: a `baseline-` diagram with a citation per step, and the ship diagram that replaces it. EPIC 051 Story 8 draws the `cut` path of the same command, and the two are different paths with different prior sets.

### Seam keys this epic introduces

- `land.begin` / `land.settle:accepted` / `land.settle:contended` — nested unit functions injected into `AcceptExecutionDependencies`. EPIC 051.4 orders them; this epic draws each unit's own path.
- `git.refUpdate` — present since EPIC 006. **No diagram of this epic draws it**: the compare and swap is EPIC 051.4's step. Its `:land` label there is a call-site name, which `.agents/plan/authoring.md` refuses; the projection must name a value the call receives, and `ref` is the one available.
- `execution.writeCheckpoint(transaction, input): CheckpointRow` — new method on `Execution`.
- `execution.stampRunHead` — present in `Execution`; the accepted settle stamps the landed head, and the recorder gains its missing `runId` projection.
- `execution.closeAttempt` — present in `Execution`. It keeps its shipped `attemptId` projection, because six authored diagrams already draw `execution.closeAttempt:A`; the outcome is asserted by test and not by label.
- `plan.setWorkspaceBranchHead` — declared by EPIC 051; this epic is its first caller.
- `journal.open:merge`, `journal.complete:landed`, `journal.discard:contended` — present in `GitJournal`. `open` projects `intent`; `complete` and `discard` project `outcome`, because `CompleteJournalRowInput` and `DiscardJournalRowInput` carry no `intent` and adding one for a label is refused.
- `storage.transact` — present since EPIC 050; unlabeled, appears once per diagram because each nested unit opens exactly one transaction.

## Stories

Each entry is a name and the output it contributes. The story file holds the change, the tasks and the diagrams, and it declares its kind.

1. **Migration 14.** Add `src/services/storage/migration-0014-checkpoint.ts` at version `14`, with its statements in this order: `CREATE UNIQUE INDEX attempt_id_run_id ON attempt (id, run_id)`; create `checkpoint` with the enumerated columns, CHECK clauses and the composite attempt foreign key, with `caller` and `subject` nullable; add the `workspace_branch` delete trigger. Register it in `src/services/storage/migrations.ts`. `story-foundation`.

2. **The checkpoint row.** Add `src/domain/checkpoint.ts` with `checkpointRow` and one refine per CHECK, and register `checkpoint: checkpointRow` in `src/domain/rows.ts`, which is what `src/services/storage/schema-parity.test.ts:90` then covers. Add `execution.writeCheckpoint` to the execution store. `story-foundation`.

3. **The land opens its journal row.** Add `src/commands/checkpoint/land-execution.ts` and draw `land-begin`: one transaction inserts the `open` `merge` row and commits, and the caller then performs the compare and swap outside every transaction. `story-implement`.

4. **The accepted settle.** Draws `land-settle-accepted`: one transaction writes the checkpoint, advances `workspace_branch.head_oid`, closes the attempt, stamps the run head, ends the run, records the node transition, appends `outcome.reported` and `run.ended`, and completes the journal row. It adds the `objective-land-accepted` trigger for an atomic objective. `story-implement`.

5. **The contended settle.** Draws `land-settle-contended`: one transaction discards the journal row, cancels the attempt, ends the run, returns the node to `ready` and appends `run.ended`. It adds the `land-contended` and `objective-land-contended` triggers and sets the `objective` column of the `running` to `ready` legality row. `story-implement`.

6. **Startup reconciles an open `merge` row.** Extend `listOpen` at `src/services/git/journal.ts:58-60` and `OpenJournalRow` to project `run_id` and `node_id`, extend `ReconcileJournalDependencies` with `execution` and `plan`, and apply the settle for a `merge` row whose ref reached `proposed_head_oid`: derive `attempt_id` from the open attempt of the run and `fence` from `run.fence`, then write the checkpoint, advance the head, record the transition and the event, and complete the row. `story-implement`.
