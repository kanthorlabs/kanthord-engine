# EPIC 022 — Project-scoped graph read

Status: **draft**.

## Goal

A `human` or a `harness` reads one project's topology without reading every other project. Two routes close the epic. `project.nodes` at `GET /v1/project/:id/node` returns the node list of one project, in the body shape `node.list` already returns. `project.graph` at `GET /v1/project/:id/graph` returns one atomic snapshot of that topology — every node, every edge and the topology revision, read in one transaction — in the wire shape `{ attributes, options, nodes, edges }`. The serialization runs inside `services/graph`, which builds the value through `graphology` and therefore validates it by construction. The epic also closes on `kanthord project node` and `kanthord project graph`.

## Non-goals

- **No filter on either route.** EPIC 018 owns the query mechanism (`018-claim-and-lease.md:125`) and binds it to both routes after it lands. This epic ships two unfiltered reads and the index those filters will need.
- **No pagination.** `plan.export` already returns every document of a project, including every `depends_on` list, with no cursor. This epic adds no new scale class. See the size decision below.
- **No write.** Both routes are `GET`, both take `idempotency: "none"` by the table at `docs/proposal/api/README.md:122-126`, and neither opens a write transaction.
- **No revision parameter.** A historical graph is not in the rows; it is the `accepted_blob` of the revision. `plan.export` and `blob.show` already serve it. Neither route accepts `?revision=`.
- **No new prose.** Neither route returns `instruction` or `acceptance`. `node.show` is the body read, per `docs/proposal/api/graph.md:103`.
- **No containment edge.** `docs/proposal/api/graph.md:123` decides that containment is not an edge. `project.graph` carries `parentId` as a node attribute and mints no synthetic edge.
- **No change detection.** No `ETag`, no projection token and no delta read. Recorded under Open items, with the use case named.
- **No subtree route.** `GET /v1/node/:id/graph` is not declared here. Recorded under Open items.
- **No change to `node.list`.** The global route keeps its path, its body and its actor set.

## Decisions

These are settled here. No story revisits one.

- **Atomicity is why `project.graph` exists.** One round trip and one adapter-free document are conveniences. The capability a client cannot rebuild is consistency: `project.nodes` followed by `edge.list` is two transactions, and a node write between them returns a node set and an edge set that describe two different topologies. `project.graph` reads the nodes, the edges and the revision in **one** read transaction, so every member of one response describes one state. The contract states this, and the route exists for it.
- **The two node routes serve two different reads, and both keep their filters.** `node.list` is the cross-project overview: it answers "what is happening across every project", and `project` stays one of the five filters `018-claim-and-lease.md:125` and `docs/proposal/api/graph.md:107` declare. `project.nodes` is the per-project read, and it is where the richer filter set goes. They are not two spellings of one question, and the earlier draft of this epic was wrong to treat them as such. The difference is not aesthetic and it is not the path: **a filter on `node.list` runs over a full-table read, and a filter on `project.nodes` runs over an indexed project range.** `PlanStore.readAllNodes` at `src/services/plan/sqlite.ts:181` is `SELECT ... FROM node ORDER BY id ASC` with no predicate, and `018-claim-and-lease.md:125` filters the returned array in the query layer. That is correct for an overview of a bounded set and it does not survive a rich filter over a large one. `edge.list` already sets the path-scoped precedent at `GET /v1/project/:id/edge` (`graph.md:21`).
- **The scoped read is only scoped once the index exists, and this epic adds it.** `node` carries **no index at all** today: the only three indexes in the schema are on `event`, from `migration-0004-event-indexes.ts:7-9`. So `readGraph` at `src/services/plan/sqlite.ts:147`, `SELECT ... WHERE project_id = ? ORDER BY id ASC`, is a full table scan followed by a sort, and the edge half at `:151` scans `edge` to join. Without an index `project.nodes` has the same cost profile as `node.list`, and the reason the route exists is unfulfilled. Migration 0008 therefore creates `node_project` on `node (project_id, id)` and `edge_from_node` on `edge (from_node, to_node)`. The first turns the project read into an index range scan that is already in `id` order, so the `ORDER BY` becomes free. The second serves the edge half of `readGraph` and `edge.list`. **This is the smallest change that makes the design claim true**, and it is in this epic rather than deferred because a route justified by an access path should ship with that access path.
- **EPIC 018 binds its filter story to both routes, and it changes how `project.nodes` filters.** `018-claim-and-lease.md:125` declares five filters over an in-memory array. That stays correct for `node.list`. For `project.nodes` the same five names, minus `project` which the path carries, become **SQL predicates in `services/plan` over the `node_project` index**, so a filtered project read never materializes the whole table. EPIC 018 owns the story and this epic owns the amendment text that splits it. `docs/proposal/api/graph.md:107` keeps its five names and gains one sentence naming the split.
- **The operation ids follow the `project.repositories` precedent.** A read of a subresource under a project is named for the subresource: `project.nodes` and `project.graph`, beside `project.repositories` at `src/http/contract/project.ts:138` and `project.status` at `:150`. `node.list` stays the name of the global route.
- **Both operations live in `src/http/contract/graph.ts` and in `docs/proposal/api/graph.md`.** The domain is the DAG, not the project. `docs/proposal/api/README.md:39` assigns the DAG to `graph.md`, and `project.status` is in `project.md` because it is a project roll-up rather than a topology read.
- **The wire shape is kanthord's, and it coincides with the graphology serialized format.** The contract owns `{ attributes, options, nodes, edges }` by declaring it in zod and in `graph.md`. It is not "whatever this graphology version exports". The daemon builds the value through `graphology` because that validates the document by construction — a document graphology built is a document `graphology.import` accepts — and then rebuilds it in an order and a key set the contract fixes. A graphology major version that changed its export shape would be a **build failure in one file**, never a silent `/v1` change. That is the whole reason the rebuild step exists.
- **The bytes are canonical, at three levels.** Top-level key order is `attributes`, `options`, `nodes`, `edges`. `options` is `allowSelfLoops`, `multi`, `type`. A node is `key`, `attributes`; an edge is `key`, `source`, `target`, `attributes`. The `nodes` array sorts bytewise by `key`, the `edges` array sorts bytewise by `key`, and **every attribute record emits its keys in bytewise-sorted order**, so an insertion order cannot reach the response. `AGENTS.md` requires the same input to produce the same bytes, and outer key order alone would not have delivered it.
- **`project.nodes` returns `nodeListResponse`, unchanged.** The item shape at `src/http/contract/graph.ts:108-122` already carries `projectId`, and it stays. One shared schema means a client renders both routes with one function.
- **Order is bytewise by identity, asserted, and the store already delivers it for nodes.** `readGraph` at `src/services/plan/sqlite.ts:147` ends in `ORDER BY id ASC`, and SQLite compares a `TEXT` column under `BINARY` collation by default, which is bytewise. `listProjectNodes` therefore asserts that order rather than re-sorting it. Edges come back ordered by `from_node, to_node` at `:151`, which is not edge-id order, so `Graph.serialize` sorts them by `key`. The guarantee is asserted at the route either way.
- **An unknown project is `404 not-found` on both routes**, through the `ListEdgeError("project-not-found")` pattern at `src/queries/edge/list-edge.ts:11-21`. An empty project is `200` with an empty node list and an empty edge list. The project row is the existence check, and a project with no revision is a legal empty graph.
- **The shared projection lives in `domain/`, and it is not a query importing a query.** `eslint.config.js:172-182` permits `queries/` to import `domain/` and a service interface, and nothing else. So `toNodeListItem` of `src/queries/node/list-node.ts:32-44` moves to `src/domain/node-view.ts`, which is pure and consumes the `StoredNode` already declared at `src/domain/plan-graph.ts:3`. Both queries import it from there. A duplicated projection was the alternative and it is refused: two copies of one response shape drift.
- **`serialize` is on `services/graph` by choice, and the choice is stated.** The one-import assertion at `src/services/graph/graphology.test.ts:277` forbids the vendor anywhere else, but a hand-built plain object would need no vendor at all, so the seam is not forced and this epic does not claim it is. The service is chosen because building through `DirectedGraph` rejects a malformed document at construction time, which a hand-built object literal would not. The transport concern stays in `http/contract/graph.ts`, which declares the schema the handler formats against.
- **The attribute sets are exact in the contract, and generic in the service.** `services/graph` stays an algorithmic capability: it takes `GraphAttributes`, a `Readonly<Record<string, string | number | boolean | null>>`, and it knows no node kind. The **contract** declares three `z.strictObject` schemas by name — `graphAttributes` is `{ projectId, revision }`, `nodeAttributes` is `{ kind, title, state, blockReason, discardReason, parentId, repositoryId }`, `edgeAttributes` is `{ relation, waivedAt }` — so a misspelled or missing attribute fails `npm run verify` at the schema, not at review. A generic record alone would have enforced nothing.
- **`serialize` declares behaviour for every input its types admit.** `GraphErrorCode` at `src/services/graph/index.ts:10` gains `graph-duplicate-edge` and `graph-self-loop`. `serialize` throws `graph-duplicate-node` on a repeated node key, `graph-unknown-node` on an edge naming an absent node, `graph-duplicate-edge` on a repeated edge key **and** on a second edge between one ordered pair, and `graph-self-loop` when `source` equals `target`. No `graphology` exception escapes the capability, and each of the five classes is asserted.
- **An edge points from the dependent to the dependency, and the relation is named in the document.** `source` is `edge.fromNode` and `target` is `edge.toNode`, which is what `edge.list` returns, so the two routes never disagree about one edge. That direction is the reverse of the precedence convention a generic topological sort assumes, so the edge attribute set carries `relation: "depends-on"` as a literal, and `graph.md` states in one sentence that a topological order of this graph is reverse execution order. Naming the relation in the document is what makes a generic client correct; a direction flip would have made `project.graph` and `edge.list` disagree about the same row.
- **`revision` is the topology revision, and it does not version the response bytes.** `PlanStore.newestRevision` advances on an import and on a node write. Node `state`, `blockReason`, `discardReason` and `waived_at` move without a new revision, so two responses can carry one `revision` and differ. The contract says exactly that, in one sentence, beside the attribute. The name stays `revision`, because `planExportResponse.revision` at `src/http/contract/graph.ts:38` is the same value and a client passes it back as `fromRevision`; a second name for one value would be worse than a documented one.
- **`repositoryId` is a node attribute.** A viewer groups objectives by repository, and without it that grouping costs one `node.show` per objective. It is a stored column on the node row, so it needs no join. The repository **name** is not in the document: resolving it is a second read, `node.show` already serves it, and no route returns a name where an id is enough.
- **Size is bounded by the same assumption `plan.export` already runs under.** `017-per-node-graph-write.md:44` bounds one project at 2000 nodes, and the edge count is bounded by that node count times the per-node `depends_on` list, which a hand-authored plan keeps small. `plan.export` already renders every node and every dependency list of a project in one unpaginated response, and `plan.import` already accepts one. `project.graph` is a smaller document than the export of the same project, because it carries no prose. This epic therefore adds no new scale class and declares no new bound. **If a bound is ever needed it belongs on the plan, not on this read**, and it is one decision for `plan.import`, `plan.export` and `project.graph` together.
- **`project.nodes` is `["human", "harness"]` and `project.graph` is `["human"]`.** A harness reads nodes today through the global unfiltered `node.list`, so a project-scoped node read is strictly less authority and it is a real least-authority improvement. `project.graph` is not less: it adds the edge set, the waiver timestamps and the revision. No harness workflow consumes the whole edge set — readiness is computed daemon-side and a harness claims a `ready` task — so the graph read stays human until an epic names the workflow. **This epic therefore edits two pinned lists by one name each**: the named harness set of `015-actor-identity.md:111` in `src/http/contract/registry.test.ts` and the registry-wide harness set of `020-wiring-and-scenarios.md:47-48` in `src/http/contract/authorization.test.ts` each gain `project.nodes` only.
- **The CLI reaches both routes and nothing else.** `kanthord project node` and `kanthord project graph`, under the existing `project` group, beside `project repository` at `src/cli/project/repository.ts:29`. Each takes `--id <id>`, which is what every other `project` subcommand takes.
- **`project graph` prints its own canonical representation, not the response bytes.** It parses the body, validates it against `projectGraphResponse`, and prints `JSON.stringify(body, null, 2)` plus one newline. Two byte contracts exist and they are separate: the daemon owns the response bytes, and the CLI owns a pretty-printed rendering of the parsed value. The command does not claim to echo the wire bytes, and the test asserts the CLI form.
- **This epic is sequenced after EPIC 021 and before EPIC 023.** A `phase-1` `routed` surface must be in the acceptance run that closes phase 1b, and the authorization sets EPIC 020 pins must be final when EPIC 025 asserts them. Landing after the acceptance run would mean the run certified a route set the product does not ship. EPIC 025 therefore covers both routes in its inventory, and this epic lands after EPIC 020 so the authorization edit is a one-name addition to a list that already exists.

- Migration 0008 applies on a database migrated to version 7 that holds nodes and edges in two projects. Every row survives, `PRAGMA foreign_key_check` returns no row, and `PRAGMA index_list` on `node` and on `edge` names the new index once each.

A recording `Storage` fake counts `transact` calls for one `showProjectGraph` invocation and asserts exactly one, and asserts that all three reads carry the same transaction object.
- Two calls to `project.graph` on an unchanged graph return byte-identical bodies, compared through `Buffer.compare` on the raw response text.

## Open items

- **Change detection for a long-lived view.** A dashboard polling `project.graph` cannot tell a state-only change from no change, because `attributes.revision` moves only on a topology write, so it re-downloads the whole document on every tick. The answer is an `ETag` over the canonical response bytes with `If-None-Match`, or a projection token that advances on any node or edge row change. It is the most useful unserved case of the eight considered, and it is a transport decision that touches every `GET`, so it belongs in its own epic rather than in this one.
- **A subtree graph.** `GET /v1/node/:id/graph`, returning the containment subtree under one initiative or one objective in the same format. At the 2000-node bound a whole-project document is servable, so this is a convenience rather than a limit.
- **A harness workflow for `project.graph`.** If one is named, the route moves to `["human", "harness"]` and that epic owns the two pinned-list edits.
- **The repository name in the graph.** The document carries `repositoryId`. A viewer that wants the name resolves it through `repository.list` once, or a later epic adds a name map to `attributes`.
- **A plan size bound.** `plan.import`, `plan.export` and `project.graph` all render a whole project unpaginated. One bound covering the three is one decision, and it is not this epic's.
