# EPIC 050.1 — The node lease removal

Status: **draft**. It follows EPIC 050 by sequence order, and it runs before EPIC 051. It consumes EPIC 050's run, fence and exclusion rules.

It carries a decimal number because EPIC 051 through EPIC 057 are authored and numbered, and renumbering them to insert a whole-number epic would break every cross-reference between them.

## Goal

One exclusion mechanism remains, and it is the run:

- the node rows of the `lease` table are gone, and `lease` holds `subject_kind = 'repository'` alone;
- a plan write refuses while an active run covers the affected graph, replacing the lease guard that refused it before;
- startup recovery and actor revocation end runs instead of clearing node leases;
- every one of the twenty-four production readers of a node lease has a stated disposition.

**This epic changes no wire shape.** EPIC 050 settled the worker protocol: the response fields, the event catalogue and the capability name are already final. A client cannot observe this epic, and it therefore retires no capability, declares no capability, and moves no major version. That is the point of doing it second.

## Non-goals

- **No repository-lease removal.** `subject_kind = 'repository'` stays, with every column, every caller and its fence semantics. `src/commands/repository/**` is untouched.
- **No actor removal.** The actor and its token stay. `revoke-actor.ts` changes only where it expires that actor's node leases.
- **No new exclusion rule.** `subtreeExclusion` of EPIC 050 is the rule. This epic gives it a second caller and deletes the mechanism it replaces.
- **No wire change.** No request field, response field, error code, event type, operation id or capability name changes. `KANTHORD_VERSION` moves by patch only.
- **No checkpoint, no workspace, no grant.** EPIC 051 and EPIC 055 own those.

## Decisions

- **A plan write refuses while an active run covers the affected graph, and the affected graph is stated per command.** The node lease guards more than a claim: `src/services/plan/sqlite.ts:549-558` exposes `leaseHeld`, and five commands refuse a plan mutation on a leased node. `assertRunAuthority` does not cover that case — it constrains a worker writing inside its own run, not a human editing a node another worker holds. Deleting the lease without this rule drops the guard silently.

  The guarded set is not "the node id in the request". It is stated per command, and it is the union of the graph before the mutation and the graph after it:

  | command        | guarded set                                                                                                                |
  | -------------- | -------------------------------------------------------------------------------------------------------------------------- |
  | `create-node`  | the parent, and the parent's ancestors                                                                                     |
  | `update-node`  | the node, and its ancestors                                                                                                |
  | `delete-node`  | the node, its ancestors, and its whole subtree                                                                             |
  | `unblock-node` | the node, and its ancestors                                                                                                |
  | `import-plan`  | every node in the submitted set, every one of their ancestors, and every node the import deletes together with its subtree |

  A descendant is included wherever the mutation changes it; an ancestor is included everywhere, because a run over an ancestor covers the whole subtree by EPIC 050's rule.

- **`runCoversNode` is a read on the plan store, it runs in the caller's transaction, and it is deterministic.** `runCoversNode(transaction, nodeIds)` reads every `active` run whose `expires_at` is null or greater than `now` over the supplied set, over every ancestor of that set and over every descendant of it, and returns one refusal or `null`.

  It runs inside the same `storage.transact` as the mutation. `services/storage` opens `BEGIN IMMEDIATE`, so a claim that opens a run and a plan write that reads coverage serialise, and neither sees a half-written graph. A read in a separate transaction would admit a write against a run opened a microsecond later.

  When several runs cover the set, it returns the one whose node id sorts first bytewise, breaking a further tie by run id, exactly as `subtreeExclusion` does. One input therefore always names the same run.

  The liveness boundary is the boundary of `subtreeExclusion` and of `assertRunAuthority`: `expires_at <= now` is expired, and the caller passes the same `now` it read once at the top of its transaction. A write admitted at that instant is safe because the same instant refuses the stale worker.

- **The refusal is `subtree-busy`, and no new error code is added.** The plan write and the claim answer the same question about the same graph — is an active run over this node — so they carry the same code and the same details. Adding a `node-busy` that differed only in which operation raised it would put two codes on one condition, and `errorStatuses` would then owe two entries and two details schemas for one meaning. `subtree-busy` is registered by EPIC 050 as a 409 precondition with the details `{ relation, nodeId, runId, expiresAt }`, and this epic adds it to the error union of the five plan operations and nothing else.

  `lease-held` is removed from every node operation's error union. It survives only where a repository lease raises it. Its details schema at `src/http/contract/error-details.ts:120-135` is unchanged, because the repository caller still produces both of its `refusal` discriminators.

- **A command never imports a command; `expireRuns` is injected.** The import matrix forbids a command importing another command, and `src/commands/node/claim-node.ts:58-61` already shows the shipped pattern: `sweepExpiredExternalLeases` arrives as a function on the dependencies record, bound in `main.ts`. Startup recovery takes `expireRuns` the same way. EPIC 050 already wired it into four callers this way; this epic adds the fifth.

- **Startup recovery ends expired runs and returns their nodes to `ready`.** `src/commands/startup/recover-expired-leases.ts` scans expired node leases, clears them and returns nodes to `ready`. Its `CANDIDATE_SQL` at `:44-60` and the `expired` scan it depends on at `src/services/lease/sqlite.ts:228-237` are both node-only, so **there is no repository half of this command to preserve** — the file becomes a run recovery outright and is renamed `src/commands/startup/recover-expired-runs.ts`. It calls the injected `expireRuns`, then returns to `ready` every node that is `running` and whose covering run just ended. Repository-lease recovery lives elsewhere and is not touched.

- **An expired run leaves its node `running` until recovery, and a plan write is still admitted.** The two facts are consistent and the epic states so rather than leaving it to be discovered: coverage is a property of the run, not of the node state. A node stuck `running` behind an expired run is editable, because the worker that held it can no longer write — `assertRunAuthority` refuses it at the same instant. Recovery then corrects the node state. A rule keyed on `node.state = 'running'` instead would block edits behind a dead worker until the daemon restarted.

- **Migration `13` deletes every node lease row and narrows the table, and it refuses nothing.** There are no deployments, so there is no node lease worth preserving and no operator to consult. A guard that refused while an owned node row existed would be unrecoverable in practice: `release` nulls the owner rather than deleting the row, a crash leaves ownership behind, and the migration runs while the daemon is stopped — so no worker exists to end the run the guard would demand. The migration therefore does `DELETE FROM lease WHERE subject_kind = 'node'` and rebuilds the table with `CHECK (subject_kind = 'repository')`, dropping the two-value CHECK. Adding a CHECK requires the rebuild; the table has no index to recreate.

- **The `Lease` interface becomes repository-only in its types, not merely in its data.** Narrowing the database while `LeaseSubjectKind` still admits `"node"` leaves the node-lease capability expressible in TypeScript and failing only at runtime against a constraint. `subjectKind` becomes the literal `"repository"` across `src/services/lease/index.ts` and `sqlite.ts`, so a node-lease call stops compiling. `src/domain/lease-hierarchy.ts` and `liveLeaseRefusal` are deleted whole, and the hierarchy probe at `src/services/lease/sqlite.ts:92-102` and the node `expired` scan at `:228-237` go with them.

- **The three outcome commands lose their lease guard and gain no replacement.** `aggregate-initiative.ts`, `close-objective.ts` and `report-objective.ts` read a node lease through `liveLeaseRefusal` to refuse while a descendant is held. Each is reached only from `report-outcome.ts`, which already asserts run authority for the caller before it delegates, and each runs inside that same transaction. A second coverage check there would refuse the very run that is reporting. They therefore lose the check outright, and a test asserts each still refuses a caller with no authority, through `report-outcome.ts`.

## Stories

1. **The run-covers-node rule.** Add `runCoversNode` to `src/services/plan/index.ts` and `src/services/plan/sqlite.ts`, taking the caller's transaction and `now`, reading every active unexpired run over the supplied set, its ancestors and its descendants, and returning the `subtree-busy` refusal or `null` with the bytewise tie-break. Add its test against real SQLite asserting each relation, the expiry boundary from both sides, an ended run, the tie-break, and that two array orders give a deep-equal result.

2. **`subtree-busy` replaces `lease-held` on a plan write.** Wire `runCoversNode` into the five plan commands with the guarded set of the Decisions table. Delete `leaseHeld` at `src/services/plan/sqlite.ts:549-558`. Add a case per command asserting the refusal, its details, the guarded set (a run on an ancestor refuses; a run on an unrelated node does not), and that the database is byte-identical.

3. **The four run commands drop the lease.** Delete every node-lease acquire, renew, release and `assertHeld` from `claim-node.ts`, `renew-run.ts`, `release-node.ts` and `report-outcome.ts`, and remove `lease-held` from each refusal union. Add cases asserting each still refuses a stale fence, an ended run and an expired run through `assertRunAuthority` alone.

4. **The three outcome commands lose their lease guard.** Delete the `liveLeaseRefusal` check from `aggregate-initiative.ts`, `close-objective.ts` and `report-objective.ts`. Add a case per command asserting a caller with no run authority is still refused, through `report-outcome.ts`.

5. **Startup recovery ends expired runs.** Rename `recover-expired-leases.ts` to `recover-expired-runs.ts`, take `expireRuns` as an injected dependency, and return to `ready` every `running` node whose covering run just ended. Bind it in `main.ts`. Add cases asserting a crashed run is ended at startup, its fence rose by one, its node is `ready`, and a repository lease row is untouched.

6. **The three run-derived readers.** Change `revoke-actor.ts` to end that caller's active runs, `read-status.ts` to project expired runs over its shipped response shape, and `readiness/dependency.ts` to read runs. Add a case per file, including one asserting `revoke-actor` leaves another caller's runs active.

7. **Delete the lease hierarchy and narrow the service.** Delete `src/domain/lease-hierarchy.ts`, the hierarchy probe and the node `expired` scan. Narrow `subjectKind` to the literal `"repository"` in `src/services/lease/index.ts` and `sqlite.ts`. Swap the `lease` blocker of `readSubtreeExecutionFacts` for a `run` blocker in `src/domain/plan-graph.ts`'s closed `executionBlockers` list and in the store.

8. **Migration 13.** Add `src/services/storage/migration-0013-repository-lease.ts` at version `13`, deleting every `subject_kind = 'node'` row and rebuilding `lease` with `CHECK (subject_kind = 'repository')`. Add its test asserting the node rows are gone, every repository row survives with its fence unchanged, and an insert with `subject_kind = 'node'` is refused.

9. **The proposal records one mechanism.** Amend `docs/proposal/phase-2/runs-and-exclusion.md` with the run-covers-node rule, the guarded set per command and the `subtree-busy` refusal on a plan write. Amend `docs/proposal/database/lease.md` to state the table holds repository subjects only, and update its DDL fence. Move `KANTHORD_VERSION` to `28.0.1` — a patch, because no wire shape changes.

Hermetic coverage required beyond the Proof:

- **The removal is proven by construction, over the whole tree.** A test enumerates every production file that references the lease capability — by the identifiers `subjectKind`, `subject_kind`, `Lease`, `leaseHeld` and `liveLeaseRefusal`, not by one SQL literal — and asserts the set is exactly `src/services/lease/**`, `src/commands/repository/**` and `src/main.ts`. `src/services/lease/**` is inside the assertion, not excluded from it, because that is where a stale node path would survive.
- The `Lease` interface admits no node subject **at the type level**. A fixture file that calls `lease.acquire` with `subjectKind: "node"` is asserted not to typecheck, through the existing lint or typecheck harness rather than a runtime assertion.
- `src/domain/lease-hierarchy.ts` is absent, asserted by a directory listing rather than by an import that would fail to resolve the test itself.
- A plan write on a node covered by an active run refuses `subtree-busy`, and the details name the covering node, its run id and its `expires_at`. One case per command, five commands.
- The guarded set is proven per command: a run on an **ancestor** refuses each of the five; a run on an **unrelated** node refuses none; and a run on a **descendant** refuses `delete-node` and `import-plan` and no other. That third case is the one a node-id-only guard would miss.
- A plan write on a node covered by an **expired** run succeeds, and on a node whose run has **ended** succeeds. Both boundaries asserted.
- `runCoversNode` and `assertRunAuthority` share one liveness boundary. For `expires_at` of `now - 1`, `now` and `now + 1`, a test asserts the plan write is admitted exactly when the worker's write is refused. Three iterations, both sides in one case.
- A claim and a plan write on the same node, issued concurrently against one real database, produce exactly one winner and no interleaved state. This proves `BEGIN IMMEDIATE` closes the race the lease used to close.
- A node left `running` behind an expired run still admits a plan write, and the worker that held it is refused at the same instant. Both halves in one case.
- `lease-held` is absent from the refusal union of every node and plan operation, asserted against the exported unions; and a repository operation still raises it, asserted by one case, so the retirement is scoped and not total.
- Exactly one terminal event per ended run still holds after the lease events are gone — asserted for a release, a report, an expiry and a revocation.
- After migration `13`, `SELECT COUNT(*) FROM lease WHERE subject_kind = 'node'` is zero, and every repository row survives with its `fence`, `owner` and `expires_at` unchanged. Both halves asserted against a seeded row.
- `lease` refuses an insert with `subject_kind = 'node'` after migration `13`, asserted against real SQLite.
- A crashed run is ended by startup recovery, its fence rises by exactly one, its node returns to `ready`, and a repository lease row is unchanged. Four assertions, one case, over a real database across a simulated restart.
- Startup recovery is atomic: a failure injected at the node transition leaves the run `active`, its fence unchanged, and no `run.expired` event.
- `revoke-actor` ends every active run whose worker is that caller and leaves every other run active. Both asserted.
- `declaredCapabilities` is **unchanged** by this epic, asserted by value against EPIC 050's four names. No capability is retired and none is declared, which is the assertion that this epic is wire-invisible.
- `KANTHORD_VERSION` is `28.0.1`, and the compatibility record gains no row.
