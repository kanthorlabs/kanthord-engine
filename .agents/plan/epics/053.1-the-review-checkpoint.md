# EPIC 053.1 — The review checkpoint

Status: **draft**. It follows EPIC 053 by sequence order, and it runs before EPIC 054. It consumes EPIC 051.3's `checkpoint` table and `execution.writeCheckpoint`, EPIC 051.4's report route, EPIC 052.1's structural member as the precedent for a new report member, and EPIC 053's parent-objective aggregation.

It carries a decimal number because EPIC 054 and every whole number after it are already authored.

**Dispatch prerequisite.** EPIC 053 ships before this one. Story 1 inserts `"053.1"` into `scripts/epic-sequence-range.ts:1` — `authoredEpics` after `"053"`, and Story 10 appends it to `shippedEpics`, which `test/sequence/conformance.test.ts:254` — `shippedEpics` requires to stay a prefix of `authoredEpics`. Story 10 is therefore last in dispatch order.

**It holds ten stories, which is the cap.** The review claim is in it because `src/commands/node/claim-node.ts:210` — `review-head-unavailable` refuses every review claim, so without the lift no review run exists and nothing can produce the report this epic accepts.

## Goal

A verdict is evidence, bound to the commit it judged:

- a review claim is admitted, and it opens a `review` run that pins no oid and writes no base;
- a review report carries a verdict, a judged checkpoint reference and an optional reason;
- the daemon refuses a judged checkpoint that is not the newest accepted execution checkpoint of a node the review node depends on;
- the attestation stores the checkpoint reference and copies its oid, so a reader needs no join;
- the review node reaches `done` for `accept` and for `reject` alike, because its state comes from its own accepted report and never from the verdict;
- accepting an attestation lands no artifact, and the verdict changes no other node's state, while the review task's ordinary parent aggregation may move its parent objective.

## Non-goals

- **No reviewer.** Nothing produces a verdict here. A test supplies one. The `re@1` adapter is EPIC 106.
- **No reviewer-mutation detection.** `worker.md:735` states the daemon detects none at a review checkpoint. The epic states the limit and adds no check.
- **No migration.** EPIC 051.3's migration `14` creates `verdict`, `judged_checkpoint_id`, `judged_oid` and `reason_blob` with the named CHECKs `checkpoint_review_verdict` and `checkpoint_review_judged`, per `.agents/plan/epics/051.3-the-checkpoint-and-the-land.md:29` — `checkpoint_review_verdict`. This epic is a writer over that table and adds no column.
- **No objective review node.** `worker.md:89` legalises `(objective, review)`, whose state owner is an attestation and then a human. Such a node reports through the `attested` member and reaches `awaiting_approval`, and this epic writes no review checkpoint for it. The epic that adds the review attestation to the objective branch owns it, and `worker.md:449`'s `done` sentence stays true for it through EPIC 056's close.
- **No aggregation change.** EPIC 053 owns every parent transition, and a review report is an ordinary task report to it.
- **No `run.judged_oid` writer.** The column stays null for every review run, and `.agents/plan/epics/057-non-null-enforcement-and-legacy-removal.md:23` names `fence`, `agents_json`, `expires_at` and `max_lifetime_at` as the four run columns it tightens, so a null `judged_oid` stays legal after migration `18`.
- **No approval evidence bundle.** `node.approvalEvidence` stays `stubbed`. EPIC 112 owns it.

## Decisions

- **The report names the judged checkpoint, and the claim pins nothing.** This is the ruling EPIC 051.4 asked EPIC 053 for, and its ask is deleted from that epic because this Decision answers it. `worker.md:447` states it directly: a review checkpoint is bound to the pinned commit it judged, and **the report names the checkpoint it judged**. `.agents/plan/epics/050.1-the-claim.md:34` — `judged_oid` assumed the pin happened at claim, and it deferred the lift to the epic that establishes a workspace head. That assumption is what `worker.md:447` overrules: the binding is a checkpoint reference on the attestation, not an oid on the run, so no head has to exist at claim time.

- **The retrospective selection is closed by a newest-accepted rule, not by the claim.** Naming the checkpoint at report would let a reviewer choose an older accepted checkpoint of the same dependency after a re-run, which is the risk EPIC 051.4's deleted ask named. The daemon therefore refuses `judged-checkpoint-superseded` unless the named checkpoint is the newest accepted execution checkpoint of its own node. EPIC 056 uses the same idiom for the close, refusing `checkpoint-stale` when the named checkpoint is not the latest accepted one, so the product states one rule twice and not two rules.

- **A review claim of a task is admitted, and it writes no base and no candidate.** `src/commands/node/claim-node.ts:210` — `review-head-unavailable` is **narrowed** to `runKind === "review" && node.kind !== "task"`, not removed. `src/domain/node-pair.ts:43` — `review` also legalises `(objective, review)` with the state owner `attestation-then-human`, and its claim trace differs, so a plain removal would admit a second path this epic does not draw. EPIC 053.2 removes the surviving term with the objective attestation lifecycle. `.agents/plan/epics/050-the-run-the-fence-and-exclusion.md:34` — `runBaseRow` fixes the cardinality at exactly none for a `review` run, so the claim writes no `run_base` row, and `worker.md:562` states a review node pushes no candidate, so it cuts no candidate ref. The refusal code stays in `src/http/contract/errors.ts` and `src/cli/exit-code.ts` and becomes unreachable from `claim-node.ts`; removing the code would be a wire change for no product gain, and `docs/proposal/api/README.md` governs a removal.

- **A review node names what it judges through `depends_on`.** A review node is atomic and holds no child, so its own subtree can never contain an execution checkpoint. `worker.md:447` states `depends_on` is what connects a verdict to its subject. A subtree lookup would be unsatisfiable, and an implicit lookup would let the reviewer choose its own subject.

- **Five refusal codes join the contract, and the kind mismatch reuses a shipped one.** `judged-checkpoint-unknown`, `judged-checkpoint-not-execution`, `judged-checkpoint-undeclared` and `judged-checkpoint-superseded` are `409`, beside the state cluster of `src/http/contract/errors.ts:15` — `illegal-transition`. `reason-too-large` is `400`, beside `src/http/contract/errors.ts:8` — `invalid-request`. A `review` member naming a run whose kind is not `review`, and an `accepted` member naming a `review` run, both refuse the shipped `body-kind-mismatch` at `src/commands/outcome/report-outcome.ts:82` — `body-kind-mismatch`, which already carries a member-against-node mismatch. Each new code is added to `src/http/contract/errors.ts`, to `src/cli/exit-code.ts:13` — `exitCodes` and to the operation's `errors` record.

- **The eighth `node.report` member is `review`, and it carries no object id.** `nodeReportRequest` at `src/http/contract/outcome.ts:23` — `nodeReportRequest` gains `{ report: "review", runId, runFence, verdict, judgedCheckpointId, reason? }`. `worker.md:562` states a review node reports an attestation and pushes no candidate, so the member carries neither `objectId` nor the `repositoryId` EPIC 051.4 adds to the `accepted` member. The discriminator is `"review"`, matching the run kind and the checkpoint kind, which is the shape EPIC 052.1 used for `structural`.

- **The review member is a wholly new path, and it supersedes nothing.** `.agents/plan/epics/052.1-the-structural-acceptance.md:25` — `report-checkpoint-gate` records the same ruling for the structural member: a new member is a new path, its prior set is empty and every token of its diagram is `+`. The five shipped members and the structural member keep the tails their own epics drew. A review claim's success path is new for the same reason, because every review claim refused before this epic.

- **The verdict is evidence, and the state comes from the report.** The review arm calls `taskReportEffect` with `outcome: "accepted"`, so the node reaches `done` for `accept` and for `reject` alike, and no code reads the verdict to decide a state. `worker.md:449` states both values deliver the node, and `worker.md:729` places the verdict under "Trusted", so a daemon that acted on it would be verifying it. `objectIdRequired` at `src/domain/outcome-report.ts:32` — `objectIdRequired` is consumed by no production file, so the review arm takes no branch on it; it closes the attempt with `headOid: null` and calls no `stampRunHead`.

- **The attestation stores a checkpoint reference, not a bare oid.** `judged_checkpoint_id` is a foreign key to `checkpoint(id)`, and `judged_oid` is stored beside it, copied from the referenced row inside the same transaction. A bare oid is not repository-qualified and does not name the accepted artifact, and every other reference to a commit in this block carries its repository. The copy is what lets a reader answer "which commit was judged" with no join.

- **`verdict` is a closed enum, and `reason_blob` is a content address.** `verdict` is `('accept', 'reject')`. `reason_blob` is nullable and references `blob(hash)`, like every other prose field in the schema, and the bytes are stored through `blobs.put` at `src/services/blob/index.ts:22` — `put`. `worker.md` does not require a reason, so the field is optional, and a verdict with no stated reason is still a legal attestation.

- **The reason cap is 65536 UTF-8 bytes, measured on the encoded body.** The command refuses `reason-too-large` when `Buffer.byteLength(reason, "utf8")` exceeds `65536`, and the contract declares `reason: z.string().min(1).optional()` with no character cap. A zod `.max()` counts characters, so a character cap would refuse a valid 65000-byte ASCII body and admit a 200000-byte multi-byte one. The blob store hashes bytes, so bytes are the only unit both ends agree on.

- **The check precedes every seam, so the refusal reaches no read.** The size check is pure over the request value, and it runs before the checkpoint read. A body that cannot be stored must not cost a lookup, and the diagram of that path holds no step at all.

- **`acceptReview` is a nested command in the caller's transaction, and it opens none.** It takes the transaction `reportOutcome` already opened, like `src/commands/outcome/report-outcome.ts:59` — `reportObjective` and `:63` — `closeObjective`. A review acceptance performs no git write, so it is not a journaled write and it needs no second transaction. Its diagrams therefore hold no `storage.transact` step.

- **Three read seams join the service interfaces.** `execution.readCheckpoint(transaction, checkpointId)` returns the stored checkpoint row or null. `plan.readDependencies(transaction, nodeId)` returns the node ids the named node depends on. `execution.newestExecutionCheckpoint(transaction, nodeId)` returns the newest accepted execution checkpoint of one node, or null. `plan.readGraph` at `src/services/plan/index.ts:71` — `readGraph` takes a `projectId` the command does not hold, and it returns the whole graph to answer one membership question. None of the three exists, and each is declared with its implementation before a diagram draws it.

- **Accepting an attestation lands no artifact, and the verdict changes no other node's state.** The accepted task report still invokes the parent-objective aggregation EPIC 053 owns, so the parent objective may reach `awaiting_approval`. That effect is identical for `accept` and for `reject`, and it is not derived from the verdict. That is what the daemon can honestly say. It does not follow that the reviewer mutated nothing during its run: `worker.md:735` states the daemon detects no reviewer mutation, and `worker.md:729` places it under "Trusted". The epic records both sentences and derives neither from the other.

- **The refusal order is fixed:** `body-kind-mismatch`, `reason-too-large`, `judged-checkpoint-unknown`, `judged-checkpoint-not-execution`, `judged-checkpoint-undeclared`, `judged-checkpoint-superseded`. **`judged-checkpoint-unaccepted` is not among them.** EPIC 052 Story 5 (`05-the-seams-the-acceptance-needs`) settled that every checkpoint row is an accepted checkpoint, and `checkpoint_execution_accepted_oid` forces `accepted_oid IS NOT NULL` for every execution row, so the condition the code would name cannot arise and no fixture can seed it. The first is decided by the report prelude, the second is pure, and the last five follow the order of the reads that decide them. Precedence is proven by a decision table over every pair that can trigger at once, in `src/commands/checkpoint/accept-review.test.ts`.
