# EPIC 112 — The objective gate and `mr@1`

Status: **ready**.

## Goal

An approved objective lands exactly what the human reviewed. The worker loop of EPIC 110 leaves the objective `running`, and `src/commands/node/freeze-candidate.ts` closes the gate: it reads the workspace head as candidate `C`, records the frozen `candidate` row of `docs/proposal/database/candidate.md` and the transition to `awaiting_approval` in one storage transaction, then runs the authoritative `unit` check against a clean checkout of that exact commit and records the result with `authoritative = 1`. An objective whose every task is `discarded` freezes nothing: the same command moves it to `discarded` with its event in one storage transaction, so no objective of a closed run stays `running`. `src/commands/node/approve-node.ts` integrates it: it takes the repository lease, imports `C` into the bare home, and lands it on `refs/heads/<branch>` by compare-and-swap, as a fast-forward when the landing tip `B` is an ancestor of `C`, and otherwise as a real merge commit `M` that is checked again before the ref moves. A compare-and-swap failure invalidates the check result of the discarded merge commit and recomputes from a fresh read of the tip; a content conflict, and the third failed attempt, move the objective to `blocked` with reason `stale-base` and invalidate the candidate. A failed merge check lands nothing, leaves the objective `awaiting_approval` and answers a refusal naming the failed check, because `docs/proposal/phase-2/integration-and-publish.md` gives `stale-base` to a content conflict and to the retry limit alone. `node.approvalEvidence` and `node.approve` move from `stubbed` to `routed` in `src/http/contract/integration.ts`, `kanthord node approval` and `kanthord node approve` call them, and every landing ref write of this epic runs the outside-writer diagnostic and carries its own `merge` journal row, following the pattern of `.agents/plan/epics/108-freshness-and-reconciliation.md`.

## Non-goals

- No publish and no chaining. EPIC 113 owns `repository.publish`, the `publish` journal row and the rejection classification. This epic records `candidate.publish_requested` and pushes nothing.
- No reconciliation and no freshness pass. EPIC 108 owns `ensureFreshBase`, `reconcileRepository`, the `sync` row, the ancestry classification, `isAncestor`, `worktreeAdd`, `worktreeRemove`, `mergeScratch`, the scratch root, the `intents` filter of the outside-writer diagnostic, `GitJournal.proposeHead`, `SqliteLease` and `SqliteCredentialStore`. This epic calls every one of them and reimplements none.
- No check runner. EPIC 107 owns the timeout, the process-tree kill, the output cap, the filtered environment, the environment identity and the toolchain identity. This epic calls `Verify.run` and persists the returned `CheckOutput`.
- No worker loop, no attempt, no task gate and no per-task diagnostic. EPIC 110 owns all four. This epic adds one injected function to `executeObjective` and reads the rows EPIC 110 wrote.
- No attempt projection of its own. EPIC 111 owns `src/domain/attempt-record.ts`, `buildAttemptRecord`, `parseReviewNdjson`, `ExecutionStore.readAttempt`, `ExecutionStore.listInvocations`, `ExecutionStore.newestRun`, `CheckStore.listByNode` and `CheckStore.listBySubjects`. The evidence query of this epic calls them and declares no second projection, so the `re@1` reason per criterion reaches the human in one shape.
- No initiative end-to-end run. `docs/proposal/phase-2/gates-and-approval.md` defers the detection, so this epic records `not-applicable` for the initiative and executes no command, exactly as EPIC 107 states its caller must.
- No inspection route and no manual control. EPIC 111 owns `node.attempts`, `attempt.show`, `node.checks`, `worker.list` and `node.abandon`, and all five keep `status: "stubbed"` here. `node.unblock` is already `routed`, by `019-outcome-report.md`, and this epic changes it not at all. The evidence query of this epic reads the same rows through the same store methods. **The one exception is the candidate invalidation**, which EPIC 111 owns no mechanism for: this epic owns it and passes it into `abandonNode`.
- No `node.discard` and no `node.waive`. Both are `phase-3` in `docs/proposal/api/outcome.md`. **Phase 2 therefore ships no operation that discards a task**, so a `discarded` task row reaches this epic as fixture data alone: the `partial` projection, the discarded-task list of the evidence and the fully discarded objective are each proven over seeded `discarded` task rows, and `node.approve` keeps the `partial` path routed, because a phase-3 discard must find it working.
- No startup recovery. Phase 3 owns an incomplete `merge` row, a scratch worktree a crash left behind and a lease race, per `docs/proposal/phase-3/recovery.md`.
- No removal of the private candidate ref. `refs/kanthord/candidate/<candidateId>` stays in the bare home forever in phase 2: it keeps the reviewed commit reachable, `gc.auto=0` is pinned by EPIC 006, and phase 3 owns pruning. This epic ships no ref deletion primitive.
- No migration and no new table. `src/services/storage/migration-0003-execution-and-journal.ts` already holds `candidate`, `check_result` and `git_operation`. This epic adds no column and no index.

## Stories

- **The candidate is a domain decision, and it stays pure** — `src/domain/candidate.ts` gains seven pure exports beside `candidateRow`, and it keeps `zod` as its only runtime dependency. `INTEGRATION_RETRY_LIMIT` is `3`: it is the maximum number of compare-and-swap attempts of one approval, and it lives in the domain rather than in `settings`, because `docs/proposal/phase-2/integration-and-publish.md` makes the retry limit the trigger of a `stale-base` block and a per-host value would make a block host-dependent. `candidateRevision(priorCount: number): string` returns `` `cand-${priorCount + 1}` ``, the spelling of the example in `docs/proposal/database/candidate.md`, so the value is a function of the candidate count of that node and never of a clock. `candidateInvalidationReasons` is the frozen tuple `["workspace-moved", "workspace-dirty", "stale-base"]`, and `CandidateInvalidationReason` is its member type. Each reason has exactly one writer in this epic: the approval refusal writes the first two, the `stale-base` block writes the third, and the workspace reset of `abandonNode` writes the first. `CandidateFreeze` is the callable contract of the freeze, `Readonly<{ objectiveId: string; runId: string; leaseFence: number; actor: string; signal: AbortSignal | null }>` as `CandidateFreezeInput` and `Readonly<{ candidateId: string | null; terminal: "discarded" | null }>` as `CandidateFreezeResult`, with `CandidateFreeze` the function type over the two. **The callable contract lives in `domain/` because two commands share it and no command may import a command**; it names no service type, and `AbortSignal` is a global type rather than a runtime dependency, so the purity rule holds. `projectCandidate(taskStates: readonly TerminalState[]): CandidateProjection` calls `aggregate("objective", taskStates)` of `src/domain/aggregation.ts` and returns `Readonly<{ freeze: true; projectedOutcome: "done" | "partial" }>` for `done` and `partial`, and `Readonly<{ freeze: false; terminal: "discarded" }>` for `discarded`, because `objectiveOutcome` of `src/domain/outcome.ts` already sends a fully discarded objective to `discarded` and a discarded objective holds nothing to approve. `aggregate` raises `AggregationError("empty-parent")` for an objective with no task, and the caller lets it propagate.
- **The evidence document is frozen and canonical** — `src/domain/approval-evidence.ts` is pure, imports `zod` and `canonicalJson` of `src/domain/canonical-json.ts`, and exports the schema `approvalEvidenceDocument` and `renderApprovalEvidence(input): Uint8Array`. The document is a strict object of exactly `candidateOid`, `landingBaseOid`, `cloneBaseOid`, `projectedOutcome`, `diffBlob`, `commits` and `discardedTasks`, which is the list `docs/proposal/database/candidate.md` names — the projected outcome, every discarded task with its title and its reason, the diff, the commit list, and the base and head object ids — plus `cloneBaseOid` alone, because the document must name the range of its own `diffBlob`. **It declares no version field and no identifier**, because the row that cites it carries `id`, `node_id` and `run_id`, and this daemon publishes no external evidence format. `commits` is an array of `Readonly<{ oid: string; subject: string }>` in parent-first order. `discardedTasks` is an array of `Readonly<{ taskId: string; title: string; discardReason: string | null }>`, ordered by `taskId` with `comparePaths` of `src/domain/plan-path.ts`, which is the bytewise comparator the plan format already uses. **A discarded task is identified by its node id and reported with its title and its `discard_reason`**, the column `docs/proposal/database/node.md` created for exactly this list, and `discardReason` is null when the row carries none. **The diff travels as a blob hash and never inline**, because `docs/proposal/api/integration.md` states that `blob.show` serves the frozen document and a diff of a whole objective would make one JSON row unbounded. `renderApprovalEvidence` serializes through `canonicalJson` and returns UTF-8 bytes with one trailing LF, so two freezes of one candidate produce identical bytes and one hash. **The document is frozen at freeze time and never derived at approval time**, the rule `docs/proposal/database/candidate.md` states: a title changes on the next import, and the client cannot open the clone.
- **The lease TTL of an integration** — `src/domain/lease.ts` gains the pure `integrationLeaseTtlMs(checkTimeoutMs: number): number`, which returns `checkTimeoutMs * INTEGRATION_RETRY_LIMIT + RECONCILE_LEASE_MARGIN_MS`, beside the constants of EPIC 108 and EPIC 110. One approval runs at most `INTEGRATION_RETRY_LIMIT` attempts and at most one check per attempt, so the holding covers the whole operation and `RECONCILE_LEASE_MARGIN_MS` of `600_000` covers the git calls and the closing transactions. The TTL bounds nothing at run time: it is what `system.status` reads to call a holding stale.
- **Four git primitives: two reads, one clean checkout, and the candidate import** — `src/services/git/workspace.ts` gains three primitives beside the three of EPIC 110, each through the `GitRunner` of `src/services/git/run.ts`, so each carries the pinned invocation, the supervised spawn and the output cap of EPIC 006. `workspaceClean({ workDir })` runs `git -C <workDir> status --porcelain -z` and returns true on empty stdout. `diffRange({ workDir, fromOid, toOid })` runs `git -C <workDir> diff <fromOid> <toOid>` and returns the stdout as UTF-8 bytes; a diff over `DEFAULT_OUTPUT_LIMIT_BYTES` of `1_048_576` raises a `GitError` from the runner whose `failure` is `"output-exceeded"`, and the primitive never truncates. **The primitive raises the git failure and the freeze translates it**, so the service holds no command vocabulary; story five names the one `catch` that turns that failure into `FreezeCandidateError("diff-too-large")`. `commitList({ workDir, fromOid, toOid })` runs `git -C <workDir> log --reverse --format=%H%x00%s%x00 <fromOid>..<toOid>`, splits the stdout on the NUL byte, drops the trailing empty segment, and returns `readonly Readonly<{ oid: string; subject: string }>[]` in that order; `%x00` is required because a subject holds no NUL byte and may hold anything else. `src/services/git/candidate.ts` exports `importCandidate(runner, input: Readonly<{ gitDir: string; workDir: string; branch: string; candidateId: string; pidFile: string }>)`, which runs `git --git-dir=<gitDir> fetch --no-tags --no-write-fetch-head <workDir> +refs/heads/<branch>:refs/kanthord/candidate/<candidateId>` and then `git --git-dir=<gitDir> rev-parse refs/kanthord/candidate/<candidateId>`, and returns `Readonly<{ oid: string }>`. It contacts no network and passes no credential, because the source is a local directory this daemon created. **It passes `pidFile` to the `GitRunner` on both invocations**, so the launcher writes the process id before it `exec`s git and the reap of EPIC 007.5 identifies the child; `docs/proposal/database/git_operation.md` requires that a spawn be identified before it starts, and it states that a spawn the closed `intent` set cannot journal is recorded by its pid file alone. **It writes exactly one ref, in the private namespace `refs/kanthord/candidate/*`**, so it never writes `refs/heads/*` and never `refs/remotes/*`, and the fetch confinement of EPIC 006 stays the rule for the one remote fetch. Every new primitive reaches `Git` in `src/services/git/index.ts` and binds in `src/services/git/binary.ts`.

- **The freeze is the last step of the objective loop** — `src/commands/run/execute-objective.ts` of EPIC 110 gains one injected dependency, `freezeCandidate: CandidateFreeze` of `src/domain/candidate.ts`, and `src/main.ts` binds this epic's command into it, because `AGENTS.md` forbids a command importing a command. **The type comes from `domain/` and never from the command file**, so the loop names no export of `src/commands/node/freeze-candidate.ts` and the boundary rule holds for the type as well as for the value. The story that closes the objective run keeps its transaction unchanged, and the loop calls `freezeCandidate` **after** that transaction and **before** the `finally` that releases the node lease, with the objective id, the closed run id, the acquired fence, the configured actor and its own run signal. **The call happens when that closing transaction observed every task of the objective terminal**, which is the `outcome: "done"` path and the path where every task is `discarded`; an objective holding a `blocked` or `ready` task closes with `outcome: "blocked"` and calls the freeze zero times, which is what keeps `blocked` out of the gate. A `FreezeCandidateError` and a `GitError` from the freeze leave the objective `running` and take the run-ending path of EPIC 110: the lease is released and the next `run.start` resumes the objective, walks no task, and freezes again. **The freeze is idempotent by re-execution**, because it re-reads the state and a `running` objective is the one state it accepts.

- **The approval refuses before it touches git** — `src/commands/node/approve-node.ts` exports `approveNode(dependencies, input)`. The dependencies are `Readonly<{ storage: Storage; git: Git; journal: GitJournal; verify: Verify; candidates: CandidateStore; checks: CheckStore; plan: PlanStore; workspaces: WorkspaceStore; blobs: BlobStore; leases: Lease; events: EventLog; ids: IdGenerator; clock: Clock; acceptsWork: (transaction: Transaction, repositoryId: string) => RepositoryWorkVerdict; scratchDirectory: string; runDirectory: string; leaseOwner: string }>`, and the input is `Readonly<{ nodeId: string; candidateRevision: string; acknowledgePartial: boolean; publish: boolean | null; actor: string }>`. `ApproveNodeError` carries the closed code list `"not-found" | "node-kind-invalid" | "state-invalid" | "candidate-missing" | "stale-revision" | "acknowledgement-required" | "candidate-check-failed" | "publish-reconcile-pending" | "needs-reconcile" | "outside-writer" | "merge-unexpected" | "merge-failed" | "merge-check-failed" | "stale-base"`.
