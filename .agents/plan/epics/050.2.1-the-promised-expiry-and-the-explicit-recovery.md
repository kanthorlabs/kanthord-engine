# EPIC 050.2.1 — The promised expiry and the explicit recovery

Status: **draft**. It follows EPIC 050.2 by sequence order, and it runs before EPIC 050.3. It consumes EPIC 050.2's run authority, its renew path and its error code table.

It carries a second decimal because EPIC 050.2 holds ten stories, which is the ceiling `scripts/verify-epic-sequence.ts:442` enforces, and because renumbering EPIC 051 through EPIC 057 to insert a whole-number epic would break every cross-reference between them. The number is bookkeeping; the ruling below is why this epic exists at all.

## Goal

A human ruled the rule this epic carries:

> The daemon promises an expiry. It must respect it. When a conflict happens because a client held a run longer than the daemon defined, the client — agent or human — must be told about the failure and choose what is good for them. Never do silent recovery.

Three properties follow:

- `max_lifetime_at` is absolute. No path renews a run past it, and no path mints a replacement run on a client's behalf.
- A renew never continues silently over a lost objective run. It refuses `objective-run-lost` before it writes anything, and it announces `objectiveExpiresAt` at every renew so a client sees the deadline while it still holds the authority.
- The recovery is a claim the client makes. A claim is admitted on a `running` objective when no live run remains under it, and it returns the new run id and fence.

## Non-goals

- **No rotation.** An earlier draft had the renew end the structural objective run and mint a replacement, returning the new authority in the response. That is silent recovery: it decides for the client that the work should continue. It is refused, and with it the `superseded` run outcome it needed.
- **No protected run.** A second draft had the expiry pass renew a due structural run that still had live work under it, past its own maximum lifetime. It is refused for the same reason as the first: it breaks the promised expiry rather than reporting it.
- **No new operation.** The client already has an operation that mints run authority, and it is `node.claim`. This epic widens what a claim admits; it adds no verb.
- **No task recovery.** `src/commands/startup/recover-expired-leases.ts:129-133` already returns a task to `ready` when its lease expires, and `:150` leaves a non-task `running`. Only the objective can strand, and only the objective is addressed.
- **No wire generation.** `worker-model` is declared by EPIC 050.2 and describes this shape too. The version does not move; EPIC 050.4 bumps it for the whole block.

## Decisions

- **`max_lifetime_at` is absolute, and the expiry is the promise being kept.** A structural objective run that reaches its lifetime expires like every other run and appends one `run.expired`. The alternative — renewing it past the cap while live work sits under it — would make a stated deadline advisory, and a deadline a client cannot rely on is worse than a deadline that hurts.

- **A renew that finds no objective run refuses, and refuses first.** `node.renew` reads `execution.activeRunOfNode(objectiveScopeOf(node))` on the task branch after the authority check and **before its first write**, and refuses `objective-run-lost` when there is none. The shipped command continued past a null and renewed the task run alone, so a worker learned that its objective authority was gone at its attest or its close — the last write it makes and the one it cannot retry. The refusal moves that discovery to the operation whose job is to tell a worker whether it may keep working. Its details key is `objectiveId`, matching `objective-busy`. EPIC 050.2 Story 3 moved the read ahead of the lease writes for this refusal alone, because a refusal writes nothing.

- **Every renew announces the deadline.** `nodeRenewResponse` carries `objectiveExpiresAt`: the objective run's expiry for a task target, and the response's own `expiresAt` for an objective target. A refusal tells a client the authority is already gone; this field tells it when the authority will go, while it still holds that authority and can act. Adding a response field is inside the closed list of `docs/proposal/api/README.md:95`, so it needs no compatibility record row.

- **The recovery is a claim, and the client makes it.** A claim is admitted on a `running` objective when no live run remains under it. `subtreeExclusion` at `src/commands/node/claim-node.ts:343` already runs before the state check at `:368` and refuses `subtree-busy` while any live run sits under the objective, so the admission cannot take authority from live work, and no second check is added for it. A node already `running` takes no state transition of its own. Until the client claims, the objective has no authority and every write bound to the old run is refused by code.

- **An objective is the only node that can strand, so it is the only node this widens.** A task whose run expired returns to `ready` when its lease expires, at `src/commands/startup/recover-expired-leases.ts:129-133`. Nothing returns an objective to `ready`, and a `running` objective was unclaimable, so an objective whose structural run expired with no claimable task left under it could never be attested or closed. That is the defect this epic removes.

## Stories

1. **The lost objective run is announced** — the objective run read moves ahead of every write on the renew path, its absence refuses `objective-run-lost`, `nodeRenewResponse` carries `objectiveExpiresAt`, and the refusal code is 409 in the contract and in the proposal's code table.

   Diagrams: renew-refusal-objective-run-lost

   Baselines: renew-refusal-objective-run-lost <- baseline-renew-task

   Seams: renew-refusal-objective-run-lost: +expiry.expireRuns, +plan.readNode, +execution.runById:R, +execution.activeRunOfNode, -plan.readAllNodes

2. **The explicit recovery** — a claim is admitted on a `running` objective when no live run remains under it. It opens a fresh structural run, returns its id and fence, and writes no state change for a node already running.

   Diagrams: claim-recovers-objective-authority

   Baselines: claim-recovers-objective-authority <- baseline-claim-objective-running

   Seams: claim-recovers-objective-authority: recorded against the real command by the story
