# EPIC 104 — Instruction compiler

Status: **ready**.

## Goal

An attempt prompt is compiled from seven typed channels, never by concatenation. `src/domain/instruction-channel.ts`, `src/domain/instruction-contract.ts`, `src/domain/instruction-resolve.ts`, `src/domain/instruction-render.ts`, `src/domain/instruction-budget.ts` and `src/domain/instruction-lint.ts` hold the whole compiler. It is pure: it takes every input as a value, it reads no database, and it calls no model. It reuses `quoteScalar` of `src/domain/plan-render.ts` and `comparePaths` of `src/domain/plan-path.ts`, so no second serialization rule exists. Precedence resolves before rendering, prose appends, a list appends, and a scalar of a more specific channel overrides. `re@1` renders from four channels and never receives implementation guidance. A non-ambient channel over its byte cap refuses and names the channel; the ambient channel drops instead, and this epic reports the drop rather than recording it. `src/queries/instruction/resolve-instruction.ts` composes one prospective prompt from the stored node and the current profile, and `instructions.resolve` moves from `stubbed` to `routed` in `src/http/contract/instruction.ts` with per-block provenance, the budget accounting and the dropped channels. `kanthord instructions resolve --agent <role> --node <id>` prints the same document, byte for byte. Golden fixture prompts for `general@1` and `re@1` are asserted byte for byte.

## Non-goals

- No ambient content. EPIC 105 loads the repository root file from the pinned commit, refuses a symlink, reads up to two switched-on host files, and returns the ambient channel as a value. This epic supplies the ambient channel as an empty contribution.
- No event. This epic owns the ambient budget drop mechanism, and it reports the drop in the response, in the budget accounting and in the CLI output. EPIC 110 appends `instruction.ambient_dropped` when the drop happens inside a real attempt, so the sentence "a drop writes an event" of `docs/proposal/phase-2/instructions-and-profiles.md` is satisfied by EPIC 110. This epic holds one query and one pure compiler, so it opens no storage transaction that writes and it appends no event.
- No agent run. EPIC 106 passes the composed prompt to `pi-coding-agent` and returns the evidence.
- No persistence, and no pinned profile. EPIC 110 pins the profile hash on the objective workspace, resolves an attempt prompt from that pinned hash, stores the rendered messages and every source blob, and writes the `agent_invocation` row. This epic resolves the **current** profile row, because the route is prospective inspection of what an attempt would receive now.
- No profile document rules. EPIC 103 owns `kanthord.profile/v1`, the `checks` map, the profile render and the `nodejs` template. This epic consumes them and restates none of them.
- No `profile.verify`. EPIC 109 gate A asserts by inspection that the verification command reached the right channel, and it calls this compiler.
- No check execution. EPIC 107 runs a declared check and returns its output. This epic renders the command as text.
- No `agent.list`. EPIC 106 routes it and returns the role contract identity this epic ships, with the deferred roles marked.
- No deferred role. `docs/proposal/phase-2/agents-and-workers.md` defers `te@1`, `swe@1` and `git@1`, so this epic ships no role contract for them.
- No `template.list`, no `template.show`, no `profile.verify` route. Each stays `stubbed`.

## Stories

- **The seven channels, typed and ordered** — `src/domain/instruction-channel.ts` holds the closed channel list, in this exact order: `daemon-invariants`, `role-contract`, `repository-profile`, `project-policy`, `task-contract`, `ambient-context`, `runtime-evidence`. `docs/proposal/phase-2/instructions-and-profiles.md` fixes that order. The module exports `instructionChannels`, the zod enum `instructionChannel`, and `channelIndex`, which returns the position. A higher index is more specific, because the proposal states that a scope adds guidance on top of the scope above it. One channel contributes one `ChannelContribution`: `{ channel, from, prose: readonly string[], lists, scalars }`. `prose` is an ordered fragment list. `scalars` is a partial record over the closed field list `instructionScalarFields` of `verificationCommand`, a `readonly string[]`, and `verificationTimeout`, a `string`. `lists` is a partial record over the closed field list `instructionListFields`, which holds `acceptanceCriteria` only, each value a string sequence. The field set is closed to what the proposal names as instruction: a worker kind is daemon control and a check map is executable configuration, so neither is a prompt field. **The ambient contribution type carries `prose` and `sources` only**, so ambient content cannot set a structured field by construction, and no runtime check is needed. `sources` is the ordered list of `{ from, bytes }`, one entry per source blob, and it holds the same length and the same order as `prose`, which is what `composeAmbientChannel` of EPIC 105 returns. The module imports `zod` only.
- **Precedence, resolved before rendering** — `src/domain/instruction-resolve.ts` exports `resolveInstruction`, which takes the contribution list and returns a `ResolvedInstruction`. Prose appends: every fragment of every channel is kept, in channel order, then in the supplied order inside one channel, and nothing is deleted. A list appends the same way, and a duplicate value is kept, because a repeated criterion is the author's text. A scalar overrides: the contribution with the highest `channelIndex` that declares the field wins, and the loser is discarded before rendering, so it renders nowhere. One channel declares at most one value per scalar, because `scalars` is a record, so no tie is possible. The result carries, per scalar field, `{ value, channel, from }`, and per list field, the appended values each with their channel. A contribution list holding two entries for one channel is a defect, and the function throws `Error`, because the caller builds exactly one contribution per channel.
- **The daemon invariants and the two role contracts, as code data** — `src/domain/instruction-contract.ts` exports `CONVENTION_VERSION` of `coding/v1`, matching `convention_version` of `docs/proposal/database/workspace.md`, and `daemonInvariants`, one prose fragment holding exactly these four lines: `The daemon owns every state change. Report a result, and never mark your own work verified.`; `Change only files inside the workspace you were given.`; `Every command you run must finish without human input.`; `Report a failure as a failure, and never make a check pass by weakening it.`. The module also exports `instructionRoles`, the frozen list `["general@1", "re@1"]`, and `roleContracts`, a record over `instructionRoles`, each entry `{ id, prose, channels }`. **Two roles are the full set for phase 2**, because `docs/proposal/phase-2/agents-and-workers.md` defers `te@1`, `swe@1` and `git@1`, and their tool sets and contracts are decided when they ship. The id is `role-contract/<role>@1`. The prose is exactly: `general@1` — `Do the task. Change the smallest number of files that satisfies the acceptance criteria. Run the verification command before you report a result.`; `re@1` — `Judge the diff against the acceptance criteria only. Answer one verdict per criterion, accept or reject, with one reason line each. Never propose an implementation.`. `channels` is the channel set of the role. `general@1` names all seven. **`re@1` names exactly four**: `daemon-invariants`, `role-contract`, `task-contract` and `runtime-evidence`. Reduction also drops the prose of `task-contract` for `re@1` and keeps `acceptanceCriteria`, so the reviewer reads the criteria, the diff and the verification output, and no implementation guidance. `docs/proposal/phase-2/instructions-and-profiles.md` requires the independence.
- **The canonical render and the per-block provenance** — `src/domain/instruction-render.ts` exports `renderPrompt`, which takes the role and the resolved instruction and returns the block list. A block belongs to one channel of the role's channel set, in channel order. A block is the line `## <channel>`, one blank line, then the block body. The body is the channel's prose fragments joined by one blank line, then, if the channel won a scalar or contributed a list value, one blank line and the structured lines. A scalar line is `- <field>: <value>`. `verificationTimeout` renders its string through `quoteScalar` of `src/domain/plan-render.ts`. `verificationCommand` is an argument vector, matching `checks.run` of the profile, so it renders each element through `quoteScalar`, joined by one space. A list line is `- <field>[]: <quoteScalar(value)>`, one line per value in append order. Field order inside a block is the declaration order of `instructionScalarFields`, then of `instructionListFields`. Escaping is the rule the plan format already carries, so no second quoting rule exists. A channel with no prose and no won field renders no block. One blank line separates two blocks, and the prompt ends with exactly one LF. Output is UTF-8 and LF only. The module also fixes the provenance record and the `from` label grammar. **One entry per source blob**, in channel order and then in source order inside one channel, and a channel that rendered no block reports no entry, which `docs/proposal/database/agent_invocation.md` requires of `sources_json`. Every channel except `ambient-context` holds exactly one source blob. The `ambient-context` channel contributes one prose fragment and one provenance entry per source blob, in source order — the frozen repository file first, then each switched-on host file in `settings.ambient.hostPaths` order — so the render accepts up to three `ambient-context` source byte sequences, each with its own `from`, and the block body joins their prose fragments in that order. EPIC 105 supplies those sources, and this epic supplies none. An entry is `{ channel, blob, bytes, from }`, the same field names that document uses, where `blob` is the `sha256:` address of the **source** bytes and `bytes` is their count. It is never the address of the rendered block, because the proposal requires a prompt to be rebuilt after its source is gone. `domain/` computes no hash, so `renderPrompt` returns the source bytes per entry and the caller addresses them through `BlobStore.hash` of `src/services/blob/index.ts`, or reuses the stored hash where one exists. The label set is closed, and `channelFrom` builds it: `daemon-invariants` is `convention:coding/v1`; `role-contract` is `code:role-contract/<role>@1`; `repository-profile` is `profile:<contentBlob>`; `project-policy` is `project:<projectId>`; `task-contract` is `node:<nodeId>@<revision>`; `ambient-context` is `ambient:<ambientBlob>` for the frozen repository source, and a host source carries the label EPIC 105 supplies beside its bytes, so `channelFrom` builds no host label; `runtime-evidence` is `attempt:<attemptId>`.
- **Golden fixture prompts per role** — `src/domain/instruction-render.test.ts` builds one fixed input from the `nodejs` template document of `src/domain/profile-template.ts` and a fixed task body, then asserts the rendered bytes against `test/fixtures/instruction/general-1.prompt.md` and `test/fixtures/instruction/re-1.prompt.md` with `Buffer.compare(actual, expected) === 0`. Two fixtures are the full set, because `instructionRoles` holds two roles. The input names no clock, no id generator and no host path, so the fixture holds no timestamp. `docs/proposal/phase-2/instructions-and-profiles.md` requires a golden fixture per role, so a template change that alters a rendered prompt fails this test.
- **The per-channel budget, a refusal and one drop** — `src/domain/instruction-budget.ts` exports `channelBudgets`, a frozen record from channel to a byte cap, and `applyBudget`, which takes the block list and the budget record. **The unit is UTF-8 bytes of the rendered block, measured with `new TextEncoder().encode(text).length`**, so the measurement holds no locale and no code unit ambiguity, and `domain/` stays pure. The default caps are code constants in this module, and no configuration key overrides them in phase 2: `daemon-invariants` 8192, `role-contract` 8192, `repository-profile` 32768, `project-policy` 16384, `task-contract` 32768, `ambient-context` 16384, `runtime-evidence` 262144. `applyBudget` never truncates. A non-ambient block over its cap returns `{ outcome: "refused", channel, bytes, cap }`, and the first refusal in channel order is the reported one. An `ambient-context` block over its cap returns the prompt without that block and lists the channel under `dropped`. Every other channel keeps its block. The budget accounting lists one entry per channel of the role's channel set, `{ channel, bytes, cap }`, in channel order, and a dropped channel reports the bytes it measured before the drop. `applyBudget` returns a value and appends no event, because the drop must be visible in a read path; EPIC 110 records it inside an attempt. `docs/proposal/api/instruction.md` states that a drop is not a refusal and that the two must look different to a reader.
- **The contradiction lint reports and never reconciles** — `src/domain/instruction-lint.ts` exports `lintContradictions`, which takes the contribution list and returns a sorted finding list. **A contradiction is detected between directives, not by reading natural language.** Every prose line is one directive. A line matching `/^\s*(?:[-*]\s+)?(?<body>.+?)\.?\s*$/` yields `body`. A `body` starting with `Always ` has polarity `require` and the predicate is the rest. A `body` starting with `Never ` or `Do not ` has polarity `forbid` and the predicate is the rest. Every other `body` is a bare imperative: polarity `require`, and the predicate is the whole `body`. The predicate normalizes to lower case with every whitespace run collapsed to one space. Two directives with the same normalized predicate and opposite polarity are one finding: `{ code: "prose-contradiction", predicate, left: { channel, from }, right: { channel, from } }`, where `left` holds the lower `channelIndex`. So `Use the repository result type` and `Never use the repository result type` are one finding, and the bare imperative needs no marker. **What the lint does not catch**, and never claims to: a paraphrase, a synonym, a negation written in other words such as `Avoid the repository result type`, a line holding two sentences, and a prose fragment that contradicts a scalar. Nothing else is a finding, so the lint is deterministic and it needs no model. The list sorts by `predicate` through `comparePaths`, then by the `left` channel index, then by the `right` channel index. The resolver never reconciles the two fragments: both still render, in channel order. `src/commands/profile/import-profile.ts` of EPIC 103 calls the lint after its findings pass, and the `profile.import` response gains a `warnings` field carrying the sorted finding list. **The import never refuses on a contradiction**: the `422 profile-invalid` contract of EPIC 103 is unchanged, and the lint reports. The import lint compares each imported role section against `daemonInvariants`, and against the matching entry of `roleContracts` when `instructionRoles` holds that role, because no node is known at import.
- **The prospective resolve query** — `src/queries/instruction/resolve-instruction.ts` takes `storage`, `plan`, `profiles` and `blobs`, and it takes `{ agent, node }`. It takes no project capability, because none exists: `PlanStore.readNode` returns `projectId`, `parentId` and `repositoryId` on `StoredNode`, and `src/queries/project/read-project-status.ts` shows the existing path for a project row, which is `Storage` and one statement. In one `storage.transact` it reads the node through `PlanStore.readNode`, walks `parentId` to the owning objective for its `repositoryId`, and reads the profile row through `ProfileStore.read` of EPIC 103. It decodes `instructionBlob` and `acceptanceBlob` through `BlobStore.get`, and it splits the body with `splitBody` of `src/domain/plan-body.ts`. **`splitBody` returns one acceptance string that includes `ACCEPTANCE_HEADING`**, so extraction is fixed here: drop the first line, normalize the rest with `normalizeBody`, then read it line by line. A line matching `/^[-*] (?<criterion>.+)$/` yields one value, the capture with trailing whitespace removed. A non-empty line that matches no bullet joins the previous value with one space. A non-empty line before the first bullet is one value of its own. An empty line yields nothing. An `acceptance` of `null` contributes no `acceptanceCriteria`. It builds exactly one contribution per channel: `daemon-invariants` from `daemonInvariants`; `role-contract` from `roleContracts[agent]`; `repository-profile` from the role section of the stored profile document, with `verificationCommand` and `verificationTimeout` from `checks.unit`; `project-policy` empty, because no prompt field of this epic comes from a project row; `task-contract` with the instruction prose and the extracted `acceptanceCriteria`; `ambient-context` empty, because EPIC 105 owns the content; `runtime-evidence` empty, because the resolve is prospective. It then resolves, renders, applies the budget, addresses every block source through `blobs.hash` or the stored blob hash, and returns `{ agent, node, prompt, provenance, budget, dropped, contradictions }`. The `task-contract` source bytes are the decoded `instructionBlob`, then one LF, then the decoded `acceptanceBlob` when the node holds one. The `repository-profile` entry reuses `contentBlob` and `BlobRecord.size` of the stored row, so no hash is recomputed. It runs no model, calls no provider and inserts no row, so the response is composed live and never read from `agent_invocation.sources_json`, which `docs/proposal/api/instruction.md` requires. A refusal throws `channel-over-budget` carrying the same provenance, budget and dropped document. An unknown node throws `not-found`, a node whose kind is not `task` throws `invalid-request`, a role that `instructionRoles` does not hold throws `invalid-request`, and a repository with no profile throws `not-found`.
- **`instructions.resolve` moves from `stubbed` to `routed`** — `src/http/contract/instruction.ts` sets `status: "routed"` on `instructions.resolve` and declares its `query`, its response, its errors and its examples. This epic is the only owner of that move, and no later epic re-declares the operation. The query schema carries `agent`, one value of `agentKinds` of `src/domain/agent.ts`, and `node`, a node identity; both are required. The schema keeps the four `agentKinds`, because EPIC 106 reports a deferred role, and the query refuses a role with no contract with `400 invalid-request`. `agent.list`, `template.list`, `template.show` and `profile.verify` keep `status: "stubbed"`. The matching row of the table in `docs/proposal/api/instruction.md` changes to `routed`, because `src/http/contract/parity.test.ts` compares the registry against that table. A new error code `channel-over-budget` with status `409` is added to `errorStatuses` of `src/http/contract/errors.ts`, immediately after `host-key-mismatch`, with the same row position in the code table of `docs/proposal/api/README.md`, and the pinned count in `src/http/contract/errors.test.ts` becomes twenty-four, because EPIC 103 made it twenty-three. `exitCodes` of `src/cli/exit-code.ts` is an exhaustive record over `ErrorCode`, so it gains `"channel-over-budget": 165`. `160` to `163` hold the current `422` codes and `164` belongs to `profile-invalid` of EPIC 103, and `src/cli/exit-code.test.ts` asserts only that a `4xx` code lands between `100` and `199`, so `165` is legal. Its three pinned counts become twenty-four. `channel-over-budget` is a `PreconditionCode`, so its `details` are required, and they carry `channel`, `bytes`, `cap`, `provenance`, `budget` and `dropped`. `src/http/server/instruction/resolve-instruction.ts` parses the query, calls exactly one query, and formats the response. It branches on no domain rule. `src/main.ts` binds the handler, and the fixture map of `src/main.test.ts` gains the operation id.
- **The CLI prints the same document** — `src/cli/instruction/index.ts` exports `instructionsCommand`, which creates the `instructions` group, and `src/cli/instruction/resolve.ts` registers `resolve` with the required options `--agent <role>` and `--node <id>`. It calls `instructions.resolve` over HTTP through `src/cli/client.ts` and imports no query, as the import matrix requires. **The output grammar is fixed byte for byte.** It prints the prompt, which already ends with one LF, then one empty line, then these line kinds in this order: one `provenance` line per provenance entry in channel order; one `budget` line per budget entry in channel order; one `dropped` line per dropped channel in channel order; one `contradiction` line per finding in lint order. A line is `provenance  <channel>  <blob>  <from>`, `budget  <channel>  <bytes>  <cap>`, `dropped  <channel>  <bytes>  <cap>`, or `contradiction  <predicate>  <left.channel>  <right.channel>`. Every field separator is exactly two spaces, every line ends with one LF, no empty line separates two line kinds, and the output ends with exactly one LF. A `409 channel-over-budget` prints `refused  <channel>  <bytes>  <cap>` and exits `165` through `src/cli/exit-code.ts`. `declaredCommands` of `src/cli/inventory.ts` gains `{ path: ["instructions", "resolve"], operationIds: ["instructions.resolve"] }`, so `src/cli/parity.test.ts` matches the program, and `src/cli/program.ts` registers the group.
