# EPIC 052.1 — The structural acceptance

Status: **draft**. It follows EPIC 052 by sequence order, and it runs before EPIC 052.2. It consumes EPIC 052's patch algebra, staging, verdicts and seams, EPIC 051.3's `checkpoint` table, EPIC 051.4's acceptance-gate shape and its `report-checkpoint-gate` diagram, and EPIC 050.2's authority prelude.

It carries a decimal number for the reason EPIC 052 states.

**This epic was split, and EPIC 052.2 carries the consumer.** The honest seam trace of `acceptStructural` draws eight diagrams, and with the lowering and the proposal amendment that is ten stories. The seventh `node.report` member, the wire error declarations, the refusal mapping and `report-structural-gate` are the eleventh and twelfth, so they became EPIC 052.2. The boundary is the consumer boundary: this epic ships a complete command with a real success path and every refusal, and EPIC 052.2 ships the only thing that calls it. The wire contract travels with the route that honours it, so no epic advertises a request member the daemon cannot serve.

## Goal

An accepted graph patch is the checkpoint of a structural run:

- `acceptStructural` is a nested callable of `reportOutcome`, and the whole acceptance is one storage transaction;
- the compare and swap is the shipped `plan.newestRevision` guard, and it runs before every graph-dependent check;
- an accepted patch pins its canonical bytes, records a new `plan_revision`, applies the mutation set in one `plan.mutateGraph`, and writes the structural checkpoint;
- the node state does not move, because a structural run never sets an initiative or parent-objective state;
- a refusal writes nothing, and the seventh `node.report` member carries the patch.

## Non-goals

- **No new refusal semantics.** Every verdict is EPIC 052's. This epic orders them, maps them to contract errors, and proves the order.
- **No node transition.** `../docs/workflow/worker.md:365` states a run never sets an initiative or parent-objective terminal state and that the initiative stays `pending` or `ready`. `.agents/plan/epics/053-node-state-ownership.md` states the same rule for a parent objective. **This epic takes the initiative assertion, and it lifts `src/commands/outcome/report-outcome.ts:116` — `initiative-not-reportable` for the structural member alone**, because that guard refuses every report on an initiative today and an initiative's run is `structural`. The other six members keep the guard. The superseded EPIC 052 wrote a transition that does not exist.
- **No wire contract, no route and no refusal mapping.** EPIC 052.2 owns the seventh `nodeReportRequest` member, the ten `errors` entries, the six 409 details schemas, `src/cli/exit-code.ts`, the `docs/proposal/api/README.md` matrix row, `src/http/server/node/refusals.ts` and `report-structural-gate`. This epic ships `acceptStructural` and injects it nowhere. `src/commands/outcome/report-outcome.ts` is untouched here, and so is `src/commands/outcome/report-outcome.test.ts`.

- **No supersession of `report-checkpoint-gate`.** `.agents/plan/stories/051.4-the-acceptance-gate-and-the-report-route/08-the-report-route-enforces-the-gate.md` states that only the `accepted` member on an execution node reaches its `accept.execution` step, and that the other five members keep the tail `report-lease-free` drew. The structural member is a seventh member and a wholly new path, so its prior set is empty and every token of its diagram is `+`. EPIC 052.2 draws it.
- **No claim change.** The completeness exemption for an `expansion` node is shipped, at `src/commands/node/claim-node.ts:179-182`, and EPIC 050.1's Decision at `:114` names that mechanism. This epic touches neither `src/commands/node/claim-node.ts` nor `src/domain/plan-completeness.ts`.
- **No migration.** EPIC 051.3's migration `14` creates every column this epic writes, and a structural revision reuses `origin: "node-write"`.
- **No worker.** Every test supplies its own registry fixture holding one expansion-capable worker, and the phase-2 worker is a registry edit.
- **No git, and no command run.** `../docs/workflow/worker.md:726` states structural evidence is the mutation set, that no diff exists and that no command runs.

## Decisions

- **`acceptStructural` is a nested callable of `reportOutcome`, and the handler keeps its one command.** `src/commands/outcome/report-outcome.ts:59-66` already injects `reportObjective` and `closeObjective` as callables taking the caller's transaction, and `AGENTS.md` requires a handler to parse, call exactly one command and format. EPIC 051.4 established the shape for `acceptExecution`, and `.agents/plan/epics/051.4-the-acceptance-gate-and-the-report-route.md:40` records that `assertRunAuthority` is a **pure** function already running inside `reportOutcome`. **`acceptStructural` therefore asserts no authority itself**: the prelude gives it the claimed node, the subtree and the pinned revision. The superseded EPIC 052 had the command assert all four conditions, which would have run the prelude twice.

- **`acceptStructural` takes the caller's transaction, and the request opens one.** It writes no git and runs no command, so unlike `acceptExecution` it needs no transaction of its own. `../docs/workflow/worker.md:726` is what removes the git and the command run, and that is the whole reason the structural path is one transaction where the execution path is three.

- **The currentness check runs before every graph-dependent check, and the refusal is the shipped `stale-revision`.** `plan.newestRevision(transaction, projectId)` at `src/services/plan/index.ts:80` is read inside the transaction and compared to the run's pinned `graph_revision`. `src/commands/node/create-node.ts:97-111` is the shipped pattern, refusing `stale-revision` with `{ guard, expected, actual }`. **`PlanStore` has no read of a graph at a past revision**: `readGraph(transaction, projectId)` returns the live graph only. So "validate against the pinned graph" is implementable exactly when the live graph _is_ the pinned graph, which is what the equality check establishes. The superseded EPIC 052 put its contention refusal last and validated against a pinned graph it had no way to read. `graph-contended` is deleted: it named the identical condition as `stale-revision`, and a second code would split the contract error and the CLI exit code for no behavioural difference.

- **The refusal order is fixed, and it is complete at fifteen codes.** The superseded EPIC 052 counted fifteen and listed sixteen.

  1. `run-not-found`, `run-ended`, `run-expired`, `run-caller-mismatch`, `fence-stale` — the authority prelude of `reportOutcome`, reached before this command is called.
  2. `patch-unparsable`, `patch-id-duplicate` — pure, before `acceptStructural` touches the caller's transaction. `reportOutcome` opened that transaction before the prelude ran, so no refusal of this epic precedes a transaction.
  3. `stale-revision`.
  4. `patch-target-invalid`.
  5. `patch-scope-invalid`.
  6. `patch-project-invalid`.
  7. `pair-fixed`.
  8. `plan-invalid`, carrying `{ findings }`.
  9. `patch-delete-ineligible`.
  10. `expansion-empty`.

  Authority precedes shape, shape precedes currentness, and currentness precedes every graph read. After that the rule is **a dominant invariant precedes a contingent defect**: report the invariant first when repairing the contingent defect cannot remove it. `pair-fixed` is such an invariant, because EPIC 052's pair fixation is permanent, so no topology repair ever legalises the pair change; reporting `plan-invalid` first would tell a caller to repair a graph that can never become acceptable. Cost does not decide a caller-visible precedence, and the cost here is small: the checkpoint read fires only for a patch that changes an existing pair. `patch-delete-ineligible` and `expansion-empty` follow `plan-invalid`, because each asks a question about a graph already known well formed. Project precedes `plan-invalid` for the reason EPIC 052 states: otherwise its refusal is unreachable.

  **Scope judges a reference that resolves, and never one that is absent.** A reference absent from the staged graph is not out of scope. It is either another project's node or no node at all, and only the cross-project projection separates them. `patch-scope-invalid` therefore covers a node the staged graph holds outside the claimed subtree. A node the projection holds and the staged graph does not is `patch-project-invalid`. A node neither holds falls to `plan-invalid`, as `parent-missing` or `reference-unresolved`. The same three-way rule decides an `update` or a `delete` target against the pinned graph. A mutation naming another project's node therefore reports the project and not the target. Without this rule `patch-project-invalid` is unreachable, because scope consumes every route to it, and EPIC 052's gate row that proves the ordering ruling cannot run.

- **The lowering is a pure function, and it derives a constraint-safe order from the staged graph.** `node.parent_id` at `src/services/storage/migration-0002-graph-and-plan.ts:21` and both `edge` columns reference `node(id)` with no `DEFERRABLE` and no `ON DELETE CASCADE`, and `src/services/storage/connection.ts:8` sets `PRAGMA foreign_keys = ON` at every open. `mutateGraph` at `src/services/plan/sqlite.ts:467-482` iterates each array in caller order, in the phase order nodes, edge deletes, node deletes, edge inserts. So `lowerPatch` emits: created and updated nodes **parent-first**; every obsolete edge id; deleted node ids **child-first**; every final edge with a fresh `ids.mint("edge")`. The phase order handles edges before nodes; the within-array order is this function's obligation, and a patch that creates a parent and its child in one mutation set fails immediately without it.

- **An `update` submits a complete row, because the upsert is not partial.** `INSERT_NODE` at `src/services/plan/sqlite.ts:43-46` is `ON CONFLICT(id) DO UPDATE SET` over every ordinary column, so an absent patch field must be read from the pinned node and resubmitted. It preserves `state` and `assignment`, which are in the `VALUES` and not in the update set, and it takes `deliverable` and `verify_json` only when their has-flags are set. `lowerPatch` therefore overlays the named fields onto the pinned row.

- **Prose becomes a blob before it becomes a node.** `instruction` and `acceptance` are prose in the patch and blob hashes in `NodeWrite`, so each is written with `blobs.put` as `src/commands/node/create-node.ts:116-127` does. The superseded EPIC 052 listed both as `create` fields and never said where the hash comes from.

- **The canonical bytes are stored in the accepted branch, and no refusal can orphan a blob.** `blobs.put` at `src/services/blob/index.ts:22` takes the transaction, and the whole acceptance is one transaction, so a refusal rolls the put back. The put therefore sits with the other writes rather than before validation, and `checkpoint.patch_blob` holds the returned hash. `../docs/workflow/worker.md:726` requires structural evidence to be the mutation set, and evidence not pinned by content is not evidence.

- **The revision is written by the shipped `Revision` service, with `origin: "node-write"`.** `revision.render(transaction, { nodes })` then `revision.record(transaction, { projectId, revisionId, parentRevision, documents })`, as `src/commands/node/create-node.ts:232-241` does. `src/services/revision/node-write.ts:103-115` puts the canonical document set as `accepted_blob` and inserts with `importId`, `submittedBlob` and `choicesBlob` null. **The ruling this needs is semantic, not convenient:** `node-write` is the origin of every single-node graph write — `create-node`, `update-node` and `delete-node` are its only users, at `:232`, `:306` and `:176` — and a structural patch is exactly an atomic batch of those three, so it is the same origin and not a new one. `plan_revision` at `src/services/storage/migration-0006-revision-origin.ts:13-21` admits no third value without a rebuild, and `accepted_blob TEXT NOT NULL` means no revision inserts without a rendered document set.

- **The whole acceptance is one `plan.mutateGraph` call.** The lowering produces one `MutateGraphInput`, so the mutation set reaches storage as one seam step. `plan.mutateGraph` returns the readiness transitions it applied, and those are the only node states this epic moves — they belong to the shipped readiness pass over the new children, not to the claimed node.

- **The run ends in the acceptance, and this epic registers no new event type.** The attempt closes as `accepted`, the run ends, the fence rises by one, and the checkpoint records the **pre-raise** fence, mirroring EPIC 051.3's accepted settle. The events are the shipped `outcome.reported` on the node and `run.ended` on the run: `subjectKind` `node` and `run`, `subjectId` the node id and the run id, appended in this one transaction. `outcome.reported.objectId` is the `patch_blob` hash, because EPIC 051.3 states a consumer reads `objectId` and joins the `checkpoint` table, and the patch is the object a structural run produced. **Ruled, not defaulted.** A structural run produces one patch and has nothing left to do after acceptance, so a run left open would need a second report the protocol defines nowhere: `worker.md` section 8 gives a structural checkpoint no step after the swap, and `worker.md` section 7 states the daemon raises the fence when it ends a run. The alternative — an acceptance that leaves the run active — would also break EPIC 050's exclusion rule for the claimed subtree, because the new children would be born under an active ancestor run.

- **The seventh `node.report` member carries the patch as an opaque value.** `nodeReportRequest` at `src/http/contract/outcome.ts:23-53` gains `{ report: "structural", fence, patch: unknown }`, and `graphPatch.safeParse` runs inside `reportOutcome` after the authority prelude. **Embedding `graphPatch` in the contract would break this epic's own proof**: HTTP validation would reject a malformed patch with `invalid-request` before `assertRunAuthority` ran, and the fixed order requires a stale fence to refuse before the patch is read. The discriminator is `"structural"`, matching the run kind and the checkpoint kind.

- **Three seam reads are conditional on patch content, and none is made unconditional to shorten a trace.** `plan.nodeProjects` fires only for a patch naming an id the staged graph does not hold, `plan.structuralDeleteBindings` only for a patch holding a `delete`, and `execution.hasAcceptedCheckpoint` only for a node whose pinned pair changes. Each answers a question a patch without that content does not ask. `plan.readAllNodes` at `src/services/plan/sqlite.ts:186` reads every node and every edge of every project with no id set, so calling it in place of the resolver is a full scan inside the acceptance transaction. `plan.readSubtreeExecutionFacts` at `src/services/plan/sqlite.ts:338` is the shipped bulk-by-id precedent both new reads follow, and it queries `run`, `workspace`, `attempt`, `commit`, `check-result` and `git-operation` from the plan store, which is why both live on `PlanStore` and not on `Execution`.

- **The conditionality decides the drawn set, and the drawn set decides the story count.** A diagram is drawn per refusal group against one declared fixture, and two groups whose declared fixtures give one token list are one diagram. `.agents/plan/authoring.md:206` states a fixed fixture is one example and that a diagram proves no branch coverage, and `:187` draws a repeated call against a fixture whose length is stated. A reachable trace of an already-drawn terminal is therefore asserted by the command's own test, and the story claims the branch coverage in prose. Eight diagrams cover the nine groups this command decides plus its success path. The count is never run backwards from the ten-story cap.
