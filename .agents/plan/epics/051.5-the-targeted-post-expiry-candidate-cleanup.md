# EPIC 051.5 — The targeted post-expiry candidate cleanup

Status: **draft**. It follows EPIC 051.4 by sequence order, and it runs before EPIC 052. It consumes EPIC 050.1's expiry pass, EPIC 051's asynchronous composed claim, and EPIC 051.1's `candidate.discard`, `git.listRefs`, `execution.activeRunIds` and `src/domain/candidate-ref.ts`.

Story 9 appends it to `shippedEpics` at `scripts/epic-sequence-range.ts:17` — `shippedEpics`, which `test/sequence/conformance.test.ts:254` — `shippedEpics` requires to stay a prefix. ## Goal

A candidate ref of a run that `node.claim` expires is deleted by that same claim:

- `candidate.reap` deletes every candidate ref of every run one expiry pass ended;
- every `node.claim` terminal that commits an expiry **and settles its own outcome** calls it once, after its last transaction commits — the three success paths and the contended-cut refusal;
- a terminal that leaves the `cut` journal row `open` reaps nothing, and startup reconciles it;
- a pass that ended no run reaches no seam at all;
- the reap never throws, and every failure it swallows becomes a finding;
- `ExpiredRun` is a domain type, so the claim declares the expiry result instead of `unknown`;
- one story of this epic supersedes one shipped diagram, and the conformance harness stays green at every story boundary.

## Non-goals

- **No second global sweep.** `candidate.sweep` of EPIC 051.1 Story 5 (`05-the-candidate-namespace-has-a-reaper`) stays the startup step and keeps its own call site. This epic adds a run-scoped deletion and changes no listing of the whole namespace.
- **No report-path deletion.** Acceptance, rejection and contention delete the ref through `candidate.discard` in EPIC 051.4. This epic touches none of those paths.
- **No reap on `renew`, `release` or `report`.** `.agents/plan/epics/050.2-the-run-renew-release-and-report.md:36` — `expiry.expireRuns` gives each of the three its own expiry pass inside its own single transaction, so each commits expiries this epic does not reap. **EPIC 051.6 owns those three paths**, and it is a separate epic because their three live diagrams — `renew-lease-free` and `release-lease-free` of EPIC 050.4 Stories 4 and 5, and `report-checkpoint-gate` of EPIC 051.4 Story 8 (`08-the-report-route-enforces-the-gate`) — would take this epic to twelve stories. The objective attestation is **not** among them: `attest-lease-free` draws no `expiry.expireRuns` step. The residue until then is the startup reaper.
- **No periodic driver.** The daemon still holds none. A run that expires while no claim, renew, release or report arrives keeps its ref until the next start — the residue EPIC 051.1 `## Non-goals` states.
- **No attempt termination.** `attempt.termination` and the class an expiry charges are EPIC 054. This epic writes no attempt row.
- **No single-transaction refusal reap.** `.agents/plan/epics/050.2-the-run-renew-release-and-report.md:36` — `expiry.expireRuns` states that a command that expires a run and then refuses rolls the expiry back with everything else. The `objective-busy` refusal of EPIC 050.4 Story 3 (`03-the-objective-busy-refusal-drops-the-lease`) is one transaction, so it commits nothing and does not move. The contended cut is the one refusal that does, and Story 9 carries it.

## Decisions

- **The deletion is keyed on the run, not on the attempt, so the reap lists a per-run prefix.** `src/commands/run/expire-runs.ts:6` — `ExpiredRun` returns `runId`, `nodeId` and `fence` and no attempt number, and `.agents/plan/epics/051.1-the-candidate-and-the-git-primitives.md:36` — `refs/kanthord/candidate/` states the expiry knows no attempt number. `reapRunCandidates` calls `git.listRefs` with `refs/kanthord/candidate/<runId>/` per ended run and deletes every ref it finds, which collects every attempt of that run in one pass.

- **The run's bare home is resolved through `run_base`, and never through the node.** `src/services/storage/migration-0002-graph-and-plan.ts:33` — `CHECK ((kind = 'objective') = (repository_id IS NOT NULL))` gives `repository_id` to an objective and to no other node kind, and `ExpiredRun.nodeId` is the task of an execution run, so `plan.readObjectiveRepository` of EPIC 051 Story 4 (`04-the-claims-begin`) returns `null` for it. `execution` owns `run_base`, so it answers the question: `execution.runBaseHomes(transaction, runIds)` joins `run_base` to `repository` and returns one `{ runId, homePath }` per run that has a base row.

- **A structural run has no base row, so the reap skips it and that is correct.** `.agents/plan/epics/046-worker-model-overview.md:166` — `expansion` states a structural worker submits a graph patch and creates no commit, so it pushes no candidate. `execution.runBaseHomes` returns no row for such a run, the reap lists nothing for it, and the deletion count stays zero. A structural-only input list therefore reaches `execution.runBaseHomes` and no git call, which Story 4's case set carries rather than a fourth diagram. **Its seam set is a strict prefix of `reap-candidates-no-ref`, not the same set** — it stops one step earlier, at `execution.runBaseHomes`. A case carries it because it is the branch a guard adds, and `.agents/plan/authoring.md:335` — `guard` rules that such a branch is proven by a case: drawing it would give Story 4 a second live diagram, which `scripts/verify-epic-sequence.ts:487` — `two` refuses. The same rule puts the four finding buckets of Story 5 in cases and in no diagram.

- **`candidate.reap` is a nested command, and it is not a call inside `expireRuns`.** `src/commands/run/expire-runs.ts:19` — `ExpireRunsDependencies` names no `Git`, takes the caller's transaction and is synchronous, and `AGENTS.md` forbids git I/O inside a storage transaction. `.agents/plan/epics/054.4-the-run-lifecycle-pays-its-attempt.md:31` — `expireRuns` forbids widening it. The seam trace of `expiry-pass-one-due` therefore does not move, and this epic supersedes no EPIC 050.1 diagram.

- **The reap sits in `claimNode` and not in the composition root, because when it runs is business sequencing.** `AGENTS.md` `## Architecture` puts the business logic of one operation in `commands/`, and the root binds an implementation. Deciding that the deletion happens after the last commit, on every terminal that commits one, is a rule of the operation. The root binds the callable; the command decides the moment. It also keeps the expired-run list out of `ClaimNodeResult`, which is a wire response.

- **Every claim terminal that commits an expiry reaps, and the contended cut is one of them. The reap is a plain statement placed before the raise, and never a `try`/`finally`.** `.agents/plan/stories/051-the-workspace-branch/07-the-loser-of-two-first-claims-refuses.md:235` — `transactions` asserts the contended composed claim opens exactly two, so its begin transaction — which holds the expiry pass at `src/commands/node/claim-node.ts:147` — `expireRuns` — commits before the refusal is raised. Nothing has to be caught to reach it: `.agents/plan/stories/051-the-workspace-branch/07-the-loser-of-two-first-claims-refuses.md:55` — `ClaimNodeError` states that `claimSettle` raises nothing and returns `{ disposition: "contended" }`, and the composed command throws `objective-busy` **after the settle returns**. `claimNode` therefore reaps between the settle and the raise, on one source line that both arms reach:

  ```ts
  const settled = await dependencies.claim.settle(/* … */);
  await dependencies.git.removePidFile(/* … */);
  await dependencies.candidate.reap(expired);
  if (settled.disposition === "contended") {
    throw new ClaimNodeError("objective-busy" /* … */);
  }
  ```

  **A `finally` is the wrong instrument and this epic does not use one.** `.agents/plan/stories/051.2-the-command-gate/index.md:98` — `finally` rules in this repository that a `finally` discards the exception it wrapped, so an `await` that rejects inside one replaces the `objective-busy` refusal the worker must see with a cleanup fault. A plain statement before the raise makes the rule total over every terminal the begin commits, and it needs no exception handling at all.

- **A throw between the begin and the settle reaps nothing, and that is what condition 6 requires.** A git failure at `git.refUpdate:cut` or `git.resolveRef:cut` leaves the `cut` journal row `open`, so the claim's logical outcome is not settled and `AGENTS.md:106` — `six conditions` forbids the deletion. Placing the reap after the settle is what excludes that arm; a `finally` would have reaped inside it. `.agents/plan/stories/051-the-workspace-branch/08-startup-reconciles-an-open-cut-row.md:1` — `Story 8` reconciles the row, and `candidate.sweep` sweeps the ref, so the residue is bounded and temporary.

- **`claimBegin` returns the runs its transaction ended, and `claimNode` reaps on two source statements.** `.agents/plan/stories/051-the-workspace-branch/04-the-claims-begin.md:138` — `ClaimBegunClaimed` is `{ kind, result }` and `.agents/plan/stories/051-the-workspace-branch/04-the-claims-begin.md:143` — `ClaimBegunCut` names twelve members; neither carries the expiry result, and `.agents/plan/stories/051-the-workspace-branch/04-the-claims-begin.md:171` — `claimed` returns from inside the transaction. The expiry pass is step 3 of every claim diagram, so it runs inside `claimBegin` and `claimNode` cannot see the ended runs unless `claimBegin` returns them. **Both variants therefore gain `expired: readonly ExpiredRun[]`, which is an amendment to EPIC 051 Story 4 (`04-the-claims-begin`).** Reading the runs back after the commit is rejected: it would open a second transaction on every claim path, and no committed column identifies which pass ended a run. The record-present arm returns through `begun.kind === "claimed"` and reaches no settle, so it needs its own statement: **two reap statements, three drawn paths, and each path reaches exactly one.** The one-source-line ruling below governs the contended and accepted arms of the cut path, and not the record-present arm.

- **The reap runs after the claim's last transaction commits, and it is a git write with no journal row.** EPIC 051 Story 6 (`06-the-first-execution-claim`) already places `git.removePidFile` after the second transaction commits. All six conditions of `AGENTS.md` `### Rules the import matrix cannot express` hold: the deletion carries no database mutation and no event; correctness does not depend on its immediacy; eligibility is the committed `state = 'ended'` the expiry pass wrote, read back through `run_base` and not from an in-flight decision; a failure leaves a ref, which is retryable and never corrupt; `candidate.sweep` at startup is guaranteed to retry it; and the claim settles its own outcome — the result or the refusal — before the reap starts. On the contended arm condition 6 holds because `claim.settle` discarded the journal row and returned before the reap statement runs, and the arm that leaves the row `open` never reaches that statement.

- **The reap is total and never throws, and every failure is a finding.** It mirrors the shape of `candidate.sweep` at `.agents/plan/stories/051.1-the-candidate-and-the-git-primitives/08-the-candidate-namespace-is-enumerated.md:143` — `findings` and returns `{ deleted: readonly string[]; findings: readonly ReapFinding[] }`. Four failures are buckets, and each is a finding and never a throw: the read transaction fails (`code: "reap-read-failed"`, no run id known); a run has no base home (`"reap-home-unresolved"`, with the run id); a listing fails (`"reap-list-failed"`, with the run id); a discard fails (`"reap-discard-failed"`, with the ref). **A failure on one run never stops a later run, and a failure on one ref never stops a later ref of the same run.** The claim discards the value; the return exists so each bucket is asserted by value rather than by absence.

- **A pass that ended no run opens no transaction and calls no git method.** `reapRunCandidates` returns before `storage.transact` when its input list is empty. That is what makes `reap-candidates-no-expired-run` a diagram with no step, which `.agents/plan/authoring.md` names the strongest statement available: every claim that expires nothing must reach no seam through this key.

- **`ExpiredRun` moves to `src/domain/run.ts`, and `ExpireDueRun` is deleted into it.** `src/commands/node/claim-node.ts:79` — `readonly unknown[]` declares the expiry result as `unknown` because `eslint.config.js:221` — `command` allows a command to import `domain/` and a service interface and never another command. The type is the value both commands name, so it belongs in `domain/`. `src/services/execution/index.ts:54` — `ExpireDueRun` declares the same three members, and a service interface may import `domain/`, so the move unifies the pair instead of leaving a third name. The closure of the two deletions is `src/commands/run/expire-runs.ts:6` — `ExpiredRun`, `src/commands/run/expire-runs.test.ts:7` — `ExpiredRun`, `test/sequence/scenarios/expiry-pass-one-due.ts:6` — `ExpiredRun`, `src/services/execution/sqlite.ts:12` — `ExpireDueRun`, `src/services/execution/sqlite.ts:143` — `ExpireDueRun`, `test/helpers/execution.ts:10` — `ExpireDueRun`, `test/helpers/execution.ts:50` — `ExpireDueRun` and `test/helpers/execution.ts:292` — `ExpireDueRun`. `Expiry.expireRuns` at `src/commands/node/claim-node.ts:76` — `expireRuns` tightens to `readonly ExpiredRun[]`.

- **The reap draws `git.listRefs:candidate`, and the projection table does not change.** `.agents/plan/stories/051.1-the-candidate-and-the-git-primitives/04-the-candidate-ref-is-deleted.md:129` — `git.listRefs` projects the call through `refNamespace`, whose table at `:106` — `refs/kanthord/candidate/` maps every ref under that prefix to `candidate`. A per-run prefix is under it, so the token is `candidate` and no table entry moves. The drawn fixture states one ended run, so the token stays unique in the diagram.

- **The reap appends no event.** `run.expired` already records the ending inside the expiry transaction. A ref deletion is not domain state, and an event appended after the transaction commits would sit in a second transaction with no journal row.

- **Supersession and dueness become per-diagram facts, because an epic that supersedes three shipped diagrams across three stories cannot otherwise be green at any story boundary.** `test/sequence/conformance.test.ts:85` — `has` treats a diagram as due when its epic is in `shippedEpics` and no **shipped** epic supersedes it, `test/sequence/conformance.test.ts:126` — `scenario files` requires exactly one scenario file per due diagram, and `test/sequence/conformance.test.ts:275` — `every due scenario conforms` replays each against the real command. So while `"051.5"` is outside `shippedEpics`, `claim-first-execution` is still due: keeping its scenario replays a trace the reaping claim no longer produces, and deleting it leaves a due diagram with no scenario. Appending `"051.5"` in Story 6 instead makes `claim-first-execution-reap` and `claim-initiative-reap` due before their scenarios exist. **Story 10 therefore keys both facts on the superseding scenario file rather than on `shippedEpics`**, so each of Stories 6, 7 and 8 swaps one scenario and stays green, and the epic-level state after Story 9 is exactly what the shipped rule produced. The guarantee does not weaken: a scenario naming a superseded diagram is still refused, and a due diagram still needs exactly one scenario. It widens no epic's authority, because `authoredEpics` still gates every supersession. EPIC 051.6 consumes the same change for the same reason, and it carries no harness story.

- **A predecessor is retired when its own scenario file is gone, and that clause is what keeps Stories 6 and 8 separable.** One `claimNode` statement serves both `claim-branch-base-task` and `claim-lease-free-initiative`, because both return through `begun.kind === "claimed"`, so Story 6 changes both traces at once. Keyed on the superseding scenario alone, `claim-lease-free-initiative` would still be due at Story 6 — `"050.4"` is shipped and `claim-initiative-reap.ts` does not exist until Story 8 — and the runner would replay a twelve-step trace against a thirteen-step claim. **Story 6 therefore retires that scenario as well as its own predecessor's, and the third clause of the supersession rule admits it.** The guarantee does not weaken: a retirement still requires an authored `Superseded by:` naming a diagram some story declares, `scripts/verify-epic-sequence.ts` still refuses a `Supersedes:` that resolves to nothing, and gate row 16 asserts all six diagrams replay once `shippedEpics` holds `"051.5"`, so a declared replacement that never ships is caught at the epic boundary. `claim-lease-free-objective-busy` of EPIC 050.4 Story 3 (`03-the-objective-busy-refusal-drops-the-lease`) is **not** superseded and keeps its scenario: its refusal throws inside the transaction, so it reaches no reap and its trace does not move — but its scenario builds `ClaimNodeDependencies`, so Story 6 widens it with the new key.

- **EPIC 054 delegates the expiry discard here, in its decision and now in its gate.** `.agents/plan/epics/054.4-the-run-lifecycle-pays-its-attempt.md:23` — `No candidate discard on the expiry path` rules that `end-attempt` writes and does not discard, and its table at `:106` — `expire-runs` names **EPIC 051.5's post-commit step** as the discarder of the expiry path. `candidate.reap` is therefore the run-scoped caller of `candidate.discard`, which `:115` — `candidate.discard` requires. Its gate row at `:235` — `end-attempt` asserted the opposite until this epic inverted it; it now asserts that `end-attempt` deletes no ref, with the caller's discard as the control, and `:236` — `expireRuns` adds the zero-count case for the expiry path.
