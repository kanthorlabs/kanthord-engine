# EPIC 108 — Freshness and reconciliation

Status: **blocked**. The external-drive block of EPICs 013 to 025 took the `services/lease` implementation, and EPIC 018 ships `SqliteLease` with `ownerKind` and the lease hierarchy rule. This epic becomes ready when EPIC 018 has landed, so the widened `Lease` interface exists to be consumed.

## Goal

A freshness pass classifies the landing base, and a divergence is repaired by hand. `src/commands/repository/ensure-fresh-base.ts` holds the repository lease, fetches with prune, classifies the landing tip `L` against the upstream tracking tip `U` with `git merge-base --is-ancestor`, records the fetched `U`, and returns one verdict per relation of the table in `docs/proposal/phase-2/integration-and-publish.md`. An upstream that advanced fast-forwards `refs/heads/<branch>` under its own `sync` journal row. A divergence refuses the clone and moves the repository to `needs-reconcile`, transition and event in one storage transaction, and it never resets or force-updates the landing branch. `src/commands/repository/reconcile-repository.ts` merges `U` into `L` in a scratch worktree of the bare home, runs the `unit` check of the repository profile against the resulting merge commit through the `Verify` service of EPIC 107, and lands that commit by compare-and-swap under its own `merge` journal row. A conflict refuses and names the files. Both ref writes run the outside-writer diagnostic of `docs/proposal/phase-1/git-foundation.md` first. `repository.reconcile` moves from `stubbed` to `routed`, `kanthord repository reconcile` calls it, and the repository returns to `ready` with both diverged object ids cleared. The epic reads the `unit` entry of the profile through the `ProfileStore` of EPIC 103, so it needs 103 as well as 107: the profile is what declares the command, and `docs/proposal/phase-2/integration-and-publish.md` requires the check before the ref moves.

## Non-goals

- No objective clone call site and no scheduler. EPIC 110 owns the worker loop, the objective workspace, the node lease and the clone that consumes the verdict of this epic. **EPIC 110 therefore owns the proof that no clone bypasses a freshness pass, and this epic does not claim it.** `ensureFreshBase` has co-located unit tests and no production caller, exactly as the journal verdict of EPIC 007.5 shipped before its caller.
- No objective candidate merge. EPIC 112 owns the frozen candidate, the recompute on a moved base, and its own `merge` rows.
- No publish. EPIC 113 owns `repository.publish`, the `publish` row and the rejection classification. This epic writes no `publish` row and contacts no remote except through the fetch of a freshness pass.
- No startup reconciliation of an incomplete `sync` or `merge` row, and no startup removal of a scratch worktree a crash left behind. Phase 3 owns both, per `docs/proposal/phase-3/recovery.md`. A leftover scratch directory never blocks a retry, because its name carries the journal row id and every attempt mints a new one.
- No profile authoring. EPIC 103 owns the document, the import, the export and the `checks` map. This epic reads the stored `unit` entry and edits no profile.
- No check runner. EPIC 107 owns the timeout, the process-tree kill, the output cap, the filtered environment and the environment identity. This epic calls `Verify.run` once and persists the result.
- No `profile.verify` gate. EPIC 109 owns gate A and gate B.
- No lease implementation, no node lease, no lease expiry recovery beyond the phase-1 rule, and no lease renewal loop. **EPIC 018 implements `SqliteLease`**, with `ownerKind`, the hierarchy rule of `src/domain/lease-hierarchy.ts` and the widened inputs. This epic is the first caller for the `repository` subject, because it is the first epic to write git on an already registered repository and `docs/proposal/database/lease.md` makes the repository lock and the objective lease one mechanism. EPIC 110 calls the same implementation for the `node` subject.
- No landing-branch operation. EPIC 029 removed it from the registry, so no such operation exists and there is nothing to route. A human who needs a different branch registers the repository again. No other phase-2 operation changes lifecycle here.
- No `binding.worker.project`. It stays `stubbed` in `src/http/contract/project.ts`, because the MVP implements one worker kind, so a project binding could only select `general@1`, and EPIC 110 owns worker binding precedence.
- No `revert` intent. This epic writes `sync` and `merge` rows only.
- No removal of `src/commands/repository/assert-no-outside-writer.ts`. EPIC 007 shipped the diagnostic a second time as a command, and a command may not import a command, so the two commands of this epic call `Git.checkOutsideWriter` and append the event themselves. That command keeps its file and its tests, and it stays without a caller until EPIC 113 either adopts it or deletes it.

## Stories

- **The ancestry classification, and it is pure** — `src/domain/repository.ts` gains `ancestryRelations`, the frozen tuple `["synchronized", "upstream-advanced", "local-ahead", "diverged"]`, and `classifyAncestry(input: Readonly<{ landingOid: string; upstreamOid: string; landingIsAncestorOfUpstream: boolean; upstreamIsAncestorOfLanding: boolean }>)`. It returns `"synchronized"` when the two object ids are equal, `"upstream-advanced"` when `landingIsAncestorOfUpstream` is true, `"local-ahead"` when `upstreamIsAncestorOfLanding` is true, and `"diverged"` otherwise. Equality is tested first, so the two ancestor flags a caller reads for an equal pair cannot decide the relation. The function takes two booleans and never a "holds unpublished commits" predicate, because `docs/proposal/phase-2/integration-and-publish.md` states that no such git predicate exists and that the ancestry test stays correct after a remote force-push. The module stays pure and imports `zod` only.
- **Three git primitives, and the scratch root** — `GitPaths` in `src/services/git/index.ts` gains `scratchDirectory`, and `buildGitPaths` in `src/services/git/probe.ts` sets it to `join(input.home, "git", "scratch")` and creates it mode `0700` beside `home`, `keyDirectory` and `runDirectory`. `src/services/git/ancestry.ts` exports `isAncestor(runner, input: Readonly<{ gitDir: string; ancestorOid: string; descendantOid: string }>)`, which runs `git --git-dir=<gitDir> merge-base --is-ancestor <ancestorOid> <descendantOid>` and returns true on exit code `0`, false on exit code `1`, and raises `GitError("unknown")` on any other code, because only `0` and `1` are answers. `src/services/git/worktree.ts` gains `worktreeAdd(runner, input: Readonly<{ gitDir: string; workDir: string; oid: string }>)`, which runs `git --git-dir=<gitDir> worktree add --detach <workDir> <oid>`, and `worktreeRemove(runner, input: Readonly<{ gitDir: string; workDir: string }>)`, which runs `git --git-dir=<gitDir> worktree remove --force <workDir>` and then `git --git-dir=<gitDir> worktree prune`. `--force` is required, because a conflicted merge leaves a dirty tree and the removal must still succeed. `src/services/git/merge.ts` exports `mergeScratch(runner, input: Readonly<{ workDir: string; incomingOid: string; message: string; authorDate: string; committerDate: string }>)`. It runs `git -C <workDir> merge --no-ff --no-edit -m <message> <incomingOid>` with `extraEnv` of `{ GIT_AUTHOR_DATE: input.authorDate, GIT_COMMITTER_DATE: input.committerDate }`, which `gitEnvironment` neither pins nor suppresses, so the merge commit is byte-reproducible; the identity is already pinned to `kanthord <kanthord@kanthord.invalid>`. **The merge names no `--git-dir`**, unlike every other command of `docs/proposal/phase-1/git-foundation.md`: an explicit `--git-dir` pointing at the bare home overrides the worktree's own git directory and the command fails with `this operation must be run in a work tree`. The result is `Readonly<{ merged: true; oid: string }>` on exit code `0`, where `oid` comes from `git -C <workDir> rev-parse HEAD`; `Readonly<{ merged: false; refusal: "conflict"; conflictPaths: readonly string[] }>` when the conflict list holds at least one path; and `Readonly<{ merged: false; refusal: "merge-failed"; cause: MergeCause; detail: string }>` otherwise, where `detail` is the stderr passed through `stripUserinfo`. `MergeCause` is exactly `"unrelated-histories" | "unknown"`: the value is `"unrelated-histories"` when the stderr holds the substring `refusing to merge unrelated histories`, and `"unknown"` otherwise, so a caller and a test read a value this service produces and never the git wording. Unrelated histories classify as `diverged` and cannot merge. **The conflict list is byte-safe.** It comes from `git -C <workDir> diff --name-only --diff-filter=U -z`. `-z` is required: without it git C-quotes a path that holds a quote, a tab or a newline, and no decoding recovers the original name. The stdout splits on the NUL byte, the trailing empty segment drops, each remaining segment maps to `Buffer.from(segment, "utf8")`, the buffers sort with `Buffer.compare`, and `conflictPaths` is the decoded strings in that order. `GitRunResult.stdout` is a UTF-8 string already, so a path whose bytes are not valid UTF-8 carries the replacement character `U+FFFD`, and this epic adds no byte channel to the runner. Every new primitive reaches `Git` in `src/services/git/index.ts` and binds in `src/services/git/binary.ts`. `--no-ff` is required, because the landing tip is not an ancestor of the incoming tip and a real merge commit must land.

Both commands of this epic pass `["merge", "sync"]` for `refs/heads/<branch>`, so the baseline is the last completed local write of that ref whichever intent wrote it. Without the change the first reconcile of every repository refuses, because registration writes a `sync` baseline row and no `merge` row exists, and every freshness pass after a reconcile refuses, because the last completed `sync` row no longer names the ref. A null baseline against a present ref stays a mismatch, which is the safe direction; registration always writes the baseline, so a registered repository never reaches it. The existing `src/services/git/outside-writer.test.ts` cases pass a one-element array and keep their asserted values. - **Every pass records the fetched upstream, and only a transition writes an event** — `docs/proposal/phase-2/integration-and-publish.md` makes the recorded `U` step three of every pass, so every pass ends in exactly one storage transaction that sets `repository.fetched_upstream_oid` to `U` and `updated_at` to `clock.now()`. `diverged` appends `repository.needsReconcile` with `subjectKind: "repository"`, `subjectId` of the repository id, `actorKind: "daemon"`, `actorId` of `input.actor` and the payload `{ landingOid, upstreamOid }`, and it sets `state` to `needs-reconcile`, `diverged_landing_oid` to `L` and `diverged_upstream_oid` to `U`, so the state transition and its event append sit in one transaction and the `repository` refine of `src/domain/repository.ts` holds by construction. **Every other relation appends no event.** `docs/proposal/database/event.md` makes an event the record of a transition or a human decision, and `synchronized`, `local-ahead` and `upstream-advanced` are none: a pass that changes no state has the recorded `fetched_upstream_oid` as its evidence, and a fast-forward has its completed `sync` row. `upstream-missing` and `landing-missing` write no column other than the two above and never set `needs-reconcile`, because a deleted upstream branch is not a divergence.
