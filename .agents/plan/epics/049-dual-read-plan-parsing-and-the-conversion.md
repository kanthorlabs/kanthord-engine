# EPIC 049 — Dual-read plan parsing and the conversion

Status: **draft**. It follows EPIC 048 by sequence order.

## Goal

A plan document carries a deliverable and a verify block, and an existing document still parses:

- `planFrontmatter` accepts `deliverable` and `verify`, and it still accepts `worker`;
- a document that carries both `worker` and `deliverable` is refused, and a document that carries neither is refused;
- `plan import` stores the deliverable and the verify block, and `plan export` round-trips both byte-identically;
- `plan convert` reads a legacy plan directory, runs every generated command at its pair's intended commit, writes only a command that ran, and emits the converted document set plus a report, with no graph row.

## Non-goals

- **No apps-tree conversion.** This epic ships the mechanism. A human runs `plan convert` against `kanthord-apps`, confirms each command, and imports the result. EPIC 046 states the boundary.
- **No unvalidated command reaches a document.** `worker.md` section 12 states the conversion runs every generated command at its intended commit before it writes that command. `plan convert` therefore runs each one. A command that did not run leaves `commands: []`, and the node stays ineligible. The report names it. Nothing writes a command a human must check afterwards.
- **No worker field in a converted document.** The conversion deletes `worker`. `worker.md` section 1 forbids it in a plan document.
- **No assignment in a document.** `assignment` is runtime state. `planFrontmatter` gains no `assignment` key, and a document carrying one is `frontmatter-invalid`.
- **No pair inference beyond the table.** The conversion maps a source field to a deliverable by the table of the Decisions. It infers nothing from a title or a body.
- **No removal of `worker` from the schema.** EPIC 057 removes it. Dual read is the whole point of this epic, per `worker.md` section 13.

## Decisions

- **Dual read is a bounded window, and the two shapes are exclusive per document.** `planFrontmatter` in `src/domain/plan-document.ts:16` gains `deliverable` and `verify` as optional keys, and `planFrontmatterKeys` at line 7 gains both. A document carrying `worker` and `deliverable` together raises `frontmatter-invalid` with the issue path `deliverable`. A document carrying neither raises `frontmatter-invalid` with the issue path `deliverable`. One shape per document, and the window closes at EPIC 057.

- **`verify` is required in the new shape, and it may be empty.** A document that carries `deliverable` and no `verify` raises `frontmatter-invalid` with the issue path `verify`. An initiative and a parent objective carry `verify: {paths: [], commands: []}`, written out in full. An implicit default would make an unwritten block indistinguishable from an author's empty one.

- **`renderDocument` emits `deliverable` and `verify` in a fixed key order, and it drops `worker` when a deliverable is present.** `src/domain/plan-render.ts:41` emits `id`, `kind`, `title`, `deliverable`, `repo`, `depends_on`, `verify`, in that order. That is the order of the four examples in `worker.md` section 2, and a canonical order that disagrees with the design document would make every example in it wrong. `worker` is emitted only for a legacy document, in its current position at line 55. The order is fixed because the round trip must be byte-identical, per the `AGENTS.md` determinism rule.

- **`verify` renders as a nested block, and its scalars are quoted by `quoteScalar`.** The renderer emits `verify:`, then `  paths:` with one `    - <quoted>` line per entry, then `  commands:` likewise. An empty list renders as `  paths: []`. `src/domain/plan-render.ts:17` already holds `quoteScalar`, and a command string holding a quote, a backslash or a tab is therefore round-trip safe.

- **Two finding codes are added, and `worker-unknown` is untouched.** `pair-illegal` names a document whose `(kind, deliverable)` pair fails `nodePairLegality`. `verify-invalid` names a **stored node** whose `verify_json` fails `verifyBlock`. It is not a document-parse finding: `planFrontmatter` embeds `verifyBlock`, so a submitted document with a malformed verify block already raises `frontmatter-invalid` at parse and never reaches a `ParsedDocument`. `verify-invalid` is therefore the `plan-candidate.ts` guard over persisted state, and persisted state is a different boundary from a submitted document. Migration 11's `CHECK (verify_json IS NULL OR json_valid(verify_json))` proves the gap is real rather than theoretical: `{"paths":["a/../b"],"commands":[]}` is valid JSON and passes the CHECK while failing `verifyBlock`. A database written by an older grammar, by manual SQL, by external tooling or by a migration defect can hold such a row, and no lint rule reaches stored data. The guard also covers a cross-column invariant that is not a grammar question at all: a node with a non-null `deliverable` and a null `verify_json` is inconsistent persisted state. The query-side `500` of EPIC 047 is not a substitute, because `validateCandidate` collects findings across a whole candidate without aborting, and a throw ends the walk at the first bad row. Both are `structural` scope in `src/domain/plan-finding.ts:42`. `worker-unknown` keeps its meaning for a legacy document until EPIC 057.

- **The conversion table is the table of `worker.md` section 12, and it adds no row.**

  | Source                            | Result                        |
  | --------------------------------- | ----------------------------- |
  | `worker: claude.te@1`             | `deliverable: test`           |
  | `worker: claude.swe@1`            | `deliverable: implementation` |
  | `kind: initiative`                | `deliverable: expansion`      |
  | `kind: objective`                 | `deliverable: expansion`      |
  | the `**Input:**` path of the body | one `verify.paths` entry      |

  A `kind` rule wins over a `worker` rule, because an initiative and an objective hold children and a child, not a commit, is their outcome. Every objective converts to `expansion` unconditionally, exactly as section 12 states. An atomic objective is legal in the model of EPIC 047, and it is not a conversion result.

  **A `worker` value outside the two rows is a refusal, not a manual reason.** `plan convert` refuses `worker-unmapped` and names the path. The tree being migrated holds exactly two values — `apps/.agents/plan` carries 77 documents with `claude.swe@1` and 68 with `claude.te@1`, and no others — so both rows of the table cover it and every other value means the operator pointed at a tree this rule was not written for. Section 12 is a migration rule for one tree, and inventing a row for a value that tree does not hold would convert a document nobody inspected. A refusal says that; a per-node manual reason would bury it in a report for a case that cannot arise.

  **An initiative and an objective take `paths: []` and `commands: []`.** Section 12 states it. The `**Input:**` rule applies to a task only, and the converter reads no body of an initiative or an objective.

- **The conversion is a document-set function, not a document function.** `convertDocumentSet(documents, templates)` in `src/domain/plan-conversion.ts` takes the whole parsed set. A single-document signature cannot answer the questions the table asks: which repository a task inherits from its objective, which `test` node an `implementation` node depends on, and what command that `test` node produced. The function is pure and it returns the converted set plus the report.

- **The converted set is a full node projection, and the CLI derives nothing the domain already derived.** `convertDocumentSet` returns `ConversionResult` holding `nodes: readonly ConvertedNode[]`. A `ConvertedNode` carries every field the renderer needs and every decision the runner needs: `sourcePath`, `identity`, `kind`, `title`, `dependsOn`, `repo`, `instruction`, `acceptance`, `deliverable`, `verify`, `passthrough`, and three decision fields — `resolvedRepository: string | null`, the objective ancestor's repository; `pendingCommand: string | null`, the raw command `C` that `applyTemplate` produced; and `manualReasons`. The CLI never calls `applyTemplate`, never walks ancestry and never re-reads a template. A CLI that re-derives a domain decision is a second expression of the rule, and it drifts. `renderConvertReport` projects `ConversionResult` down to the report's four keys; the report stays the human's document and the result stays the machine's.

- **A task inherits its repository from its nearest objective ancestor, walked through `derivedParentPath`.** `worker.md` section 2 puts `repo` on the objective, and `repo-on-task` is already a finding code at `src/domain/plan-finding.ts:27`. The parent edge is `ParsedDocument.derivedParentPath` at `src/domain/plan-document.ts:38`, which the directory layout derives. `depends_on` is a dependency edge between siblings and it is not ancestry; walking it would inherit a repository from an unrelated node. `ConversionInput` therefore carries `derivedParentPath`, and the walk follows it upward to the first `objective`.

- **An implementation node with two `test` dependencies reaches `manual`.** The reason is `test-dependency-ambiguous`. Picking one would write a command nobody chose.

- **`convertDocumentSet` is two-pass and its output does not depend on input order.** An implementation node copies the converted `verify.paths` of the `test` node it depends on, so a single pass over the input array fails whenever the implementation precedes its test. The function first indexes every document by path, then runs pass 1 over the initiative, objective, passthrough, unmapped-worker and `test` documents, then runs pass 2 over the `implementation` documents against the pass-1 index. The returned `nodes` array sorts by `sourcePath` through `comparePaths`. A test submits the same set in two different input orders and asserts the two results are deep-equal, so the order independence is proved and not assumed.

- **`plan convert` is a declared, breaking rename of the shipped command, and the old name moves.** `src/cli/plan/convert.ts` already ships `plan convert` as the harness converter, registered at `src/cli/program.ts:256`. This epic takes the name for the plan-tree converter, and the harness converter becomes `plan convert-harness` in `src/cli/plan/convert-harness.ts`. The exported symbols move with it — `registerPlanConvertHarness` and `PlanConvertHarnessCliInput` — so the two modules never collide at the `program.ts` import site. The duplicate-registration guard at `src/cli/plan/convert.ts:28-31` returns silently when a `convert` subcommand already exists, so a collision would not fail a test; it would ship a CLI missing one of the two commands. The rename is therefore ordered before the new command, and a test asserts both subcommands are registered and distinct.

- **`plan convert` writes files and a report, and it touches no database.** It is a CLI command under `src/cli/plan/convert.ts`, and it reaches no command and no query. `AGENTS.md` states `cli/` imports `domain/`, `http/contract/` and `cli/` only. The conversion rule is the pure function above, and the CLI owns the file system only.

- **Process execution reaches the CLI through an injected callable, and the implementation is a service.** The CLI never imports `node:child_process`, and it never imports a service interface either; `main.ts` composes the callable and passes it in, exactly as it passes the migration handler for `kanthord db migrate`. `src/cli/plan/convert.ts` declares its own `ConvertRunner` callable type over plain data, and `main.ts` binds it. The capability behind it is `services/verify`, whose `Verify` interface at `src/services/verify/index.ts` already takes a `CheckRequest` of `command`, `cwd`, `env`, `timeoutMs` and `outputLimitBytes` and returns a `CheckOutput`. This epic adds the first real implementation beside `NotImplementedVerify`.

- **`node:child_process` is allowed, and portability is a runtime refusal rather than a compile-time ban.** A deployment target without process creation — a Cloudflare Worker, an AWS Lambda — cannot be served by refusing the import at build time, because the same source ships to every target. `src/services/verify/node-spawn.ts` therefore imports `node:child_process` and probes the capability at construction: when process creation is unavailable it refuses every `run` with `VerifyError` and a new code `process-unavailable`, naming the runtime. A second implementation can drive a remote executor over the same interface without one line of the CLI changing. `eslint.config.js:245-258` enumerates which modules may create a process; add `src/services/verify/node-spawn.ts` to that list beside `src/services/git/launcher.ts`. That rule states which module owns process creation, which is an architecture rule, and it is not the portability check.

- **The checkout is a `git archive` extraction, never a working-tree checkout.** `git --work-tree <dir> checkout <ref> -- .` writes the source repository's index, so a converter run would dirty a repository the human still uses. The runner extracts the commit tree instead, and it touches no index. The temporary directory is removed in a `finally`, so a throw does not leak it.

- **The report names every node the human must finish by hand, and `manual` is a closed set of six reasons.** `convert-report.json` holds, per node, the source path, the derived deliverable, the derived `verify.paths`, the derived `verify.commands`, and a `manual` list. The six reasons are `command-failed`, `input-ambiguous`, `input-missing`, `template-missing`, `test-dependency-ambiguous` and `test-dependency-missing`, and the tuple is pinned in that alphabetic order. `worker-unmapped` is not among them: it is a refusal, per the conversion table above. `worker.md` section 12 names `test-dependency-missing` and counts 8 such nodes in the apps tree. `command-failed` is the reason a generated command did not run as expected at its intended commit, and it is the reason section 12's validation rule produces. The tuple `manualReasons` is exported and asserted by deep equality, so a seventh reason is a deliberate change.

- **The report is canonical JSON, and its shape is pinned.** Keys sort bytewise at every level. A node entry sorts by its source path through `comparePaths`. A `manual` list sorts by the index of the reason in `manualReasons`. The file ends with one newline. Two-space indentation. A report that is not canonical cannot be compared across two runs, and the idempotence rule below depends on that comparison.

- **A command template is per repository, and its file format is pinned.** `--template <file>` reads a JSON object mapping a repository name to a template string. The template holds exactly one placeholder, `{path}`, which the converter replaces with the node's single `verify.paths` entry, verbatim and unquoted. No other placeholder exists, and an unknown placeholder is a parse error naming it. One placeholder is enough for the shipped apps tree, and a grammar admits an expression nobody can validate. A repository with no entry yields `commands: []` and the reason `template-missing`.

- **A `test` node inverts its command, and an `implementation` node repeats it.** The template yields one command string `C`. A `test` node emits `"! " + C`. An `implementation` node emits the `C` of the `test` node named by its `depends_on`. `worker.md` section 2 states the inversion rule and section 11 states why it is verifiable as a pair.

- **Every generated command runs at its intended commit before it is written, and the intended commit is keyed to the test/implementation pair.** `worker.md` section 12 states the validation rule and section 11 states that a `test` and its `implementation` are verifiable **as a pair**. The polarity of a command is a property of a commit, not of a repository: a `test` node writes `"! C"`, which exits zero only where `C` fails, and its `implementation` writes `C`, which exits zero only where `C` passes. One ref per repository cannot satisfy both. One ref per objective cannot either, because an objective holds many tasks that landed at different commits, and nothing makes an objective's first commit the failing commit for every test beneath it. The pair is therefore the key. `--repo <name>=<path>` names a checkout per repository, and `--at <test-source-path>=<failing-ref>..<passing-ref>` names the pair's two commits. The `test` node runs `"! C"` at `failing-ref`, and every `implementation` node whose `depends_on` names that test runs `C` at `passing-ref`. The key is the test node's own `sourcePath`, which `ConvertedNode` already carries, so the CLI resolves it without walking ancestry. There is no repository-wide shorthand: one `--at` namespace holding both repository names and source paths would need collision, duplicate and precedence rules, and it would buy nothing the pair key does not already give. The converter extracts the commit through `git archive` into a `mktemp` directory it owns, runs the command through the injected runner, and asserts a zero exit. It never writes the source repository's index. A command that exits non-zero, or that cannot run because no checkout was supplied, is dropped: the node takes `commands: []` and the reason `command-failed`. A generated command never reaches a document unvalidated.

- **Both refs resolve to immutable commit object ids before the first command runs.** `--at` accepts a ref, and a branch moves. The converter resolves `failing-ref` and `passing-ref` to object ids once, up front, and every later extraction names the object id. A branch that moves between pass 1 and pass 2 would otherwise change the answer inside one run.

- **A node that would take a command and is covered by no pair range is a refusal.** `plan convert` refuses `commit-range-missing` and names the test source path it needs, unless `--commands-none` is passed. The reasoning is the reasoning of `checkout-required`: an operator who omitted a range must not receive a plausible tree with a command silently dropped.

- **`--repo` is required for a node that would take a command, and its absence is a refusal, not a silent empty list.** `plan convert` run with no `--repo` refuses with `checkout-required` and names the repositories it needs, unless `--commands-none` is passed. `--commands-none` converts deliverables and paths only, and every node with a template reaches `manual` with `command-failed`. An operator who forgot the flag must not receive a plausible tree with every command silently dropped.

- **The input is a legacy tree, and a new-shape document in it is a refusal.** `plan convert` refuses `already-converted` and names the path. There is no deployed tree to preserve and no partial migration to resume: the apps tree converts in one run, so a document that already carries `deliverable` means the operator pointed at the wrong directory. Refusing says so. Accepting it would require a passthrough rule, and a passthrough rule cannot be made honest — a document carrying `verify: {paths: [], commands: []}` may be a failed conversion, a `--commands-none` run, a hand-authored node, `input-missing`, `input-ambiguous` or a missing test dependency, and the document holds no provenance separating them. Re-deriving would also apply the legacy `**Input:**` convention to a document that never owed it. The converter therefore never reads its own output.

- **`plan convert` is deterministic over its inputs, and determinism is not a validity claim.** Two runs over the same legacy tree, the same template file and the same resolved object ids, into two empty output directories, write byte-identical documents and a byte-identical report. That is the property an operator actually exercises, because a run that refuses or converts badly is retried against the same legacy input with better flags, never against its own output. A byte-stable command can still be the wrong command; the validation rule above is what makes it right. Both properties are required, and neither substitutes for the other.

- **The determinism claim covers the conversion, not the commands it runs.** `convertDocumentSet` is pure and reproduces exactly. A command is an external input, like the template file: an immutable checkout does not make a command deterministic, because a command may read the clock, the environment or the network. The hermetic test therefore pins the outcomes it asserts, using a template whose command deterministically fails and one whose command deterministically succeeds. Claiming byte-identity across two runs that execute an arbitrary command would be a claim the converter cannot keep.

- **The output directory must be empty or absent, and it must not sit inside the input directory.** `plan convert` refuses `output-not-empty` and `output-inside-input`. Overwriting in place would destroy the legacy tree the human still needs to compare against, and an output nested in the input would feed the converter its own output on the next run, which `already-converted` would then refuse for a reason that names the wrong cause.

- **A report path is relative to the input directory root.** An absolute path would make two runs from two working directories produce two reports, and the determinism assertion would fail for a reason that is not a defect.
