# EPIC 055.1 — The grant governs the run

Status: **draft**. It follows EPIC 055 by sequence order, and it runs before EPIC 056. It consumes EPIC 055's grant row, grant service, caller principal and `Grant` scheme, EPIC 050.1's claim, EPIC 050.2's renew and report, and EPIC 051.1's candidate.

It carries a decimal number because EPIC 056 and EPIC 057 are already authored, and renumbering them would break every cross-reference to them.

**Dispatch prerequisite.** EPIC 055 ships before this one, because every enforcement here reads a row and a caller kind that epic creates. Story 1 inserts `"055.1"` into `scripts/epic-sequence-range.ts:1` — `authoredEpics` after `"055"`, and Story 9 appends it to `shippedEpics`, which `test/sequence/conformance.test.ts:254` — `shippedEpics` requires to stay a prefix of `authoredEpics`. Story 9 is therefore last in dispatch order.

## Goal

The grant is the authority of every external write:

- `claim`, `report` and `renew` each read the grant inside their own transaction and refuse an operation the list omits or a node outside `root`;
- the run records the grant that opened it, so a limit, a revocation and an adoption rule all have a subject;
- both limits are read, checked and incremented inside the claim transaction;
- an expiry, a revocation and a closed root each have an implemented effect on a new claim and on an open run;
- a grant-backed worker never opens a structural run, and the refusal is at claim.

## Non-goals

- **No grant row, no migration and no new operation.** EPIC 055 ships migration `17`, `src/domain/grant.ts`, `src/domain/grant-scope.ts`, `src/services/grant/**`, `src/domain/caller.ts`, the `Grant` scheme and the four grant operations. This epic writes columns that already exist and wires functions that already pass their own tests.
- **No holder key, no process identity and no client.** EPIC 055 states all three, and this epic does not restate them.
- **No new refusal on the actor branch.** Every guard here is reached only when `caller.kind` is `grant`. A harness actor's claim, report and renew keep the seam trace EPIC 050.1 and EPIC 050.2 drew.
- **No `release` grant.** EPIC 055 rules `release` is not a granted operation. `node.release` keeps `allowedActors` without `grant`, and an abandoned external run expires on `runTtlMs`.
- **No non-null constraint.** `run.grant_id` stays nullable. EPIC 057 enforces.

## Decisions

- **Every grant guard is on the grant branch, and no shipped claim path moves.** `src/commands/node/claim-node.ts:96` — `callerRecord` is a plain value dependency bound once at `src/main.ts:565` — `callerRecord`, and the four worker commands take the authenticated principal as command input. The guard is therefore `caller.kind === "grant"`, and the grant paths are new paths with empty prior sets. Putting the grant read on the shared prelude would move the seam trace of `claim-success-task`, `claim-success-initiative` and `claim-refusal-objective-busy` of EPIC 050.1 and of `renew-success` and `report-authority-prelude` of EPIC 050.2, forcing five supersessions to prove a read no actor caller performs. `.agents/plan/authoring.md` states a branch is a separate diagram with its own id, and this is that branch.

- **The grant prelude reads its whole snapshot, then one pure function judges it.** Inside the claim transaction and in fixed order: the grant row by id, the root node, the target node, and the count of the grant's active runs. `grantClaimVerdict` in `src/domain/grant-scope.ts` then returns the first refusal of the fixed order below, or `ok`. Refusing between the reads would put the refusal order in the command and give each refusal its own terminal step, so the claim would owe one diagram per refusal group. Reading a snapshot the refusal does not need costs one count query inside a transaction already open, and it buys one refusal diagram, one decision table and a refusal order that is a pure function a unit test enumerates.

- **The claim's grant refusals precede every shipped claim refusal, and their order is fixed:** `operation-not-granted`, `grant-revoked`, `grant-expired`, `root-closed`, `outside-root`, `root-not-claimable`, `client-not-author`, `max-claims-exhausted`, `max-active-runs-exhausted`. Authority is judged before the plan, because a caller with no authority must not learn the state of the graph. Within the group the order is the operation, then the grant's own liveness, then the root's liveness, then the scope, then the node kind, then the two limits. Every pair that can hold at once is enumerated in a decision table, and the three-way case `grant-expired` with `root-closed` with `max-claims-exhausted` is asserted, because those three are independent conditions that a single fixture can hold together.

- **The in-transaction read refuses `grant-revoked`, and that is the revocation race.** `src/http/server/auth.ts:28` — `resolveActor` runs before the command transaction opens, so a revocation may commit between authentication and the command. The middleware therefore proves only that the grant was live when the request arrived. `claim`, `report` and `renew` re-read the grant inside their own transaction and refuse `grant-revoked` when `revoked_at` is set. Without the re-read a revoked client lands one more write, which is exactly the window revocation exists to close.

- **`root` is a scope, never a unit of work.** `grantScopeVerdict` returns `outside-root` for a node outside the subtree and `root-not-claimable` for `targetId === root`, per `worker.md` section 10. EPIC 055 ships the function; this epic reaches both verdicts from the claim.

- **A grant-backed worker never opens a structural run, and the refusal is at claim.** `worker.md` section 10 states an external client does orchestration only: it submits no graph patch and creates no node. Refusing only at acceptance lets a client hold an unusable structural run for a full lifetime. `claim` refuses `client-not-author` when the node's run kind is `structural` and the caller is a grant, and the acceptance keeps the same refusal as the second gate.

- **A client asserts its own availability, and the daemon trusts it.** `worker.md` section 4 states a worker runs a self health check before it claims. A client has no supervisor, so it makes the assertion itself, in the `available` field EPIC 050 adds to the claim request. A client that asserts `true` when it is not available holds a run it cannot use until the run expires. `worker.md` section 11 lists that among the client failure modes the daemon does not detect.

- **`max_claims` counts claims that opened a run.** `worker.md` section 10 states it. The replay branch of `src/commands/node/claim-node.ts` adopts an existing run and opens none, so it raises nothing.

- **Both limits are read, checked and incremented inside the claim transaction.** `worker.md` section 10 states the daemon counts every limit against the grant id in one operation. The `BEGIN IMMEDIATE` transaction of EPIC 050 serialises two concurrent claims, and the increment is conditional on the value read, per the grant service EPIC 055 ships.

- **The run records its grant, and the claim is the first writer.** The claim writes `run.grant_id` when the caller is a grant, and leaves it null otherwise. The `CHECK ((driver = 'external') OR grant_id IS NULL)` of migration `17` therefore first carries traffic here. A `report` or `renew` whose grant is not the run's grant refuses `run-grant-mismatch`, and a new grant adopts no run whatever the two grants name, per `worker.md` section 4.

- **A revocation and a root close end their runs in the same transaction that records them.** A revocation that left a run alive for one more write would let a revoked client land a commit. `revoke-grant.ts` writes `revoked_at`, ends every open run of the grant and raises each fence in one transaction. `close-objective.ts` and `delete-node.ts` do the same for every grant whose `root` is that node.

- **The grant caller reaches a handler for the first time here, so the handler context changes here.** EPIC 055 leaves `src/http/server/app.ts:36` — `actor` and `src/http/server/dispatch.ts:39` — `actor` untouched, because no operation admits a grant caller there and `demand(c, "actor")` is never reached by one. This epic admits the grant caller to `node.claim`, `node.report` and `node.renew`, so `HandlerContext` carries `caller` instead of `actor`, and the twenty-four `context.actor` sites across nineteen handler files read the actor through one helper that throws `internal-error` for a non-actor caller. That throw is unreachable, because `src/http/server/authorize.ts:11` — `allowedActors` refuses a grant caller on every operation those handlers serve. The sweep lands with the change that forces it, per `.agents/plan/authoring.md`.

- **The caller kind admitted per operation is registry data, and three rows change.** `src/http/contract/execution.ts:303` — `node.claim` and `src/http/contract/outcome.ts:140` — `node.report` and EPIC 050.2's `node.renew` each add `grant` to `allowedActors`. `node.release` does not. The four grant operations of EPIC 055 keep `["human"]`.

## Stories

Each entry is a name and the output it contributes. The story file holds the change, the tasks and the diagrams, and it declares its kind. `.agents/plan/authoring.md` is the standard.

1. **The grant caller reaches the worker handlers.** Add `grant` to `allowedActors` on `node.claim`, `node.report` and `node.renew`; replace `actor` with `caller` on `HandlerContext` at `src/http/server/app.ts:36` — `actor` and on `src/http/server/dispatch.ts:39` — `actor`; add the actor-reading helper and repoint the twenty-four `context.actor` sites at it; replace `actorId` and `actorKind` with the caller union on the input of the four worker commands, starting at `src/http/server/node/claim-node.ts:31` — `actorId`. Insert `"055.1"` into `authoredEpics`. `story-foundation`.

2. **The claim refuses under the grant.** Add the grant prelude and `grantClaimVerdict` to `src/commands/node/claim-node.ts`, and the nine refusal codes to `src/http/contract/errors.ts` and `src/cli/exit-code.ts`. Draws `claim-grant-refusal`, with an empty prior set: the transaction, the expiry pass, the grant read, the root read, the target read, the active-run count, and the refusal. `story-implement`.

3. **The claim of a task under a grant.** The success path writes `run.grant_id`, increments `claims_used` conditionally, and derives the caller record from the grant as `{ worker: grant.worker, authorized: [grant.worker] }`, which `.agents/plan/epics/050.1-the-claim.md:57` — `EPIC` already rules. Draws `claim-grant-success`, with an empty prior set. Carries the concurrency cases and the replay case. `story-implement`.

4. **Revoke, and the runs it ends.** Add `src/commands/grant/revoke-grant.ts` writing `revoked_at`, ending every open run of the grant and raising each fence, in one transaction, with the handler at `src/http/server/grant/revoke-grant.ts` and the `src/main.ts` binding. Draws `grant-revoke-success`, with an empty prior set. `story-implement`.

5. **The report enforces the grant.** Add the operation check, the in-transaction `grant-revoked` re-read and `run-grant-mismatch` to `src/commands/outcome/report-outcome.ts`, on the grant branch. Draws `report-grant-authority`, with an empty prior set. `story-implement`.

6. **The renew enforces the grant.** Add the same three to EPIC 050.2's `src/commands/run/renew-run.ts`, on the grant branch, and keep the `max_lifetime_at` cap ahead of the expired-grant admission. Draws `renew-grant-authority`, with an empty prior set. `story-implement`.

7. **A human close of the root ends the grant's runs.** Extend `src/commands/outcome/close-objective.ts` to end every open run of every grant whose `root` is that node, in the close transaction. Draws `close-objective-root-grants`, superseding `baseline-close-objective`. This is the first drawing of the close path, so it draws the pair. `story-implement`.

8. **A discard of the root ends the grant's runs.** Extend `src/commands/node/delete-node.ts` with the same effect. Draws `delete-node-root-grants`, superseding EPIC 050.3's `delete-node-guard`. `story-implement`.

9. **The proposal records the enforcement.** Extend `docs/proposal/phase-2/grants-and-clients.md` with the three enforced operations and their in-transaction read, the fixed refusal order and its decision table, the revocation race and the re-read that closes it, the run binding and `run-grant-mismatch`, the two limits and their counting rule, the three end effects with their implementations, and the orchestration-only rule with its claim-time refusal. Append `"055.1"` to `shippedEpics`. It is last in dispatch order. `story-foundation`.
