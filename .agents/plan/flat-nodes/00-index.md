# Plan 00: Index

## Scope

This plan set implements the flat-node model of the Mission Service and the rulings R1 to R14 that Ulrich ruled on 2026-10-17 (`docs/brainstorm/HANDOFF.md:36`). The design pages of the root pull request #87 (branch `design/flat-nodes`, head `5fa6db3`) are the rule. The set covers:

- Tasks as optional content of an `implement` node, with `task_<ulid>` identities and no `mission_node` row. A node with no task is its own single work unit (`docs/brainstorm/mission-service.md:40-46`, `mission-service.impl.md:17`, `:42`).
- One node kind: a node holds `work` (`implement` or `examine`) and `requires` (`mission-service.md:27-38`). No containment, no `parent_id`, no `node move`, no ancestor closure, no wait edges, no initiative steps condition (`mission-service.md:48-69`, `:514-520`).
- The `examine` reads of the direct dependencies, `dependency_outcome_ids`, the fix-node proposal and the `mission.execution.dependency.*` reads (`mission-service.md:221-225`, `mission-service.impl.md:261-312`). An `examine` node checks out each repository binding that it names read-only at the base-branch head (`worker-service.md:422-431`).
- The binding rule table by work with no binding from the project, and the ordered storage list with the grant failover of plan 03b (`mission-service.md:73-89`, `:303-308`, `mission-service.impl.md:49-61`, `:363-386`).
- The match of the Scheduler Service: `declared_works`, binding `traits`, `admits`, `unmatchedClaims` and the two coverage refusals (`scheduler-service.md:233-268`, `scheduler-service.impl.md:149-188`, `project-service.md:98-109`).
- The worker methods by work (`worker-service.md:39-40`, `worker-service.impl.md:54-56`).
- An `implement` node with two or more repository bindings (`mission-service.md:77-82`, `worker-service.md:289-359`). Plans 01 to 09a limit it to one binding, and plan 09b lifts the limit (decision D28). Plan 10 documents it in the root.
- The E2E proof against the todoapp plan (`docs/brainstorm/assets/todoapp/`).
- The dashboard (`apps`) and the root reference, explanation and how-to pages.

The decisions D1 to D29 that the plans cite are in [decisions.md](decisions.md).

## Out of scope

- Every alternative that `proposal-v2.md` section 6 closed with `action:NO`: labels, exclusive bindings, a model tier field, node concurrency, trait probes and dependency reads for an `implement` node.
- A data migration, a legacy read mapping, a quiescence check and an upgrade report (RULED 2026-10-17, decision D2).
- The open HANDOFF items, also `HANDOFF.md:80` (a node names a worker binding). A task implements the page as written and states a gap in one line (decision D1).
- The Scheduler eligibility report and the on-demand request. Neither exists in code (`src/apps/cli/completeness.test.ts:38-41`, `docs/cli/scheduler.md:559-563`). The plans change their documentation only (decision D23).
- The executed plan sets `erd-01-setup/`, `erd-02-execution/` and `erd-03-integration/`. They stay as a record.
- A live run against a real provider inside `pnpm run verify`. Plan 08 runs `make e2e` by hand as the acceptance step.

**Rationale for order.**
Plan 01 removes the task rows first, because every later plan reads a node row as a schedulable node. The old grammar (`kind: task`, `parent:`) still maps onto content, so the product stays usable.
Plan 02 moves every semantic that reads children onto the direct dependencies while containment still exists, so plan 03 deletes containment with no reader left.
Plan 03 deletes the kinds and the containment and adds `work` and `requires`. The worker unit switches from the `tasks` inference to `work` in the same plan, because `nodeKindOf` reads a field that plan 03 removes.
Plan 03b holds the storage failover, because its record key and its refusal code wait for the rulings B1 and B2. Plan 03 grants on the first storage binding, so no later plan waits for 03b before plan 08.
Plan 04 is a pure rename. It follows plan 03 so that its diff holds no semantic change.
Plan 05 needs `work` and `requires` on the revision (plan 03) before the claim walk can read them.
Plan 06 needs the final engine contract of plan 05, because the todoapp import needs covering worker bindings.
Plan 07 follows the engine contract of plan 05. It runs in parallel with plan 06.
Plan 08 needs the merged plans 06 and 07 and the regenerated workbench tool table of the final engine. Its first task merges pull request #87, so the root fixture and the engine change together (R14).
Plan 09a adds the Mission and Intake rules of the multi-repository node and keeps the limit, so the node API still refuses a second binding. Plan 09b adds the worker loops and lifts the limit. Each loop keeps the one-binding path unchanged.
Plan 10 moves the root `engine` pointer to plan 09b and deletes the limit from the root pages.

An initiative and an objective still exist after plans 01 and 02, and plan 03 removes both. Pull request #87 stays open until task 08.1, so no live `make e2e` runs on the new fixture before plan 08 (decision D3).
