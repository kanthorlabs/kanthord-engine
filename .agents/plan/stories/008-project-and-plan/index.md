# EPIC 008 — Project and plan — stories

Epic: `.agents/plan/epics/008-project-and-plan.md`
Prereq: EPIC 007.5 (sequence order), expanded at `.agents/plan/stories/007.5-startup-recovery/` (seven stories, untracked at the time of writing). Nothing in this epic touches the startup sequence, so the two are independent in practice. EPIC 007's stories are at `.agents/plan/stories/007-repository-registration/`.

A human creates a project, binds a repository, imports a hand-written plan, exports it byte-identical, and re-imports it with a decision per node. A re-import never applies a partially valid graph.

This is the largest epic in phase 1. It carries the conflict resolution of `docs/proposal/phase-1/plan-format.md`, and it is the epic that fills `src/domain/` with the plan vocabulary.

## Dispatch order

This is a dependency graph, not a line. Every edge runs one way, and there is no cycle — see the note under `08`.

```
02 ─┐
    ├─→ 05 ─→ 06 ─┐
03 ─┤             ├─→ 12 ─→ 10 ─→ 08 ─→ 09 ─→ 11 ─→ 13 ─┐
04 ─┤             │                                     │
07 ─┘             │                                     ├─→ 15
02.5 ─────────────┘                                     │
01 ─────────────────────→ 14 ────────────────────────────┘
```

- **`01`, `02`, `02.5`, `03`, `04` and `07` depend on nothing in this epic.** Dispatch them in parallel. Two of them edit `src/domain/layout.test.ts:101-123`: `02.5` inserts `"plan"` and `03` inserts `"document"`, so they must not run concurrently — whichever lands second writes the final fourteen-plus-`home-lock` title. `02.5` also creates `test/helpers/plan.ts`, which `02` and `03` each add one factory to, so the three touch one file and must be sequenced among themselves.
- **`02.5` owns every shared plan type.** `StoredNode`, `StoredEdge`, `ContainmentFacts` and `ValidationContext` all live in `src/domain/plan-graph.ts`, which it creates. Later stories import them and never redeclare one. Declaring `ValidationContext` in Story 05's `plan-validate.ts` would make `02.5` depend on `05` while `05` depends on `02.5`.
- `05` needs `02` (`cycles`), `03` (the reader), `04` (the path grammar) and `02.5` (the shared types).
- `06` edits `src/domain/plan-validate.ts`, which `05` creates. They are a **coupled pair** and must not run concurrently.
- `12` needs `02.5` and `07`. It lands before `08` and before `11`, because both consume `PlanStore.readGraph` and because `08`'s and `11`'s round-trip assertions call `exportPlan`.
- `10` needs `02.5` only, and `08` needs its `containmentMovable`. Dispatch it before `08`.
- **`08` does not depend on `09`.** `08` ships `plan.validate` returning the **local** suggestion per node, and `09` then replaces that one step with the set-level repair. Grown in that order the edge is one-way; specified the other way round the two stories are a cycle.
- `11` needs `08`, `09`, `10` and `12`.
- `13` needs `02.5` only, but it writes the **final** contract test counts, so it lands after `11`.
- `14` needs `01`. `15` needs `08`, `11`, `12` and `14`.
- **The five stories that edit the contract test counts do so in dispatch order**, and each states its own expected values: `01` (19 schema keys) → `12` (21) → `08` (23) → `11` (25) → `13` (28). A story dispatched out of that order leaves `npm run verify` red on a count.

## Decisions this expansion settled

Every choice the EPIC and the proposal leave open is pinned in a story below, so none reaches build time.

- **The YAML parser goes behind a service, and the renderer does not.** `src/services/document/` parses (`plan-format.md:11` makes `yaml` the parser), and `src/domain/plan-render.ts` emits the bytes by hand. Parsing needs a hardened library; rendering is a byte contract of six rules, and a stringifier's output is not a contract. `src/http/contract/openapi.ts:65-67` uses `YAML.stringify` precisely because it has no byte contract beyond stability.
- **Every `node`, `edge` and `plan_revision` statement lives in `src/services/plan/`.** This is a **choice, not a boundary requirement**: nothing stops each caller from using the `Storage` interface directly and writing its own SQL, which is what Story 01 does for `project`. What the boundary rules do force is the _either-or_ — five call sites need the same reads, and they cannot share a file outside `domain/` or a service. So the options are five copies of the same statements or one capability, and this expansion takes the capability. It is a broad entity store spanning nodes, edges, revisions, validation context and containment facts, which is a real cost. `src/services/event/` and `src/services/blob/` are the precedent for the shape. See O2.
- **Every shared plan type lives in `src/domain/plan-graph.ts`, owned by the store story.** `StoredNode`, `StoredEdge`, `ContainmentFacts` and `ValidationContext`. A type declared beside its consumer would make the store story depend on a story that depends on it.
- **`ProjectView` lives in `src/domain/project-view.ts`.** One command and two queries return it, and a query may not import a command.
- **A test reaches a real implementation through `test/helpers/plan.ts`, never directly.** `AGENTS.md` lets a test import its module under test, `domain/`, a service interface and `test/helpers/`. A domain test needing real YAML parsing or a real Tarjan would otherwise either import an implementation it does not cover or re-implement it in a fake. `test/helpers/database.ts:30` already constructs a real `SqliteStorage` for exactly this reason, so the pattern is the repo's own.
- **`upsertNode` cannot write a state.** `NodeWrite` has no `state`, `block_reason` or `discard_reason` member, and the `ON CONFLICT` update list names none of the three. A choice of `submitted` never writing a state is enforced by the shape of the write rather than by review.
- **There is no `deleteNode`.** A node absent from an import is reported, and a deletion is `node.discard`. The absence of the member is what makes "import never deletes" structural.
- **Almost all plan logic is pure and lives in `src/domain/`.** The three capabilities it needs — frontmatter parse, cycle finding, component finding, identity minting — arrive as plain function types declared in `domain/` (`FrontmatterReader`, `CycleFinder`, `ComponentFinder`, `mint`). `domain/` may import only `domain/`, and the query and the command each adapt their service to those types. That is what lets one validator, one differ, one candidate builder and one repair loop serve both.
- **`plan.validate` is a query.** It writes nothing, so `AGENTS.md`'s write/read split puts it under `src/queries/`. `repository.inspect` is the precedent: a `POST` route served by a query.
- **`BlobStore` gains a `hash` member.** `plan.validate` must hash the normalized documents without inserting a row. Duplicating the hashing expression in a query would put one rule in two places.
- **The four-part idempotency fingerprint needs no new column and no change to `choices_blob`'s meaning.** `docs/proposal/api/graph.md:72` covers the documents, the choices, `fromRevision` and `validatedRevision`. The first two compare as blob hashes; **both** revisions compare against `plan_revision.parent_id`, because steps 4 and 5 of the import each compare their field against the same newest revision, so any committed import had `fromRevision === validatedRevision`. `choices_blob` therefore stays exactly what `docs/proposal/database/plan_revision.md:26` says it is.
- **Two canonical JSON strings serve three purposes each.** `canonicalDocumentsJson` is the `documentsHash`, the `submitted_blob`, the `accepted_blob` and one fingerprint input; `canonicalChoicesJson` is the `choices_blob` and one more. Both sort first, so a reordered array is a retry.
- **The three revision columns carry blob hashes, and the three blobs are `put` first.** `plan_revision.submitted_blob`, `choices_blob` and `accepted_blob` are `NOT NULL REFERENCES blob(hash)`, so the canonical JSON is inserted as a blob and the returned hash is what the row stores.
- **Nothing is minted and no clock is read before the refusals.** The revision id and the timestamp are taken at the start of the write. Minting earlier would let a legitimate retry consume an identity or exhaust a mock generator before the lookup that recognises it.
- **A `documentsHash` mismatch is `400 invalid-request`.** The proposal names no code. It is a binding failure of the submission, not a topology conflict, and `invalid-request` is already what a missing or extra choice returns.
- **The refusal order inside the import transaction is fixed.** `importId` lookup, `fromRevision`, `validatedRevision`, validation, `documentsHash`, choice completeness, legality recompute, candidate validation, commit. The lookup is first so a genuine retry is never rejected as stale.
- **The edge set is written as a diff.** An unchanged pair keeps its `id` and its `waived_at`, because `docs/proposal/api/outcome.md:39` has a human name an edge by its `edgeId` and a waiver is a human decision that survives a re-import.
- **A `depends_on` path resolves against two bases**, the declaring document's directory and `plan/`, and a collision between them is `reference-ambiguous`. `edge.md:27` shows a bare sibling basename and `plan-format.md:29` fixes no base, so two plausible bases is exactly the condition the word "ambiguous" names. Preferring one silently would make the other base a trap.
- **The acceptance heading belongs to `acceptance_blob`.** `instruction + acceptance` then reproduces the normalized body byte for byte, and the renderer needs no knowledge of the heading. The alternative — storing the section without its heading and re-emitting it — puts one literal in two places.
- **An empty `depends_on` is omitted, not rendered as an empty block sequence.** An empty block sequence has no canonical spelling in the six rules, and an absent field being omitted is already the rule.
- **The task ordinal walk ignores `waived_at`.** A waiver must never rename a file. `taskOrder` filters on the flag, so Story 07 passes `waived: false` for every edge.
- **`database` is legal in every choice case.** Keeping the daemon's own row is never illegal, and asserting it over the whole case table is what catches a table row transcribed wrong.
- **A suggestion repair resets by component, never node by node and never wholesale.** A node in a different component keeps its `submitted` suggestion, which is the assertion a whole-set reset would fail.
- **The suggestion engine grows in two layers.** Story 08 ships `plan.validate` with the local per-node verdict; Story 09 replaces that one step with the set-level repair. Specified as one story the two are circular, because the repair needs the verdict and the route needs the repair.
- **A submitted path holding an unpaired surrogate is refused.** `comparePaths` compares code points, and code-point order equals UTF-8 byte order for every scalar-value string — but `Buffer.from` encodes a lone surrogate as `U+FFFD`, so the equivalence fails there and nowhere else. Refusing the input at the grammar is cheaper than encoding UTF-8 by hand inside `domain/`.
- **`projectView` carries no `worker` and no `e2eJson`.** Both are written only by a `stubbed` or `deferred` route, so a member that is always `null` would be contract for a value this phase cannot produce. Same rule as EPIC 007's exclusion of the profile hash.
- **A repository reaches the wire as an id and the CLI resolves the name.** `--repository <name>` calls `repository.list` first, exactly as `src/cli/repository/register.ts:60` resolves a credential name.
- **`kanthord plan import` never skips `plan.validate`.** The handshake is `plan.revisions`, `plan.validate`, `plan.import`, asserted as a recorded request sequence, and the documents sent are the ones validate returned.
