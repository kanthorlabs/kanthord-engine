# Story 02.5 — the plan store

Epic: `.agents/plan/epics/008-project-and-plan.md`

Every statement over `node`, `edge` and `plan_revision` lives in one capability. This story is an addition this expansion makes; the EPIC declares no such story. It exists because the boundary rules leave no other home — see index item O2.

## Why one capability

`eslint.config.js:117-129` allows a command and a query to import `domain/` and a service **interface**, and nothing else. `src/domain/layout.test.ts:175-189` and `:191-205` additionally assert that no non-test file under `src/commands/` or `src/queries/` relatively imports a sibling inside its own directory. So a command cannot import a query, a query cannot import a query, and a command cannot import a command.

Five call sites of this epic need the same reads: `plan.validate`, `plan.import`, `plan.export`, `node.list`/`node.show` and `edge.list`. Without one capability, the stored-graph read, the newest-revision read, the validation-context read and the containment-facts read are each written four or five times. `src/services/event/` and `src/services/blob/` are the established answer to exactly that: an entity-owning service whose every member takes a `Transaction` from the caller, so `AGENTS.md`'s transaction rule holds.

## Change

### 1. `src/services/plan/index.ts` (new — the interface, no implementation)

```ts
import type { Transaction } from "../storage/index.ts";
import type { NodeKind, NodeState } from "../../domain/state.ts";
import type {
  StoredNode,
  StoredEdge,
  ContainmentFacts,
  ValidationContext,
} from "../../domain/plan-graph.ts";

export type RevisionRecord = Readonly<{
  id: string;
  parentId: string | null;
  importId: string;
  submittedBlob: string;
  choicesBlob: string;
  acceptedBlob: string;
}>;

export type NodeWrite = Readonly<{
  id: string;
  projectId: string;
  kind: NodeKind;
  parentId: string | null;
  title: string;
  instructionBlob: string;
  acceptanceBlob: string | null;
  worker: string | null;
  repositoryId: string | null;
  revision: string;
  updatedAt: number;
}>;

export type EdgeWrite = Readonly<{
  id: string;
  fromNode: string;
  toNode: string;
}>;

export interface PlanStore {
  readGraph(
    transaction: Transaction,
    projectId: string,
  ): Readonly<{
    nodes: readonly StoredNode[];
    edges: readonly StoredEdge[];
  }>;
  readNode(transaction: Transaction, id: string): StoredNode | null;
  readAllNodes(transaction: Transaction): readonly StoredNode[];
  newestRevision(transaction: Transaction, projectId: string): string | null;
  listRevisions(
    transaction: Transaction,
    projectId: string,
  ): readonly RevisionRecord[];
  findByImportId(
    transaction: Transaction,
    projectId: string,
    importId: string,
  ): RevisionRecord | null;
  readValidationContext(
    transaction: Transaction,
    projectId: string,
  ): ValidationContext;
  readContainmentFacts(
    transaction: Transaction,
    nodeId: string,
  ): ContainmentFacts;
  readSubtreeContainmentFacts(
    transaction: Transaction,
    nodeId: string,
  ): ContainmentFacts;
  insertRevision(
    transaction: Transaction,
    record: RevisionRecord & Readonly<{ projectId: string }>,
  ): void;
  upsertNode(transaction: Transaction, node: NodeWrite): void;
  insertEdge(transaction: Transaction, edge: EdgeWrite): void;
  deleteEdge(transaction: Transaction, id: string): void;
}
```

Every member takes the `Transaction` as its first argument and never opens one. `src/services/event/index.ts:47` is the precedent, and it is the whole atomicity contract: a state write and its event append never sit in two transactions.

`upsertNode` writes `state`, `block_reason` and `discard_reason` **only on an insert**. `NodeWrite` has no member for any of the three, so no caller can pass one. The statement is

```sql
INSERT INTO node (id, project_id, kind, parent_id, title, instruction_blob, acceptance_blob,
                  worker, repository_id, state, block_reason, discard_reason, revision, updated_at)
VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, 'pending', NULL, NULL, ?, ?)
ON CONFLICT(id) DO UPDATE SET
  kind = excluded.kind, parent_id = excluded.parent_id, title = excluded.title,
  instruction_blob = excluded.instruction_blob, acceptance_blob = excluded.acceptance_blob,
  worker = excluded.worker, repository_id = excluded.repository_id,
  revision = excluded.revision, updated_at = excluded.updated_at
```

Import is one of the two writers of `pending` (`docs/proposal/phase-1/state-machine.md:19`), and a choice of `submitted` never writes a state (`docs/proposal/phase-1/plan-format.md:84`). Making the update list unable to name the three columns is how that rule is enforced by construction rather than by review.

There is no `deleteNode`. A node absent from an import set is reported, never deleted (`docs/proposal/api/graph.md:82`), and a deletion is `node.discard`.

### 2. `src/domain/plan-graph.ts` (new — pure types)

```ts
export type StoredNode = Readonly<{
  id: string;
  projectId: string;
  kind: NodeKind;
  parentId: string | null;
  title: string;
  instructionBlob: string;
  acceptanceBlob: string | null;
  worker: string | null;
  repositoryId: string | null;
  state: NodeState;
  blockReason: string | null;
  discardReason: string | null;
  revision: string;
  updatedAt: number;
  dependencies: readonly string[];
}>;

export type StoredEdge = Readonly<{
  id: string;
  fromNode: string;
  toNode: string;
  waivedAt: number | null;
}>;

export type ContainmentFacts = Readonly<{
  lease: boolean;
  workspace: boolean;
  attemptCommit: boolean;
  retainedCommit: boolean;
}>;

export type ValidationContext = Readonly<{
  workerKinds: readonly string[];
  boundRepositories: readonly string[];
  knownRepositories: readonly string[];
}>;
```

**All four shapes live in this one file, and this story owns it.** They live in `domain/` because a service interface, a command and a query all name them, and `domain/` is the one directory all three may import. They live _here_ rather than beside the logic that consumes them so that no dependency runs backwards: `PlanStore` names all four, and `plan-validate.ts` (Story 05), `plan-containment.ts` (Story 10) and `plan-candidate.ts` (Story 09) import from here rather than declaring their own. Declaring `ValidationContext` in `plan-validate.ts` would make this story depend on Story 05 while Story 05 depends on this one.

### 3. `src/services/plan/sqlite.ts` (new)

`export class SqlitePlanStore implements PlanStore`. Every statement is a module-level string constant with named columns and no `SELECT *`, and no value is ever interpolated into SQL.

```sql
-- readGraph, nodes
SELECT id, project_id, kind, parent_id, title, instruction_blob, acceptance_blob,
       worker, repository_id, state, block_reason, discard_reason, revision, updated_at
FROM node WHERE project_id = ? ORDER BY id ASC

-- readGraph, edges
SELECT e.id, e.from_node, e.to_node, e.waived_at
FROM edge e JOIN node n ON n.id = e.from_node
WHERE n.project_id = ? ORDER BY e.from_node ASC, e.to_node ASC

-- newestRevision
SELECT id FROM plan_revision WHERE project_id = ? ORDER BY id DESC LIMIT 1

-- listRevisions
SELECT id, parent_id, import_id, submitted_blob, choices_blob, accepted_blob
FROM plan_revision WHERE project_id = ? ORDER BY id DESC

-- findByImportId
SELECT id, parent_id, import_id, submitted_blob, choices_blob, accepted_blob
FROM plan_revision WHERE project_id = ? AND import_id = ?

-- readValidationContext, bound repositories
SELECT target_id FROM project_binding WHERE project_id = ? AND kind = 'git' ORDER BY target_id ASC

-- readValidationContext, known repositories
SELECT id FROM repository ORDER BY id ASC

-- readContainmentFacts, four statements
SELECT 1 FROM lease WHERE subject_kind = 'node' AND subject_id = ? AND owner IS NOT NULL LIMIT 1
SELECT 1 FROM workspace WHERE node_id = ? LIMIT 1
SELECT 1 FROM attempt a JOIN run r ON r.id = a.run_id WHERE r.node_id = ? AND a.head_oid IS NOT NULL LIMIT 1
SELECT 1 FROM candidate WHERE node_id = ? LIMIT 1

-- readSubtreeContainmentFacts, the descendant walk
WITH RECURSIVE descendant(id) AS (
  SELECT ? UNION ALL SELECT n.id FROM node n JOIN descendant d ON n.parent_id = d.id
)
SELECT id FROM descendant ORDER BY id ASC
```

- `readGraph` fills `StoredNode.dependencies` from the edge list, bytewise ascending, de-duplicated. A **waived** edge is included: a waiver changes readiness, not topology, and export must reproduce the `depends_on` a human wrote.
- `edge` carries no `project_id`, so the join through `from_node` is the only scope available, and `edge.from_node` is `NOT NULL REFERENCES node(id)` (`src/services/storage/migration-0002-graph-and-plan.ts:43`) so the join never drops a row.
- `newestRevision` is the greatest `id`, because a ULID sorts by creation time (`docs/proposal/database/plan_revision.md:20`).
- `readSubtreeContainmentFacts` runs the four fact statements over the node and every descendant and returns the disjunction per member. The `IN` clause is built from one `?` per id.
- `readAllNodes` is `readGraph`'s node statement with no `WHERE`, and it fills `dependencies` from every edge row. It serves `node.list`, which reads no query parameter.
- `readValidationContext` returns `{ workerKinds, boundRepositories, knownRepositories }`, with `workerKinds` from `src/domain/worker.ts` — a closed set in code (`docs/proposal/phase-1/domain.md:22`).

A released lease (`owner IS NULL`) does not block a move: `lease.owner` is nullable and the fence survives a release, so the row's existence proves nothing. An attempt commit is an `attempt.head_oid` on a run of the node; there is no `commit` table, and commit identity lives in `*_oid` columns (`docs/proposal/database/README.md:43`). A retained commit is a `candidate` row for the node.

`plan-format.md:120-121` — a task changes parent only while it holds none of the four; an objective needs that of every descendant, which is why there are two readers.

### `plan-graph.test.ts`

- The four types are structural, so the test asserts the member name sets: `Object.keys` of one literal of each shape, bytewise sorted, deep-equal to the fifteen, four, four and three member names. This is what catches a member added on one side of the store and not the other.

### `sqlite.test.ts`

- `readGraph` on the seeded project returns three nodes ascending by id, each asserted field by field, and no edge.
- Two edges inserted directly are returned ascending by `(from_node, to_node)`, asserted with an insertion order that is the reverse.
- An edge whose `from_node` belongs to a second project is not returned by that project's `readGraph`.
- A waived edge is returned with its `waivedAt` value, and it appears in the dependent's `dependencies`.
- `dependencies` is bytewise ascending and de-duplicated.
- A project with no node returns `{ nodes: [], edges: [] }`.
- `readNode` returns the seeded task with every member; an unknown id returns `null`.
- `readAllNodes` returns the nodes of two projects, ascending by id across both.
- `newestRevision` returns the greatest id, proved with a second revision row whose id sorts above the first; an empty project returns `null`.
- `listRevisions` returns newest first, and the second row's `parentId` is the first row's `id`.
- `findByImportId` returns the row for `("project_a","imp_a")`, `null` for an unknown import id, and `null` for the same import id under a second project.
- **`upsertNode` inserts with `pending`.** A fresh node lands with `state = 'pending'`, `block_reason` and `discard_reason` `null`.
- **`upsertNode` never rewrites state.** Move the seeded task to `blocked` with `block_reason = 'attempt-limit'` and a `discard_reason`, upsert a new `title`, then assert `state`, `block_reason` and `discard_reason` are byte-identical to before and `title` changed. Repeat for a `discarded` node — a prose edit does not clear `discard_reason`.
- Read the module source and assert the `ON CONFLICT` update list contains none of `state`, `block_reason`, `discard_reason`.
- `insertEdge` and `deleteEdge` write and remove one row, and `deleteEdge` on an unknown id is a no-op.
- `insertRevision` writes every column, and a second row with the same `(project_id, import_id)` throws — `UNIQUE (project_id, import_id)` is the idempotency mechanism (`docs/proposal/database/plan_revision.md:14`).
- `readValidationContext` returns `boundRepositories` `["repo_a"]` and `knownRepositories` `["repo_a"]`; a second repository row appears in the second list only; a `provider` binding row appears in neither; `workerKinds` deep-equals the array exported by `src/domain/worker.ts`. Both lists are bytewise ascending.
- **Containment facts.** A node with nothing attached returns all four `false`. A `lease` with `owner = "daemon-1"` gives `lease: true`, and setting `owner` to `null` gives `false`. A `repository` lease with the same `subject_id` text does not match. `seedExecution`'s workspace on `objective_a` gives `workspace: true` for the objective and `false` for the task. The seeded attempt has a `null` `head_oid` so `attemptCommit` is `false`; setting a 40-character oid makes it `true`; an attempt on a run of another node does not match. A `candidate` row for `task_a` gives `retainedCommit: true`.
- **The subtree.** `readSubtreeContainmentFacts(initiative_a)` returns `workspace: true` while `readContainmentFacts(initiative_a)` returns `false`. That pair is the whole objective-versus-task rule. A three-level subtree with the blocking row on the deepest task is found from the initiative, and a leaf task's subtree facts equal its own.
- The descendant walk does not follow an `edge` row: insert an edge from a node outside the subtree and assert the facts are unchanged.
- **No interpolation.** Read the module source and assert no string passed to `transaction.run`, `.get` or `.all` contains `${`, and that no statement contains `SELECT *`.
- Determinism: every read is called twice and the two results `deepEqual`.
