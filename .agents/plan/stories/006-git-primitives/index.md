# EPIC 006 — Git primitives — stories

Epic: `.agents/plan/epics/006-git-primitives.md`
Prereq: EPIC 005 (sequence order), expanded at `.agents/plan/stories/005-test-infrastructure/`. Two fixture remotes serve a real git transport on loopback ports, and `test/helpers/remote/` holds the resolved tool paths and the byte-reproducible seeded repository.

The git service runs the `git` binary under a pinned environment, through one launcher that makes every child recordable and signallable. It refuses a url before any process starts, delivers a credential without touching an argument vector, writes a ref as a compare-and-swap, confines a fetch to the tracking namespace, reports an unexpected ref value, and produces a clone that shares no object file with the bare home.

## Dispatch order

This is a dependency graph, not a line. Only two edges are real.

```
02 ──────────────────────┐
                         │
04 ──→ 01 ──┬──→ 03 ──→ 06
            ├──→ 05
            ├──→ 07
            └──→ 08
```

- `02` and `04` depend on nothing in this epic and on each other not at all. Dispatch both first, in parallel.
- `04` precedes `01`. `04` owns the only `spawn` call in the product, and `01`'s runner cannot spawn anything without it. Splitting them the other way would make `01` spawn `git` directly and then rewrite it, and the pid-file contract would not exist while the environment tests were written.
- `01` is the gate for everything else. `03`, `05`, `06`, `07` and `08` all call `createGitRunner` and build no argument vector of their own. `01` also owns `redact.ts`, so no later story owns the redaction.
- `03` precedes `06`, and that is the only other real edge. A fetch against either fixture authenticates.
- `05` does **not** precede `06`. `fetch.test.ts` writes its landing branch with `runGit(["--git-dir=…", "update-ref", …])`, not with the product `refUpdate`. A test of `fetch.ts` that depends on `ref-update.ts` proves two units at once and serialises the epic for no gain.
- `08` does **not** depend on `03`. An objective clone is local and authenticates nothing; its only shared import is the redaction, which `01` owns.
- `07` needs `01` alone. It is listed last because it is the only story that opens the database, not because anything blocks it.

Measured behaviour — each of these changes an assertion. Every item was observed on `git version 2.50.1 (Apple Git-155)` and `node v24.17.0` under `LC_ALL=C`.

- **`execFile` does not forward `detached` to `spawn`.** A child started by `execFile({ detached: true })` keeps the parent's process group, so `process.kill(-pid, …)` names the daemon's own group. Measured `pgid` equals the node process group with `execFile`, and equals `pid` with `spawn`. `docs/proposal/phase-1/git-foundation.md:56` names `execFile`, and it cannot deliver the cancellation `:260` requires — see B2.
- **A group signal is required, not preferred.** With `spawn({ detached: true })`, a `SIGTERM` to `-pid` kills `git` and its ssh child. The same signal to `pid` alone leaves the ssh child alive. Both halves are asserted, because the second is what proves the first is load-bearing.
- **`exec` keeps the process id.** A launcher that writes `$$` and then `exec`s `git` yields a pid file whose content equals the `spawn` return value, and `ps -o comm=` of that id names `git`. `ps` reports a full path on Darwin and a 15-character name on Linux, so the assertion is on `path.basename`.
- **`set -C` alone does not stop the launcher.** A redirection failure in a non-interactive `/bin/sh` prints `cannot overwrite existing file` and the shell still reaches `exec`. `|| exit 111` is what stops it, and the measured exit code through `spawn` is `111`.
- **`update-ref` reports the observed object id only for a non-empty expected value.** A wrong non-zero expected value yields `cannot lock ref '<ref>': is at <observed> but expected <expected>`, exit `128`. An empty **or** all-zero expected value against an existing ref yields `cannot lock ref '<ref>': reference already exists`, exit `128`, with no object id. `observedOid` is therefore `null` in the second case by nature, not by a parse defect.
- **The `update-ref` diagnostic is the same for a packed ref.** `pack-refs --all` before the call changes neither the exit code nor the message.
- **A pre-existing `.lock` file yields `Unable to create '<absolute path>.lock': File exists.`** The message carries the absolute path of the home. That is acceptable inside `GitError.detail`, and it is why `docs/proposal/api/README.md:181` forbids a path in an HTTP response — the command that catches this error must not forward the detail verbatim.
- **`--no-tags` is not replaced by the refspec.** Against a remote holding `refs/tags/v1`, a fetch with `+refs/heads/*:refs/remotes/origin/*` and `--no-tags` leaves `refs/tags` empty. Tag auto-follow ignores the refspec.
- **A remote force-push force-updates the tracking ref and touches no local head.** Measured: `refs/remotes/origin/main` moved to the new object id, `refs/heads/land` kept the old one.
- **`clone --no-hardlinks --no-local` produces a packfile, not copied loose objects.** Every regular file under `<workspace>/.git/objects` has `nlink === 1`. A `--local` clone shares inodes and yields `nlink === 2` on the source's loose objects, which is the positive control.
- **`credential.helper` resets on an empty value, and later entries survive.** With `bad`, then empty, then `good`, only `good` is invoked. The empty entry must therefore come **before** the daemon's own helper.
- **`git` calls the helper with `erase` on a rejected credential.** Measured against a live forge: `get` then `erase` for a wrong token, and `get` alone for an accepted one. This is the structured evidence that makes `auth-failed` a fact rather than a message match.
- **`new URL` silently strips a control character from a path.** `new URL("https://h/x\n.git").pathname` is `/x.git`. The control-character scan therefore runs on the raw string, before any parse.
- **`new URL` rejects `git@host:path` with `ERR_INVALID_URL`.** The scp-like spelling is recognised by a regular expression before the parse, not by catching the failure.
- **`new URL("http://[::1]:9/x.git").hostname` is `"[::1]"`, with the brackets.** Story 02 strips them before it calls `isLoopbackHost`.
- **`ls-remote --symref <url> HEAD` prints nothing and exits `0` against a repository whose `HEAD` is unborn.** EPIC 007 reads a `null` default branch from that, not an error.
- **`config --get-regexp` exits `1` when nothing matches.** One call covers the three keys a partial clone sets.
- **`GIT_SSH_COMMAND` is shell-parsed by `git`, and quoting a path is not a general defence.** A path carrying a double quote, a `$`, a backtick or a backslash survives no naive interpolation. Story 03 therefore writes an ssh **wrapper script** and passes the key path to it through the environment, so the only value `git` shell-parses is the wrapper path, and that one value goes through a tested POSIX single-quote function.

## Decisions this epic settled

Fourteen choices the EPIC and the proposal leave open. Each is pinned in a story, so none reaches build time.

- **The runner is `spawn`, not `execFile`.** Measured: `execFile` drops `detached`, so its child keeps the daemon's process group and `kill(-pid)` names the daemon. `git-foundation.md:56` names `execFile`, and `:260` requires cancellation to signal the group; the two cannot both hold. The group wins, because the reap of `recovery.md:46` signals a group and a transport child outlives a killed parent. Story 01 also drops the `timeout` option for the same reason — a `spawn` timeout signals the process — and runs its own timer with `SIGTERM`, a two-second grace, then `SIGKILL`, each to the group. B2 carries the proposal amendment.
- **The launcher is `/bin/sh -c` with a fixed script, and the pid-file path arrives through the environment.** `/bin/sh` is a stated platform prerequisite rather than an injected path, which is the one exception to the injection rule and is written down for that reason. `set -C; printf "%s" "$$" > "$KANTHORD_PID_FILE" || exit 111; exec "$@"`. `set -C` makes the create exclusive, `|| exit 111` is what stops the shell from reaching `exec` after a failed redirection, and `exec "$@"` keeps the process id. The path is an environment entry, never interpolated into the script text, because a path inside the script would be shell-parsed. Exit `111` is reserved and classified.
- **`GitPaths` is one injected record, and this epic adds no configuration key.** `git`, `ssh`, `sshKeyscan`, `home`, `keyDirectory`, `knownHosts`, `runDirectory`, all absolute. The epic states the runner "resolves nothing itself", and `.agents/plan/epics/007.5-startup-recovery.md:22` owns the `tools.*` keys and the version probe. `main.ts` derives the four directories from `settings.home` when it wires the service: `<home>/git/home`, `<home>/git/keys`, `<home>/git/known_hosts`, `<home>/git/run`. B1 carries the ordering problem that follows.
- **The pinned environment is built from an empty object, and the suppressed names are absent rather than empty.** `gitEnvironment` never spreads `process.env`, so there is nothing to unset: `GIT_DIR`, `GIT_WORK_TREE`, `GIT_CONFIG_COUNT` and every `GIT_TRACE*` simply have no key. The test asserts absence with `Object.hasOwn`, because an empty `GIT_DIR` and an absent one are different to `git`. `extraEnv` is the one door left open, and it throws on any pinned or suppressed name so a caller cannot re-introduce ambient state through it.
- **No commit date is pinned in this epic.** `GIT_AUTHOR_DATE` and `GIT_COMMITTER_DATE` belong to a command that writes an object, and no command here writes one. The identity variables **are** pinned, because `git-foundation.md:263` requires an object id never to depend on a file the daemon does not own.
- **`auth-failed` comes from the helper's `erase`, and the message rules cover only what has no structured channel.** `classifyFailure` tests `eraseObserved` first, so an HTTPS verdict never depends on wording. Rules two to five match `stderr` for the host-key, ssh-key, policy and network cases, where `git` and `ssh` expose no other signal. `unknown` is a real outcome, so an unclassified failure is visible rather than mislabelled. Story 03 asserts the precedence directly: `eraseObserved: true` with `stderr` reading `"Connection refused"` is still `auth-failed`.
- **`GitFailure` gains `timed-out` and `output-exceeded`.** `git-foundation.md:261` makes a bound breach a failure rather than a truncation, and a caller reports a timeout differently from `unknown`. Both are raised by the runner, so no later story classifies them.
- **`stripUserinfo` lives in `redact.ts`, and it is defence in depth rather than the mechanism.** The mechanism is that no url the daemon passes to `git` carries a credential: Story 02 refuses a password in a userinfo, and Story 03 delivers the secret through the helper. The strip catches what a diagnostic echoes back anyway, and it removes the username too — a username is not a secret, and a redaction that keeps it needs a second rule to decide which half of `user:pass@` to drop. It sits in its own file because `run.ts`, `fetch.ts` and `clone.ts` all use it and `clone.ts` must not import `credential.ts` for it.
- **One failure precedence, fixed in the runner.** When two conditions are true of one invocation, the runner reports in this order: `output-exceeded`, then `timed-out`, then the launcher's `111`, then the exit code as data. The bound comes first because a breach is what usually causes the timeout that follows it, and reporting the timeout would name the symptom. The runner records the first decision it takes and never overwrites it, clears both timers in a `finally`, and drains both streams to a discard after a cancellation so a descendant writing to a full pipe cannot block on exit.
- **The last-completed baseline is the maximum `(completed_at, id)` tuple among rows that reported a ref value, and its limit is written down.** `git_operation` carries no monotonic completion sequence, and a ULID encodes creation order rather than completion order, so two rows completing inside one millisecond have an order this query cannot recover. The query is therefore deterministic and its semantics are "the latest row by recorded completion time, tie-broken by identity" — not "the operation that finished last". That is honest for a check `docs/proposal/phase-1/git-foundation.md:191-197` already calls a diagnostic and not a boundary. The query also requires `result_head_oid IS NOT NULL`, so a row that completed with `auth-failed` and reported no ref value is not a baseline. S4 records the phase-2 fix.
- **The outside-writer check returns a verdict and writes nothing.** The EPIC bullet says the diagnostic "refuses, writes an event, and reports both object ids". The refusal and the event belong to the caller: `AGENTS.md` puts business logic in `commands/`, the epic's non-goal excludes registration, and the Proof globs only `src/services/git/**`, so an event written here would be untested by the epic's own gate. Story 07 therefore returns `OutsideWriterVerdict` and asserts, by snapshotting `git_operation` and `event` before and after, that nothing is written. S1 carries the EPIC amendment.
- **The last-completed query orders by `completed_at DESC, id DESC`.** `completed_at` is a millisecond epoch and two rows can share one, so the identity breaks the tie and the order is total. The ULID prefix is monotonic, so the higher identity is the later row. Story 07 inserts two rows in both orders and asserts one verdict, which is how the determinism rule of `AGENTS.md` is proved rather than claimed.
- **A caller-supplied pid file is never removed by the runner; a minted one always is.** `refUpdate` and `fetch` take a required `pidFile`, because those two are the writes a `git_operation` row journals and `recovery.md:73` commits the path first. `clone` takes none and the runner mints one under `runDirectory`. Required rather than optional: an optional member would let a caller journal nothing and still write a ref.
