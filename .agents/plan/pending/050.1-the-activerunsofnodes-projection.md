# `execution.activeRunsOfNodes` has a projection its signature cannot supply

**The obligation.** `.agents/plan/stories/050.1-the-claim/06-the-conformance-harness.md:41` declares
the projection of `execution.activeRunsOfNodes` as _"the caller-supplied set name"_. No caller
supplies a name. `.agents/plan/pending/050.1-the-claim-seams.md` pins the signature:

```ts
activeRunsOfNodes(
  transaction: Transaction,
  nodeIds: readonly string[],
): readonly RunRecord[];
```

`.agents/plan/authoring.md` requires that _"a projection names a value the call actually receives"_,
so `:siblings` and `:subtree` are unproducible as written. Twelve tokens across the EPIC 050 family
carry those two labels.

**Adding a parameter is refused, and is not the fix.** `.agents/plan/authoring.md` states it
directly: never add a parameter to a production interface so a diagram can separate two calls. The
seams document argues the same point from the domain — a method named after the objective hierarchy
would put plan topology inside the execution capability, which owns runs and not the tree.

**The fix is available without touching the interface.** The two calls of the claim receive different
values in `nodeIds`: `subtreeExclusion` passes the subtree ids from `plan.readSubtree`, and
`objectiveBusy` passes the sibling ids from the graph read. A projection over `nodeIds` therefore
separates them, and the harness's own rule renders each id through the `aliases` map, so a token holds
`T` and never a ULID. Deciding the exact rendering — the whole set, or its first element — is the
work, and it is one row of one table.

**The owner.** EPIC 050.1 Story 6 (`06-the-conformance-harness`), which owns the projection table.
The table lives in that file once, so the edit is one row and every diagram of the range reads it.

**The trigger.** The implementation of EPIC 050.1 Story 6. The harness does not exist yet:
`test/helpers/sequence-conformance.ts` and `test/sequence/` are absent, and
`src/services/execution/index.ts:76` declares `activeRunOfNode` and no plural form. Nothing is red
today, and the first scenario that replays a claim path is what fails.

**Why this is a pending document and not an epic amendment.** EPIC 050.1 is in flight. Its story
files are the contract the running loop reads, and rewriting a projection under a loop mid-cycle
changes the oracle of cases already green.

**What breaks if the answer arrives late.** EPIC 050.1 Stories 2 to 5 each add a scenario file. The
first one to replay a claim path records two calls on one method, the projection yields no label for
either, and the two steps collapse to one token — which the parser refuses, because no two steps of
one diagram may carry the same token. The story then cannot go green, and the loop reaches the human
with a diagram defect rather than an implementation defect.

**What is deliberately not requested.** Do not relabel the twelve tokens in the story files ahead of
the table. The label is derived from the projection, so a hand-edited token that the harness does not
produce fails the same comparison, one layer later. Do not exempt the method from projection either:
it is called twice on every claim path, and a method with no projection admits one call per diagram.

**Downstream, and already handled.** EPIC 050.4 draws four of the twelve tokens, in
`claim-lease-free-task`, `claim-lease-free-initiative` and `claim-lease-free-objective-busy`. They are
context tokens there, so
`.agents/plan/stories/050.4-the-node-lease-removal/index.md` states the rule that they are copied
from the landed EPIC 050.1 diagram and never decided locally. That epic needs no further change when
this one lands.
