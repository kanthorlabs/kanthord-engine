# Workbench API specification

[CLI specification index](./README.md) · [Shared conventions](./other.md)

## Scope

The Workbench Service has **no CLI command**. A human drives a workbench session through the chat of the dashboard or through the API.
[Workbench Service](https://github.com/kanthorlabs/kanthord/blob/main/docs/brainstorm/workbench-service.md) and its [implementation contract](https://github.com/kanthorlabs/kanthord/blob/main/docs/brainstorm/workbench-service.impl.md) own the rules.
The Workbench opens sessions of `swe@1` and `re@1` only.
This page lists the operations and the error codes. It introduces no design rule.
The [operation contracts](../../src/workbench/contract.ts) and the generated OpenAPI publish the wire names, paths and output shapes.

## Operations

Every operation has `human` access, except `workbench.invite.join` (`public`) and the three `workbench.guest.*` operations (`guest`).

Each item of `workbench.session.list` answers `notice`, a string or null. See [Completion notice](https://github.com/kanthorlabs/kanthord/blob/main/docs/brainstorm/workbench-service.impl.md#completion-notice).

`workbench.session.scopeRequest.approve` and `reject` are human-only acts of the owner. No agent tool list holds them. A delegate identity, a read-only identity and a guest token answer `401 gateway.authentication.unauthorized`.

`workbench.session.autoMode.set` takes the body `{ enabled }` and answers `{ session_id, enabled }`. It is a human-only act of the owner. The run snapshot of `workbench.session.events` answers `auto_mode`.

The pending approval of the run snapshot carries `guard`. `guard` is `null` for an evidence card. Every other card carries `{ cause, reason, confidence }`. `cause` is one of `import`, `auto_mode_off`, `unavailable`, `oversize`, `no_verdict`, `classifier` and `guest_run`. The pending approval also carries `requested_by` `{ kind, name }`: the author of the run that made the call. A mutation of a run that a guest started always waits on a card with cause `guest_run`. `reason` and `confidence` are `null` for every cause other than `classifier`.

## Conversations

A conversation is its host session. The agent of `workbench.session.create` is the host. `create` writes an opening pair to the host file with no model call: an internal user message that the answers hide, and the greeting of the host.

A message that starts with `@<display name>` runs the member with that display name. `@` followed by a space is no mention, and only a leading mention routes.
The name set holds the display name of every catalog session agent and of every variant. The match is case-insensitive and takes the longest name at the start of the text. The match ends at whitespace, at the end of the text or at a character outside `[A-Za-z0-9 _-]`. A failed boundary falls back to a shorter name. A newline is whitespace. Example: with "SWE" and "SWE Lead", `@SWE Lead fix it` routes to "SWE Lead" and `@SWE Leader` routes to "SWE". A leading `@` with a name that matches nothing answers `404 agent.catalog.not_found`. The server reads the variant names at each message, so a create, a rename or a delete applies to the next message.
A member is one agent or one variant: the pair `agent_name` and `variant_id`, with `variant_id` `null` for a catalog agent. A conversation holds one session per member. "SWE" and a variant of `swe@1` are two members. A host that is a variant session is the member of that variant, and a mention of its base agent creates a separate base member.
The first mention of a member that is not yet a member creates a participant session of it. A variant participant lives in the variant session directory, and its header names the host file. An untagged message runs the member that answered last, and the greeting counts as the answer of the host.

The session answers of `workbench.session.get` and `workbench.session.events` are one merged transcript of the conversation.

- `members` lists `{ session_id, agent_name, display_name }` of every member, the host first, then the participants by creation time.
- Every entry carries `session_id` and `agent_name` of the member file that holds it.
- `after` of `workbench.session.events` holds one `<session_id>:<entry_id>` pair per member, separated by commas. A member with no pair starts from the first entry. A plain entry id names the host pair, and the participant entries start from the first entry. The answer holds no cursor field; the client builds `after` from the `session_id` and `id` of the entries it holds.
- `version` is one counter for the whole conversation.

The run snapshot reads the running member. `pending_approval` carries `session_id`, the member that made the call. `workbench.session.approve` takes that `session_id`.

`workbench.session.get`, `events`, `message`, `abort`, `queue.remove` and `autoMode.set` accept the host session id only. A participant session id answers `409 workbench.session.not_host` with details `{ session_id, host_session_id }`. `configure` accepts a participant session id and answers `409 workbench.session.run_active` while the conversation holds a run.

`workbench.session.list` answers one item per conversation. An item adds `display_name`, `variant_id`, `host_session_id` and `participants`. A host item answers `host_session_id: null`, the items of its participants in `participants` and, as `modified`, the latest `modified` of its members. A participant item answers the id of its host in `host_session_id` and an empty `participants`. A participant is never a top-level item. The filter `agent_name` selects the host agent. A new conversation answers `first_message: ""` and `message_count: 1`. After the first human message, `name` holds that message.

`workbench.session.message` answers `{ session_id, agent_name, run_active, queued_message_id, cleared, kind }`. `session_id` is the host id. `agent_name` is the member that runs the message now, the member that a queued message names, or `null` for an untagged queued message. A queued message and an item of `cleared` carry `agent_name`, `variant_id` and `display_name` of their mention, or `null` for all three when untagged. For a variant item, `agent_name` is the base agent, `variant_id` is the variant and `display_name` is the current variant name, read at each answer. A rename between the queue and the start keeps the target. A queued item resolves its member when it starts, and an untagged item runs the member that answered last at that moment. A queued item whose agent or variant is refused at its start is dropped, and `error_message` of the snapshot holds the refusal. `kind` is `run` for a message that starts or queues a run. In a conversation with a live invite, an untagged message is a note: it appends a `note` record, starts no run, and answers `kind` `note` with `agent_name` `null`, `queued_message_id` `null` and `cleared` `[]`. After the last invite ends, an untagged message runs the member that answered last again.

## Variant sessions

`workbench.session.create` takes the optional body field `variant_id`, an `agent_variant` identity. The session is then a single-agent session of that variant. The agent of the session is the base agent `agent_name` of the variant, and its tools, guard floor and classifier input stay those of the base agent.
A variant of another agent than the body `agent_name`, or an unknown variant, answers `404 agent.variant.not_found`. The create creates no directory in that case. A refused configuration or a refused runtime also leaves no variant directory.
The session file lives in the variant session directory `<state>/pi/sessions/workbench/<agent_name>/<variant_id>/`. The header `cwd` is the base workbench directory `<state>/workbench/<agent_name>`. The base session directory never holds a variant file, and the variant directory never holds a base file.
The directory marks the variant as in use: `agent.variant.delete` answers `409 agent.variant.in_use` while it exists.
The session answer, every item of `workbench.session.list` and the answer of `workbench.session.get` carry `variant_id: string | null`. A base session answers `null`.
`display_name` of a list item, and `display_name` of the host item of `members`, answer the current variant name for a variant session. The greeting of the opening names the variant.
The agent open composes the system prompt with the current variant row, so a new name or a new instruction applies at the next agent open, also after `workbench.session.configure`.
`workbench.session.fork` of a variant session keeps the variant, and the fork file lives in the same variant directory.
A `plan@1` variant run composes each phase with the variant. The phase session files stay in the `phases/` directory of the base `plan@1` session directory. `workbench.session.list` never treats `phases/` as a variant directory and lists no phase session.
`workbench.session.list` creates no directory. The filter `agent_name` selects the base agent and includes the variant sessions of that agent.

## Guests and project scope

`workbench.invite.create` takes the body `{ invitee_name, project_ids, granted_operations }`. `project_ids` names 1 to 50 existing projects, each once. The set never changes. Revoke the invite and create a new one to change it. `granted_operations` lists the project-scoped operations that the guest-started runs of the invite run with no card. The list is fixed at create. A refused or repeated id answers 400 `workbench.invite.grant_invalid`.

`workbench.invite.list` answers `{ items, project_ids, grantable }`. Each item adds `projects`: `{ id, name }` of each project of the invite, with `name` `null` for an id with no project. Each item adds `granted_operations`: `{ operation_id, guard_class }` of each id of the live grant. `project_ids` holds the set of the live invites, or `null` when no invite is live. `grantable` lists `{ operation_id, guard_class, description }` of each operation that the host agent of the conversation lets an invite grant.

`workbench.guest.get` adds `projects` (the projects of the invite, as in `invite.list`), `granted_operations` (the live grant of the invite, as in `invite.list`) and `mention_names` (the display names that a guest can mention: the agents with no built-in tool, and the variants whose base agent holds no built-in tool).

`workbench.guest.message` answers `{ kind: "note" }` for a message with no leading mention. It answers `{ kind: "run", agent_name, queued_message_id }` for a mention that starts or queues a run. `queued_message_id` is `null` when the run starts now.

A run that a guest started reads and acts only on the projects of the invite. Its reads run under the read-only identity of the inviter. A mutation runs under the human who approves it, or under a one-call delegate identity for a granted act. A call outside the projects answers 403 `gateway.scope.refused` or 404 `gateway.scope.not_found`. A foreign record and an absent record answer the same 404. The guard blocks a call of such a run before any card with one of these texts:

- `workbench.guard.guest_scope: <operation_id> is not available in a run that a guest started.` The run called a `workbench.*` operation or `evidence_read`.
- `workbench.guard.project_scope: The record is not available in this conversation.` The call names a record outside the projects of the invite, an absent record, or a global record.

## Out-of-scope requests

A guest-started run that calls `request_owner_act` for an act outside the projects of the invite ends. The server keeps one request in memory. No session entry, frame or guest read holds it. A restart, an invite revoke or the invite expiry deletes it.

The owner reads the requests in `scope_requests` of `workbench.session.get` and `workbench.session.events`. A host item of `workbench.session.list` adds `scope_requests`, the count of the requests. The tool result of `workbench--session--list` drops that key.

`workbench.session.scopeRequest.approve` takes the body `{ project_name, expected }` and answers `{ request_id, outcome, error_code }`. `project_name` is the exact name of the project of the act, byte for byte. `expected` holds one value for each key of `expected_keys` of the request. The act runs once under the identity of the owner. `outcome` is `done` or `failed`. A failed act leaves the request open with its `error_code`. `workbench.session.scopeRequest.reject` takes the body `{}`, deletes the request and answers `{ request_id }`.

Each approve and reject writes one info log line `workbench.scope_request.settled`.
