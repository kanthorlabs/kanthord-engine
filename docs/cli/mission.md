# Mission CLI specification

[CLI index](./README.md) · [Shared CLI rules](./other.md)

## Status and scope

This internal specification includes implemented Mission contracts and the
remaining target CLI. The owning design pages determine the domain rules.
Unresolved contracts are called out explicitly; a placeholder is not an
implementable schema. A proposed command below is available only when it is
included in the delivered scope here.

The current [Mission dispatcher](../../src/apps/cli/mission.ts) implements
mission get, node planning and human control, criterion set, dependency edits,
edge list, import/export, and attempt, external-action, assessment and outcome
reads. Remote commands accept the shared endpoint and token options.
The [Mission contract](../../src/mission/contract.ts) declares 58 operations
with handlers and generated OpenAPI: 54 CLI operations, the execution-only
`mission.evidence.asset.complete` and `mission.evidence.request` operations, and
the service-only `mission.delivery.admit` and
`mission.delivery.unresolved_request.count` operations.
Completion checks object storage before publication and repeats claim admission
in the publication transaction. Requests record one published platform asset
under a live evaluation claim. These four operations have no standalone CLI leaf.

Evidence submit is implemented for repository and produced assets in the CLI;
the API also prepares object uploads. Evidence list/get include pending assets
and attempt-zero records. Human and execution-bound content reads are implemented;
the execution CLI refuses object answers without printing presigned URLs.
Assessment submission is implemented with atomic claim revocation and eligible
attempt closure. Node check commits each successful Intake check independently
and returns per-request failures. Asset deletion removes remote content before
the row and supports a forced delete on a live chain. Whole-evidence deletion
also removes evidence-set references and pauses an open-attempt request owner.
Execution pinned-revision and revision list/get enforce the claim's upper bound.
Execution evidence list, cleared-outcome get, cleared-assessment get and rework-assessment get use the claimed attempt.
Execution dependency, outcome and evidence lists use the direct dependencies and
their current outcome revisions. Graph get, criterion list and the host upload helper remain target work.
The execution schemas, admission checks, content checks and assessment admission
checks are implemented building blocks. The production Intake check collaboration
remains explicitly unwired; local stand-ins verify its contract. The server wires
no object storage, so every operation that calls object storage answers 503
`mission.evidence.storage_unavailable`.

The [operation contract](../../src/kernel/operation.ts),
[identity validator](../../src/kernel/identity.ts),
[caller types](../../src/kernel/caller.ts) and
[client configuration](../../src/gateway/client.ts) supply the existing
mechanical baseline. In particular, current machine identity types do not establish a Mission
execution identity by themselves.

One project has one mission: its nodes, tasks and dependency edges.
The proposal contains **57 leaf commands**: 56 remote commands and one host-local upload helper.
They use **57 Mission operations**, because the upload helper calls `mission.evidence.submit`, which row 32 also uses, and `mission.evidence.asset.complete`.
Group help is not a leaf.
A mission exists from project creation, empty at mission version 1. No operation creates or deletes a mission. Project discovery
provides a project ID; `mission get` returns that project's mission ID.

## Domain boundaries that every command must preserve

- A mission is a directed graph, and dependency is its only edge kind. The work
  of a node is `implement` or `examine`. An `implement` node names exactly one
  repository binding and holds zero or more tasks. An `examine` node names zero
  or more repository bindings and holds no task. A task belongs to exactly one
  `implement` node. A human changes the work only while the attempt reads 0.
- The requires list of a node names the traits that a worker binding needs to
  claim the node. A trait key matches `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)*$`
  and holds at most 64 bytes.
- A dependency relates two nodes, never tasks. The closure of a dependent is
  the set of its direct dependencies. Every write checks the dependency edges
  for cycles. Only
  `Completed` satisfies a dependency; `Discarded` does not. An unsatisfied
  dependency produces unavailability, not a block.
- A dependency addition or removal on a dependent in `Waiting`, `Evaluating`,
  `External.Requested`, `External.Success` or `External.Failed` answers 409
  `mission.node.state_conflict`. A dependency addition on a `Paused` dependent
  whose open attempt holds a request evidence answers the same code. The rule
  applies to `dependency add`, `dependency remove`, the import and a forced
  retirement.
- Humans own planning, node edits, the criterion and imports. Execution authority
  grants no planning authority. A human edit during an attempt affects a later
  attempt; it does not retarget the open attempt or change state.
- A node has revisions, state and attempts. A task has none of these
  independently: its content belongs to the revision of its node,
  and it holds no evidence, assessment or outcome.
  Task order in a plan is not a Mission scheduling order.
- At most one node attempt is open. Its node revision is pinned at opening,
  and its required external actions derive from the binding row that the
  pinned revision names. Records never migrate between attempts, and closed attempts
  never reopen. Revision numbers and attempts are independent.
- `Completed` and `Discarded` are terminal. No edit, unblock, override or outcome
  correction reaches a terminal node. Follow-up work requires a new node. A
  genuine no-op import of a terminal node is allowed; a substantive change is
  not.
- Execution provides evidence; evaluation provides assessments; Mission records
  outcomes on attempt closure. A command returning successfully establishes
  acceptance of that operation, not success of the node. A passing assessment
  and the observed expected end state of every required external action are
  both necessary for ordinary success. An `examine` node requires no external action.
- Evidence, assessments and outcomes are historical records. A later record
  does not become current merely because it arrived later. Context, authority
  and order all govern assessment currency. The context uses the pinned
  revision, named evidence subset and the selected immutable outcomes of the
  direct dependencies.
- A terminal transition requires no unresolved requested external action.
  Pausing does not cancel a platform action, and blocking does not undo one.
  A request whose end state has not been observed cannot be bypassed by discard
  or a success override.

## Common calling convention

Every synopsis starts with `kanthord mission` and uses the
[common synopsis notation](./common-flags.md#synopsis-markers). Shared flag
syntax, defaults, and validation are defined once in that reference:

| Named flag set                                                   | Applies to               |
| ---------------------------------------------------------------- | ------------------------ |
| [`[M]` — Mutation flags](./common-flags.md#mutation-flags-m)     | Every proposed mutation. |
| [`[L]` — Pagination flags](./common-flags.md#pagination-flags-l) | Paginated lists.         |

[Remote flags](./common-flags.md#remote-flags-r) apply to every remote command.
A resolved [`--token`](./common-flags.md#--token) is required for every
operation here; its identity must satisfy the access legend below.
[`--help`](./common-flags.md#--help) also exists at every group level.
No remote command accepts [`--config`](./common-flags.md#--config).
See [shared rules](./other.md) for client-file handling and errors.

- Complex JSON input uses required [`--file`](./common-flags.md#--file), with the schemas below.
- A Markdown import names each plan file as a command-line positional, relative to the current directory.
- The CLI sends each base name as `filename` and its unchanged bytes as `content`; it never parses Markdown.
- No directory scan or implicit discovery expands the authoritative import set.

All optional flags default to absent unless a default is stated. Flags that
filter records map to same-named snake_case query fields (`--attempt` to
`attempt`, `--work` to `work`). Positionals
map to the route parameters shown in the inventory. File contents map to the
request body, except the raw-file collection for Markdown import.
GET requests have no body. `--help` is never sent to the server.

The shared [`--idempotency-key`](./common-flags.md#--idempotency-key) retry
rules apply. Import and unblock carry no domain request identifier. After a lost answer, a retry answers 409 `mission.version.conflict` or `mission.node.state_conflict`, and the human reads the mission again.

### Operation contracts

- Every Mission route follows the [operation contracts](https://github.com/kanthorlabs/kanthord/blob/main/docs/brainstorm/mission-service.impl.md#operation-contracts).
- Each route uses the shared error envelope, the default 30 s timeout and the 10 MiB body limit.
- A stale expected revision answers 409 `mission.revision.conflict` with the current value in `details`. A stale expected mission version answers 409 `mission.version.conflict` with the current value in `details`.
- An absent mission answers 404 `mission.mission.not_found`. An absent node answers 404 `mission.node.not_found`. An absent record answers 404 `mission.record.not_found`.

### Scalars and schema notation

In the schema tables, **required** fields have no default. **Optional** fields
are absent by default unless specified otherwise; nullable is stated explicitly.
Arrays contain values of the stated type and reject duplicates when described
as a set. Unknown JSON fields are rejected. Safe integers fit JavaScript's safe
integer range. All server timestamps are integer Unix milliseconds in UTC.
Wall-clock time and ULIDs do not establish causal order.
Every version, revision, `expected*Version` and `expected*Revision` field holds a positive safe integer.

### Access legend

No operation in this inventory is anonymous. Under the server-owner ruling,
every authenticated human holds the same authority over every mission; no
per-project authorization applies.

| Code | Proposed route access and domain check                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| H    | Existing policy value `human`, with verified human identity and the applicable planning or human-control authority. A client JWT is insufficient, including a client started by a human.                                                                                                                                                                                                                                                                                                                                                                                                    |
| E    | Existing policy value `client` plus live registration, live claim and a validated execution identity belonging to that claim, node and attempt. It also governs the execution-scoped reads below: the server derives the node, the attempt and the revision bound from the live claim, and a read under E never returns a revision newer than the pinned one. Steps/evaluation authority is checked per operation. The invocation chain proves the execution identity against the claimant of its live claim before the handler runs, so the identity in the input self-authorizes nothing. |

No operation accepts both a human and a machine. The read of a human (H) is keyed by a node and returns every revision; the read of a worker (E) is keyed by the execution identity. Both call one domain query with a required bound that the server derives from the caller, and return one record schema; the query rejects a missing bound. A human inspection of the view of an execution is a possible third `human` operation and is not in this inventory.

All positional IDs are required, typed as their names indicate, and have no
default. `<depends-on-id>` is a `NodeId`. `<revision>` is a positive safe integer.
`node list --work` accepts `implement|examine` and filters by the work at the
claim revision. `--state` accepts the exact `State` spelling. `--node` selects
incident dependency edges. `--include-retired` is boolean, default false. Omitted filters select all
authorized matching records. `--revision` defaults to the latest revision for a human.
`--include-retired` maps to `include_retired`; `--node` maps to `node_id`.
`--force` is boolean and defaults to false. On preview it maps to query `force`;
on apply it maps to `force` in the request body, and the file does not carry `force`.
An execution reads no content of another node through the execution-scoped
reads below. The one exception is a direct dependency of its node.
The execution reads that dependency at the revision that its current outcome pins.

**Effects and results:**

- `get` returns `Mission`.
- `graph get` returns `Graph` with the dependency edges and computed closure and availability explanations.
  This read decides no work allocation.
  The answer holds at most 10 MiB; a larger graph answers 413 `mission.graph.too_large`.
  The error holds the node count and the paged reads `node list` and `edge list` in `details`.
  The client then pages `node list` and `edge list` under the [operation contracts](https://github.com/kanthorlabs/kanthord/blob/main/docs/brainstorm/mission-service.impl.md#operation-contracts).
- `node list` returns `Page<Node>`. For a blocked node, its row includes the
  outcome of the closed attempt and the request evidence of the attempt with
  its end states; the cause is read from the outcome's closing event, never
  inferred from record order. `node get` returns `Node` with revision/attempt
  links. A node read answers `work`, `requires` and `tasks: TaskContent[]` at
  the claim revision: the revision that the open attempt pins, else the current
  revision. `content` and `visible_revision` stay current. The `tasks` of a
  node read can come from an older revision. An edit of the tasks reads the
  current tasks with `node revision get` at `visible_revision`.
- `node create` accepts `NodeCreate`, returns `NodeChange`, and validates the complete graph.
  It requires `filename`, the plan file name.
  The commit rechecks admission under the [node API rule](https://github.com/kanthorlabs/kanthord/blob/main/docs/brainstorm/mission-service.impl.md#node-api-admission).
  An `implement` node takes its tasks in `tasks`, each with a new `task_<ulid>` identity.
  An `examine` node with a nonempty `tasks` list answers `mission.node.content_invalid`.
  The import keeps its stricter import condition.
- `node update` accepts `NodeUpdate` and returns `NodeChange`. It replaces the
  named node's editable content, preserves identity and records reason/actor/time.
  It does not change dependencies, priority or state. Its `tasks`
  list creates, updates and retires the tasks of the node in the new revision. A node with an attempt remains
  editable by human override authority while nonterminal; import admission
  conditions do not govern this human update. A change of `work` while the
  attempt reads 1 or more answers 409 `mission.node.work_locked` with
  `details: { node_id, attempt }`.
- `node rebind` accepts `Rebind` and returns `RebindResult`, with `node_change` and the skipped nodes. It moves the pinned binding revision of one node, or of every node of the mission, to `<binding-id>`, a later revision of the same binding, under [the rebind](https://github.com/kanthorlabs/kanthord/blob/main/docs/brainstorm/mission-service.impl.md#the-rebind). A mission rebind returns `skipped: { node: Node, condition: "terminal" \| "retired" }[]`. A named retired node answers 409 `mission.node.retired`; a named terminal node answers 409 `mission.node.terminal`. A target from another project answers 404 `mission.binding.not_found`. The new revision applies at the next attempt.
- `node retire preview` returns `RetirePreview`; `node retire` accepts `Retire` and returns `NodeChange` under the [node retire ruling](https://github.com/kanthorlabs/kanthord/blob/main/docs/brainstorm/mission-service.impl.md#node-retire).
  The retirement set holds the node alone. `mission.node.retire_refused` and `mission.node.retire_has_dependents` refuse inadmissible acts.
  `--force` removes the dependencies of nonterminal dependents; a terminal dependent keeps its dependency.
  The apply sends the preview digest; a mismatch answers `mission.node.retire_mismatch`.
  A retirement is final. Every write and human control on a retired node, or a write that names one as a dependency, answers 409 `mission.node.retired`.
- `node revision list` returns `Page<Revision>` in descending revision order;
  `get` returns `Revision`; an absent revision of a present node answers 404
  `mission.node.not_found`. Execution-scoped revision reads below enforce the pinned bound.
- `edge list` returns `Page<Edge>`. Edges use endpoint composites, not invented
  opaque edge IDs. `dependency add/remove` accept `GraphEdit` and return
  `NodeChange`; they are graph operations, not arbitrary field updates.
  Addition requires no live claim on the dependent;
  removal requires a nonterminal dependent. An addition that forms a cycle
  answers 409 `mission.import.cycle`. Terminal edit prohibition still
  applies. These special conditions replace import eligibility for dependency
  edits on both write paths. Same-transaction routing updates all affected
  claim-free nodes between `Pending` and `Available`; a node in `Waiting` is
  not routed back by adding a dependency.
- `criterion list` returns `Page<Text>` with the single criterion text and its content-owner revision.
  `criterion set` accepts `CriterionSet`, returns `NodeChange`, and replaces the criterion and verifications as one human revision.
  It creates no independent criterion revision, state or opaque criterion ID.

### Import — 2 commands

| #   | Synopsis after `kanthord mission`                              | Proposed HTTP route                            | Proposed operation       | Access |
| --- | -------------------------------------------------------------- | ---------------------------------------------- | ------------------------ | ------ |
| 17  | `import preview <mission-id> --file <path> [<plan-file>...]`   | `POST /api/mission/:mission_id/import/preview` | `mission.import.preview` | H      |
| 18  | `import apply <mission-id> --file <path> [<plan-file>...] [M]` | `POST /api/mission/:mission_id/import`         | `mission.import.apply`   | H      |

- `<mission-id>` is a required `MissionId` value.
- Preview accepts `ImportSnapshot`; apply accepts `ImportApply`.
- For `format: "markdown"`, the CLI reads each command-line plan file and sends `files: { filename, content }[]`.
- With no plan-file positionals, the CLI sends the raw `files` from the input JSON unchanged.
- An input without plan-file positionals and without `files` fails the schema check with `cli.file.schema_invalid`; the CLI sends no request.
- The CLI refuses an input that supplies both plan-file positionals and `files`.
- The Mission Service parses Markdown under the [plan file grammar](https://github.com/kanthorlabs/kanthord/blob/main/docs/brainstorm/mission-service.impl.md#the-plan-file-grammar).
- For `format: "json"`, the CLI sends `entries` from the input JSON and accepts no plan-file positionals.
- Preview uses POST but changes no state. It returns `ImportPreview` and stores no receipt.
- A preview with violations answers 200 and lists each violation in `violations`. The CLI exits 0.
- For preview, a violation code of the error table is an entry of `violations`, not an error answer.
- Only apply answers the first violation as an error. The CLI then exits 1.
- Preview lists every current node that the import set omits as a retirement.
- Apply checks `preview_digest` and `confirmed_retirements` against that exact set at commit, then returns `ImportResult`.
- The CLI reports the map. It writes no assigned identity back to a plan file and asks no interactive confirmation.
- An import covers the whole mission: an absent ID creates, a known ID updates, and omission retires.
- Unknown IDs, duplicate IDs, foreign-mission IDs, retired IDs, duplicate plan file names and unresolved `node` or dependency names fail.
- Every `node` of a task file and every `depends_on` names a plan file inside the import set, never a path or a boundary reference.
- A task file names an `implement` node in `node`. A node file names its `work`, its `depends_on` list and its `requires` list.
- A stale mission version fails. A preview reserves no node against subsequent work.

Creation, update and retirement require `Pending|Available` and attempt
zero for each modified owner; task eligibility is the eligibility of its node.
Retirement checks the references; explicit dependency edits use the special dependency rule
described above. A dependency-resolution change is a dependency edit, not a no-op, even if
the Markdown bytes are unchanged. A real no-op skips modification checks.
One failed check aborts the whole import. Validation and commit share the lock
and transaction; unrelated work is not grounds to reject an import. Import
does not unblock, reopen, retarget attempts, carry priority or establish human
authorship/approval. Attribution records the submitting human only.

### Export — 1 command

| #   | Synopsis after `kanthord mission`                                | Proposed HTTP route                   | Proposed operation | Access |
| --- | ---------------------------------------------------------------- | ------------------------------------- | ------------------ | ------ |
| 19  | `export <mission-id> --format <markdown\|json> --out <path> [R]` | `GET /api/mission/:mission_id/export` | `mission.export`   | H      |

- The required `--format` maps to the query `format=markdown` or `format=json`, with no default.
- The required `<mission-id>` is a `MissionId`; access is `human`.
- The JSON answer is `{ mission_id, mission_version, entries: ImportEntry[] }`, where `bindings` holds binding names.
- The Markdown answer is `{ mission_id, mission_version, files: [{ filename, content }] }`.
- Each Markdown `content` follows the [plan file grammar](https://github.com/kanthorlabs/kanthord/blob/main/docs/brainstorm/mission-service.impl.md#the-plan-file-grammar).
- JSON entries follow `ImportEntry`: a node entry holds `work`, `requires` and `depends_on`, and a task entry holds `node`.
- Each answer is the exact plan payload that the import of its format accepts unchanged.
- Import controls accompany the payload; `mission_version` supplies the expected mission version.
- The export excludes retired nodes and preserves each plan file name.

### Host-local evidence upload

The helper runs in the kanthord component on the file's host: the server, the `worker` application or the harness extension.
The harness helper accepts required `<node-id>` and `<path>` positionals; it obtains execution context and evidence metadata from the execution.
The agent-facing host helper is `evidence upload <path>`; its execution supplies the node identity.

| Operation                         | Proposed HTTP route                                   | Input              | Answer                 | Access |
| --------------------------------- | ----------------------------------------------------- | ------------------ | ---------------------- | ------ |
| `mission.evidence.submit`         | `POST /api/mission/node/:node_id/evidence`            | `EvidenceSubmit`   | `EvidenceSubmitResult` | E      |

1. The component calls submit with the execution context, the evidence metadata and the asset list, where the file is an `object` asset with its size, media type and optional SHA-256.

   It creates the evidence and one pending asset for each `object` asset, with the server-generated key `<prefix>/<project>/<mission>/<node>/<attempt>/<evidence asset id>`.
   The asset pins that storage binding revision in `storage_binding_id`.
   The answer supplies one presigned PUT for each `object` asset, with a lifetime of 1 hour, which the Intake Service signs.

   The helper returns those values and the evidence identity to the agent, not the presigned URL.

A pending asset expires 1 hour after the submission; a complete of an expired asset answers 409 `mission.evidence.upload_expired`.
An evidence is published when every asset of it is published.
SHA-256 is optional for object evidence; the store verifies it when both sides support it.
kanthord enforces no object immutability and records the version when the store returns one.
A human who disables versioning accepts that choice; the binding write probes no store capability.
Every placement and co-location uses this flow.
Readers get a presigned GET through their kanthord component, for the recorded version when one exists.
The URL is an API answer and never travels through the credential handover or the agent context.
The storage credential stays inside the server process; the MCP server exposes no upload write.
No cleanup process exists; a human deletes an expired asset with `evidence asset delete`.
The [retention contract](https://github.com/kanthorlabs/kanthord/blob/main/docs/brainstorm/mission-service.impl.md#evidence-retention) defines the delete.

| Schema                 | Fields, requiredness and validation                                                                                                                                                                                                                                                                                                    |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

The complete operation takes `ExecutionContext`; the route supplies its required `EvidenceAssetId`.

`TestedInput` holds one of four forms:

- One `RepositoryAddress` for a node with one repository binding.
- `RepositoryAddress[]` for a node with two or more repository bindings, one commit for each binding in binding order.
- A `ProducedAddress` when no repository supplies the tested input.
- An `ObjectAddress` when the verifications read an object that a storage binding holds.

A node with at most one repository binding accepts a `ProducedAddress` or an `ObjectAddress`.
A node with no repository binding refuses a `RepositoryAddress`.
A node with two or more repository bindings accepts only the list form.
An `examine` node names zero or more repository bindings of its own.
The reviewer of an `examine` node checks out each base-branch head under `checkouts/<binding name>/`.
When an `examine` node names no repository, the reviewer places the produced evidence in the workspace.

The [verification run](https://github.com/kanthorlabs/kanthord/blob/main/docs/brainstorm/mission-service.impl.md#the-verifications) uses list order, one item at a time, never in parallel.
Each verification runs through `bash -c` in the execution workspace root.
The run stops at the first failed item.
The `verification` records each started command, its exit code, signal and timeout fact.
A run passes when `results` hold one entry per verification and every entry has `exit_code` 0.
The start refuses a host without bash.
No execution infers a verification from prose.
The execution code, never the agent, runs the verifications of the pinned revision before judgement, whatever the work.
For an `implement` node, the reviewer runs the verifications of the node and of each current task of the pinned revision.
A human writes an assessment only through a success override, a discard or a block; `assessment submit` serves an execution only.
The actor and evaluation fields identify who judged; no assessment holds a method field.
A reviewer assessment names its evaluation identity.
An external harness assessment identifies the client identity of the harness worker.

The assessment result follows this order:

1. A failed or unrun verification gives `criterion-not-met`, without a judgement.
   The reviewer execution writes the assessment immediately; its required rationale names that verification.
   In a steps execution, a failed task verification leads the agent to revise within the resource budget first, and the execution records no task assessment.
2. Otherwise, judgement against the criterion gives `success`, `criterion-not-met` or `undetermined`.
3. For a worker that kanthord hosts, a default-standard violation turns `success` into `criterion-not-met`.

Only the first case permits an empty judgement; the rationale is never absent or blank.
HTTP 400 with an issue list rejects a method field, absent or blank rationale, or a result that violates this order.
The service refuses an assessment that asserts success with a failed or unrun item with `mission.assessment.verification_failed`.
A success counts only an evidence whose `verification` covers every required command of the pinned revision. A success with no such evidence, with more than one, or with one that fails answers the same code. An evidence that covers only part of the commands does not count and does not refuse the success.
Judgement decides success only after every verification passes.

The actor, accepted time, record identity, currentness, derived required actions
and outcome basis are server-derived. They cannot be forged through extra JSON
fields. Tested-input binding is an attributable executor assertion unless a
clean isolated checkout establishes it; a zero exit code proves only that the
verification returned zero, not adequacy, coverage or absence of suppressed failures.

## Proposed result schemas

CLI result JSON goes to stdout; diagnostics go to stderr.
Failures exit nonzero; successful reads and mutations exit zero.
Presigned URLs are component-only API answers, never agent-facing stdout. A successful mutation reports its
effective `idempotency_key: string` alongside the domain result. Sensitive tokens
are never echoed. The exact transport envelope follows the
[shared rules](./other.md); the names below describe its domain data.

Fields listed below are required unless marked optional or nullable. These are
output fields, with unresolved sub-schemas explicitly identified.
List pages use descending primary-key order under the shared [pagination rule](https://github.com/kanthorlabs/kanthord/blob/main/docs/brainstorm/architecture.impl.md#pagination).
Pagination order establishes no causal record order.
Every node-attempt field of a record holds a nonnegative integer, including fields that inherit an execution input schema.
No such field is null.
The `attempt` of `ControlResult` is an attempt object or null, not a node-attempt field.

commit stands on the human assertion, not an invented durable repository address.

## Operations deliberately outside this CLI inventory

These boundaries define legitimate public operations; they are not missing
aliases for internal mechanisms.

- Queue insertion/deletion in Mission's transaction, Scheduler wake-up,
  dependency rerouting, claim serialization, attempt opening/closure,
  and assessment currency recomputation are
  service responsibilities. There is no `mission reconcile`, `queue insert`,
  `attempt open`, `attempt close`, `evaluation retry` or `set-state` command.
- Claim, release, loss declaration and work pull belong to Scheduler.
  Worker registration and platform action performance belong to their owners.
  Mission records are not platform merge/push/notification commands.
- Delivery admission, `mission.delivery.admit`, is a `service` operation that the Intake Service calls, and it has no CLI command. It sets the end state of a request evidence after the check of the Intake Service, without an execution claim. A generic human or client end-state write would manufacture authority that the identity contracts do not establish; a human uses `node check`. Its input holds `inbound_event_id`, `project_id`, `platform`, `resource`, `event` and `metadata`, and it answers `{ disposition, reason }`. A `branch_push` event with no exact match selects each unresolved `pull_request` request of the same resource whose frozen `base_branch` equals the pushed branch. Each selected request goes to the Intake check. A `conflict` result returns the node to rework, and admission skips a request whose node holds a live claim. Automatic detection needs a poll or webhook inbound for the repository.
- `mission.delivery.unresolved_request.count` is a `service` operation that only the Intake Service calls, and it has no CLI command. Its input holds `project_id` and `resource_identity`, and it answers `{ count }`: the request evidences of the open attempts of the project that hold no end state and name that resource, of every address kind. It writes nothing. A poll inbound requests its platform only while that count is above zero.
- `mission.evidence.request` is the operation of the Worker action performer, and it has no CLI command. Its route is `POST /api/mission/node/:node_id/evidence/request` under access E, and its input holds every field of `ExecutionContext` plus `requirement_key: Key`, `subject: Text` and `address: PlatformAddress`; it answers `Evidence`.
- Evidence and asset deletes have commands in this inventory; kanthord runs no automatic delete and no cleanup process.
  Corrections append through the authorized submission path and never rewrite history.
- Ordinary node outcomes are written by closing transitions. No unrestricted
  `outcome create/update`, human assessment impersonation, terminal correction
  or human failure override is exposed. The defined success override and discard
  have explicit authority and state restrictions. Non-success override precedence remains **[blocked][mission-recovery]**.
- Planning from external deliveries remains **[blocked](https://github.com/kanthorlabs/kanthord/blob/main/docs/brainstorm/HANDOFF.md#scheduler-service-and-delivery)**. No
  client import or automatic inbound-message-to-node command is introduced.
