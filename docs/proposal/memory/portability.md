# Portability

Reviewer: architect and developer experience. The model is [README.md](README.md). This file defines how something that is not KanthorD reads the memory.

## Two surfaces, one canonical store

The database is canonical, on the same rule that already governs the profile and the work graph. A working tree never feeds a recall, and a file on disk is a projection.

| Surface       | For                                      | Direction      |
| ------------- | ---------------------------------------- | -------------- |
| Markdown tree | a harness that reads files               | export, import |
| HTTP routes   | the CLI, and a client on another machine | read, write    |

## The markdown tree

`kanthord memory export --out <directory>` writes the tree. It writes nothing outside that directory, and it refuses two things before it writes anything: a file that is not in a manifest it wrote, and a **manifested file whose current hash no longer matches the manifest**. The second is a human edit that was never imported, and overwriting it destroys work.

`--force` proceeds past the second refusal, naming every file it will overwrite. Nothing proceeds past the first.

Checking only for unknown files was the first design. It put the changed-file detection on the import side alone, so export, edit, export again silently erased the edit.

```
<directory>/
  MANIFEST.json
  CATALOG.md
  fact/backend-developer/messaging/outbox-pattern-01j9z4.md
  index/backend-developer/database.md
```

### One body, one file

A fact is written **once**, under its primary filing, in `fact/<domain>/<topic>/`. Every other filing produces a line in an index file under `index/<domain>/<topic>.md`, which is a list of links.

Writing the body once per filing was the first design and it was a footgun. The export exists so a human can edit a fact, and three editable copies of one fact have no answer for which copy wins, no way to detect that two diverged, and no way to stop the next export overwriting an edit that was never imported. A harness that ingests every matching file received the same fact three times.

`index/backend-developer/database.md` lists **every** fact filed at the topic, in one place, ordered by fact ULID:

```markdown
# backend-developer / database

Every fact filed at this topic. 12 facts.

- [schema-migration-order](../../fact/backend-developer/database/schema-migration-order-01j8k2.md) — Run a migration in one transaction or not at all. _(primary here)_
- [outbox-pattern](../../fact/backend-developer/messaging/outbox-pattern-01j9z4.md) — Send a webhook through an outbox table rather than from the request handler.
```

A fact whose primary filing is this topic is marked, so a reader knows which file is the editable one without following the link.

### `CATALOG.md`

The card index, and the file a harness reads first. One line per topic.

```markdown
# Memory catalog

schema: kanthord.memory/v1
Generated by kanthord. Do not edit. Facts are under fact/.

## backend-developer

Server-side application work: services, data, transport.

- [messaging](index/backend-developer/messaging.md) — Queues, brokers, webhooks, delivery guarantees. 7 facts.
- [database](index/backend-developer/database.md) — Schema, query, transaction, storage engine. 12 facts.
```

**The catalog links the topic index, never the fact directory.** The directory holds only the facts whose primary filing is that topic, so its file count is smaller than the count the catalog states, and a harness following a directory link silently misses every fact filed there from elsewhere. The index lists all of them, so the link and the count agree.

This is the same shape as the index a coding harness already loads at session start, which is why it needs no adapter.

### A fact file

```markdown
---
schema: kanthord.memory/v1
id: fact_01J9Z4...
kind: failure
scope: personal
primary: backend-developer/messaging/outbox-pattern
paths:
  - backend-developer/messaging/outbox-pattern
  - backend-developer/database/outbox-pattern
cited:
  origin: local
  node: task_01J9Z...
  run: run_01J9Z...
  attempt: attempt_01J9Z...
occurrences: 3
state: active
supersedes: null
contradicts: []
---

Send a webhook through an outbox table rather than from the request handler.

**Problem:** the handler committed the row and then failed to deliver, so the
receiver never saw an event that the database says happened.

**Solution:** write the event to an outbox table in the same transaction as the
row, and deliver from a separate reader.
```

Frontmatter holds what the daemon owns, in the fixed order above. The body holds the memory. A `failure` fact renders its `problem` and `solution` as the two bold sections, through the same renderer that produced the canonical body, so the file round-trips.

`scope` is singular because a fact has one scope: a promotion creates a new fact in the destination scope citing the source, per [write-path.md](write-path.md). `paths` is plural because filings are many.

### Filenames

`<topic-slug>/<fact-slug>-<id suffix>.md`. The fact slug is derived from the first line of the body, canonicalized to the slug rules of [vocabulary.md](vocabulary.md) and cut at 40 bytes. The id suffix is the last 6 characters of the fact ULID.

The suffix is not decoration. Two facts under one topic can produce the same slug, and a filename collision resolved by an arbitrary tiebreak is a filename that moves between exports. The suffix makes the name a function of the fact alone.

### `MANIFEST.json`

Every file the exporter wrote, with its byte length and its content hash, plus the store state the export was taken from and the schema version.

The manifest is what makes the tree safe to overwrite. Both sides read it: the exporter refuses an unknown file and refuses a manifested file whose hash changed, and the importer uses the same hashes to tell an edited file from an untouched one.

### The export is byte-identical

Two exports of one store state produce identical bytes. Directory entries and file names sort bytewise through `Buffer.compare`. Frontmatter keys appear in the fixed order above. Line endings are LF, with one trailing newline. Nothing carries a generation timestamp, because a timestamp in a generated file makes every export a diff.

### Import

`kanthord memory import --from <directory>` reads the tree back. It exists for the reason profile import exists: a human edits memory in an editor, and a human moves memory between machines.

Import is not a merge.

- A fact whose id exists and whose body changed is replaced by a new fact that supersedes it.
- A fact whose id is absent is created.
- A fact in the store and absent from the tree is untouched, because a partial tree must not delete.
- A fact whose stored body no longer matches the manifest hash it was exported at is **refused**, naming the id. The store moved under the edit, and silently overwriting is how an edit destroys a write.
- An index file is read for validation only. It creates no filing, because the fact file already names its paths.
- A path naming a domain or topic that does not exist is refused, with the missing segment named. Import never creates vocabulary, because vocabulary is curated and a file is not a curation decision.

### Import across two daemons

A tree carries local identities. `owner` names a project that exists on the source daemon, and `cited` names a node, a run and an attempt that exist there. The destination daemon usually has none of those rows, and this is the case the export exists to serve.

Two rules resolve it, and neither invents a mapping.

- **Provenance becomes opaque.** An imported citation is stored as **foreign provenance**: the source daemon identity, the schema version, and the node, run, attempt and actor ids as uninterpreted text. It carries no foreign key, it resolves to nothing locally, and it is displayed rather than followed. A local citation is unchanged and still carries real foreign keys.
- **The owner is named by the human.** `--owner <id>` is required for any fact whose scope needs one, and an import of a `project` fact with no `--owner` is refused. A `personal` fact takes the destination daemon's human.

Silently dropping the citation was the alternative, and it loses the provenance the frontmatter carries for no gain. Silently reusing the source id was the other, and it either violates a foreign key or points at an unrelated local row.

`session` and `feature` facts are never exported and never imported. They belong to a run and an objective on one machine, and neither exists on the other.

### Deferred: continuous export

The export is a command a human or a hook runs. A daemon that rewrites a directory on every write needs a watched path in configuration, a debounce, and an answer for a target directory that disappeared. Ship the command, measure whether the manual step is the friction, then decide.

## Routes

Conventions are `../api/README.md`. Every segment below is in the closed set of that grammar, and every resource segment is singular.

| operationId          | Method and path                             | status | Source                                  |
| -------------------- | ------------------------------------------- | ------ | --------------------------------------- |
| `memory.remember`    | `POST /v1/memory`                           | routed | write-path.md, capture                  |
| `memory.list`        | `GET /v1/memory`                            | routed | read-path.md                            |
| `memory.show`        | `GET /v1/memory/:id`                        | routed | read-path.md                            |
| `memory.forget`      | `DELETE /v1/memory/:id`                     | routed | write-path.md, retention                |
| `memory.catalog`     | `GET /v1/memory/catalog`                    | routed | read-path.md, stage one                 |
| `memory.recall`      | `POST /v1/memory/recall`                    | routed | read-path.md, stage two                 |
| `memory.export`      | `GET /v1/memory/export`                     | routed | this file                               |
| `memory.import`      | `PUT /v1/memory`                            | routed | this file                               |
| `memory.promote`     | `POST /v1/memory/:id/promote`               | routed | write-path.md, promotion                |
| `memory.review`      | `GET /v1/memory/review`                     | routed | write-path.md, drafts and nominations   |
| `memory.resolve`     | `POST /v1/memory/:id/resolution`            | routed | write-path.md, a human resolves a draft |
| `memory.supersede`   | `POST /v1/memory/:id/supersession`          | routed | write-path.md, a correction             |
| `memory.dispute`     | `POST /v1/memory/:id/dispute`               | routed | write-path.md, contradiction            |
| `memory.undispute`   | `DELETE /v1/memory/:id/dispute`             | routed | write-path.md, a human dismisses        |
| `memory.decline`     | `DELETE /v1/memory/:id/nomination`          | routed | write-path.md, promotion                |
| `vocabulary.show`    | `GET /v1/memory/vocabulary`                 | routed | vocabulary.md                           |
| `vocabulary.declare` | `POST /v1/memory/vocabulary`                | routed | vocabulary.md                           |
| `vocabulary.amend`   | `PATCH /v1/memory/vocabulary/:id`           | routed | vocabulary.md, lifecycle                |
| `vocabulary.resolve` | `POST /v1/memory/vocabulary/:id/resolution` | routed | vocabulary.md, proposals                |

`memory.recall` is a `POST` because the query is a body. It writes nothing.

Every route refuses a `team` or `company` scope with `422`, naming the scope. The segment exists in the grammar and the row exists in the schema; the daemon serves one user, and [README.md](README.md) says why.

`memory.export` returns the tree as a stream, and the CLI writes it to disk. The daemon does not write to a path a client names, because a path a client names is a path a client chose.

## The CLI

`cli/` reaches the daemon over HTTP and imports no command and no query, on the rule of `AGENTS.md`. Memory adds no exception.

| Command                                           | Route              |
| ------------------------------------------------- | ------------------ |
| `kanthord memory remember --text <t> --scope <s>` | `memory.remember`  |
| `kanthord memory recall --query <t> --select <m>` | `memory.recall`    |
| `kanthord memory catalog`                         | `memory.catalog`   |
| `kanthord memory show --id <id>`                  | `memory.show`      |
| `kanthord memory forget --id <id>`                | `memory.forget`    |
| `kanthord memory export --out <dir>`              | `memory.export`    |
| `kanthord memory import --from <dir>`             | `memory.import`    |
| `kanthord memory review`                          | `memory.review`    |
| `kanthord memory resolve --id <id>`               | `memory.resolve`   |
| `kanthord memory supersede --id <id>`             | `memory.supersede` |
| `kanthord memory dispute --id <id> --memory <id>` | `memory.dispute`   |
| `kanthord memory promote --id <id> --scope <s>`   | `memory.promote`   |
| `kanthord memory vocabulary`                      | `vocabulary.show`  |

A command names its own subject `--id`, and a reference to another entity by its entity name, per the settled rule in `../open-items.md`.

## Deferred: an MCP surface

A harness that speaks MCP would call recall directly rather than read a file. It is a new transport in a daemon that has one, it needs its own authentication story, and the file tree already gives every harness the same facts with no integration. Revisit when a harness that cannot read the exported tree is the one that matters.
